## 2. 四阶段实验安排

前三阶段均已有实现与验收记录，第二阶段复核发现的未知结果问题已修复。下文保留各阶段的依赖顺序和范围，第四阶段继续作为后续方向。

```text
第一阶段：应用经运行时和驱动完成计算（已完成）
  → 第二阶段：用户发布 AQL，CP 取包派发，Signal 报告完成（已验收，复核问题已修复）
  → 第三阶段：引入 DRM，建立并隔离 GPU 地址空间（已实现并验收）
  → 第四阶段：完善异常恢复与资源回收
```

### 2.1 第一阶段：跑通应用到设备的计算流程

已完成 Linux 驱动、用户态运行时、代码加载和参数传递，让计算 kernel 接收输入、执行并返回可核对的结果。A57、PCI / BAR、VRAM、DMA、SMMUv3、MSI-X、RV32 计算解释器及已有计算示例继续作为后续阶段的基础。新增 CP 队列路径时，保留原同步路径的回归验证。

### 2.2 第二阶段：用户 AQL Queue、Doorbell、CP 与 Signal

本阶段要让应用连续发布任务，由设备独立推进计算，再通过 Signal 等待结果。用户态向上实现到 HSAKMT 风格接口库，封装驱动的设备、内存、队列和事件能力；实验程序等调用方组织命令包，CP 固件负责读取、解析和派发。ROCr/HSA 运行时及高层任务接口留待后续评估。

```text
Host 装载 CP 固件，建立首次 KIQ
  → 驱动经 KIQ 建立 HIQ，确认可用后经 HIQ 建立用户队列
  → 调用方准备代码、参数和 Signal，向用户 Ring 发布 AQL Packet
  → Doorbell 通知设备检查生产进度
  → CP 从自己的消费位置读取任务，交给计算执行器
  → 计算完成并收尾，CP 发布 Signal，回报消费进度
  → IH 记录经中断交给驱动，驱动定位事件并唤醒等待者
  → 应用检查结果，驱动按卸载协议释放队列资源
```

第一版的队列分工、阻塞执行、消费时序和管理完成协议以[规格](<./CP_MEC 第一版规格.md>)为准。本大纲不再单独规定队列数量、Ring 容量、索引位宽或内存布局。

#### 2.2.1 实现顺序与范围

以实验子仓库 `57543dd54b6b046b888277272fa84af81746b1ac` 和当前已确认规格为基线，沿用双进程设备、RV64 裸机 CP、RV32 计算执行器及一次完整执行一个 Dispatch 的模型。队列先使用 `REMOTE=1、IOMMU=none、VMID=0`。原同步路径继续单独回归。

1. **建立可重复的内核构建。** 根据缓存包固定 Linux `6.18.57` 对应的 Alpine 构建提交、源码校验值、配置和补丁顺序。按 2026-10-19 的调整，默认使用固定版本的宿主机交叉工具链，独立保存源码和输出；客体原生方式保留为可选入口，其默认资源为 32 GiB 构建盘、4 个虚拟 CPU、4 GiB 内存。构建并行度、资源和超时可调整。配置、补丁及构建脚本进入仓库，源码与产物放在 `build/`，保留原环境。启用内置 `GPU_BUDDY=y`，补齐隐藏配置项、模块签名路径和依赖，生成同版本内核、模块、开发文件、`Module.symvers` 和启动镜像；开发文件中的构建工具须能在 ARM64 客体执行。先验证启动、驱动编译及第一阶段回归。
2. **落实共享定义与完整访存。** 集中定义对象布局、寄存器、IH 地址、提交结果、执行器错误枚举和新增 ioctl，用编译期检查核对大小、偏移和对齐。共享首部和 W/R 使用完整 32 位访问，Signal、管理标记和通知槽使用完整 64 位访问。消息 DMA 对自然对齐的 4/8 字节直接 RAM 访问采用等宽原子读写，保留地址翻译、权限、映射引用、脏页及指令翻译失效处理；其余搬运沿原路径。核对 Host 进度映射可供 CPU 原子取号。
3. **接入 HQD、Doorbell 与 IH。** Host 选槽窗口和 CP 本地窗口访问同一份 HQD，检查访问来源、宽度和状态。Doorbell 按完整 8 字节处理，通过配置匹配队列，只提示重新检查。IH 使用第四个 MSI-X 向量，实现记录发布、消费回报、屏蔽恢复和确认后的再次通知；IH 故障通过原错误中断交付。
4. **接入执行器交接和 Host 参数窗口。** 保留 RV32 解释器，增加配置快照、代码及参数范围检查、执行状态和结果确认。任务对象保存线程状态、工作组位置和累计预算，由后续 QEMU 回调分段推进。只读参数窗口保留完整 Host 地址。相关访问结束后才发布终态，CP 仍等待整个 Dispatch 完成。
5. **实现 CP 固件。** 先完成末尾 4 MiB 固件区的链接、栈、全局数据初始化和访存异常处理，再实现 KIQ 建立 HIQ、HIQ 管理用户队列、AQL 取包及派发。固件分别保存槽位绑定和管理请求结果，按既定顺序检查队列。成功路径依次完成执行确认、Signal、通知槽、IH、无效首部及消费回报；错误路径保留首次错误和已有写入，按规定范围停止取包。
6. **接入驱动资源管理。** 驱动装载时选择互斥的旧同步模式或队列模式。队列模式支持多个进程上下文，取消打开、关闭及等待超时触发的全局复位，分别处理 DMA、IH 和错误。设备统一使用 `gpu_buddy` 管理前 60 MiB VRAM，登记首个保留页。Host 内存、队列、事件、管理请求及用户映射分别持有引用；Doorbell 按进程分配独占映射页，管理入口使用单独页面。
7. **贯通管理、事件和正常卸载。** 驱动装载固件并初始化首次 KIQ、IH。管理锁只保护命令对发布，释放后各请求等待独立结果区；事件处理先保存通知或故障，再唤醒。正常销毁先由调用方停止提交、完成发布并排空，驱动复核后请求卸载；确认 MQD 保存和旧通知处理结束，再解除引用。创建失败、超时或进程退出时，尚不能确认访问结束的资源继续保留。
8. **接入 HSAKMT 风格库和调用方。** 库按[规格 9.7](<./CP_MEC 第一版规格.md#spec-host-api-scope>)提供设备、内存、队列和事件接口，分别返回句柄、映射资料和设备访问地址，检查版本与状态。实验程序共用辅助代码实现 AQL 取号、填包、发布、Doorbell 和 Signal 等待，不增加逐任务 ioctl。先验证连续向量加法，再复用矩阵乘和 ReLU。固定少量提交线程，每线程最多保留一个未发布编号，限制在途预留。默认等待从本次等待开始主动检查约 `200 μs`，再进入事件等待并复查 Signal。

设备按现有职责增加 HQD、IH 和参数访存组件；固件分开组织主循环、访存与异常、管理命令、AQL 派发与完成；驱动分为 PCI 入口、内存、队列和事件，接口库按四组接口分文件。接口说明输入输出、所有权和完成条件，关键锁、屏障及引用位置添加中文注释。原 ioctl 和同步库接口保留，新接口独立检查版本。为将多个源文件链接为原来的 `gpgpu_pci.ko`，仅将入口源文件改名为 `gpgpu_pci_main.c`，同步源码清单、构建指纹及装载逻辑。

当前基线的 Doorbell 写回调为空且最大访问宽度为 4 字节，消息 DMA 的通用内存拷贝也尚未证明并发 64 位访问完整性；旧驱动会全局清中断并在超时和会话关闭时复位。这些缺口分别由步骤 2、3、6 处理，队列协议继续以规格为准。AMD 的 Doorbell 分页、原子取号、完整首部发布和事件等待实现只用于补齐实现细节。

**[BOUNDARY]** 多 VMID、抢占、强制中止、运行中复位恢复、预留空洞修复、完整 ROCr 和共享存储留在后续扩展。第二阶段等待超时只结束本次等待，资源保留规则仍须验证。SMMUv3 下的队列地址翻译接入不在本轮范围；已有 DMA 和 CP Host 窗口继续保留两种 IOMMU 配置回归。

#### 2.2.2 五组验收与完成标准

设备边界用例加入现有 QTest，Linux 侧增加一个队列测试程序，按以下五组检查：

1. **正常提交。** 两条用户队列连续运行，逐轮改变输入；检查结果、Signal、消费进度和管理结果，覆盖物理槽及 32 位编号回绕。
2. **并发与可见性。** 同队列多线程取号，覆盖前包延迟发布、W 不变时补发布、乱序 Doorbell、两个进程管理命令成对发布。验证首部先失效再回报 R，用高低位均变化的数值检查 64 位完整访问。任务数据与屏障位置按[规格 6.4 节](<./CP_MEC 第一版规格.md#spec-dispatch-visibility>)核对。
3. **等待与通知。** 覆盖主动检查期间完成、阻塞后完成、通知先于登记、多个等待者和超时，合并检查 IH 屏蔽恢复及确认时新记录到达。
4. **基本错误退出。** 覆盖非法 Dispatch、参数访问失败、普通管理失败、管理通道及 IH 故障，检查停止范围、等待退出、首次错误及资源保留。逐次写入失败组合的穷举留到[异常恢复扩展](#failure-recovery-extension)。
5. **正常卸载与寿命。** 未排空时拒绝正常销毁，排空后卸载并重建；旧通知、等待者或映射仍在时禁止提前复用。进程退出不能释放设备仍可能访问的资源。

继续保留 CP 原 8 项、单／双进程 IOMMU 各 2 项、ARM64／RISC-V 设备各 21 项、汇编检查 4 项，以及第一阶段单／双进程与 `none/smmuv3` 四种组合回归。新增用例后更新实际数量检查，同时核对日志和退出码。

完成标准是应用能连续发布多个 AQL 任务，提交不等待 Kernel 完成；CP 按规格处理队列，任务结果、消费进度和管理完成分别可观察；默认等待支持短暂轮询后转入内核等待，IH 唤醒后复查 Signal；正常卸载后设备不再访问已释放资源，旧通知和驱动后续处理不引用已回收对象。每步记录实际实现与运行结果，未运行或未通过的检查明确保留，不能以代码或文档已写完代替整体验收。

<a id="stage-three-vmid"></a>

### 2.3 第三阶段：固定存储下的 GPUVM 与多进程隔离

第三阶段完成后用于 GPU 驱动岗位面试，本期只保留一条可重复演示的主线：应用申请受管理的对象，设备按 GPUVA 和所属 VMID 访问，两个进程互不越界，结束后安全回收。具体方案见[GPUVM 第一版规格](<./GPUVM 第一版规格.md>)。

```text
应用 A / B 分别打开设备、准备全部对象
  → 驱动创建 GEM 对象、分配固定存储并建立 GPUVA 映射
  → 相同 GPUVA 在两套页表中指向不同对象
  → 创建各自 Queue，MQD/HQD 关联所属 VMID
  → CP 与执行器按 VMID 翻译取包、取指、数据和完成访问
  → 写回各自结果，Signal / IH 完成通知
  → 排空并销毁 Queue，结束旧通知
  → 撤销映射、等待 TLB 失效，回收对象与 VMID
```

**[DESIGN]** 本版已实现单一 DRM 入口、一文件一地址空间、32 位 GPUVA、三级 4 KiB 页表和两个固定用户 VMID；全设备保留两个用户 Queue 名额，每个地址空间最多一条。控制页、参数窗口、零页和内部通知页不进入普通 GPUVA 分配范围。

默认应用只需“准备全部对象 → 建 Queue → 重复提交与等待 → 统一关闭”。库封装整对象创建、GPUVA 分配和映射；Queue 存活时不新增或撤销 GPU 映射。Host RAM / VRAM 存储位置在对象寿命内固定，不接入 TTM，不做换页、迁移、驱逐、按需补页或故障恢复。分配不足明确失败，未映射访问明确报错。

#### 2.3.1 第二阶段收尾与访问路径核对

先修复[第二阶段未知管理结果码问题](#stage-two-spec-review)，对不能确认访问结束的请求、队列及资源继续保留。本轮已完成，并用独立测试模块分别注入映射管理结果未知、卸载管理结果未知及 TLB 失效未确认，核对退出后的 VMID 保留与停机后的安全清理。

随后沿一次向量加法核对 Ring、进度、MQD、代码、描述对象、参数、数组、Signal、通知槽和 IH 的地址域与访问主体。

#### 2.3.2 DRM/GEM 与固定存储对象

核对目标 Linux `6.18.57-0-gpgpu-virt` 的 DRM/GEM 接口，接入一个文件上下文持有一个地址空间；GEM 包装现有 Host 一致性内存与 VRAM `gpu_buddy`，不重建存储分配器。

先验证一个对象的创建、CPU 访问、引用和释放，再接入队列。关闭句柄、撤销 GPU 映射和释放实际存储分别处理，不能提前归还仍被队列、CPU 映射或旧通知使用的对象。

#### 2.3.3 跑通单地址空间的真实 AQL 访存

驱动建立整对象映射、填写页表，设备完成页表遍历、范围和读写取指权限检查。先验证单页和跨页访问，再让现有向量计算通过 GPUVA 运行。

用户 Ring、进度、描述对象、代码、参数、数组、Signal 和通知槽逐项接入正确上下文。管理 MQD、管理队列、管理完成、IH 与固件保持受信任管理路径，不向用户开放物理访问旁路。保留 RV64 CP、RV32 执行器、16 字节描述对象和只读参数窗口，减少执行模型改动。

先在 A57、双进程设备、`IOMMU=none` 下跑通。随后用同一端到端程序在 `IOMMU=smmuv3` 下追加验证 Host RAM 的两层访问，不为第三阶段新增覆盖所有启动模式的组合矩阵。已有 SMMUv3 DMA 回归继续保留。

#### 2.3.4 加入双进程隔离、TLB 与安全复用

为两个应用维护独立页表，固定分配两个用户 VMID，通过 MQD、HQD、CP 访存和执行器快照传递上下文。VMID 不足时失败，不做超额轮换；同一 VM 内多 Queue 协调不在首版范围。

实现小型 TLB，缓存按 VMID 区分。映射更新只允许在该 VM 的 Queue 已安全卸载后进行：正常 Queue 先排空，故障 Queue 沿第二阶段错误卸载协议确认访问结束，无法确认则保留。采用 CPU 同步写表、按 VMID 全量失效和本次 ACK，不加入异步页表依赖或运行中暂停更新协议。通知页提前映射，创建事件只分配已有槽。

复用 VMID 前结束旧访问和通知处理，完成失效与解绑。未映射、越界和权限错误记录源队列、VMID、地址及访问类型，停止源队列并使等待错误退出；另一进程的健康队列继续运行。不补页、不恢复故障指令、不重放任务；无法确认访问结束时保留相关资源。

<a id="stage-three-acceptance"></a>

#### 2.3.5 阶段验收与结束条件

设备侧用例和 Linux 端到端验证只围绕以下五组核心场景增加，实际命令、数量与结果随代码记录：

1. **对象与完整访存。** 分配并映射 Host RAM / VRAM 对象，向量计算结果正确；取包、取指、参数、数组和完成访问均经过正确翻译，覆盖跨页与范围边界。
2. **双进程隔离。** 两进程把相同 GPUVA 映射到不同对象并得到各自结果；用户无法指定另一上下文的 VMID，不能访问管理、页表或固件区域。
3. **基本故障退出。** 未映射和权限错误可定位，源队列及相关等待以错误退出，另一进程继续运行；失败前的部分写入保留，不补发成功或自动重跑。
4. **映射与编号更新。** 排空卸载后撤销并重新映射，读取新对象而非旧 TLB；旧 VM 关闭后复用 VMID，新上下文看不到旧映射，旧通知不关联新对象。Queue 存活时修改映射被拒绝。
5. **正常回收与回归。** 关闭后能重新申请并再次运行，引用未结束时资源继续保留。复用受影响的设备、CP、队列和同步回归；补一次 GPUVM 与 SMMUv3 的端到端验证，分别记录新旧路径结果。

五组核心验收通过、运行结果可重复，并固定代码基线、配置、命令及已知限制后，第三阶段即完成。整理第一阶段设备访问、第二阶段 AQL 提交和第三阶段 GPUVM 的项目演示与实现说明，开始用于面试；不等待换页、完整 TTM 或第四阶段恢复功能。

只接入 GEM 或只翻译数组地址不足以完成本阶段。资源安全与隔离不能为赶进度省略；不再把后续扩展加入本期验收。

#### 2.3.6 工作安排

本轮按以下依赖顺序完成，保留工作划分供复现和项目讲解：

1. **基线与对象。** 已修复未知管理结果码；在独立输出目录构建启用 DRM/GEM 与 `GPU_BUDDY` 的内核，保留原环境；完成对象创建、CPU 访问与引用寿命验证。
2. **单地址空间。** 已实现页表和全部用户存储访问翻译，适配接口库，增加可重复运行的 GPUVM 向量计算验收程序。
3. **隔离与更新。** 已接入两个用户 VMID、TLB 失效和安全复用；相同 GPUVA 的双进程隔离、撤销重映射与 SMMUv3 端到端验证均通过。
4. **收尾并固定成果。** 五组 Linux 验收在 `none/smmuv3` 下各通过 5/5，未知结果保留检查 3/3；原物理队列及四种同步组合回归通过。具体通过数、代码快照、日志和命令集中记录在[软件栈验收说明](<./gpu-study-qemu/software/gpgpu/README.md#stage-three-validation>)，规格与硬件手册同步维护。

**[BOUNDARY]** 本阶段不实现普通 DRM 命令提交或 `drm_sched`，AQL 继续直接经用户队列发布。运行中强制中止、复位重建和恢复按[第四阶段](#24-第四阶段完善异常处理与资源释放)处理，其余 GPUVM 动态管理见[后续扩展](#gpuvm-advanced-extension)。教学页表和寄存器不作为 MI300X 硬件结论。

### 2.4 第四阶段：完善异常处理与资源释放

在第二阶段的队列卸载和资源保护基础上，围绕非法命令、访问 fault、任务超时及进程退出，完善 CP / 执行引擎中止、设备复位和恢复，验证恢复后能够继续执行正常任务。任务卡住后的强制停止与复位重建按[异常恢复扩展](#stalled-task-recovery-extension)在后续阶段细化。AQL 用户队列仍属于第二阶段的必达范围。

## 3. 后续扩展与进度维护

多 VMID 的管理与设备访问隔离按[第三阶段](#stage-three-vmid)推进。后续还需要增加 Kernel 执行中途暂停、让出计算资源和恢复执行的能力。第一版暂不采用上下文保存寄存器组；相关接口、现场保存与恢复、完成状态管理见[后续扩展](<./CP_MEC 软件实现、参考与扩展.md#extensions>)。暂停与恢复的实施阶段随执行器和多队列功能的进展确定，当前不预设工期。

<a id="gpuvm-advanced-extension"></a>

GPUVM 动态管理不作为第三阶段验收内容。TTM 接入、存储迁移和驱逐用于管理多个存储位置；换页与按需补页需要额外的存储后备、故障处理和继续执行协议；运行中或异步更新需要安排旧访问及后续任务依赖。VMID 超额轮换、别名与部分撤销、跨进程共享和更细的通知权限也按实际需求后续评估。本期分别用固定存储、提前分配、Queue 存活期间冻结映射和资源不足时明确失败来限制范围，不预先设计这些扩展的完整接口。

<a id="rocr-runtime-extension"></a>

ROCr/HSA 运行时、高层任务提交与自动回收、通用内存池、通用 Kernel 装载器及完整设备拓扑留待后续单独评估。第二阶段先实现[HSAKMT 风格接口库](<./CP_MEC 第一版规格.md#spec-host-api-scope>)，通过实验程序验证内核功能和既定 AQL 协议。以后是否采用标准 HSA 接口、兼容到哪一层，根据届时的设备与驱动能力决定；当前不设计精简 ROCm 软件栈，也不承诺原版 libhsakmt 或 ROCr 可以直接运行。

<a id="queue-unmap-extension"></a>

取消未执行任务、保留未执行任务跨卸载续跑，以及提交线程异常退出后的预留空洞填补与自动恢复列为后续扩展。第一版正常卸载按[规格 7.4 节](<./CP_MEC 第一版规格.md#spec-unmap-drain>)先停止提交并等待排空；故障队列沿用错误退出和资源保留规则。需要上述扩展时，再确定未执行任务的结果、等待退出和重新装载后的处理方式，当前不增加执行中途保存恢复。

<a id="stalled-task-recovery-extension"></a>

任务长时间不结束时的挂死判断、强制中止、单队列或管线复位、设备整体复位恢复及自动恢复，留到后续优化，不作为第二阶段必做或验收内容。运行期间 KIQ 重配、故障 HIQ 重建、复位后旧队列与旧请求的处理也随此扩展细化，范围见[规格 9.6.4](<./CP_MEC 第一版规格.md#spec-stalled-task-scope>)和[9.6.5](<./CP_MEC 第一版规格.md#spec-runtime-reset-scope>)。第二阶段的等待超时只结束本次等待；尚不能确认设备访问结束时，相关资源继续保留。后续根据实际故障需求确定停止方法、完成确认和恢复步骤，当前不预先固定复位方案。

<a id="failure-recovery-extension"></a>

失败包的基本退出与资源保留按[规格 7.3 节](<./CP_MEC 第一版规格.md#spec-failure-retirement>)执行。各个写入步骤失败后的状态组合、逐步故障注入、自动重试和原地恢复列为后续扩展，第一版不逐项细化。扩展时再确定安全重试条件，避免重复执行 Kernel 或重复更新完成状态；已确定的完整读写、发布顺序和资源释放前提继续作为第一版要求。具体范围随异常处理的实际需求确定。

<a id="signal-atomic-extension"></a>

第二阶段由 CP 单独更新 Signal，不要求原子读改写接口。如果以后引入多个并发更新者，再扩展对应的原子操作及访存后端，参考关系见[Signal 原子操作扩展](<./CP_MEC 软件实现、参考与扩展.md#signal-atomic-extension>)。实施阶段随需求确定。

<a id="signal-active-wait-extension"></a>

`HSA_WAIT_STATE_ACTIVE` 的持续主动等待列为后续扩展，第二阶段只实现默认的短暂轮询后阻塞等待。扩展时再增加调用者选择等待模式的接口，并明确错误与超时返回，参考关系见[持续主动等待扩展](<./CP_MEC 软件实现、参考与扩展.md#signal-active-wait-extension>)；具体实施阶段随需求确定。

<a id="compute-resource-extension"></a>

工作组共享存储、组内屏障和可配置寄存器资源列为后续扩展，参考 AMD 的 LDS 与资源配置用途，具体实施阶段随执行器需求确定。第一版继续为每个线程固定提供通用、浮点寄存器；`ax+b` 中的只读标量通过参数块传入，不要求共享存储。扩展时一起确定资源声明、每组共享区域、访问边界、屏障与内存可见性，并调整当前逐 warp 执行的方式，使同组线程能够完成同步。概念与例子见[线程寄存器、参数与共享存储](<./CP_MEC 软件实现、参考与扩展.md#kernel-registers-lds>)，功能范围见[计算资源扩展](<./CP_MEC 软件实现、参考与扩展.md#compute-resource-extension>)；当前不增加 AMD 的完整资源寄存器或 MQD 字段。

四阶段说明推进方向，不预先固定全部功能和接口。每完成一段实验，或遇到影响计划的问题，就根据代码、运行结果与学习反馈调整近期工作。实验计划统一在本大纲维护，当前阶段同步到根目录 `AGENTS.md`；学习笔记中的理论缺口仍补回首次需要它的位置，第七章大纲继续管理后续笔记。
