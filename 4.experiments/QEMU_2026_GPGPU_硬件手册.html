当前版本与执行路径

本手册用于本仓库的 QEMU 教学设备。基础设备部分来自原实验资料，第二阶段部分收录已确认的 CP/MEC 规格第 1～8 节及第 9.7 节的 Host 接口约定，保留原节号方便核对。寄存器名称借鉴 AMD，本实验的布局和简化行为不代表 MI300X 的硬件接口。

当前实现固定于实验子仓库 3217651a83c00c14a39712cefda9394b6e977ff3（2026-10-19）。RV64 原生 CP 处理队列固件，RV32 执行器运行应用 Kernel；全设备共 4 个 HQD 槽，KIQ、HIQ 各占一个，用户队列共享两个名额，VMID 固定为 0。队列验收采用双进程、IOMMU=none；原同步路径保留单／双进程及 none/smmuv3 回归。

Host 准备 KIQ 并启动 RV64 CP
  → KIQ 建立 HIQ → HIQ 建立用户 Queue
  → Host 原子预留包编号、填写 AQL、发布 Header、写 Doorbell
  → CP 读取 AQL 与描述对象，向 RV32 执行器提交 Kernel
  → 执行器写回结果，CP 保存终态并 ACK
  → Signal = 0 → 通知槽 = 事件编号 → IH 通知
  → Header = INVALID → 回报消费进度 R
  → Host 复查 Signal、读取结果，满足寿命条件后回收资源

既有验收记录包含 CP QTest 16/16、Linux 队列 5/5 和四种同步组合回归。规格复核仍有一项待修复：驱动未校验未知管理结果码，创建失败分支可能提前释放 MQD 及相关引用。实现、历史验收与当前复核范围见实验大纲；本手册描述的安全回收规则仍是必须满足的规格要求。

1. 概述¶

GPGPU 是为 QEMU 训练营定制的虚拟 PCIe 3D 加速器设备。其设计目标是提供一个覆盖 GPU 关键子系统的硬件抽象，用于：

  • PCIe 设备建模（BAR 映射、MSI-X 中断、配置空间）
  • DMA 引擎建模（Host↔VRAM 双向传输）
  • SIMT 执行模型（Warp 锁步、线程层次）
  • RISC-V 指令集解释器（RV32I + RV32F + 低精度浮点扩展）

2. 文档约定¶

2.1 数值与端序¶

  • 除非特别说明，所有数值均为十六进制，形如 0x1001_8000（下划线仅用于分组）。
  • 地址均为 字节地址（byte addressable）。
  • 所有多字节寄存器访问均按 小端序（little-endian） 解释。

2.2 术语¶

  • 未定义（undefined）：实现可以产生任意结果；软件不得依赖其行为。
  • 实现定义（implementation-defined）：实现必须在某处给出选择；若未给出，软件仍不得依赖。

3.4 双进程的 BAR、DMA 与中断路径¶

[DESIGN] A57 Linux 运行在进程 A，通过 vfio-user-pci 访问进程 B 的 gpu0。进程 B 使用 gpgpu-cp machine，包含原有寄存器、VRAM、DMA、中断与计算解释器，以及由 TCG 执行的原生 RV64 CP。CP 默认保持复位；原同步计算和 DMA 可继续使用。

进程 A：A57 Linux
  └─ PCIe 设备代理
       ├─ 配置空间、BAR0/BAR2/BAR4 请求 ─→ 进程 B：GPGPU
       ├─ PCI DMA 接口 ←─ B 的读写请求       ├─ 原计算解释器
       │    └─ SMMUv3（启用时）→ Host RAM    └─ 原生 RV64 CP
       └─ Linux 驱动 ←─ 完成与错误中断            └─ 访问同一份 VRAM

none 与 smmuv3 都使用 x-dma-via-socket=on：B 把设备 DMA 地址、方向和数据请求发送给 A，A 调用该 PCI 设备的 DMA 接口，并返回数据或错误。SMMUv3 的翻译、权限检查和故障记录保留在 A。该启动选项只选择通信方式，不增加硬件寄存器。

BAR 访问通过消息转发，MSI-X 表和屏蔽状态在两端同步。计算完成、DMA 完成和错误事件沿原有向量传给 A 的 Linux 驱动。DMA 继续同步搬运数据，并通过原定时器报告完成。本版不支持断线重连和迁移。

4.3 MMIO 访问规则¶

  • BAR0 寄存器按 32-bit 对齐访问（min=4, max=4）。
  • BAR2 VRAM 支持 1–8 字节访问。
  • 对标记为 Reserved 的位：软件 必须写 0，读出值为 实现定义。

6.5 软复位行为¶

写 GLOBAL_CTRL.RESET = 1 后：

  • global_ctrl 清零
  • global_status 恢复 READY
  • 所有错误/中断状态清零
  • SIMT 上下文清零
  • 内核参数、DMA 状态清零
  • VRAM 不清零
  • 连接 CP 时，使 CP 保持复位并将入口恢复为 0

第二阶段在原中断位之外增加 IRQ_IH = bit 3，使用 MSI-X 向量 3；IH 故障和固件异常分别记录到全局错误 bit 4、bit 5。确认与重触发规则见IH 中断协议。

9.5 CP 复位与固件入口（0x0500）¶

[DESIGN] Host 已取得 BAR0、BAR2 映射，接下来要装载固件并使 CP 从指定入口执行。CP 的地址 0～vram_size-1 映射 VRAM 的相同字节偏移；例如入口为 0x1000，Host 写 BAR2 基址 + 0x1000，CP 从地址 0x1000 取指。两者访问同一份存储，不复制显存。这里的低地址入口用于基础固件示例；第二阶段固定保留末尾 4 MiB VRAM，队列固件入口为 0x03c0_0000，详见第二阶段固件布局。

Host 写 CP_CTRL.RESET_HOLD = 1，读回确认
  → 通过 BAR2 装载代码、数据和初始结果
  → 设置 CP_RESET_VECTOR（CP 地址，也为 VRAM 偏移）
  → 执行访问屏障和读回，确认写入完成
  → 清零 RESET_HOLD
  → CP 从入口执行，把结果写回 VRAM
  → Host 经 BAR2 读取结果
9.5.1 CP_CTRL（0x0500）¶

对齐、小端的 32 位寄存器。bit 0 RESET_HOLD 可读写，默认 1；bit 1 PRESENT 只读，连接 CP 时为 1。远端设备默认读回 3，解除复位后读回 2。保留位读零、写入忽略，写 PRESENT 忽略。

置位 RESET_HOLD 使 CP 恢复原生复位状态并保持不取指；清零后从入口运行。重复写入相同复位状态不会重新启动 CPU。复位和启动在目标 CPU 线程中同步完成，Host 可通过读回确认。

9.5.2 CP_RESET_VECTOR（0x0504）¶

对齐、小端的 32 位启动地址寄存器，默认 0。只有保持复位时可修改；地址必须位于 VRAM 内，并满足原生 RISC-V CP 的 2 字节指令对齐。有效修改同步更新 CPU 复位向量和复位态 PC。非法地址或运行期间修改入口时保留原值，并通过已有 ERROR_STATUS.INVALID_CMD 报错。

单进程设备没有连接 CP 时，这两个寄存器读零、写入忽略。

9.5.3 复位范围与固件替换¶

CP 单独复位保留 VRAM、入口和原 DMA、派发、中断状态。GLOBAL_CTRL.RESET 复位设备状态并使 CP 回到保持复位、入口为 0 的默认状态，VRAM 保留。设备冷复位先停止 CP，再清零 VRAM 并恢复全部默认状态。GLOBAL_CTRL.ENABLE 不自动解除 CP 复位。

替换固件时先保持 CP 复位并读回确认，再通过 BAR2 覆盖原代码、设置入口、执行屏障和读回，最后解除复位。BAR、DMA、计算解释器和冷复位的 VRAM 写入会使修改范围的 TCG 翻译失效，支持从相同地址执行新固件。固件测试与原软件栈测试分别运行，并明确各自的代码、结果地址。

[BOUNDARY] 当前 RV64 CP 已接入 Host 访存窗口、管理队列、用户 AQL、Doorbell、计算派发与完成通知。运行中的强制停止和复位恢复仍属后续范围；本节基础固件替换示例不提供活动队列的安全恢复流程。该教学接口不作为 MI300X 的寄存器或控制核结构结论。

第二阶段 · 1. 整体架构与执行路径

[DESIGN] 第一版使用一个 QEMU 原生 RV64 CP，由 TCG 在 M-mode 执行裸机固件，不启用页表；现有 RV32 计算解释器继续执行应用 Kernel。4 个 HQD 槽位中，槽位 0 用于 KIQ，槽位 1 用于 HIQ，槽位 2、3 由 CP 按创建请求分配给用户 AQL Queue。计算执行器一次处理一个完整 Dispatch。

Host 准备 KIQ 的 Ring、MQD 与 HQD，启动 CP
  → 驱动经 KIQ 请求建立 HIQ，确认管理操作完成
  → 应用经内存接口申请 Ring 和进度区，再请求创建用户 Queue，驱动准备 MQD
  → 驱动经 HIQ 提交 MAP_QUEUES，指定 USER_AQL 和 MQD 地址
  → CP 从槽位 2、3 中选择空闲槽位；无空闲槽位则报告创建失败
  → CP 读取用户队列的 MQD，配置并激活所选 HQD
  → 驱动确认配置成功，接口库将队列标识和 Doorbell 入口交给调用方
  → Host 向用户 AQL Ring 发布 Dispatch 并通知设备
  → RV64 CP 根据 HQD 找到 Ring，读取并解析 Dispatch
  → CP 通过分发接口向 RV32 计算执行器提交任务，等待完成
  → CP 发布完成 Signal，释放包槽并回报消费进度
  → Host 读取结果，复用已经消费的 Ring 槽

原生 CP 执行队列固件，计算执行器执行应用 Kernel，两者各自保存寄存器和取指位置。2026-10-17 的 RV64 迁移只改变原生 CP；计算线程的寄存器和 Kernel 指令仍按 RV32 执行。执行主体、构建入口及参数交接边界见CP 与计算执行器的位宽。上图规定本阶段的队列执行顺序，实际运行结果见大纲进度说明。

本文用户态流程中的“运行时”泛指准备 AQL 和等待 Signal 的调用方，第二阶段由实验程序承担。HSAKMT 风格接口库封装驱动的设备、内存、队列和事件操作，分工按第 9.7 节执行，不要求实现 ROCr/HSA 运行时。

[DESIGN] 第二阶段全设备最多同时存在 两条用户 Queue，所有应用共享这两个名额，KIQ、HIQ 不计入其中。用户队列按申请创建，各自的 Ring、MQD 和进度区由驱动分配。文中的 Queue A、B、MQD_A、MQD_B 只是示例名称，不是预先固定的队列身份或地址，也不与槽位 2、3 永久绑定。

假设其他创建条件均满足，下面演示两个名额的分配与复用；槽位选择只用于举例：

第 1 次申请 → 驱动提交 MAP_QUEUES → CP 选择空闲槽位 2，创建队列
第 2 次申请 → 驱动提交 MAP_QUEUES → CP 选择空闲槽位 3，创建队列
第 3 次申请 → 驱动提交 MAP_QUEUES → CP 发现无空闲用户槽位
                                  → 报告失败，驱动向应用返回名额已满

槽位 2 对应的队列成功销毁，完成清理并归还名额
  → 后续申请可以创建新的 Queue，复用槽位 2
  → 为新 Queue 准备自己的 Ring、MQD 和进度区

驱动负责准备资源和提交请求，CP 负责判断用户槽位是否空闲并分配；满额时报告失败，驱动将结果返回应用。本版不先创建更多逻辑队列再等待 HQD。仅有 ACTIVE = 0 或发出销毁请求，尚不能归还名额；仍需满足既有卸载与资源回收条件。CP 的占用记录、重复请求处理和槽位释放条件见第 4.2 节，每次管理请求的结果通过第 4.4 节的独立结果区返回。错误退出与正常卸载按第 7 节执行，强制恢复留作后续扩展；应用创建接口与错误返回见9.7.3 的已确认接口。

HQD 保存状态，CP 读取状态并执行命令，计算执行器执行 Kernel。管理命令与 AQL Packet 直接保存在各自的 Ring 中，本版不引入 IB 间接命令执行，也不建立 IQ 或 EOP 缓冲区。不提供可配置的队列／管线优先级和时间片，也不实现运行中的抢占和计算现场保存；取舍详解见AMD 寄存器对照，后期方向见扩展项。

[DESIGN] 第一版沿用 RV32 执行器为每个 lane 固定提供的通用、浮点寄存器，不增加 COMPUTE_PGM_RSRC1/2 资源配置寄存器。Y[i] = a × X[i] + b 中不随线程变化的只读 a、b 放在参数块中，各线程读取后计算，无需 LDS。工作组共享存储、组内屏障和可配置寄存器资源列为后续扩展；概念与已有实现见线程寄存器、参数与共享存储。第二阶段仍只运行不依赖工作组共享存储和屏障的 Kernel。

2.1 CP 通过窗口读写 Host RAM

本节先记录已经实现的通用 DMA 访问路径，包含 SMMUv3 翻译配置，再说明队列访存上下文和 Signal 更新规则。当前队列主线按直通配置使用这条路径，窗口基址保存对应的 Host RAM 物理地址；下文保留既有寄存器名称和 IOVA 测试案例。

[DESIGN] Host 使用 BAR2 直接读写 VRAM，也可以配置现有 DMA 在 Host RAM 与 VRAM 之间批量搬运。CP 直接使用同一份 VRAM；需要访问 Host RAM 时，通过本地窗口执行普通 load/store，不配置 Host 的 DMA 搬运寄存器。

Host CPU → BAR2 → VRAM ← CP 的本地 load/store
Host 配置现有 DMA → 在 Host RAM 与 VRAM 之间搬运

CP 的窗口 load/store
  → 窗口 IOVA 基址 + 窗口内偏移
  → 设备发起 PCIe 访存请求
  → Host SMMUv3 翻译与检查（启用时）
  → Host RAM

窗口只提供访问入口，不分配新的 RAM，也不要求先把 Host 数据搬到 VRAM。Host 的 DMA 和 CP 的窗口可以在同一运行时期使用；访问同一份数据时，软件仍须保证准备、读取和复用顺序。

下图保留 Host 窗口接入时的本地地址范围；它们不是 Host 的 BAR 地址。图中当时预留的 HQD 区域已按第 8.3 节接入：

0x0000_0000 … vram_size-1    原有 VRAM
0x8000_0000 … 0x8000_ffff    64 KiB Host 访存窗口
0xfffe_0000                  CP_HOST_IOVA_BASE_LO
0xfffe_0004                  CP_HOST_IOVA_BASE_HI
0xffff_0000                  留给 HQD；本次窗口实现不接入 HQD

两个基址寄存器保存按 64 KiB 对齐的 64 位 IOVA。访问 IOVA 0x1_0000_1234 时，CP 写 BASE_HI = 1、BASE_LO = 0，随后读取窗口地址 0x8000_1234。只有实际访问范围需要有效映射，不要求整个窗口都有映射。

CP 的通用寄存器为 64 位，本地地址仍使用原有 4 GiB 布局。例如固件从参数区取得窗口地址时，按下面的路径访问：

参数区保存 32 位本地地址 0x8000_1234
  → LWU 零扩展为 0x0000_0000_8000_1234
  → 选择 Host 窗口，得到窗口内偏移 0x1234
  → 加上 64 位窗口基址，访问 Host RAM

使用 LUI 构造本地地址后也须清除高 32 位的符号扩展。这里处理的是 CP 本地入口地址；Host 地址仍由两个基址寄存器完整保存，不截成 32 位。

  • 基址寄存器采用自然对齐的 32 位读写。BASE_LO[15:0] 读零、写入忽略；固件写完高低位后才能访问窗口，更新期间中断处理程序也不能使用窗口。
  • 窗口采用自然对齐的 1、2、4、8 字节小端读写，8 字节访问使用 LD/SD。成功时，当前指令取得读值或完成相应写请求；地址或权限检查失败时，CP 收到原生 load/store access fault，由固件处理。失败不承诺撤销已经发生的写入。
  • 窗口不修改 Host 的 DMA_STATUS、ERROR_STATUS 或完成中断，不增加 CP 专用 DMA 寄存器。其可用性不额外依赖 GLOBAL_CTRL.ENABLE，CP 启停仍按第 3 节执行。
  • CP 复位将窗口基址清零；零基址表示访问 IOVA 0 附近，不表示窗口关闭。Host DMA 状态仍按现有复位规则保留。
  • Host 保持实际访问范围的映射、权限和内存寿命有效。当前窗口沿用该 PCIe 设备的 IOMMU 上下文，尚未实现按队列 VMID 选择页表。

现有窗口提供普通数据读写，固件代码与栈继续放在 VRAM。对象地址采用第 2.4 节的字节地址编码；队列访存上下文和 Signal 的单一更新者规则见下文，32 位进度与 64 位完成值的完整访问及发布顺序遵守第 2.2.1 节。调用路径与验证方式见窗口实现说明。

[DESIGN] 固件在访问前保存所属 HQD 槽位、访问阶段和完整目标地址，访问失败后据此区分“读取 Ring 失败”“写回消费进度失败”等情况。队列归属由槽位确定，VMID 仍统一为 0。处理 KIQ 或 HIQ 的映射命令时，记录来源管理队列、目标种类和 MQD 地址；CP 选定目标槽位后，再记录该槽位，例如“HIQ 正在为 CP 选定的槽位 2 读取 MQD”。尚未选定目标槽位时，错误仍关联到来源管理队列和本次请求。

失败后不自动重新执行整个任务，也不盲目重试完成更新。例如 Kernel 已执行完、Signal 更新失败时，不能重新运行 Kernel。已经发生的写入保留；停止取包后仍须按卸载或恢复协议确认访问结束，才能释放资源。具体错误编码、Host 通知、失败阶段的收尾及恢复步骤见第 7 节和 9.6。

2.1.2 Signal 的 64 位读写与单一更新者

Host 为任务 T1 准备 Signal S，提交前将 64 位的 S.value 初始化为 1。发布任务后，Host 只读取这个值，由 CP 在任务成功完成后将它减为 0。本阶段一次使用中的 Signal 对应一个任务，不作为多个任务的共享完成计数。

Host 准备任务 T1
  → 将 Host RAM 中的 S.value 初始化为 1（64 位）
  → 发布引用 S 的 Dispatch
  → 此后 Host 只查询或等待，不再修改本次任务的 value

CP 执行任务 T1
  → 确认结果写回并完成任务清理
  → 通过 Host 窗口读取 S.value = 1
  → 在 CP 本地减一，得到 0
  → 通过 Host 窗口将完整的 64 位值 0 写回 S.value

Host 等待任务 T1
  → 观察到 S.value == 0
  → 按完成发布协议读取任务结果

[DESIGN] value 保留 64 位有符号整数，按 8 字节对齐。Host 在提交前初始化为 1；从任务发布到本次使用结束，只有 CP 可以更新 value，Host 不与 CP 并发写入。CP 在正常完成路径上执行一次“读取、减一、写回”，将 1 改为 0，无需专门的原子加或原子读改写入口。计算执行器不另行更新同一 Signal。

S.value 的 Host 物理地址保留完整的 64 位；按第 2.5.2 节的布局，value 位于 Signal 起始地址的偏移 0x00。每次任务的完成更新只执行一次；访存失败仍按所属队列记录错误，不盲目重复减一。Host 重新初始化或复用 Signal 前，必须先满足第 2.5.3 节及第 7.1.7 节已经确定的旧任务、旧通知与对象引用条件；应用释放接口见9.7.4 的已确认接口。

[BOUNDARY] 单一更新者省去了并发读改写之间的冲突，仍须保证 Host 与 CP 取得完整的 64 位值，并保证结果写回先于完成值发布。窗口支持对齐的 8 字节读写；完整字段访问遵守第 2.2.1 节，具体可见性操作见第 6.4 节。通知槽标记和防止漏唤醒的等待协议已按第 2.5.3 节确定，中断交付沿用第 7.1.5 节。多更新者的原子读改写列为后续扩展，不作为第二阶段必需接口。

  • 进度区按队列分配。 每条队列独立分配一块进度内存，生产进度与消费回报均保存 32 位数值，使用其中不同的位置，各位置至少按 8 字节对齐，与 Ring 包槽分开。用户队列的进度区映射给所属应用；运行时写生产进度、读消费进度，CP 执行相反方向的访问。KIQ、HIQ 也各有独立进度区，由驱动承担 Host 侧读写，不映射给普通应用。进度区在创建队列时准备，卸载并满足回收条件后释放。
  • 管理标记按管理请求使用。 驱动单独管理一块完成标记区，按请求分配结果区。每个在途管理请求独占 16 字节，至少按 8 字节对齐，包含 8 字节完成标记、4 字节结果码和 4 字节保留空间，仅供驱动和 CP 访问。WRITE_COMPLETION 携带结果区起始地址和待写入的 64 位无符号序号，先写结果码、再写完成标记，命令布局见第 4.1 节，结果区布局见第 4.4 节。结果区的保留与回收由管理请求控制，不与目标队列的进度区绑定；驱动确认卸载结果并满足生命周期条件后，再回收目标队列资源。标记初值为 0、预期值使用递增序号，等待和复用规则见第 4.3 节。
  • Signal 按应用上下文管理。 调用方经内存接口申请驱动分配的 Host 共享块，映射到所属应用，并在本上下文中按需布置、初始化和使用 Signal。该区域可以作为内存池，不要求每个 Signal 单独占用整页。Signal 的生命周期独立于 Ring 槽和具体队列；任务 T1 完成且包槽已复用时，只要应用还在使用 S1，就不能将 S1 分给新任务。本阶段一次使用中的 Signal 只对应一个任务，重新初始化沿用通知与对象寿命条件，应用释放接口见9.7.4 的已确认接口。

[BOUNDARY] 本节确定存储位置、分配归属和映射范围。普通进度和管理标记通过 CP Host 窗口读写；Signal 按单一更新者规则由 Host 初始化、CP 完成时减为 0。动态字段的完整读写要求见下节，具体字段编码及失败收尾按第 9 节的已确认约定执行。一次提交中四类值的配合见进度与完成值的使用过程。

2.2.1 动态字段的完整读写

Host 等待任务完成时会读取 Signal，CP 则在完成路径中更新同一字段。管理完成标记和通知槽也有读写交错的情况。一次读取必须取得完整值，不能把两次更新中的不同部分拼在一起：

CP 正在更新一个 64 位值
          ↓
Host 只能读到完整旧值或完整新值
不能读到“高半部是新的、低半部是旧的”

[DESIGN] Signal 的 value、管理完成标记和通知槽中的 64 位字段均至少按 8 字节对齐。Host 与 CP 每次按完整的 64 位值读取或写入，不采用拆成两个 32 位、反复读取再拼接的协议。Signal 保留 64 位有符号含义，管理完成标记保留 64 位无符号含义；具体布局仍按各对象的约定确定。

完整读取和写入是 Host、CP 与 QEMU 访存后端共同承担的接口要求，覆盖指令、窗口回调、消息传输到最终内存访问的路径。CP 发出一次 LD/SD 或消息长度为 8 字节，只能说明访问形式；后端仍须保证读取方取得完整旧值或完整新值。当前代码已接入等宽原子访问，并通过 CP 回归中的并发读写检查；验证范围及端到端验收状态见大纲进度说明。

字段值完整，还须满足相关数据的发布顺序。AQL 继续按第 5.2.2 节先更新 W 预留，再填写包体、发布有效 Header；CP 确认 Header 有效并保证包体可见后才解析。按第 6 节，CP 确认结果写回后发布 Signal，结束旧槽访问并将 Header 置为 INVALID 后回报新 R；Host 完成相应同步后，才读取结果或复用槽。具体屏障须结合 Host 映射、CP 窗口和后端落实并验证。

[BOUNDARY] Signal 继续由 CP 单独更新，不增加原子读改写入口；固定地址配置仍按原有高低位寄存器和配置完成规则处理。AQL 首部按第 5.2.2 节以完整的 32 位值访问，提交者模型已按 9.4.4 确认；通知槽布局与唤醒流程已按 9.5.4 确认。

2.4.2 地址位宽、对象对齐与访问校验

CP 已从 Dispatch 取得描述对象的 VRAM 偏移，接下来要读取描述对象并取得代码入口。沿用第 2.3 节的取值，先检查字段和访问范围，再把入口交给计算执行器：

CP 取得 kernel_object：64 位无符号偏移，数值为 0x4000
  → 检查高 32 位为零、描述对象地址按 8 字节对齐
  → 按描述对象大小检查整段范围落在 VRAM 内
  → 读取 VRAM 偏移 0x4000 处的描述对象
  → 取得其中的代码入口偏移：32 位无符号数，数值为 0x8000
  → 交给 RV32 计算执行器
  → 执行器检查入口按 4 字节对齐，并检查实际访存范围

[DESIGN] kernel_object 保留 64 位无符号字段，保存 VRAM 字节偏移；当前阶段要求高 32 位为零，且访问范围位于实际 VRAM 容量内。Kernel 描述对象中的代码入口偏移，以及参数块中 X、Y、Z 等数组的 VRAM 偏移，使用 32 位无符号数，配合现有 RV32 计算执行器。从更宽接口取得这些 32 位偏移时，必须先检查范围再转换。Host RAM 物理地址仍保留完整 64 位。

[DESIGN] 对象采用以下最低对齐要求：

  • 用户 AQL Ring、KIQ Ring、HIQ Ring 的起始地址按 64 字节对齐。
  • KIQ、HIQ 中每条管理命令固定为 32 字节，命令起点按 32 字节对齐，字段布局见第 4.1 节。
  • MQD、Kernel 描述对象、参数块、生产／消费进度存放位置和管理完成标记位置，至少按 8 字节对齐。Signal 和通知槽沿用第 2.5 节的 8 字节对齐要求。
  • RV32 Kernel 代码入口按 4 字节对齐；普通数组按元素类型自然对齐，例如 32 位元素按 4 字节对齐。
  • 结构内的多字节标量字段按自身宽度自然对齐，例如 32 位字段按 4 字节、64 位字段按 8 字节对齐。

驱动在创建和配置对象时检查，CP 在解析对象引用时检查，计算执行器检查实际执行的访存。检查内容包括地址对齐、乘加计算不溢出，以及整段访问范围有效。VRAM 访问必须完整落在实际容量内；Host RAM 访问还必须处理访存接口返回的错误。

校验失败就拒绝该次访问，不截断地址、不自动调整地址。访存过程中发生的失败交给错误协议处理，不承诺撤销已经发生的写入。第二阶段 VMID 固定为 0，驱动用软件对象管理 Host 侧资源归属，按 VMID 的设备访问隔离留到第三阶段；访存失败按第 2.1.1 节关联当前队列并停止相应取包，具体错误码、通知及失败收尾已按第 7 节和 9.6 确认。

[BOUNDARY] 这些是教学设备的接口约定，不套用 AMD 的完整对象布局。MQD 布局已在 9.2.1 确认，见第 2.6 节；管理命令布局已在 9.3.2 确认，见第 4.1 节。进度值采用第 5.2.1 节确定的 32 位包编号；Kernel 描述对象、参数布局和访问窗口已按 9.5.2 确定，见第 6.2 节；Signal 的 24 字节布局及通知、等待协议已按9.5.4确定，见第 2.5.2 节和第 2.5.3 节。

2.5.1 默认等待先短暂轮询，再进入内核事件等待

Host 已发布任务 T1，接下来等待 S.value == 0。第二阶段默认采用 HSA_WAIT_STATE_BLOCKED 对应的等待方式，由实验运行时先读取完成值，必要时经 Host 驱动进入事件等待。以下按 Signal 有效、任务尚无已知错误的正常路径说明：

Host 开始等待 S.value == 0
  → 先读取 S.value
       ├─ 已经是 0：完成必要的同步后返回
       └─ 仍然是 1：短暂主动轮询
                        │
                        └─ 仍未完成、也未超时
                             → 进入 Host 内核事件等待，线程睡眠
                             → 设备通知到达，驱动唤醒线程
                             → 再读 S.value，判断条件

[DESIGN] 主动轮询预算为约 200 μs，从本次等待开始计时。等待条件提前满足时直接结束等待；等待期限先到时按超时规则返回，不要求先用完轮询预算。约 200 μs 后仍未完成且未超时，才进入内核事件等待。唤醒后复查 S.value；若仍未满足条件且未超时，继续事件等待，不重新计算一轮 200 μs 的主动轮询预算。

阻塞等待依赖设备通知和 Host 驱动的事件处理。正常完成通知经 IH 记录交付，驱动用记录中的 MQD 地址找到队列所属进程，再按 event_id 找到等待事件。驱动保存“已通知”状态，在登记等待者后再次检查条件，处理通知先到、线程后登记的情况；具体规则见第 2.5.3 节。S.value 更新与读取结果之间的同步规则见第 6.4 节，错误退出按第 7.3 节执行，事件查询、等待的返回值与超时参数见9.7.4 的已确认接口。

[DESIGN] 第二阶段只提供上述默认等待方式，HSA_WAIT_STATE_ACTIVE 的持续主动等待列为后续扩展。默认方式开头的短暂轮询属于本阶段流程；运行时的单次查询接口也不等同于持续主动等待模式。

[SOURCE] ROCr 固定版本 ba56a24c6132c5d195686ae4adf969ca1222fbba：runtime/hsa-runtime/core/runtime/interrupt_signal.cpp 的 138–198 行在等待开始时记录时间，设置 200 μs 阈值，并在主动检查、超时判断和内核事件等待之间选择；201–207 行补充 acquire 同步。这是本实验默认等待方式的参考。

2.5.2 Signal 的 24 字节布局

Host 为任务 T1 准备 Signal S，CP 根据 Dispatch 中的 completion_signal 找到 S。沿用前文已确定的 Host RAM 位置、字段位宽和最低对齐，本节补齐具体布局：

偏移 0x00：value              64 位有符号数，提交前为 1
偏移 0x08：event_id           32 位无符号事件编号
偏移 0x0c：reserved           32 位，填 0
偏移 0x10：event_mailbox_ptr  64 位通知槽物理地址
总大小：24 字节

[DESIGN] Signal 位于 Host RAM 一致性内存，起始地址至少按 8 字节对齐，所有多字节字段采用小端格式。偏移 0x0c 的 4 字节保留字段用于让后面的 64 位地址自然对齐。完整 24 字节对象和通知槽的对齐、地址溢出及访问范围按第 2.4.2 节检查。这是本实验的布局，不套用 AMD 的完整 Signal 对象格式。

Host 在发布任务前填好 Signal，提交后保持固定字段不变，完成值仍按单一更新者规则由 CP 更新一次。CP 在发布完成值前取得并保存通知所需的事件编号和通知槽地址，之后按保存的信息完成通知。

2.5.3 通知槽标记与防止漏唤醒的等待登记

以下仍使用 Signal S、事件编号 7 和通知槽 M7。完成值、默认等待方式和 IH 交付顺序沿用前文，本节补齐通知槽写入值及驱动如何记住提前到达的通知：

Host 准备 Signal S
  → value = 1，event_id = 7，通知槽初值为 0
  → 发布 Dispatch
          ↓
CP 确认计算完成、结果写回
  → S.value：1 → 0
  → 向通知槽写入 7
  → 提交 SIGNAL_NOTIFY，事件编号为 7
          ↓
驱动找到所属进程中的事件 E7
  → 记住“通知已经到达”
  → 唤醒等待线程
          ↓
Host 重新读取 S.value
  → 确认等于 0，完成同步后返回

[DESIGN] 每个使用中的 Signal 独占事件和通知槽。驱动在所属进程内分配非零的 32 位无符号 event_id，同一进程中存活事件的编号不能重复。通知槽占 8 字节，至少按 8 字节对齐，提交前初始化为 0；CP 完成时写入零扩展到 64 位的 event_id，本例写入 7。

驱动处理对应 IH 记录时，用 mqd_addr 找到队列所属进程，再按 event_id 找到事件，确认事件与通知槽的关联。在事件对象中记录“已通知”后，再清零通知槽并唤醒等待者。事件状态保存在驱动内部，不占用 Signal 的保留字段。

清零通知槽不清除事件对象中的“已通知”状态。Signal、事件和通知槽只有在旧通知及相关处理全部结束后，才能按资源复用协议重新初始化；不能只因 S.value == 0 就立即复用事件编号或通知槽。复用继续遵守旧记录与对象寿命，具体资源接口已按 9.7 确认。

[DESIGN] 默认等待仍先检查 Signal，约 200 μs 后仍未完成且未超时，再进入内核事件等待。驱动中的通知处理与等待登记必须正确同步，通知状态与等待者的关联不能在竞争中丢失：

通知先到：
  驱动保存“已通知”
    → 线程随后请求等待
    → 发现通知已到，直接返回复查 Signal

线程先进入等待：
  登记等待者
    → 再次检查通知状态
    → 尚未通知才睡眠
    → 驱动先保存通知状态，再唤醒线程

等待返回不清除“已通知”状态；同一任务有多个等待线程时，可以一并唤醒。线程最终仍通过 S.value == 0 判断成功，重复唤醒不会重复修改 Signal。等待期限、唤醒后的复查以及不重新开始一轮主动轮询的规则继续按第 2.5.1 节执行。

[BOUNDARY] 本节与第 2.5.2 节已按9.5.4确认。具体内存屏障见第 6.4 节；Signal 访问失败、通知失败和错误唤醒按第 7 节执行，资源管理接口已按9.7确认。

2.6 MQD 的字段布局与装载、保存范围

驱动已经为 Queue A 准备好 Ring 和进度内存，接下来把这些对象的地址写进 MQD_A。CP 根据管理命令选择空闲用户槽位并找到 MQD_A，本例假设选中槽位 2。下面按正常装载、运行和卸载的顺序展示这份描述对象的使用过程：

Host 驱动填写 Host RAM 中的 MQD_A
  ├─ 队列配置：Ring 地址、进度地址、容量控制、Doorbell、VMID、格式
  └─ 保存状态：saved_rptr、saved_error；首次均为 0
       │
       │ HIQ 中的 MAP_QUEUES 携带 queue_kind = USER_AQL、MQD_A 物理地址
       ▼
CP 选择空闲用户槽位，本例选中槽位 2；读取并校验 MQD_A
  → 把 MQD_A 自身地址写入 HQD 的 CP_MQD_BASE_ADDR / HI
  → 把 MQD_A 中的队列配置装入 HQD
  → 从 saved_rptr 恢复消费位置，从 wptr_poll_addr 读取当前生产进度
  → 最后设置 ACTIVE = 1
       │
       ▼
Queue A 驻留期间
  → CP 使用 HQD 中的配置和消费位置处理命令
  → 消费进度另行回报到 rptr_report_addr 指向的 Host RAM
       │
       │ Host 停止提交并排空 Queue A，再经 HIQ 提交 UNMAP_QUEUES
       ▼
CP 开始卸载：清除 ACTIVE、关闭 Doorbell 使能，槽位仍占用
  → 确认目标队列相关在途访问已经结束
  → 将 32 位消费位置零扩展到 64 位，写入 MQD_A.saved_rptr
  → 将错误快照写入 MQD_A.saved_error
  → 达到卸载完成条件后，按管理结果和完成标记协议通知 Host

[DESIGN] KIQ、HIQ 和用户 AQL Queue 共用以下 MQD 布局。每个对象占 64 字节，位于驱动分配的 Host RAM 一致性内存中，起始地址至少按 8 字节对齐。多字节字段采用小端格式；除保留字节外，下列字段均为无符号整数。偏移从 MQD 起始地址计算：

MQD：64 字节，偏移范围 0x00～0x3f
  ├─ 0x00  ring_base          64 位 / 8 字节：Ring 的 Host RAM 物理地址
  ├─ 0x08  rptr_report_addr   64 位 / 8 字节：消费进度回报位置的物理地址
  ├─ 0x10  wptr_poll_addr     64 位 / 8 字节：生产进度存放位置的物理地址
  ├─ 0x18  pq_control        32 位 / 4 字节：Ring 容量与控制
  ├─ 0x1c  doorbell_control  32 位 / 4 字节：队列 Doorbell 配置
  ├─ 0x20  vmid              32 位 / 4 字节：第二阶段固定为 0
  ├─ 0x24  aql_control       32 位 / 4 字节：0 为非 AQL，1 为 AQL
  ├─ 0x28  saved_rptr        64 位 / 8 字节：零扩展保存 32 位消费位置，高 32 位为 0
  ├─ 0x30  saved_error       32 位 / 4 字节：卸载时保存的错误快照
  └─ 0x34～0x3f reserved              12 字节：保留

ring_base、rptr_report_addr 和 wptr_poll_addr 都保存完整的 Host RAM 物理字节地址，分别装入 HQD 的 CP_HQD_PQ_BASE / HI、CP_HQD_PQ_RPTR_REPORT_ADDR / HI 和 CP_HQD_PQ_WPTR_POLL_ADDR / HI。每组地址按第 2.4 节直接拆成低、高 32 位。四个配置字段分别对应 HQD 的 Ring 控制、Doorbell 控制、VMID 和 AQL 控制寄存器；pq_control 保存 Ring 字节容量，doorbell_control 保存偏移和独立使能，完整编码见第 8.1 节。

[DESIGN] 驱动和 CP 按以下规则使用这份布局：

  1. 首次初始化。 每条存活队列使用独立的 MQD。驱动填写配置，并把 saved_rptr、saved_error 和保留区清零。从发布映射请求到成功卸载，驱动保持配置字段不变；相关管理操作和卸载收尾完成前，MQD 内存及其物理地址保持有效，不释放或复用。首次启动的 KIQ 由 Host 按同一套配置填写 HQD，再按第 3 节启动 CP。
  2. 装载与激活。 MAP_QUEUES 提供目标队列种类和 MQD 物理地址；CP 根据种类确定可用的 HQD 范围，并为用户队列选择空闲槽位，再读取、校验并装入配置，恢复消费位置，最后激活。MQD 不重复保存自身地址，也不保存 ACTIVE；两者分别来自管理命令和装载流程。错误队列按第 7.2.4 节清理后重建；未绑定 MQD 的 saved_error 非零时拒绝激活，返回参数非法结果 status = 4，重新映射不清错或重放失败任务。
  3. 驻留与卸载保存。 驻留期间 CP 在 HQD 中维护活动状态，不在每个包完成后更新 MQD。正常卸载前由 Host 排空队列；CP 开始卸载时清除 ACTIVE、关闭 Doorbell 使能，确认相关在途访问结束后，只写回 saved_rptr 与 saved_error，配置字段保持原值。保存失败继续保留槽位占用，能够安全回报时按第 4.4 节返回结果码 5；目标队列尚无错误时记录编号 10，已有首次错误时保留原值，见第 7.2.3 节。异常退出按第 7.3 节处理，需要强制停止或故障复位的处理列入后续异常恢复扩展，正常回收继续遵守已确认的对象寿命条件。
  4. 重新装载。 正常成功卸载后，CP 从 saved_rptr 恢复消费位置；生产进度始终从 wptr_poll_addr 指向的共享内存读取，MQD 不缓存一份生产进度。正常重装要求 saved_error = 0；错误快照非零的队列须按清理后重建规则处理，不直接清错续跑。

[DESIGN] 消费进度 R 表示下一待消费包的编号，采用 32 位无符号数。卸载保存时，CP 将 HQD 中的完整 R 零扩展写入 64 位 saved_rptr；正常重新装载先检查高 32 位为零，再恢复低 32 位，高位非零则拒绝配置。例如当前 R = 7：

HQD 中 R = 7（32 位）
  → 卸载保存：saved_rptr 的高 32 位 = 0，低 32 位 = 7
  → 正常重装：检查高 32 位为 0，再把低 32 位的 7 装回 HQD
  → 从共享内存读取保留的生产进度 W，继续处理剩余包

进度初值、包地址、满空判断和计数溢出的规则见第 5.2.1 节。MQD 不随每个包更新，正常重装也不清零已保存的进度。

[BOUNDARY] 故障队列清除 ACTIVE 并保留占用，按第 7.2 节处理。正常卸载前排空、清除 ACTIVE 和关闭 Doorbell 的规则见第 7.4 节，任务卡住后的强制停止和复位恢复列入后续异常恢复扩展。

第二阶段 · 3. 固件装载、KIQ 配置与 CP 启动

3.1 固件存储与已有控制寄存器

Host 装载固件后，CP 要持续从 VRAM 取指，并使用其中的栈和全局数据。驱动为 Kernel 和应用数据分配显存时，需要避开这些空间。

[DESIGN] 第二阶段采用 64 MiB VRAM 配置。Linux 内核驱动维护设备统一的显存管理功能，管理从偏移 0 开始的前 60 MiB；最后 4 MiB 固定保留给 CP 固件。下面的地址均为 VRAM 字节偏移，不引入设备虚拟地址：

VRAM：0x0000_0000 ～ 0x03ff_ffff（64 MiB）
│
├─ Linux 内核驱动统一管理：0x0000_0000 ～ 0x03bf_ffff（60 MiB）
│    ├─ 首个 Host 页：登记为保留，避免普通显存分配结果为 0
│    └─ 其余空间：由驱动分配、记录占用和回收
│         └─ Kernel 描述对象、Kernel 代码、X/Y/Z 等应用数据
│
└─ CP 固件保留区：0x03c0_0000 ～ 0x03ff_ffff（4 MiB）
     │
     ├─ 0x03c0_0000 ～ 0x03fe_ffff（4032 KiB）
     │    ├─ 固件入口：0x03c0_0000
     │    ├─ 固件代码、只读常量
     │    ├─ 已初始化的全局变量
     │    └─ 启动时清零的全局变量、静态工作区
     │
     └─ 0x03ff_0000 ～ 0x03ff_ffff（64 KiB）
          └─ CP 栈，向低地址增长
               初始 sp = 0x0400_0000

CP 地址 0～vram_size-1 对应 VRAM 的相同字节偏移。Host 经 BAR2 基址 + 0x03c0_0000 写入入口代码，将 CP_RESET_VECTOR 设置为 0x03c0_0000；解除复位后，CP 从这个本地地址取指。Host 的 BAR 总线地址不能直接填入 CP 入口寄存器。

固件按固定入口链接，第一版不处理运行地址重定位。链接脚本安排代码、只读常量、全局变量和静态工作区，检查它们完整落在前 4032 KiB 内，不得越入栈区。Host 装载时检查目标范围，固件内容越界就拒绝装载。sp 初始指向栈区末尾的后一位置，压栈时先减小，再访问栈内地址；栈预算为 64 KiB。4 MiB 是固定保留容量，后续若调整容量或地址布局，须同步修改链接脚本和驱动中的范围定义。

驱动中的显存管理功能按设备维护一份统一的空闲、占用和保留状态，记录已分配区间及其所属上下文，负责实际 VRAM 空间的分配与回收。管理范围从偏移 0 开始，覆盖完整的前 60 MiB；首个 Host 页也由该功能登记为保留，普通分配从保留页之后开始。

[DESIGN] 参考 AMD 驱动的做法，底层复用内核通用伙伴分配器：目标内核提供 gpu_buddy 时使用该接口；目标内核仍提供 drm_buddy 时使用对应实现。驱动按设备建立一个分配器实例，管理前 60 MiB，并负责请求校验、并发保护、对象归属及释放时机。本阶段没有设备页表，普通显存对象申请连续区间，继续按起始偏移访问。

应用通过运行时申请 VRAM
  → Linux 内核驱动检查大小、对齐和其他请求条件
  → 调用 gpu_buddy 或目标内核的 drm_buddy，从前 60 MiB 分配区间
  → 驱动记录占用与所属上下文，将分配结果交给运行时
  → 运行时准备数据，CP 和执行器按已分配对象的偏移访问 VRAM
  → 设备访问结束且满足资源释放条件后，驱动调用分配器回收区间

QEMU 提供显存存储和设备访问接口；应用、运行时和 CP 使用驱动已经分配的显存对象。通用伙伴分配器组织空闲块并完成分配、拆分、回收与合并，驱动维护对象所属上下文及使用状态。构建时须核对目标内核的头文件、配置与导出符号，并启用对应组件；两种接口的关系和 AMD 依据见通用伙伴分配器说明。

末尾 4 MiB 固件保留区不进入普通显存分配池。这块保留区属于设备，应用退出、队列销毁或 CP 暂时复位都不释放它。更新固件前先停止 CP，并确认相关设备访问已经结束；CP 单独复位的影响见第 3.3 节。

[BOUNDARY] 这一布局通过分配范围避免正常分配发生重叠，Kernel 越界访问的设备隔离留到第三阶段。当前工作区已接入固定保留区、链接布局和启动初始化，原同步路径与队列模式分别运行；代码与测试说明见实现说明。

BAR 写入、DMA 写入、计算解释器写入和冷复位清零都应使对应 TCG 指令翻译失效，支持在相同地址替换固件。以下控制寄存器已经接入：

0x0500 CP_CTRL 与 0x0504 CP_RESET_VECTOR 都采用对齐、小端的 32 位访问。

CP_CTRL 的 bit 0 是可读写的 RESET_HOLD，默认 1；bit 1 是只读的 PRESENT。连接 CP 的设备默认读回 3，解除复位后读回 2。写入相同复位状态不会重新启动 CPU，保留位读零、写入忽略，PRESENT 的写入也忽略。置位 RESET_HOLD 恢复 CP 的原生复位状态，并持续阻止取指；清零后从已配置的入口运行。

CP_RESET_VECTOR 保存 CP 地址空间中的 32 位入口，默认 0。只有保持复位时可以修改；入口必须位于 VRAM 内且按 2 字节对齐。有效修改同步更新 CPU 的复位向量和复位态 PC。非法地址或运行期间修改入口会保留原值，并置位已有 ERROR_STATUS.INVALID_CMD。

没有连接 CP 的单进程设备对这两个寄存器读零、写入忽略。

3.2 配置并激活 KIQ 后解除复位

[DESIGN] 队列模式在固件启动流程中配置 KIQ，顺序如下：

Host 写 CP_CTRL.RESET_HOLD = 1，读回确认
  → 经 BAR2 将固件代码和已初始化数据装入固定保留区
  → 设置 CP_RESET_VECTOR = 0x03c0_0000
  → 准备 KIQ Ring、MQD 和相关内存，保持 KIQ 槽位 ACTIVE = 0
  → 通过 HQD 窗口填写 Ring 地址、容量、指针、MQD 地址、Doorbell 配置和队列格式
  → 保证配置和内存初始化对 CP 可见
  → 最后设置 KIQ 槽位 ACTIVE = 1
  → 执行访问屏障，读回确认写入完成
  → 写 CP_CTRL.RESET_HOLD = 0
  → CP 从固定入口执行固件，设置 sp = 0x0400_0000
  → 清零未初始化全局变量，初始化异常处理和内部状态
  → 检查 KIQ 的 ACTIVE 和可用命令，开始处理队列

Host 必须同时准备内存中的 KIQ MQD 和对应 HQD；只准备 MQD，尚未运行的 CP 无法据此找到 KIQ Ring。ACTIVE = 0 时暂不处理该队列；ACTIVE = 1 时检查可用命令。Ring 可以为空，激活不要求 Kernel 已开始执行。无需额外增加“通知 CP 检查 KIQ 配置”的寄存器。

CP_HQD_AQL_CONTROL 的整个 32 位值定义为：0 表示非 AQL，1 表示 AQL。KIQ、HIQ 配置为 0，申请创建的用户 AQL Queue 配置为 1；CP 据此选择解析流程。其他数值属于非法编码，不能把任意非零值都当作 AQL。队列格式须在激活前配置好，非法编码和运行期间修改格式按第 8.2 节拒绝并报告；解释与 AMD 参考见队列格式选择。

3.3 复位的影响范围

复位与启动在目标 CPU 线程中同步完成。GLOBAL_CTRL.ENABLE 只控制原有设备功能；CP 通过自己的控制位解除复位。

CP 单独复位清零 Host 访存窗口的基址，保留 VRAM、入口，以及原 DMA、派发和中断状态。GLOBAL_CTRL.RESET 复位设备状态并使 CP 回到保持复位、入口为 0 的默认值，VRAM 保留。设备冷复位先停止 CP，再清零 VRAM 并恢复全部默认状态。

[DESIGN] 设备冷复位或整体复位将所有 HQD 寄存器与 HQD_SELECT 清零；CP 单独复位保留 HQD 内容，供诊断和后续恢复使用。寄存器默认状态见第 8.2 节，故障后的队列恢复列入后续异常恢复扩展。

[DESIGN] 固件重新启动仍按第 3.2 节装载和初始化：Host 恢复已初始化数据，固件设置栈、清零未初始化全局变量并初始化内部状态，不能依赖 CP 单独复位清空这些内容。

CP 单独复位不能据此被解释为目标队列的全部访问已结束。队列的恢复、错误和资源释放条件按第 7、9 节确定。

            └─ 无空闲：报告创建失败

MQD 中的 aql_control 只说明包格式：KIQ、HIQ 均为 0，用户 AQL Queue 为 1，不能单靠这个字段区分 KIQ 和 HIQ。CP 结合命令来源与 queue_kind 判断本次映射或卸载的目标种类是否合法。

UNMAP_QUEUES 匹配到队列后，使用该 HQD 中保留的 MQD 地址保存必要状态。WRITE_COMPLETION 没有目标队列字段，偏移 0x04 的零是保留值，不表示操作槽位 0。

4.2 槽位绑定、重复请求与释放

驱动按申请动态准备队列和 MQD，再向管理 Ring 提交请求。CP 处理映射或卸载前，需要根据 queue_kind 确定目标范围，并用 mqd_addr 的完整物理地址查找当前绑定。下面的流程统一按实际地址识别目标：

Host 提交管理命令
  ├─ queue_kind：目标队列种类
  └─ mqd_addr：完整的 MQD 物理地址
       │
       ▼
CP 检查允许范围内的槽位及当前绑定
  ├─ 映射：判断重复、选择空闲槽位或报告满额
  └─ 卸载：查找绑定、完成卸载并释放槽位

[DESIGN] CP 固件在已有固件保留区的私有数据中，维护每个 HQD 槽位的占用状态和绑定的 MQD 物理地址。装载中、已绑定、卸载中、异常尚未清理的槽位都算占用。已装载队列的记录与 HQD 保存的 MQD 地址对应；ACTIVE = 0 不能单独作为空闲依据。这些是固件内部记录，不增加 MQD 字段或 HQD 寄存器。

CP 按完整 MQD 物理地址检查重复映射。同一个地址已经出现在占用记录中时，返回失败，结果含义为“重复映射”，保留原绑定、配置和消费位置，也不为它分配第二个槽位：

收到 MAP_QUEUES
  ├─ mqd_addr 已在占用记录中
  │    → 返回“重复映射”
  │    → 保留原绑定、配置和消费位置
  │
  └─ mqd_addr 尚未绑定
       ├─ 有可用槽位 → 分配并装载
       └─ 无可用槽位 → 返回失败

新的用户队列由 CP 从槽位 2、3 中选择空闲槽位，满额时返回“名额已满”。HIQ 使用专留槽位 1；该槽位已占用时，拒绝用另一份 MQD 覆盖。全设备仍最多同时存在两条用户 Queue，创建名额和复用范围沿用第 1 节。

收到 UNMAP_QUEUES 后，CP 在允许范围内匹配 mqd_addr。找到当前绑定时，处理对应队列的卸载；没有找到时，返回失败，结果含义为“队列未映射”，不修改其他槽位。成功卸载后，该地址尚未重新绑定时，再次提交卸载也返回“队列未映射”。本版不为此保存历史卸载记录。

正常卸载前，Host 按第 7.4 节停止提交并等待排空，再请求 CP 卸载。CP 按以下顺序释放槽位：

将槽位标为卸载中，清除 ACTIVE、关闭 Doorbell 使能，停止继续取包
  → 确认相关在途访问结束
  → 成功写回 saved_rptr、saved_error
  → 解除绑定，将槽位标为空闲

保存失败或无法确认访问结束时，继续保留占用。映射中途失败时，只有确认队列尚未激活、相关访问已结束、部分配置已经撤销，才归还槽位；否则保留占用，故障恢复留作后续扩展。Host 释放 MQD、Ring 等内存，仍须确认管理结果并满足已有生命周期约定。

[BOUNDARY] 本节确定请求处理结果和槽位释放条件。“重复映射”“名额已满”“队列未映射”的结果码、返回位置及后附标记处理见第 4.4 节；强制停止和故障复位步骤列入后续异常恢复扩展。

4.3 管理完成标记的取值、发布与复用

驱动已准备好本次用户队列的 MQD，接下来经 HIQ 请求 CP 建立队列，并等待配置结果。管理命令和后附的 WRITE_COMPLETION 都放在提交该请求的 HIQ Ring 中；新建的用户 Ring 保存 AQL Dispatch，结果区则是 Ring 外的独立内存。下面的对象均位于 Host RAM，M 表示本次请求结果区的起始物理地址，完成标记位于结果区开头：

HIQ Ring：保存驱动提交的管理命令
  │
  ├─ 第 1 条：MAP_QUEUES
  │    └─ mqd_addr → 本次分配的 MQD
  │                       └─ ring_base → 本次用户队列的 Ring
  │                                        └─ 保存 AQL Dispatch
  │
  └─ 第 2 条：WRITE_COMPLETION
       └─ completion_addr → Host RAM 中的结果区 M
                              ├─ completion：完成标记
                              └─ status：本次管理结果

管理 HIQ 时，对应的映射或卸载命令及其 WRITE_COMPLETION 放在 KIQ Ring 中。每次请求的两条命令必须位于对应的管理 Ring，按 Ring 的逻辑顺序相邻。相邻是命令保存顺序，CP 仍可按既有调度规则在不同轮次处理这两条命令。

以下以正常成功路径说明标记的使用，本次预期序号假设为 7：

驱动为本次请求取得结果区 M
  → 初始化 completion = 0、status = 0xffff_ffff，保留字段填 0
  → 本次预期值假设为 7

HIQ Ring 中按顺序放入：
  ① MAP_QUEUES 或 UNMAP_QUEUES
  ② WRITE_COMPLETION
       completion_addr  = M
       completion_value = 7

CP 完成前面的管理操作，暂存本次成功结果
  → 执行 WRITE_COMPLETION，先向 M + 8 写入 status = 0
  → 保证本次结果状态对 Host 可见
  → 向 M 写入完整的 64 位值 7

Host 读到 M 处的 completion == 7
  → 完成读取同步，再读取 M + 8 的 status
  → 满足回收条件后，归还结果区

[DESIGN] 每个在途管理请求独占一个 16 字节结果区，至少按 8 字节对齐。一次映射或卸载请求及其后附完成命令共用本次结果区；其中完成标记占 8 字节，结果码占 4 字节，另有 4 字节保留空间，布局见第 4.4 节。驱动按请求分配，尚未结束的请求使用不同结果区，不固定绑定某条用户队列。

驱动将标记初始化为 0，并按设备为每次管理请求分配新的 64 位无符号序号，从 1 开始。例如本次预期值为 7，下一次分配 8。CP 直接写入命令中的 completion_value，Host 按“等于本次预期值”判断，不把任意非零值当作完成。第一版不支持序号回绕复用。

驱动必须先完成整个结果区的初始化，再将管理命令和 WRITE_COMPLETION 成对发布到对应管理 Ring。CP 先结束前面的管理操作并暂存结果，再由 WRITE_COMPLETION 写结果码、写标记，保证 Host 看到预期值后能够读取本次结果。完成标记的完整读写沿用第 2.2.1 节和 9.4.3 已确认的规则：每次取得完整的 64 位旧值或新值，不能取得新旧部分拼出的混合值。具体屏障与后端访问路径遵守第 6.4 节。

Host 使用带超时的轮询等待管理标记，两次检查之间可以短暂休眠。读到本次预期值后，Host 完成相应读取同步，再检查管理结果；标记出现本身不替代成败判断。

[DESIGN] KIQ、HIQ 各自串行保护管理请求的发布。两个进程同时创建或销毁队列时，驱动在对应 Ring 的提交锁内检查消费回报，确认至少两个可复用槽，再将本次管理命令和 WRITE_COMPLETION 写入逻辑相邻的位置。两条命令都写完并保证可见后，一次将 W 增加 2，按模 2^32 发布，再通知 Doorbell。不能只发布前一条命令，就让另一请求插入其后。

例如请求 T1、T2 同时使用 HIQ，T1 先取得提交锁：

驱动准备 T1 的 MQD 和独立结果区
  → 取得 HIQ 提交锁，确认两个空槽
  → 写入 T1 的管理命令、T1 的 WRITE_COMPLETION
  → 保证两条命令可见，一次发布新 W，再通知 Doorbell
  → 释放提交锁，T1 等待自己的结果区

T2 随后取得同一提交锁
  → 按相同规则发布自己的命令对
  → 释放提交锁，T2 等待自己的结果区

相邻按逻辑包编号判断，允许前一条命令位于 Ring 末槽、后一条位于槽 0；单条命令仍不跨 Ring 末尾。空间不足时，本次请求尚未发布，不能推进 W 或覆盖旧槽。驱动发布 W 前完成命令写入同步，CP 读到新 W 后完成读取同步，再读取命令。等待结果时已释放提交锁，也不能持有会阻塞中断处理或其他必要操作的锁；各请求继续独占自己的结果区。这些锁与屏障只约束管理命令发布，不改变用户 AQL 的并行取号和填包规则。

只有确认 CP 不会再写入旧请求的结果区，且 Host 已结束旧请求的等待和结果处理，才允许复用这块内存。复用时将完成标记重新置为 0、结果码置为 0xffff_ffff、保留字段填 0，交给使用新序号的请求。等待超时不能直接清零、释放或复用结果区；必须保留，直到旧请求结束，或恢复流程确认相关访问已终止，再按上述条件回收。

[BOUNDARY] 本节确定标记的使用、等待和结果区复用规则。管理失败的结果码、回报顺序，以及管理通道故障后的等待退出方式见第 4.4 节；强制停止和故障复位步骤列入后续异常恢复扩展。

4.4 管理结果的写回与失败处理

驱动已经为新申请的用户队列准备好 MQD，并向 HIQ 提交映射请求。假设两个用户队列名额都已占用，CP 无法创建本次队列，需要把失败原因返回给驱动。下面以本次预期序号为 7、结果区起始物理地址为 M 举例：

HIQ Ring 中的本次请求
  │
  ├─ ① MAP_QUEUES
  │      mqd_addr → 本次申请的 MQD
  │
  │    CP 发现没有空闲槽位
  │      → 在固件私有数据中暂存 status = 1
  │
  └─ ② WRITE_COMPLETION
         completion_addr  = M
         completion_value = 7
           │
           ├─ 先向 Host RAM 的 M + 8 写入 status = 1
           ├─ 保证结果码对 Host 可见
           └─ 再向 Host RAM 的 M 写入 completion = 7

Host 读到 completion == 7
  → 完成读取同步
  → 读取 M + 8 处的 status
  → 得知本次创建失败，原因是“无可用槽位”

[DESIGN] 每个在途管理请求独占一个 16 字节结果区，位于 Host RAM，至少按 8 字节对齐，多字节字段采用小端格式。结果区开头的 8 字节保存完成序号，后面保存本次管理操作的结果码。以下偏移从结果区起始物理地址 M 计算：

0x00  u64  completion   8 字节，完成标记
0x08  u32  status       4 字节，本次管理操作的结果码
0x0c  u32  reserved     4 字节，保留并填 0

驱动发布请求前将 completion 初始化为 0，status 初始化为 0xffff_ffff，reserved 填 0。completion_addr 保存 M，CP 按完整的 16 字节结果区校验访问范围，包含地址加法和范围溢出检查。不同在途请求使用不同结果区；请求数量增加时增加结果区份数，每个完成标记仍使用完整的 64 位序号。序号分配、等待与复用继续遵守第 4.3 节。

[DESIGN] CP 执行 MAP_QUEUES 或 UNMAP_QUEUES 后，在固件保留区的私有数据中暂存本次结果。KIQ、HIQ 各有一份暂存状态，按来源管理 Ring 关联，不混用交替调度的结果：

CP 固件私有数据
  ├─ KIQ：等待后附 WRITE_COMPLETION 回报的管理结果
  └─ HIQ：等待后附 WRITE_COMPLETION 回报的管理结果

紧随其后的 WRITE_COMPLETION 取出该 Ring 的暂存结果，先向 completion_addr + 8 写入完整的 32 位结果码，保证结果可见，再向 completion_addr 写入完整的 64 位 completion_value。回报完成后，清除本次暂存状态。该命令同时负责结果码和完成标记的写回；第 4.1 节的 32 字节命令布局保持不变，结果码不增加到命令包、MQD 或 HQD 中。

名额已满、重复映射、卸载目标不存在等普通管理失败，也执行后附完成命令，随后可以继续处理该管理 Ring。MQD 访问失败时，只有固件能够安全结束本次处理并继续回报，才走相同流程。槽位保留、停止目标队列取包和资源释放仍按第 4.2 节及已有访存错误规则执行；收到失败结果后，Host 仍须检查生命周期条件才能回收资源。

[DESIGN] status 使用以下 32 位编码：

0：成功
1：无可用槽位，包括 HIQ 专留槽位已被占用
2：重复映射
3：队列未映射
4：管理命令参数非法
5：MQD 读取或状态保存失败
6：操作未能正常收尾，需要恢复

0xffff_ffff：初始值，尚无有效结果

Host 先等待完成标记等于本次预期序号，再完成读取同步并读取 status。0 表示本次管理操作成功，1～6 表示对应失败；完成序号已经匹配，但结果码仍是初始值或未知编码时，报告协议错误。这些是每次请求的结果码，CP_HQD_ERROR 的队列故障编号、首次记录和清理后重建规则见第 7.2 节。

[DESIGN] 无法读取管理 Ring、已发布命令配对错误、结果码或完成标记写回失败，均按管理队列故障处理。配对错误包括管理命令后面已发布的下一条命令不是 WRITE_COMPLETION，以及没有前一条管理操作的孤立完成命令；不能把旧请求的暂存结果交给下一请求。尚未发布的 Ring 空间仍按发布协议等待，不据此判断命令配对错误。

CP 将故障记录到来源 KIQ／HIQ 的 CP_HQD_ERROR，停止该管理 Ring 后续消费，不自动重放管理操作。结果码写入失败时不继续写完成标记；标记写入报错时不盲目重试，也不承诺撤销已经发生的写入。KIQ 实际通道故障统一按第 7.2.2 节停止全部新取包和新派发；HIQ 故障停止 HIQ，KIQ 和已驻留的正常用户队列继续处理。

Host 使用带超时的轮询，并在本次标记未匹配时检查来源管理队列的故障：

本次完成序号已匹配
  → 同步并读取本次结果码

本次序号未匹配，但来源管理队列已故障
  → 返回管理通道故障，本次操作结果可能尚无法确定

未取得完成结果或明确故障，且等待超时
  → 返回超时

故障或超时后继续保留相关内存，按第 4.3 节和恢复流程确认结果区及目标队列资源的回收条件。返回通道故障或超时本身不结束设备访问。

[BOUNDARY] 9.3.5 的结果区布局、请求结果码、后附完成命令行为和故障等待退出方式均已确认。队列故障编号、首次记录和停止范围已按第 7.2 节确定，失败后的进度处理与等待退出已按第 7.3 节确定，强制恢复列入后续异常恢复扩展，正常回收继续遵守已确认的对象寿命条件；驱动向应用返回的接口形式已按 9.7 确认。

第二阶段 · 5. 命令发布、进度读取与队列选择

5.1 Ring 固定包槽与末尾回绕

驱动已分配 Ring，Host 要向空槽填写完整命令，CP 要按槽位顺序读取。下面以一个 256 字节、每包 64 字节的用户 AQL Ring 为例，说明包槽边界与循环复用；图中的槽位均指 Ring 包槽。

Ring 内字节范围：

槽 0            槽 1            槽 2            槽 3
[0～63]   →     [64～127]  →    [128～191]  →   [192～255]
  ↑                                                 │
  └────────────── 末尾回绕 ─────────────────────────┘

槽 0 的再次使用：
CP 消费旧包并回报进度
  → Host 确认槽 0 可复用
  → Host 填入并发布下一轮的新包
  → CP 再次走到槽 0 时，按发布状态判断能否读取

[DESIGN] KIQ、HIQ 的管理 Ring 每槽固定为 32 字节，用户 AQL Ring 每槽固定为 64 字节，每条命令完整占用一个槽。Ring 基址沿用第 2.4.2 节的 64 字节对齐要求；从基址起按包大小连续划分，管理命令起点按 32 字节对齐，AQL 包起点按 64 字节对齐。两类 Ring 的字节容量仍为第 8.1 节规定的 64 字节～64 KiB 的 2 的幂。

管理 Ring 的槽数为“字节容量 ÷ 32”，AQL Ring 的槽数为“字节容量 ÷ 64”。因此同样是 256 字节，管理 Ring 可放 8 条命令，AQL Ring 可放 4 个包；图中的 256 字节只用于举例，不指定各队列的默认容量。

[DESIGN] 每个包必须完整位于 Ring 内，不能拆成位于末尾和开头的两段。现有容量都是包大小的整数倍，按固定槽位排列即可，无需末尾填充命令。最后一个槽处理完后，下一个物理槽回到槽 0，继续使用原内存，不整体清空 Ring；物理槽回绕时，逻辑包编号按第 5.2.1 节继续累计。

[DESIGN] 创建用户 AQL Ring 时，Host 将每个槽的 Header 初始化为 INVALID。正常 Dispatch 按第 6 节完成并收尾后，CP 将旧包槽标为 INVALID，推进并回报消费进度；Host 观察到对应消费回报后，才能覆盖该槽并发布下一轮的新包。

CP 回绕到槽 0 时，先根据生产、消费进度确认当前编号是否已被预留，再根据 Header 判断能否处理。AQL Header 仍为 INVALID 时等待，不能仅凭槽内残留的旧包体再次执行任务。管理 Ring 不使用 AQL Header，按管理命令的发布协议判断可读范围。

[BOUNDARY] 本节确定固定包槽、物理末尾回绕和再次取包的条件。进度单位、位宽、满空判断和计数溢出见第 5.2.1 节；完整字段读写按 9.4.3 执行；包体、Header、生产进度、Doorbell 的发布与刷新规则已按 9.4.4、9.4.5 确认。失败包按第 7.3 节停止正常收尾。

  ▼

  ▼
Host 读取消费回报，可以复用包 6 原来占用的槽

[DESIGN] 两类 Ring 均按包计数，使用 32 位无符号进度，R 表示下一待消费包的编号。用户 AQL Queue 的 W 表示下一待预留包的编号：Host 通过原子读改写推进 W，取得本次预留编号，然后等待对应物理槽可复用。取得编号时，物理槽可能仍由旧包占用，也可能已经归还、Header 为 INVALID；取得编号本身不允许覆盖旧包。包体写完后，再以 release 语义发布有效 Header；CP 取得新 W 后仍须检查当前包的 Header。已预留但尚未发布的包计入 W。

管理 Ring 没有 AQL Header，沿用以 W 标出已发布命令范围的约定：驱动准备好命令，再更新 W。管理命令占 32 字节、AQL 包占 64 字节，但每消费一包，R 都增加 1。正常 Dispatch 仍按第 6 节完成并收尾后才推进 R。两类 Ring 的发布条件见下节。

包编号持续累加，仅在超过 32 位范围时按模 2^32 回绕。找到物理包槽时，才按 Ring 槽数取模：

S = 每包字节数：管理命令为 32，AQL 为 64
N = Ring 字节容量 ÷ S

包编号 P 对应的槽号 = P mod N
包地址 = Ring 基址 + 槽号 × S

上例中，包 6 位于 6 mod 4 = 2 号槽，地址为“Ring 基址 + 128 字节”；包 7 位于槽 3，包 8 回到槽 0。物理槽回到开头时，包编号仍为 8，不随槽号改成 0。

[DESIGN] 用户 AQL Queue 允许先取编号、再等空槽。对观察到的进度，差值 D = (W - R) mod 2^32 表示已预留但尚未归还的编号数量，包括正在等待旧槽释放的预留。因此，D 可以大于物理槽数 N，不能直接把它当作物理占用槽数，也不能仅凭 D > N 报进度错误。

D = (W - R) mod 2^32

D = 0       → 本次进度快照中没有已预留、尚未归还的编号
0 < D < N   → 已有预留，当前窗口内仍有未预留的位置
D >= N      → 当前窗口内的位置均已预留；后续编号可以先取，但须等槽

AQL 包是否已经发布，仍由该包的 Header 判断。

每个提交线程必须按自己的包编号 P 判断能否填写物理槽。下面的 R 使用 Host 读取到的消费回报，N 为这条 Ring 的槽数：

先原子推进 W，取得本次编号 P
  → 反复读取完整的消费回报 R
  → 计算本次编号到回报位置的距离：(P - R) mod 2^32
      ├─ 距离 >= N：旧槽尚不可复用，等待并重读 R
      └─ 距离 < N：本次编号已进入可写窗口
          → 完成消费回报对应的同步，确认旧 Header 为 INVALID
          → 在 P mod N 号槽填写包体
          → 发布有效 Header，再通知 Doorbell

等待时使用已取得的 P，不能要求全局 W - R 先降到容量以内。后面的线程也可能已经取号，使 W 继续增加；这不妨碍已经进入可写窗口的较早编号填包。

例如仍取 4 个槽，当前 R = 10、W = 14，包 10～13 已预留且尚未归还。另一个线程继续取号：

Host 原子取到 P = 14，W 从 14 增加到 15
  → D = 15 - 10 = 5，大于容量 4，属于允许的预留状态
  → 包 14 使用槽 2，但槽 2 当前仍保存包 10
  → P - R = 14 - 10 = 4，Host 等待，不改动槽 2

CP 完成包 10 的处理和收尾
  → 将槽 2 的 Header 置 INVALID，再向 Host 回报 R = 11

Host 取得新回报并完成同步
  → P - R = 14 - 11 = 3，小于容量 4
  → 可以在槽 2 填写包 14

全部 N 个槽都可使用，不额外空出一个槽。消费回报尚未更新时，Host 继续等待相应旧槽。CP 使用 HQD 中的 R 和取得的 W 判断是否存在待处理编号；即使 D > 0，当前 Header 为 INVALID 时也须等待发布。

管理 Ring 的 W 保存已发布边界，仍由驱动在有空间时写完整命令后推进。它的有效已发布范围不能超过 N 个尚未归还的包，不能套用用户 AQL 的提前取号规则。每次管理请求须先取得两个可复用槽，再成对发布；并发保护按第 4.3 节执行，失败处理按第 4.4 节执行。

[DESIGN] 进度增量和差值都明确按模 2^32 计算。下面仍取 4 个槽，展示数值溢出前后的连续使用：

R = 0xffff_fffe
W = 0x0000_0001

D = (W - R) mod 2^32 = 3

三个已预留、尚未归还的包编号：
0xffff_fffe → 0xffff_ffff → 0x0000_0000

对应物理槽：
     2      →      3     →      0

不能用普通的 W < R 判断进度错误，也不因计数溢出而清空 Ring。现有容量除以包大小后，槽数都是 2 的幂，最大为 2048；每个槽数都整除 2^32，因此计数溢出后仍可用同一公式定位下一槽。用户 AQL 允许预留超出物理容量的编号，但每个线程仍须满足上述 P 与 R 的条件才能写槽，差值检查也不能代替 Header 发布协议。32 位模运算还要求预留进度领先最老未归还编号的距离必须小于 2^32；运行时必须限制在途预留数量，避免活跃编号重复。验证须覆盖预留上限与跨计数溢出的并发行为，已运行的用例及结果见大纲进度说明。

[DESIGN] CP_HQD_PQ_RPTR 的整个 32 位值保存当前 R，固件不另存消费编号的高位。Host RAM 中的生产进度和消费回报也保存 32 位无符号数，存放位置沿用至少 8 字节对齐的约定；指定这些位置的地址仍为完整的 64 位 Host RAM 物理地址。

首次创建时，W、HQD 消费进度、消费回报和 MQD.saved_rptr 均初始化为 0。正常卸载前，Host 按第 7.4 节停止提交并等到消费回报 R == W；CP 卸载时将当前 R 零扩展到 64 位，保存到 MQD.saved_rptr，高 32 位填零。重新装载先检查高 32 位为零，再恢复低 32 位；高位非零则拒绝该配置。生产进度继续从共享内存读取保留的 W，不因重新装载而清零。MQD 的字段布局与装载、保存流程见第 2.6 节。

[BOUNDARY] 本节已确定进度数值及正常初始化、恢复规则。字段完整读写和发布同步遵守第 2.2.1 节，用户 AQL 的多生产者主方案见第 9.4.4 节，Header 的完整 32 位访问、管理 Ring 的串行发布及取号约束也已确认。生产进度按第 5.2.3 节刷新；失败包和回报失败按第 7.3 节处理，强制恢复步骤列入后续异常恢复扩展。

5.2.2 包发布与队列选择

Host 已准备任务资源，接下来向一个可复用的 AQL 槽填包。Kernel Dispatch 的 header、setup 各占 16 位，位于包开头的同一个 32 位字中：

包起始地址 + 0x00：32 位 full_header
  ├─ 低 16 位：header，包含包类型等控制位
  └─ 高 16 位：setup，包含执行维度

Host 保持包类型为 INVALID，填写其余包体
  → 将有效 header 与 setup 合成一个 32 位值
  → 按 release 顺序完整写入 full_header
  → 通知 Doorbell

CP 完整读取同一个 32 位字
  ├─ 类型为 INVALID：保留 R，后续再检查
  └─ 类型有效：完成读取同步，再读取、校验其余包体

[DESIGN] 包开头的 4 字节按 4 字节对齐，Host 与 CP 均以完整的 32 位值读写，只能观察到完整旧值或完整新值；不把共享 Ring 中的 header、setup 拆成两次 16 位访问。Host 可以在私有临时变量中分别准备字段，向共享槽发布时必须合并。槽初始化和 CP 归还槽时，将这个 32 位字写为 0x0000_0001，即包类型为 INVALID、其余首部位清零；无需清空后面 60 字节。填包期间首部保持无效，最后一次完整的 32 位写入才发布有效包。

这里要求完整的原子读取或写入，不增加首部的原子读改写操作。Host 发布前后沿用第 6.4 节的屏障，CP 取得有效首部后同步读取包体；Host、CP 窗口与 QEMU 后端共同保证该 32 位访问完整。归还槽时，CP 先恢复 INVALID 并保证可见，再回报新 R；Host 读取相应消费回报并同步后才复用，具体顺序见第 6 节。

[SPEC] HSA System Architecture 1.2，2018-05-02，§2.8.3，原文第 20～21 页要求包开头的 32 位采用 32 位原子事务，并要求 INVALID 全局可见后才推进读索引。规范允许在任务仍未完成时归还包槽；本实验仍按已确认流程，在整个 Dispatch 完成及成功收尾后归还，不能据此推定 MI300X 固件采用相同的回收时机。

[SOURCE] ROCr 固定提交 ba56a24c6132c5d195686ae4adf969ca1222fbba：runtime/hsa-runtime/inc/hsa.h 的 2959～2976 行定义两个 16 位字段与 32 位 full_header 的共用布局；runtime/hsa-runtime/core/runtime/amd_blit_kernel.cpp 的 863～901 行在 BlitKernel::PopulateQueue() 中保持无效类型填包，再以 32 位 release 存储发布 full_header。

[DESIGN] 用户 AQL Queue 先更新预留进度 W，再填写包体，最后发布有效 Header 并通知 Doorbell。继续上例，假设 CP 已归还包 6～8，此时 R = W = 9，Host 接着预留包 9。下图展示 CP 提前观察到新 W 时可能发生的交错；包 9 位于 9 mod 4 = 1 号槽：

Host 原子预留包 9，W 从 9 增加到 10
  → 读取 R = 9，确认包 9 对应的槽 1 可复用
  → 槽 1 的 Header 仍为 INVALID

CP 若此时检查这条队列
  → 读到 W = 10、R = 9
  → 检查包 9 的 Header，读到 INVALID
  → 保持 R = 9，等待该包发布，暂不按有效包解析包体

Host 继续填写包 9
  → 保持 Header 为 INVALID，写完包体
  → 以 release 语义发布有效 Header
  → 按通知协议写 Doorbell；同一个包不再增加 W

CP 再次检查包 9 的 Header
  → 确认有效，并取得包体的可见性
  → 读取、解析包体，再提交执行
  → 正常完成并收尾后，按第 6 节推进和回报 R

W 让 CP 知道当前编号已被预留，Header 才完成包体与消费者之间的交接。CP 可以读取 Header 来判断状态；看到 INVALID 时，不能把尚未完成填写的包体当作有效命令，也不跳过当前 R 处理后面的包。这个队列暂时没有可处理包，按下文调度规则等待后续检查。

Host 发布有效 Header 后，W 可以保持不变。因此重试协议必须能在 W 不变时发现 Header 的变化，不能只等写索引再次增长。CP 按正常队列选择规则重新检查，通知与生产进度刷新按第 5.2.3 节处理。AMD 运行时的固定源码与本版取舍见预留与发布参考。

[DESIGN] 同一条用户 AQL Queue 支持多个 Host 线程提交。Host 原子更新共享内存中的 32 位 W，为各线程分配不同包编号；CP 只读取 W。每个线程等自己的物理槽可复用后，独立填写和发布，不用一把锁把所有线程的填包、Header 发布和通知过程串起来。

假设 R = W = 10，且至少有两个可复用槽，两个线程分别提交一包：

线程 1：原子更新 W，取得包编号 10 → 填写包 10
线程 2：原子更新 W，取得包编号 11 → 填写包 11
两个线程取得不同编号后，可以并行填包。

线程 2 先写完：
  → 发布包 11 的有效 Header，再通知 Doorbell

CP 检查包 10，发现仍为 INVALID：
  → 保持消费位置，等待后续检查

线程 1 写完：
  → 发布包 10 的有效 Header，再通知 Doorbell
  → CP 按包 10、包 11 的顺序处理

取号必须是一次原子读改写，不能由独立的读取和写回拼成；它保证各线程取得不同编号，包体可见性则由后续 Header 发布保证。W 保持 32 位对象和 32 位访问，存放位置至少按 8 字节对齐，并映射为支持 Host CPU 原子操作的共享普通内存。原子预留在 Host 线程之间完成，不要求 CP 的访存窗口提供原子加法。

每个线程只能填写自己预留、且已满足槽复用条件的包；填写期间 Header 保持 INVALID。CP 遇到当前包尚未发布时不跳过它，按下文规则检查其他队列，后续仍能在 W 不变时发现 Header 发布。调用方须在原子取号前完成可能失败的资源准备和参数检查。正常路径取号后必须完成发布，第一版不提供取消预留编号的能力，不能回退共享 W。

[DESIGN] 调用方先准备代码、参数、Signal 和事件等资源，再进入预留、填包、发布过程。以下以线程已取得编号 P 为例：

可能失败的资源准备、参数检查 → 成功后才原子取号
  → 取得 P，等待对应物理槽
  → 填包、发布有效首部、通知 Doorbell
  → 本次发布结束

取号后线程异常退出，P 留下 INVALID 空洞
  → CP 仍停在 P，不跳过它
  → 调用方停止继续使用这条队列，保留必要资源
  → 不回退 W、不自行填补空洞；补洞和自动恢复留作扩展

异常退出的资源保护沿用第 7 节和第 9.7 节，不能把提交线程退出当作设备访问已结束。CP 看到 INVALID 仍按未发布处理，不新增自动识别空洞或超时清除包槽的协议。在途预留数量由调用方的提交代码限制，保证 W 领先最老未归还编号的距离小于 2^32；具体限额随接入落实，须防止活跃编号重复。

管理 Ring 没有 AQL Header，仍以已发布的 W 确定可读命令范围：驱动按管理 Ring 串行发布规则取得两个空槽，写完本次命令对，再一次发布 W 并通知设备。opcode 只表示操作类型，不作为独立发布标记。

CP 根据 CP_HQD_PQ_WPTR_POLL_ADDR / HI 读取对应队列的软件进度，并用固件变量保存本次处理所需的值；本版不采用 CP_HQD_PQ_WPTR_LO / HI。

Doorbell 通知设备有包发布，CP 通过读取共享 W 刷新自己掌握的生产进度。队列驻留期间，以 CP_HQD_PQ_RPTR 保存的消费位置为依据，由 CP 按实际消费情况推进。通知不能覆盖消费位置或跳过尚未消费的包。例如下一待消费包为 10，Host 连续发布并通知包 10、11、12 后，CP 仍从 10 开始按序处理。

Ring 地址、容量、消费位置、生产进度及包的发布状态共同决定可处理的命令。Doorbell 通过 HQD 中的 BAR4 相对偏移与队列关联，字段编码见第 8.1 节，入口分配、通知写入值和重新读取生产进度的时机见第 5.2.3 节。看到尚未发布的 AQL INVALID 槽，应按发布协议等待，不能仅凭该值报告坏包。

[DESIGN] 裸机固件按固定规则选择队列：

开始一轮检查
  → 检查 KIQ、HIQ，各处理至多一条可处理的管理命令
  → 从上次记录的位置开始，轮流检查用户槽位 2、3
      ├─ 未激活或没有可处理命令：跳过
      ├─ 两条都没有可处理命令：回到主循环
      └─ 找到可执行 Dispatch
          → 提交整个 Dispatch，轮询执行器直到完成
          → 按第 6 节收尾，记录下次优先检查另一条用户队列
          → 回到主循环

等待计算完成期间，CP 暂不处理其他队列，包括 KIQ、HIQ；Host 在 Ring 有空位时仍可继续发布。以下把当前分配在用户槽位 2、3 的两条队列记作 A、B。若 A、B 始终就绪，执行顺序为 A1、B1、A2、B2；B 无任务时跳过 B，继续 A。轮流选择保证提交机会，不保证两条队列占用相同计算时间。

A、B 的 HQD 可以同时保持驻留，轮换处理无需换出另一个槽位。若当前 Dispatch 一直不结束，普通队列处理也会停住；等待超时只结束本次等待，强制中止和复位收尾列入后续异常恢复扩展。本版不增加可配置的优先级或时间片寄存器，也不实现中途抢占。调度限制及扩展依据见固定轮流选择与阻塞执行。

5.2.3 Doorbell 入口、通知值与队列复查

沿用上一节的两个线程例子：Queue A 已激活，包 10、11 均已取得可复用槽，此时 W = 12、R = 10，本例不再预留其他包。线程 2 先发布包 11，线程 1 随后发布包 10；两次通知写入同一个 Doorbell 入口：

线程 2：发布包 11 的有效 Header → Doorbell ← 11
CP 检查 Queue A：
  → 读取 W = 12，从 R = 10 检查 Header
  → 包 10 仍为 INVALID，保持 R，暂时检查其他队列

线程 1：发布包 10 的有效 Header → Doorbell ← 10
CP 再次检查 Queue A：
  → W 仍为 12，包 10 的 Header 已有效
  → 处理包 10，正常完成并收尾后推进 R = 11
  → 按既定调度再次轮到 Queue A，继续处理已发布的包 11
  → 包 11 正常完成并收尾后，R = 12，此时队列为空

包 11 不需要补发 Doorbell 通知。

[DESIGN] KIQ、HIQ 和每条用户 Queue 各用独立的 Doorbell 入口。管理队列的入口由驱动保留，用户 Queue 的入口在创建时由驱动分配；驱动将 BAR4 相对偏移写入 MQD，CP 装入 HQD 后建立入口与队列的对应。用户入口不固定绑定 HQD 槽位 2 或 3；入口与队列一同保留，旧映射和销毁后的复用按 9.7 的生命周期规则落实。

每个入口按 8 字节对齐，Host 每次完整写入 64 位小端值。低 32 位保存已发布包的编号 P，高 32 位填零；共享内存中的 W、R 继续按 32 位访问。Doorbell 控制字段仍以 4 字节为偏移单位，8 字节入口要求对应的偏移字段值为偶数；完整 8 字节访问必须落在 BAR4 内。配置值与通知值的换算见第 8.1 节。

用户 AQL 包先发布有效 Header，再向 Doorbell 写 P。同一线程连续发布一批包时，可以在这批包全部发布后，用最后一个包编号通知一次；通知不能引用尚未发布的包。管理 Ring 先写完整命令、发布新的 W，再以本次最后一个包编号通知，即 (W - 1) mod 2^32。

多个 Host 线程的通知值允许乱序，如上图中的 11 → 10。后写入的 10 不会撤销包 11 的通知，也不能把消费位置或已知工作范围缩回包 10。设备不能仅因数值较小或与前次相同就丢弃有效通知；重复、连续或合并通知都必须保留继续发现已发布包的能力。CP 从当前 R 按顺序检查 Header，不能用通知值直接覆盖 R，也不能把最后一次通知值直接当作共享 W。

[DESIGN] 第一版 CP 每次按主循环轮到一条活跃队列时，都根据 CP_HQD_PQ_WPTR_POLL_ADDR / HI 重新读取 W，再从 R 检查当前包。W = R 时本次无包可取；用户 AQL 的当前 Header 为 INVALID 时保留 R，转去检查其他队列，后续再次读取 Header。这个复查过程不以 W 增长或再次收到 Doorbell 为前提。

Doorbell 提供有包发布的通知，CP 在该队列下一次被检查时取得最新进度和发布状态。队列读空后仍参加后续轮询；CP 等待计算完成期间到达的提交，在返回主循环后检查。已发布的包可按序继续处理，无需为同一批已通知工作逐包补发通知。调度仍按第 5.2.2 节执行，不要求一次清空整条 Ring；本实验仍在整个 Dispatch 完成并收尾后推进 R，任务结果通过 Signal 和错误协议确认。

[BOUNDARY] Doorbell、队列轮询及并发提交遵守本节约定。AMD/HSA 的乱序通知、按序派发与任务完成语义见Doorbell 参考；本实验每次检查队列时读取 W，不据此推定 AMD 固件的内部轮询方式。

第二阶段 · 6. 计算提交、完成 Signal 与 Ring 槽复用

CP 按第 6.1 节检查 AQL Dispatch，从包中取得任务规模、参数块物理地址和完成 Signal，并根据 kernel_object 中的 VRAM 偏移读取 Kernel 描述对象，再把代码入口、代码长度、完整的 Host 参数地址、参数长度及任务规模交给计算执行器。执行器通过只读参数窗口读取 Host RAM 参数，根据其中的偏移访问 VRAM 数组，见代码与参数的访问关系。

[DESIGN] 保留现有分发寄存器及 PCIe BAR 映射，正常任务改由 CP 访问这些分发接口。CP 向执行器交付的描述字段和参数访问方式见第 6.2 节，CP 地址映射、长度寄存器、提交与结果确认规则见第 6.3 节。这些接口与分段执行已接入，代码说明见计算派发实现。

正常成功路径采用以下顺序：

读取并解析 Dispatch，保持原消费位置
  → 提交计算，阻塞等待整个 Dispatch 完成
  → 确认结果写回，完成任务清理
  → 按完成协议发布 Signal，此后不再访问该任务的参数等资源
  → 完整写入 32 位首部，将原 Ring 包槽恢复为 INVALID
  → 保证 INVALID 对 Host 可见
  → 推进 CP_HQD_PQ_RPTR
  → 向 RPTR_REPORT_ADDR 指向的内存回报新进度
  → Host 观察到新进度后，可以复用已消费包占用的 Ring 槽

[DESIGN] CP 结束旧包槽访问后，以完整的 32 位写入恢复无效首部，执行带编译器内存约束的 fence iorw, iorw，再推进 HQD 中的 R 并向 Host 回报；后端须保证无效首部先于新回报可见。Host 取得允许本次编号使用该槽的消费回报后，执行带编译器内存约束的 dmb sy，以完整的 32 位读取确认首部为 INVALID，然后填写新包。读取和写入仍遵守完整访问规则，某一步失败时按第 7.3 节停止正常收尾。

读进度用于判断 Ring 槽是否可复用，任务结果按 Signal 和错误协议判断。回报内存保存 CP 发布的进度副本；MQD 在卸载保存时接收需要恢复的状态，下次驻留时再装回 HQD。Host 不独立推进这些副本。回报尚未完成时，Host 可能读到旧值，因此应暂缓复用对应槽位。进度副本与槽位复用的例子见消费进度与回报。

本版的 32 位消费进度按第 5.2.1 节表示，不采用 CP_HQD_AQL_DISPATCH_ID / HI，推进时机仍遵守上述顺序。Signal 按第 2.1.2 节由 CP 单独更新，仍须保证 64 位读写完整性和结果可见性。Dispatch 必须提供有效 Signal，包校验失败按下节停止所属队列后续取包；执行失败、写回失败及基本资源收尾按第 7 节和 9.6 执行，强制恢复留作后续扩展。

6.1 Kernel Dispatch 的布局、尺寸与字段校验

Host 要计算 1024 个元素的向量加法，已经准备好 Kernel 描述对象、参数块和完成 Signal。下面沿一次提交说明包里的信息怎样交给执行器：

Host 准备一个 64 字节 Kernel Dispatch 包
  ├─ kernel_object：Kernel 描述对象的位置
  ├─ kernarg_address：参数块的位置，保存数组位置和 N
  ├─ grid_size = (1024, 1, 1)：总共启动 1024 个线程
  ├─ workgroup_size = (256, 1, 1)：每组 256 个线程
  └─ completion_signal：本次任务的完成 Signal
          ↓
CP 检查包，读取 Kernel 描述对象
  → 换算成 4 个工作组，每组 256 个线程
  → 交给执行器
  → 成功完成并确认结果写回后，更新 Signal

[DESIGN] 第一版用户 AQL Queue 只执行 Kernel Dispatch。采用标准 AQL Kernel Dispatch 的 64 字节布局，保留字段偏移和位宽；字段取值的支持范围，以及描述对象、参数和 Signal 的引用方式，按本实验约定执行。独立的 Barrier-AND、Barrier-OR、Agent Dispatch 和厂商自定义包暂不支持；管理命令继续使用 KIQ、HIQ 的独立格式。

6.1.1 标准包布局与本版字段取值

以下按包起点列出字节偏移，多字节字段采用小端格式。grid_size 和 workgroup_size 分别由三个轴的字段组成；参数地址和完成引用都保留完整 64 位：

字节偏移  字段                     位宽
0x00      header                   16
0x02      setup                    16
0x04      workgroup_size_x         16
0x06      workgroup_size_y         16
0x08      workgroup_size_z         16
0x0a      reserved0                16
0x0c      grid_size_x              32
0x10      grid_size_y              32
0x14      grid_size_z              32
0x18      private_segment_size     32
0x1c      group_segment_size       32
0x20      kernel_object            64
0x28      kernarg_address          64
0x30      reserved2                64
0x38      completion_signal        64
总大小：64 字节

header 和 setup 各占 16 位，共用包开头的 4 字节；共享槽的这个首部按第 5.2.2 节以完整的 32 位值读写和发布。字段布局保持不变。有效 Dispatch 的 Header 按以下规则填写：

header：
  bits 7:0    type          = 2（KERNEL_DISPATCH）
  bit 8       barrier       = 0 或 1
  bits 10:9   acquire scope = 2（SYSTEM）
  bits 12:11  release scope = 2（SYSTEM）
  bits 15:13  保留，填 0

setup：
  bits 1:0    dimensions = 1、2 或 3
  bits 15:2   保留，填 0

因此，有效 Dispatch 的 header 为 0x1402 或 0x1502，区别只在 barrier 位；这两个值不用于槽初始化或尚未发布的状态。CP 读到 type = 1（INVALID） 时按发布协议等待，不继续用未发布的包体做字段校验。其他包类型按本版不支持处理。

[DESIGN] reserved0、reserved2 及 Header、setup 中的保留位全部填零。group_segment_size = 0，不申请工作组共享存储；private_segment_size = 0，不通过 Dispatch 申请每线程私有存储。线程继续使用现有固定寄存器，相关扩展见资源说明。

三个对象引用都必须有效：kernel_object 保存 VRAM 中 Kernel 描述对象的字节偏移，kernarg_address 保存 Host RAM 参数块的物理地址，completion_signal 保存 Host RAM 完成 Signal 的物理地址。第一版每个任务都提供独立的完成 Signal，不采用省略完成 Signal 的提交方式。对象的位宽、对齐、计算溢出和完整访问范围按第 2.4.2 节检查，描述对象、参数长度和向量加法参数布局见第 6.2 节，Signal 的 24 字节布局见第 2.5.2 节。

[SPEC] HSA System Architecture 1.2，2018-05-02，§2.9.1、表 2–4，原文第 25 页规定 Header 位域；§2.9.6、表 2–7，原文第 29 页规定 64 字节 Kernel Dispatch 布局。标准中的 completion_signal 是 Signal 句柄，本实验采用物理地址引用；布局沿用标准，不能据此认定完整 HSA 兼容。运行时字段定义与枚举见包格式参考。

6.1.2 从线程数量换算工作组数量

[DESIGN] setup.dimensions 支持 1、2、3。三个轴的 grid_size、workgroup_size 均必须大于零；一维任务的 y、z 轴都填 1，二维任务的 z 轴填 1。第一版只接受完整工作组，每一维的 grid_size 必须是对应 workgroup_size 的整数倍。

AQL 的 grid_size 表示各轴的线程数量，现有执行器的 grid_dim 表示各轴的工作组数量。CP 先检查整除条件，再逐轴换算；上面的向量加法对应：

AQL 包：
  grid_size      = (1024, 1, 1)
  workgroup_size = (256, 1, 1)
          ↓ 逐轴相除，得到工作组数量
执行器启动状态：
  grid_dim       = (4, 1, 1)
  block_dim      = (256, 1, 1)

CP 还须检查三个乘积：

  • 每组线程数：三个 workgroup_size 分量相乘，最多 1024。
  • 工作组总数：三个换算后的 grid_dim 分量相乘，最多 4096。
  • 实际启动线程总数：三个 grid_size 分量相乘，最多 65536。

计算过程必须检查溢出，不能先得到截断结果再与上限比较。

末尾数据不足一个完整工作组时，由运行时在发布前补齐包里的线程数量，并由 Kernel 检查实际数据范围。例如实际处理 N = 1000 个元素、每组 256 个线程：

运行时：grid_size_x = 1024，workgroup_size_x = 256，参数 N = 1000
  → CP 换算成 4 组，每组 256 个线程
  → Kernel：i < 1000 时处理元素，i >= 1000 时直接退出

这个任务按 1024 个实际启动线程检查上限。CP 收到 grid_size_x = 1000、workgroup_size_x = 256 时，按不满足整除条件拒绝该包，不自行补齐已经发布的任务尺寸。

[SOURCE] 实验子仓库固定版本 57543dd54b6b046b888277272fa84af81746b1ac：hw/gpgpu/gpgpu_core.h的 31–34 行定义三项上限；hw/gpgpu/gpgpu_core.c的 570–628 行检查乘积并遍历三维工作组。这些是教学执行器在该基线中的约束，不是 MI300X 的硬件上限；当时尚未接入 AQL 到执行器的换算。

6.1.3 任务同步与非法包处理

[DESIGN] Dispatch 的 acquire、release fence scope 均要求 SYSTEM。执行前落实输入和参数的可见性，任务完成时先保证结果写回，再发布完成 Signal；CP、执行器和 Host 软件须实际完成相应同步，不能只检查字段值。包体与 Header 的发布仍按 9.4 的规则执行，Host 等待完成后的同步按第 6.4 节执行。

Header 的 barrier 位允许 0、1。barrier = 1 要求当前任务在同队列前序任务完成后启动；本版每次完整执行一个 Dispatch 后才选择下一个，因此两种取值都满足这项要求，0 也不使当前执行器并行运行多个 Dispatch。独立 Barrier-AND、Barrier-OR 包仍不支持。

[DESIGN] CP 对已发布的包检查类型、保留位、必填对象引用、维度、整除条件、资源字段、同步字段和规模上限。遇到不支持的包或非法字段时，拒绝执行，记录到所属队列的 CP_HQD_ERROR，停止该队列后续取包，不静默忽略，也不把 Signal 更新为成功完成。INVALID 继续按正常等待处理。队列错误编号见第 7.2.1 节；失败后的消费进度、Host 等待退出和资源保留按第 7.3 节处理。

[BOUNDARY] Dispatch 校验、尺寸换算、计算交接及同步遵守本节约定。Kernel 描述对象与 RV32 计算执行器的参数约定已按9.5.2确定，完整规则见下节；RV64 CP 到执行器的寄存器和结果接口已按9.5.3确定，见第 6.3 节。

6.2 Kernel 描述对象与计算执行器参数窗口

Host 要提交 1024 个元素的向量加法，已准备好代码、数组和任务规模。以下是第二阶段用户 AQL 路径已确认的代码与参数交付流程；RV64 CP 执行固件，RV32 计算执行器运行应用 Kernel：

Host 准备
  ├─ VRAM：Kernel 描述对象、代码、数组 X/Y/Z
  └─ Host RAM：参数块，保存 X/Y/Z 的 VRAM 偏移和 N
                  ↓
RV64 CP 读取 Dispatch 和描述对象
  → 取得代码入口和长度、完整的 64 位 Host 参数地址、参数长度
  → 将这些信息和任务规模交给计算执行器
                  ↓
RV32 计算执行器启动各线程
  → 向 Kernel 提供参数访问入口
  → Kernel 读取参数，再访问 VRAM 中的数组

本节规定描述对象、参数块和计算线程的访问规则。CP 通过分发寄存器交付这些信息、启动和等待执行器的规则已在第 6.3 节确定。

6.2.1 16 字节 Kernel 描述对象

[DESIGN] 运行时在加载 Kernel 时，根据代码和该 Kernel 的参数约定生成描述对象，存放在驱动分配的 VRAM 中，至少按 8 字节对齐。Dispatch 的 kernel_object 保存描述对象的 VRAM 字节偏移。描述对象固定为 16 字节，四个字段均为 32 位无符号小端值：

偏移 0x00：code_entry    代码入口的 VRAM 字节偏移
偏移 0x04：code_size     代码区域的字节长度
偏移 0x08：kernarg_size  这个 Kernel 所需的参数块字节长度
偏移 0x0c：reserved      保留，填 0

第一版代码区域从 code_entry 开始。CP 在启动前检查入口按 4 字节对齐、code_size 为非零的 4 字节整数倍、地址加法不溢出，并确认整段代码落在有效 VRAM 范围内。执行器的每次取指都必须完整落在这段声明范围内。

同一 Kernel 的多次提交可以复用描述对象，每次 Dispatch 通过 kernarg_address 提供该次参数块的 Host 物理地址。运行时负责使参数布局与 Kernel 的读取方式一致。这里的 16 字节布局是本实验约定，标准 AQL Dispatch 包继续采用第 6.1 节的 64 字节格式。

6.2.2 Host 参数块的布局与长度

[DESIGN] 参数块位于驱动分配并映射给所属应用的 Host RAM 一致性内存，由运行时填写。基址至少按 8 字节对齐，长度由描述对象的 kernarg_size 给出，范围为 4 字节至 64 KiB，且为 4 字节的整数倍。运行时按该长度准备参数存储；没有参数的 Kernel 使用一个填零的 4 字节占位块。

第一版参数按 32 位小端字段排列，可保存数组的 VRAM 偏移、整数或浮点标量。字段顺序和含义由运行时与具体 Kernel 共同约定，CP 只检查地址和长度，不解释应用参数。向量加法的参数块为 16 字节，描述对象填写 kernarg_size = 16：

偏移 0x00：X 数组的 VRAM 偏移，32 位
偏移 0x04：Y 数组的 VRAM 偏移，32 位
偏移 0x08：Z 数组的 VRAM 偏移，32 位
偏移 0x0c：N，本例为 1024，32 位

其他 Kernel 可以使用不同的字段和长度，仍须满足上述对齐、长度和编码要求。数组内容保存在 VRAM，参数块中的数组位置继续使用 32 位无符号字节偏移。

6.2.3 计算线程通过只读窗口读取 Host 参数

[DESIGN] RV64 CP 把 Dispatch 中完整的 64 位参数地址 kernarg_address 和描述对象中的 32 位参数长度 kernarg_size 交给计算执行器。执行器保存本次任务的 Host 参数基址与长度，在计算执行器自己的地址空间提供固定的只读窗口。每个计算线程启动时，a0 保存这个窗口的入口：

参数窗口：0x9000_0000～0x9000_ffff，共 64 KiB
每个计算线程启动时：a0 = 0x9000_0000

Kernel 通过 a0 + 偏移 读取参数。执行器先根据窗口地址得到参数偏移，再加上保存的完整 Host 基址，按需读取 Host RAM；整块参数不搬到 VRAM。以读取向量加法的 N 为例：

执行器保存的 Host 参数基址：0x1_9000_2000
参数长度：16 字节

Kernel 执行 lw t0, 12(a0)
  → 访问计算执行器窗口地址 0x9000_000c
  → 执行器计算：Host 参数基址 + 12
  → 读取 Host 地址 0x1_9000_200c
  → t0 得到 N = 1024

64 位 Host 地址由执行器保存，32 位 a0 保存计算线程可访问的窗口入口。窗口范围固定为 64 KiB，实际允许读取的范围由本次 kernarg_size 限定；Host 参数基址只要求按 8 字节对齐，不要求按窗口大小对齐。

这个只读窗口服务于计算线程，需要接入 RV32 执行器的参数读取路径。CP 已有的 Host 访存窗口位于 CP 自己的地址空间，继续供固件读写 Host RAM。两者分别保存访问上下文；CP 的窗口映射不会自动成为计算线程的地址映射。

6.2.4 访问校验、资源寿命与失败处理

[DESIGN] 第一版参数窗口只接受自然对齐的 4 字节整数或浮点读取。执行器每次读取都检查访问范围完整落在 kernarg_size 内、整次读取的 Host 地址计算不溢出，并确认 Host 访存返回成功。向参数窗口写入也按错误处理。

例如 kernarg_size = 16 时，偏移 12 处的 4 字节读取覆盖字节 12～15，可以访问；偏移 16 处的读取已经越界，即使对应地址仍在 64 KiB 窗口内也必须拒绝。

Host 在发布 Dispatch 前准备好描述对象、代码和参数。发布后保持内容、存储和设备访问条件有效，直到确认任务不再访问它们。正常成功路径沿第 6 节完成任务清理后发布 Signal；异常结束按第 7.3 节处理，应用释放接口见9.7.4 的已确认接口，不能仅凭等待超时释放资源。

描述对象字段非法、取指越界、参数访问越界、向只读参数窗口写入或 Host 读取失败，都使本次任务失败。CP 记录所属队列错误并停止该队列后续取包，不发布成功 Signal。执行器通过第 6.3 节的状态和错误寄存器返回结果；CP 的队列错误编号见第 7.2.1 节，失败后的资源保留按第 7.3 节处理，执行器细分错误码见第 6.3.3 节，强制停止和故障复位按既定范围留作后续扩展。

[BOUNDARY] 队列模式已接入 16 字节描述对象、代码范围检查、Host 参数窗口及相关失败处理。旧同步路径仍把 VRAM 参数偏移写入 RV32 计算线程的 a0，源码与接口位置见参数访问说明。上述参数窗口和描述对象格式只用于本实验，不作为 AMD 硬件格式或既有 QEMU 能力。

6.3 CP 提交计算与读取执行结果

CP 已读取一个有效 Dispatch，接下来把描述对象中的代码信息、包中的 Host 参数地址和任务规模交给执行器。以下继续使用 1024 个元素的向量加法；本节采用 CP 解析描述对象、执行器接收解析后配置的分工：

CP 读取 Dispatch 和 Kernel 描述对象
  → 取得代码入口、代码长度、Host 参数地址和参数长度
  → 换算任务规模：4 个工作组，每组 256 个线程
  → 填写执行器配置，最后写 DISPATCH
          ↓
RV32 计算执行器
  → 从 VRAM 取指，检查是否超出代码范围
  → 通过只读窗口读取 Host 参数，检查是否超出参数范围
  → 执行计算并写回结果
  → 保存成功或失败状态
          ↓
CP 读取并确认执行结果
  → 成功：完成收尾，发布 Signal，再释放 Ring 槽
  → 失败：记录队列错误，停止该队列后续取包

6.3.1 CP 访问入口与原有启动配置

[DESIGN] 保留原有分发寄存器及其 BAR0 偏移。CP 按 0xfffd_0000 + BAR0 字节偏移 访问本节定义的寄存器；例如 Host 的 BAR0 + 0x0330 与 CP 的 0xfffd_0330 都指向同一个 DISPATCH。两条入口访问同一份设备状态。

原有配置在队列路径中采用以下含义：

0x0300 / 0x0304  KERNEL_ADDR_LO/HI：代码入口的 VRAM 偏移
0x0308 / 0x030c  KERNEL_ARGS_LO/HI：完整的 64 位 Host 参数物理地址
0x0310 / 0x0314 / 0x0318  GRID_DIM_X/Y/Z：工作组数量，本例为 (4, 1, 1)
0x031c / 0x0320 / 0x0324  BLOCK_DIM_X/Y/Z：每组线程数量，本例为 (256, 1, 1)
0x0328  SHARED_MEM_SIZE：第一版填 0
0x0330  DISPATCH：写 1，提交本次配置

KERNEL_ADDR 继续保存代码入口的 VRAM 偏移，第一版高 32 位填零；描述对象由 CP 读取，执行器不再解析描述对象。KERNEL_ARGS 保存本次 Host 参数地址，不能截掉高 32 位；参数内容由执行器经第 6.2.3 节的只读窗口按需读取。

所有寄存器采用对齐的 32 位小端访问。CP 在空闲时分高、低两次填写 64 位地址，全部配置写完并保证顺序后才写 DISPATCH；设备在提交时统一保存本次配置。这里不要求将两个地址寄存器合成一次 64 位原子写入。

6.3.2 代码与参数长度的交付

[DESIGN] 增加两个 32 位长度寄存器，CP 分别写入描述对象的 code_size、kernarg_size，单位均为字节：

BAR0 偏移  寄存器           CP 写入的值
0x032c     KERNEL_CODE_SIZE  code_size
0x0334     KERNEL_ARGS_SIZE  kernarg_size

执行器每次取指都检查整条指令落在本次声明的代码区域内；每次读取参数都检查整次读取落在实际参数块内。长度、对齐、地址溢出和失败处理沿用第 6.2 节，越界使本次任务失败。

例如参数块为 16 字节时，偏移 12 处的 4 字节读取合法，偏移 16 处的读取越界；固定窗口有 64 KiB，不代表本次任务可以读取整个窗口。两个长度用于精确检查本次访问范围，线程退出仍按现有指令约定处理，任务规模仍由工作组配置决定。

6.3.3 提交、执行状态与结果确认

[DESIGN] 一次只接收一个任务。新增三个 32 位寄存器，分别保存本次执行状态、失败原因和确认操作：

BAR0 偏移  寄存器          访问与含义
0x0338     DISPATCH_STATUS  只读：0=IDLE，1=BUSY，2=DONE，3=FAILED
0x033c     DISPATCH_ERROR   只读：本次失败原因，成功时为 0
0x0340     DISPATCH_ACK     写 1，确认已经读取本次结果

CP 只在 IDLE 时填写配置，最后向 DISPATCH 写 1。设备统一保存本次配置，校验通过后进入 BUSY 并执行；提交校验失败则直接返回 FAILED，不执行 Kernel。

IDLE → 提交 → BUSY → DONE 或 FAILED
                                  ↓
                         CP 读取并保存结果
                                  ↓
                         写 ACK → 回到 IDLE

提交校验失败：IDLE → 提交 → FAILED → CP 读取结果并写 ACK → IDLE

BUSY 或存在未确认结果时，拒绝修改配置和再次提交，保留当前任务及结果。DONE、FAILED 和对应结果保持到 CP 读取并确认；DISPATCH_ACK 只用于确认终态结果，不能中止正在执行的任务。CP 必须先保存结果，再确认取走，不能用尚未开始下一任务时读到的旧完成状态判断新任务成功。

本次执行结果单独保存。现有全局错误还会记录 DMA、非法寄存器访问等其他故障，CP 不能仅凭全局状态判断这个 Dispatch 的成败。基本错误退出按第 7 节执行，故障复位恢复留作后续扩展。

[DESIGN] 本次接入将 DISPATCH_ERROR 定义为以下独立编号，保留到终态确认；这些编号不直接写入 HQD。CP 读取失败结果后，仍以队列错误 4（执行器失败）记录所属队列：

0  NONE            没有执行错误
1  INVALID_CONFIG  提交配置不满足本版尺寸、地址或长度约束
2  CODE_RANGE      取指超出声明代码范围或不满足指令对齐
3  ARG_RANGE       参数读取越界、未对齐或访问宽度不支持
4  ARG_READ        Host 参数读取失败
5  ARG_WRITE       试图写入只读参数窗口
6  INSTRUCTION     无法执行的指令
7  VRAM            计算访问超出 VRAM
8  BUDGET          累计执行预算耗尽

忙时重提、未确认时修改配置、非法寄存器宽度或越权访问均保留当前任务及结果，另置全局 INVALID_CMD，不能借此覆盖当前 DISPATCH_ERROR。

6.3.4 执行器分段推进与 CP 等待

[DESIGN] 启动操作及时返回，执行器后续分段执行，各段之间保留线程状态，执行预算持续累计。CP 检查执行状态期间，执行器必须能够继续推进；Host 在 Ring 有可复用槽时也能继续发布任务。

第一版仍按整个 Dispatch 调度。CP 等待当前任务时不启动其他队列的任务，完成当前任务及收尾后再返回队列主循环。执行器分段推进只是让 QEMU 有机会处理其他活动，不改变本版一次完整执行一个 Dispatch 的队列选择规则。

6.3.5 提交权限、结果写回与 Signal

[DESIGN] 正常队列路径中，配置、DISPATCH 和 DISPATCH_ACK 由 CP 写入，Host 可以读取诊断状态。第二阶段队列路径沿用 9.5.2 已确定的 Host RAM 参数方案：CP 将完整的 Host 参数物理地址写入 KERNEL_ARGS_LO/HI。第一阶段已有的 Host 直接提交实现继续使用 VRAM 参数偏移，仅保留用于独立回归，不与队列路径同时运行。

执行器只有在计算结束、结果写回完成且相关访问结束后，才能发布 DONE；失败也须结束相关访问后再发布 FAILED。CP 读取并保存结果、完成必要清理后，写 DISPATCH_ACK 确认取走结果。

确认取走结果后，成功路径继续按第 6 节发布 Signal、通知 Host 和归还 Ring 槽；失败路径记录所属队列错误并停止后续取包，不发布成功 Signal。执行器结果供 CP 收尾使用，Host 仍按 Signal 和错误协议判断任务结果；正常队列路径不直接沿用旧同步提交的计算完成中断来代替 Signal 通知。

6.4 任务输入、执行结果与完成通知的可见性

继续使用 1024 个元素的向量加法。Host 已准备代码、描述对象、输入数组和参数；CP 取到包后要读取本次输入，Host 看到 Signal 完成后要取得本次输出。各步沿用已经确定的顺序，本节补齐屏障和访问接口的要求：

Host 完成输入准备，发布有效 Header，再通知 Doorbell
  → CP 确认 Header 有效，读取包体和描述对象，配置并启动执行器
  → 执行器完成计算、结果写回及相关访问，发布 DONE
  → CP 保存结果并清理、确认，依次发布 Signal、通知槽和 IH 通知
  → Host 读到 Signal = 0，完成同步，再读取结果

6.4.1 Host 准备输入并发布 Header

[DESIGN] Host 发布前须完成代码、描述对象和输入数组的 VRAM 上传，写好 Host RAM 参数与包体；通过 DMA 上传时，先确认传输成功完成。Host 仍按第 5.2.2 节原子预留编号，等待对应物理槽可复用，填写期间保持 Header 为 INVALID。

A57 用户态运行时封装带编译器内存约束的 dmb sy，在有效 Header 发布前及 Doorbell 写入前分别执行：

完成输入准备和包体填写
  → dmb sy
  → 按发布规则写有效 Header
  → dmb sy
  → 按规定宽度写 Doorbell

第一个屏障使输入与包体的写入先于有效 Header 对设备可见；第二个屏障保证 Header 发布先于 Doorbell 通知。共享内存采用一致性映射仍须落实这些顺序，volatile 访问也须配合屏障。上传接口须以实际传输完成作为可发布的条件，执行一次屏障不能代替等待 DMA 完成。

  • Documentation/memory-barriers.txt 的 1914–1956 行区分共享内存的 DMA 屏障与设备寄存器访问顺序。

本实验用户态采用上述 dmb sy 封装；内核的 dma_* 宏用于驱动中的相应访问，不能直接作为用户态调用。

6.4.2 CP 读取输入并启动执行器

[DESIGN] RV64 CP 固件封装带编译器内存约束的 fence iorw, iorw。确认 Header 有效后先执行屏障，再读取包体和描述对象；填写全部执行器配置后再执行屏障，最后提交：

读到有效 Header → fence iorw, iorw → 读取包体、描述对象等输入
写完执行器配置 → fence iorw, iorw → 写 DISPATCH = 1

第一处落实包发布后的读取顺序；第二处保证代码、参数地址、长度和任务规模全部配置完成后才启动计算。读取 Header、轮询状态及共享字段须使用规定的访问方法，不能让编译器复用上次读取的值。Dispatch 的 acquire、release scope 继续为 SYSTEM，输入可见性由 Host 发布、CP 同步与后端访问共同落实。

6.4.3 执行器写回结果后，CP 发布完成通知

[DESIGN] QEMU 执行器后端须先完成结果写回及本次相关访问，再发布 DONE。跨线程传递配置、结果或终态时，使用锁或 release/acquire 同步保证数据先于状态可见；发布 FAILED 也须遵守第 6.3.5 节的访问结束要求。CP 的内存屏障不能代替后端的实际完成和线程同步。

CP 取得并保存 Signal 的事件编号和通知槽地址后，成功路径按下列顺序处理。每处 fence 均指带编译器内存约束的 fence iorw, iorw：

读到 DONE
  → fence，读取并保存执行结果，完成必要清理，写 DISPATCH_ACK
  → fence，按单一更新者规则将 Signal 从 1 减为 0 并写回
  → fence，向通知槽写入零扩展后的 event_id
  → fence，经 IH_SUBMIT 提交通知

确认取走结果后再发布 Signal，Signal 写回成功后再写通知槽，通知槽写入成功后再提交 IH。各次 Host 访问必须确认成功，后端也须保证前一步写入已对后续观察者可见，才能继续后一步；不能把仅已排入请求队列当作写入完成。任何一步失败都转入第 7.3 节的异常退出流程，停止正常收尾并保留已经发生的写入。

包槽继续在 Signal 发布后按第 6 节归还，完整字段访问仍按第 2.2.1 节执行。内存屏障只补齐顺序要求，不能替代动态字段的完整读写约定。

6.4.4 Host 确认完成后读取结果

[DESIGN] Host 按完整 64 位访问规则读到 Signal = 0 后，通过同一运行时封装执行带编译器内存约束的 dmb sy，再访问结果，落实完成读取的 acquire 语义：

完整读取 Signal，确认值为 0
  → dmb sy
  → 通过现有接口读取或复制 VRAM 结果
  → 若使用 DMA 复制，等待成功完成
  → CPU 使用 Host 结果缓冲区

中断或事件唤醒只使线程重新检查 Signal；短暂轮询直接读到完成和阻塞唤醒后读到完成，都执行上述同步。通知处理与等待登记继续按第 2.5.3 节配合，等待者以 Signal 值判断正常完成。

验证时连续提交多轮向量加法，每轮改变输入和预期结果，分别覆盖短暂轮询读到完成、转入阻塞后唤醒，以及前一任务完成时后续任务已经发布的情况；检查参数、输入和结果都属于对应任务，不能只反复计算同一组数据。还须核对后端完成条件和跨线程同步，运行结果不能代替访问顺序审查。

第二阶段 · 7. 错误记录、卸载与资源释放

[DESIGN] 保留每槽位的 CP_HQD_ERROR，用于记录取包、命令校验、执行与完成写回中的实际异常。需要覆盖 Ring 或写指针读取失败、已发布命令非法或不受支持、Dispatch 描述或参数不可用、执行器返回失败、读进度回报失败，以及完成 Signal 无效或无法更新。访存失败的归属与停止取包规则已在第 2.1.1 节确定。管理请求通过独立结果区返回成败；管理通道取包、已发布命令配对和结果写回故障记录到来源管理队列，并停止该 Ring 后续消费。错误通知采用IH 记录通路，队列错误编号、首次记录、停止范围及清理后重建按第 7.2 节执行；失败收尾按第 7.3 节处理，强制恢复步骤列入后续异常恢复扩展。各类异常及诊断关系见队列错误记录。

访存或执行器必须把失败结果返回 CP，固件才能将错误归到所属队列。原有设备级 ERROR_STATUS 不能直接作为已经实现的 CP_HQD_ERROR 协议。Host 可通过选槽窗口查询错误；MQD 的 saved_error 在卸载保存时接收错误快照，Host 诊断缓冲区在驱动读取时接收副本，均不会自动同步。

Ring 为空、当前 AQL 槽仍为 INVALID 或执行器忙属于正常等待。已发布的不支持包和非法字段按第 6.1.3 节拒绝执行并停止所属队列后续取包；第一版不执行独立 Barrier 包，也不把它当作依赖等待。Host 等待超时只表明等待期限已到，不能直接据此认定 Kernel 执行失败。

正常卸载时，Host 先停止提交并等待队列排空，再请求 CP 卸载；CP 停止目标队列取包，确认相关访问结束，保存 MQD 后解除绑定。完整流程与 HIQ 关闭顺序见第 7.4 节。保存字段继续使用第 2.6 节的 saved_rptr 和 saved_error，槽位释放仍遵守第 4.2 节的条件。

本版不采用 CP_HQD_DEQUEUE_REQUEST 寄存器入口。故障队列的清理不要求先排空，尚未完成的等待按第 7.3 节报错退出；卸载结果只确认管理操作，任务结果和资源释放仍按各自协议判断。只读到 ACTIVE = 0、发现错误或等待超时，都不能证明设备已经结束相关访问。故障时清除 ACTIVE 并保留占用的规则见第 7.2.2 节；当前任务无法结束时的强制停止、运行期间 KIQ 重配及复位恢复列入后续异常恢复扩展。

7.1 IH 记录与 Host 错误通知

CP 发现一条用户队列无法继续处理后，需要把队列身份和错误原因交给 Host。驱动再找到对应 Queue 对象，保存错误状态并通知等待者。

[DESIGN] 第二阶段采用简化 IH：全设备共用一个 Host RAM IH Ring，设置七个管理寄存器和一个 CP 提交入口，中断控制沿用 IRQ_ENABLE / IRQ_STATUS / IRQ_ACK。设备将记录写入 Ring，发布后中断通知 Host，驱动读取记录并分发处理。本节于 2026-10-18 确认，设备、固件和驱动路径现已接入；记录编码及提交接口属于本实验设计。

以下沿一条按申请创建的用户队列说明完整路径。Host 访存采用 DMA 直通配置，Host RAM 地址为完整的 64 位物理字节地址，VRAM 地址为字节偏移：

CP 发现队列错误
  │
  ├─ 保存到该队列的 HQD.CP_HQD_ERROR
  ├─ 按错误规则停止后续取包
  │
  └─ 在固件私有 VRAM 中准备一条 32 字节记录
       ├─ type     = QUEUE_ERROR
       ├─ hqd_slot = 出错队列所在槽位
       ├─ mqd_addr = 该队列的 MQD 物理地址
       └─ data     = 错误码
                │
                │ 将这条临时记录的 VRAM 偏移
                │ 写入 IH_SUBMIT
                ▼
QEMU 设备中的 IH 模块
  │
  ├─ 读取并校验临时记录
  ├─ 根据 Ring 基址、IH_SIZE、IH_WPTR 找到写入位置
  ├─ 将记录写入 Host RAM 中的 IH Ring
  ├─ 保证记录可见，再推进 IH_WPTR
  └─ 通过设备中断通知 Host
                │
                ▼
Host 驱动
  │
  ├─ 根据 IH_RPTR、IH_WPTR 读取记录
  ├─ 用 mqd_addr 找到驱动中的 Queue 对象
  ├─ 直接从 data 取得错误码
  ├─ 保存错误并通知相关等待线程
  └─ 推进 IH_RPTR，归还已经读完的槽

mqd_addr 用于查找驱动中的队列对象，错误码已经保存在 IH 记录的 data 中。Host 处理这条通知时不需要先读取 MQD 或 HQD 才能取得错误码。CP_HQD_ERROR 继续提供驻留队列的错误状态查询，MQD.saved_error 在卸载保存状态时更新。

IH Ring 保存设备交给 Host 的通知记录。KIQ、HIQ 和用户 AQL Ring 保存 Host 交给 CP 的命令，继续使用各自已有的进度与管理协议。通知到达后，队列卸载和资源释放仍须满足各自的完成条件。

7.1.1 Ring 存储与记录布局

Linux 内核驱动分配并管理 Host RAM 中的 DMA 一致性内存，作为全设备共用的 IH Ring。基址按 4 KiB 对齐，IH_SIZE 保存实际字节容量，驱动默认配置为 4096。容量必须非零、为 32 字节的整数倍，并采用 2 的幂；驱动分配的内存须覆盖配置容量。

Host RAM：IH Ring

默认字节容量 IH_SIZE = 4096
每条记录大小         = 32 字节
记录槽数量 N         = 4096 / 32 = 128

槽 0       偏移 0x0000
槽 1       偏移 0x0020
……
槽 127     偏移 0x0fe0

设备侧由 IH 模块统一串行写入，Host 侧由驱动串行消费；128 个槽都可使用。每条记录固定为 32 字节，多字节字段小端：

偏移    大小      字段

0x00    4 字节    type
0x04    4 字节    hqd_slot
0x08    8 字节    mqd_addr
0x10    4 字节    data
0x14   12 字节    reserved，全部填 0

三种记录按以下方式解释：

type = 1：SIGNAL_NOTIFY
  hqd_slot = 用户队列所在槽位，取 2 或 3
  mqd_addr = 该队列的 MQD 物理地址
  data     = event_id

type = 2：QUEUE_ERROR
  hqd_slot = 出错队列所在槽位，取 0～3
  mqd_addr = 该队列的 MQD 物理地址
  data     = 提交通知时 CP_HQD_ERROR 的 32 位错误值

type = 3：DEVICE_ERROR
  hqd_slot = 0xffff_ffff，表示没有具体队列
  mqd_addr = 0
  data     = 全局 ERROR_STATUS 的 32 位错误位快照

type = 0 和其他值暂不使用。记录保存事件发生时的队列身份；Host 不能只按槽位编号，把旧记录交给后来使用同一槽位的新队列。MQD 地址和事件编号的复用条件见第 7.1.7 节。队列错误值采用第 7.2.1 节的 32 位编号。

7.1.2 管理寄存器与状态字段

Host 配置 Ring 后，IH 模块根据基址、容量和写进度写入记录；Host 通过读进度归还槽位。以下七个寄存器统一采用对齐的 32 位小端访问。本次接入固定以下 BAR0 字节偏移；CP 诊断读取仍按 0xfffd_0000 + 偏移 访问：

0x0800  IH_BASE_LO       Ring 基址低位
0x0804  IH_BASE_HI       Ring 基址高位
0x0808  IH_SIZE          Ring 字节容量
0x080c  IH_WPTR          已发布范围
0x0810  IH_RPTR          Host 消费回报
0x0814  IH_STATUS        通道故障与本次提交结果
0x0818  IH_CTRL          使能与复位
0x081c  IH_SUBMIT        CP 专用提交入口，见下一节

字段含义如下：

IH_BASE_LO
  Ring 起始物理字节地址的低 32 位

IH_BASE_HI
  Ring 起始物理字节地址的高 32 位

IH_SIZE
  Ring 的字节容量，驱动默认配置为 4096

IH_WPTR
  下一条待写记录的编号
  由 IH 模块推进，Host 和 CP 只读

IH_RPTR
  下一条待读记录的编号
  由 Host 推进，设备检查更新是否合法

IH_CTRL
  bit 0：ENABLE，使能 IH
  bit 1：RESET，复位请求，处理后自动清零
  其余位保留为 0

IH_STATUS
  bit 0      ：BUSY，当前有 IH 操作正在进行
  bit 1      ：FAULT，IH 通道发生故障
  bits 7:2   ：保留为 0
  bits 15:8  ：ERROR_CODE，锁存首次 IH 故障原因
  bits 23:16 ：LAST_SUBMIT_RESULT，最近一次 CP 提交的结果
  bits 31:24 ：保留为 0

Host 只在 IH 已禁用且没有在途写入时修改 IH_BASE_LO / HI、IH_SIZE。两部分地址按原值直接拆分，完整基址为 ((uint64_t)IH_BASE_HI << 32) | IH_BASE_LO，不使用移位后的地址编码。IH_CTRL 由 Host 控制，IH_STATUS 对 Host 只读；CP 对这七个寄存器均只读，通过下节的专用入口提交记录。

ERROR_CODE 保存 IH 通道首次故障的原因；LAST_SUBMIT_RESULT 保存最近一次 CP 提交的结果，0 表示记录已写入且 IH_WPTR 已发布，非零表示本次提交失败。其他设备事件可以使通道进入故障状态，但不得覆盖 LAST_SUBMIT_RESULT。CP 因而可以分别判断本次记录是否提交成功，以及 IH 通道是否还能继续使用。

[DESIGN] 两个字段采用同一组编号，但分别锁存，不能相互替代：

0  OK        成功；错误字段中表示尚无故障
1  DISABLED  IH 未使能时提交
2  CONFIG    基址、容量或完整范围非法
3  FULL      未消费记录已占满 Ring，仍继续提交
4  DMA       Host Ring 写入失败
5  PROTOCOL  非法读进度、权限或寄存器操作
6  RECORD    临时记录地址或记录内容非法
7  FAULTED   通道已故障，拒绝本次提交

例如第一次满环提交使 ERROR_CODE = 3、LAST_SUBMIT_RESULT = 3；再次提交被拒绝后，前者仍为 3，后者更新为 7。IH 故障同时置全局 ERROR_STATUS 的 bit 4；无法归属队列的固件异常使用 bit 5，二者均通过原错误中断交付。

7.1.3 CP 临时记录与同步提交

CP 在固件私有 VRAM中准备 32 字节临时记录，然后向专用的 IH_SUBMIT 写入该缓冲区的 32 位 VRAM 字节偏移。入口同样采用对齐的 32 位小端写入：

固件私有 VRAM
  └─ 临时记录缓冲区：32 字节
          │
          │ CP 填好记录，并保证内容先于提交可见
          ▼
CP 写 IH_SUBMIT
  写入值 = 临时记录缓冲区的 VRAM 字节偏移
          │
          ▼
IH 模块同步处理
  ├─ 成功：写入 Host Ring，发布 W，记录提交成功
  └─ 失败：记录提交失败及必要的通道故障
          │
          ▼
提交写操作返回
  → CP 读取 LAST_SUBMIT_RESULT
  → 此后可以复用临时记录缓冲区

固件串行执行“准备记录 → 提交 → 读取结果”，期间不插入另一条 CP 提交。临时缓冲区在提交结束前保持内容不变，IH 模块在写操作返回前完成读取和本次提交的结果更新。提交成功表示记录已经发布给 Host，Host 对记录的消费可能尚未开始。

7.1.4 读写进度、回绕与发布

IH 的 W、R 都是 32 位无符号记录编号，初始进度为 0。设备用 W 选择下一写入槽，Host 用 R 选择下一读取槽：

W = IH_WPTR：下一条待写记录
R = IH_RPTR：下一条待读记录
N = IH_SIZE / 32

未读取记录数 D = (W - R) mod 2^32

D = 0：空
D = N：满

记录所在槽 = 记录编号 mod N
记录地址   = Ring 基址 + 槽编号 × 32

IH 只发布已经写完的记录，正常运行时满足 0 ≤ D ≤ N。默认 128 槽时，物理槽按以下方式循环使用：

写记录 127 → 槽 127
写记录 128 → 槽 0
写记录 129 → 槽 1

写记录 128 前，必须确认槽 0 的旧记录已经由 Host 归还。物理槽回绕时 W 不归零，编号继续增加，直到自身发生 32 位回绕；W、R 的差值始终按上述模运算计算。

Host 更新 R 时，设备检查本次归还数量：

本次归还数量 = (新 R - 旧 R) mod 2^32

要求：本次归还数量 ≤ 当前未读取记录数 D

非法更新被拒绝，旧 R 保持不变，并按 IH 协议故障处理。D = N 表示容量已用满，只有此时继续提交且仍无可用槽，才触发满环提交失败。

发布与归还遵守以下顺序：

设备：
写完整记录 → 保证记录可见 → 更新 W → 发出中断

Host：
读取 W → 完成读取同步 → 读完或复制记录 → 更新 R

Host 通过 W 判断记录是否已经完整发布，不要求整条 32 字节记录原子写入。Host 只有读完或完整复制记录后才可归还槽；复制后延后处理所需的对象仍须保留引用。具体内存同步操作随设备、固件和驱动接入落实并验证。

7.1.5 中断确认与 Signal 通知

已有中断控制寄存器增加 IH 对应的 bit 3，MSI-X 使用向量 3：

IRQ_ENABLE.bit3   允许 IH 中断
IRQ_STATUS.bit3   IH 中断待处理
IRQ_ACK.bit3      Host 确认本次 IH 中断

屏蔽 IH 中断不停止写 Ring。重新允许中断时，如果仍有未读记录，设备继续通知。Host 写 IRQ_ACK 时若 Ring 仍非空，也必须保留或重新产生通知，避免遗漏并发到达的记录。IRQ_ACK 处理的是中断状态，槽位由 IH_RPTR 归还。

正常任务完成时，CP 在发布完成值前取得并保存事件编号和通知槽地址，确认结果写回后，依次更新完成值、写通知槽，再提交 SIGNAL_NOTIFY：

CP 确认任务结果写回
  → 将 S.value 从 1 更新为 0
  → 按保存的 event_mailbox_ptr，向通知槽写入零扩展到 64 位的 event_id
  → 提交 SIGNAL_NOTIFY，data = event_id
  → IH 写记录并通知 Host
  → 驱动用 mqd_addr 找到 Queue 及其所属进程
  → 在该进程事件表中按 event_id 找到事件
  → 确认事件与通知槽的关联，保存“已通知”状态，再清零通知槽
  → 唤醒等待线程
  → 线程重新检查 S.value

Signal 值仍是正常完成的判断条件，IH 负责将通知交给驱动。事件编号结合队列所属进程查找，不能直接在所有进程间按同一个编号查找。默认等待继续采用短暂轮询后进入内核事件等待的流程；Signal 的 24 字节布局、通知槽标记和防止漏唤醒的登记协议已按第 2.5.2 节、第 2.5.3 节确定，具体可见性操作见第 6.4 节。

7.1.6 IH 故障与恢复前提

Ring 已满时再次提交、Host RAM 记录写入失败或非法协议操作，都使 IH 进入故障处理。设备不能覆盖尚未消费的记录：

锁存 IH_STATUS.FAULT 和首次错误原因
  → 拒绝后续提交，保留已经发布的记录
  → 停止继续取包和调度
  → 通过已有 IRQ_ERROR 通知 Host

IRQ_ERROR 直接走已有错误中断，不依赖故障中的 IH Ring。失败记录不推进 W，也不自动重试；一次失败写入即使已经改变了部分内存，Host 也不能把未发布的槽作为有效记录消费。CP 本次提交的结果继续由 LAST_SUBMIT_RESULT 返回。

读取状态或写 IRQ_ACK 都不清除 IH 故障。Host 恢复前须停止相关生产者、确认在途写入结束，并处理或按恢复协议明确作废旧通知，然后在 IH 已禁用且 BUSY = 0 时请求复位。停止取包和调度后，已经开始的计算或 DMA 仍须按各自停止协议收尾，资源释放条件不能由 IH 故障状态代替。

[DESIGN] 冷复位和 GLOBAL_CTRL.RESET 清零 IH 基址、容量、W/R、控制与状态。合法的独立 IH_CTRL.RESET 仅清零 W/R 与整个 IH_STATUS，保留基址和容量，IH 继续禁用；该写入不能同时设置 ENABLE。CP 单独复位保留所有 IH 状态。独立 IH 复位不清除全局错误位，也不清空 Host Ring 内容；旧记录由重置后的发布范围判定，不能把残留字节视为新通知。运行期间的恢复流程仍属于后续扩展。

7.1.7 旧记录与对象寿命

驱动收到记录时，HQD 槽位可能已经卸载或用于另一条队列。驱动按记录中的完整 MQD 地址查找原 Queue 对象，并保留旧通知处理所需的对象关系。

队列停止并卸载
  → 确认设备不会再产生该队列的旧记录
  → 处理完已发布记录及驱动已经取走的后续工作
  → 结束旧 Queue、事件和通知槽的相关引用
  → 才允许复用对应 MQD 地址和事件编号

仅收到卸载成功结果或中断确认，还不能证明旧通知已经处理完。若驱动先复制记录、归还 IH 槽，再延后处理，复制记录对应的 Queue 和事件引用必须保留到处理结束。应用释放接口见9.7.4 的已确认接口；故障复位后的旧通知处理随后续异常恢复细化，当前继续保留尚不能安全回收的资源。

7.2 队列错误编号、停止范围与重建

CP 读取一条按申请创建的用户队列时，发现 Ring 无法访问，需要保存最初的失败原因，停止这条队列，并让 Host 结束相关等待。以下假设这是该队列的首次故障：

CP 读取某条用户队列的 Ring 失败
  │
  ├─ 将该队列的 CP_HQD_ERROR 记为 1
  ├─ 停止该队列后续取包，ACTIVE = 0
  ├─ 保留槽位占用及 MQD 绑定
  │
  └─ 提交 QUEUE_ERROR 中断记录
       ├─ mqd_addr = 该队列的 MQD 地址
       └─ data     = 1
                │
                ▼
Host 驱动
  → 找到对应 Queue，保存队列故障
  → 唤醒相关等待者
  → 通过卸载或设备恢复，确认相关访问结束
  → 处理完旧通知后，再回收资源

[DESIGN] 本节于 2026-10-18 确认。CP_HQD_ERROR 使用 32 位错误编号，由 CP 保留首次错误；队列第一次进入故障状态时提交一次 QUEUE_ERROR。错误队列停止取包并清除 ACTIVE，但槽位和 MQD 绑定继续保留。以下编号和行为属于本实验协议。

7.2.1 错误编号与首次记录

CP_HQD_ERROR 采用以下编号：

 0：未记录错误
 1：Ring 或共享写进度读取失败
 2：已发布包的类型不支持，或通用格式、字段非法
 3：Kernel 描述对象或参数范围非法、无法读取
 4：计算执行器报告失败
 5：Signal 引用非法，或读取、更新失败
 6：通知槽引用非法，或写入失败
 7：包槽释放或消费进度回报失败
 8：管理命令与 WRITE_COMPLETION 配对错误
 9：管理结果码或完成标记写回失败
10：目标 MQD 状态保存失败

CP 在队列第一次出错时写入对应编号；已有非零错误后，后续异常不覆盖它。Host 对该寄存器只读，读取寄存器、处理 IH 记录和确认中断都不清错。固件不因反复检查同一个错误而重复提交 QUEUE_ERROR；IH 提交本身失败时按第 7.1.6 节处理。

上述编号表示队列停止的原因。执行器返回失败时，CP 记录编号 4；执行器的 DISPATCH_ERROR 仍单独保存本次执行的具体原因，其枚举值见第 6.3.3 节。已识别管理命令的普通参数错误继续按第 7.2.3 节返回本次请求结果，不据此把来源管理队列记为编号 2。

7.2.2 出错队列与停止范围

CP 根据故障对象决定哪些队列停止新取包与新派发：

用户队列故障
  → 停止这条用户队列
  → KIQ、HIQ 和其他正常用户队列继续处理

HIQ 故障
  → 停止 HIQ
  → KIQ 和已驻留的正常用户队列继续处理
  → 暂时不能通过 HIQ 创建或卸载用户队列

KIQ 故障
  → 停止所有队列的新取包与新派发
  → 保留相关资源，设备恢复留作后续扩展

固件代码、栈等无法可靠归属队列的异常
  → 记录设备级故障，停止所有队列调度

IH 自身故障
  → 停止继续取包和调度
  → 经已有 IRQ_ERROR 通知 Host

KIQ 的实际通道故障统一按停止全部调度处理，包括取包、已发布命令配对和结果写回故障；普通管理请求失败仍按下一节处理。能够可靠归属队列的故障由 CP 清除该队列的 ACTIVE，并在固件槽位占用记录中保留异常占用状态。

停止新取包与新派发后，已经开始的计算或访存仍须完成收尾。Host 继续保留相应内存和对象引用，直到卸载或恢复流程确认访问结束；ACTIVE = 0 不能作为释放资源或归还槽位的依据。故障 HIQ 重建、任务卡住后的强制停止及设备复位步骤列入后续异常恢复扩展，不作为第二阶段必做内容。

7.2.3 管理请求结果与目标队列故障

名额已满、重复映射、卸载目标不存在，以及已识别管理命令的参数非法，都通过既有的独立结果区返回。来源 KIQ 或 HIQ 可以继续处理后续请求：

本次管理请求失败
  → 暂存本次 status
  → 执行后附 WRITE_COMPLETION
  → Host 取得失败原因
  → 管理队列继续处理后续请求

这些失败不把来源管理队列标为故障，结果码继续使用第 4.4 节的编码。管理 Ring 无法读取、已发布命令配对错误、结果码或完成标记写回失败，则记录来源管理队列错误，并按前节确定停止范围。

目标 MQD 状态保存失败时，如果管理通道仍能安全回报，则返回既定的 status = 5，目标槽位继续占用。目标队列尚无错误时，CP 记录 CP_HQD_ERROR = 10；已有首次错误时保留原值。这样，Host 能从本次请求结果得知保存失败，同时保留目标队列最初的故障原因。MQD 读取失败也沿用既有请求结果和安全收尾条件，不套用仅表示状态保存失败的编号 10。

7.2.4 错误保存与清理后重建

错误队列须先确认访问结束并清理旧状态，再重新创建。第二阶段处理能够安全卸载的故障队列，需要强制停止或故障复位的情况留作后续扩展；清理顺序如下：

错误队列
  → 停止取包
  → 卸载或设备恢复，确认相关访问结束（设备恢复留作后续扩展）
  → 保存诊断信息，处理完旧通知及驱动后续工作
  → 回收旧对象
  → 重新创建队列

卸载时，CP 将错误快照保存到 MQD.saved_error；保存失败仍按前节保留槽位。saved_error != 0 的 MQD 不允许直接重新激活，映射请求返回既定的参数非法结果 status = 4。仍处于绑定状态的 MQD 继续先按重复映射规则拒绝，不能借重新映射清除原状态。

槽位完成清理、用于建立新队列时，由 CP 初始化其错误状态。设备冷复位或整体复位清零 HQD；CP 单独复位保留 HQD，不能借此清错恢复。MQD 地址、事件编号及相关内存的复用继续遵守旧通知与对象寿命规则。

出错后停止正常收尾，保留已经发生的写入，不自动重放任务或补写成功 Signal。失败包、部分完成状态和等待退出按第 7.3 节处理。

  → 记录错误，按 9.6.1 的范围停止处理

7.4 Host 排空队列与 CP 卸载

[DESIGN] 第一版正常卸载采用 Host 先排空队列、CP 再卸载的顺序。以一条用户队列为例，运行时先停止新的提交，并让已经开始的提交完成发布，随后等待已有任务完成：

Host 停止该队列的新提交
  → 等已经开始的提交完成发布
  → 等已有任务完成，消费回报 R 追上 W
  → 向 HIQ 发布 UNMAP_QUEUES → WRITE_COMPLETION

CP 开始处理 UNMAP_QUEUES
  → 槽位标为“卸载中”
  → 清除 ACTIVE，关闭该队列的 Doorbell 使能
  → 确认相关在途访问结束
  → 将 saved_rptr、saved_error 保存到原 MQD
  → 解除绑定，将 HQD 槽位标为空闲
  → 管理操作达到完成条件，CP 暂存成功结果
  → 执行后附 WRITE_COMPLETION，先写结果码，再写完成标记

  → 处理完旧通知，满足对象寿命条件后回收相关资源

正常路径以消费回报 R == W 确认包已经全部消费。例如队列还有三个未执行包，Host 先让它们完成，再提交卸载。停止提交包含等待已开始的提交完成发布；不能在其他线程仍可能预留或发布包时，以一次 R == W 判断队列已经排空。进度的完整访问与同步继续沿用第 5.2.1 节的规则。

CP 开始执行卸载时清除 ACTIVE，同时关闭该队列的 Doorbell 使能；此时槽位仍保持占用。确认相关访问结束、成功保存 MQD 后，才解除绑定并归还槽位。保存失败继续保留占用，按已有错误规则处理。Host 读到本次预期完成序号，同步并确认 status = 0 后，再按旧通知与对象寿命规则释放相关内存。

故障队列的清理不要求先排空，尚未完成的等待按第 7.3 节报错退出，相关资源继续保留。任务一直不结束时的强制停止方法列入后续异常恢复扩展，第二阶段不要求实现。取消未执行任务、保留未执行任务跨卸载续跑列为后续扩展；正常重装仍保留已有消费位置，不把进度清零。

正常卸载 HIQ 前，驱动先完成用户队列清理，并等待 HIQ 的管理请求回报：

停止接受新的用户队列创建请求
  → 经 HIQ 卸载所有用户队列，确认用户槽位全部空闲
  → 确认 HIQ 中的管理请求及后附完成命令全部处理结束
  → 经 KIQ 提交卸载 HIQ 的命令和完成标记命令
  → 确认 HIQ 卸载成功

第一版由 Host 保证上述关闭顺序，CP 不在卸载 HIQ 时自动连带卸载用户队列。HIQ 的卸载仍按本节停止取包、结束访问、保存状态、解除绑定和回报结果；返回管理结果的是 KIQ。

8.1 Ring 容量、Doorbell 与地址字段的编码

驱动已为 Queue A 分配 Ring，接下来填写 MQD_A，供 CP 装入 HQD。以下示例使用 4096 字节的 Ring，并假设驱动为 Queue A 分配的 Doorbell 位于 BAR4 内偏移 0x20；这是演示地址，实际入口按第 5.2.3 节由驱动分配。

Host 驱动填写 MQD_A
  ├─ pq_control       = 4096
  └─ doorbell_control = 0x4000_0020
         │
         │ CP 执行 MAP_QUEUES，读取并装入配置
         ▼
Queue A 的 HQD
  ├─ CP_HQD_PQ_CONTROL = 4096
  ├─ CP_HQD_PQ_DOORBELL_CONTROL
  │    ├─ OFFSET = 8  → BAR4 内字节偏移 = 8 × 4 = 0x20
  │    └─ ENABLE = 1  → 启用该队列的 Doorbell 入口
  └─ CP_HQD_ACTIVE = 1（完成配置后最后设置）
         ▲
         │ 对应这个队列的通知入口
Host 写入 BAR4 + 0x20

[DESIGN] CP_HQD_PQ_CONTROL 的整个 32 位无符号数值保存 Ring 的字节容量，KIQ、HIQ 和用户 AQL Ring 使用同一规则。容量必须是 2 的幂，范围为 64 字节～64 KiB，0 为非法容量。例如写入 4096 表示 4096 字节，可容纳 64 个 64 字节 AQL 包。本版不采用 AMD 的容量对数编码；管理命令固定为第 4.1 节的 32 字节格式，包槽边界与末尾回绕按第 5.1 节处理。

[DESIGN] CP_HQD_PQ_DOORBELL_CONTROL 只采用偏移和独立使能两个字段，MQD 中的 doorbell_control 使用相同编码：

CP_HQD_PQ_DOORBELL_CONTROL：32 位

bit 31       保留，填 0
bit 30       DOORBELL_EN
bits 29:28   保留，填 0
bits 27:2    DOORBELL_OFFSET
bits 1:0     保留，填 0

DOORBELL_OFFSET 保存相对于整个 BAR4 起点的偏移，单位为 4 字节。这个字段用于定位通知入口，不保存队列编号或 BAR4 的完整物理地址。上例的换算如下：

Doorbell 位于 BAR4 + 0x20

OFFSET 字段值 = 0x20 / 4 = 8
ENABLE       = 1

寄存器值 = (1 << 30) | (8 << 2)
         = 0x4000_0020

0x4000_0020 是 HQD 的配置值。应用发布包 P 后，向该入口完整写入 64 位值，低 32 位为 P、高 32 位为零。入口按 8 字节对齐，因此 OFFSET 必须为偶数，解码后的完整 8 字节访问范围必须落在 BAR4 内。图中的 0x20 和字段值 8 满足这些条件；通知与队列复查规则见第 5.2.3 节。

使能位按以下规则使用：

  • ENABLE = 0：关闭该队列的 Doorbell 入口，不改变 ACTIVE 或消费位置。
  • ENABLE = 1：启用该队列的 Doorbell 入口，不自动激活队列。
  • ENABLE = 1、ACTIVE = 0：通知入口已开启，CP 暂不消费该队列。
  • 正常装载时先配置 Doorbell，再读取生产进度，最后设置 ACTIVE = 1。首次 KIQ 仍由 Host 在 CP 保持复位时配置；后续队列由 CP 按管理命令装载。

字段位置参考 AMD 的对应定义。独立使能与队列激活的关系、AMD 直接装载 HQD 的顺序及源码依据见Doorbell 控制说明；本版的通知处理按上述设计与 9.4.5 的协议实现。

[DESIGN] CP_HQD_ACTIVE 只使用 bit 0，其余位填 0：

CP_HQD_ACTIVE
  ├─ bit 0 = 0：队列未激活，CP 不继续从该队列取包
  ├─ bit 0 = 1：队列已激活，CP 可以检查并处理命令
  └─ bits 31:1：保留，填 0

故障队列按第 7.2.2 节清除 ACTIVE 并保留占用；ACTIVE = 0 不单独代表在途访问已经结束。正常卸载按第 7.4 节由 Host 先排空，CP 开始卸载时清除 ACTIVE 并关闭 Doorbell 使能。CP_HQD_VMID 的整个寄存器固定填 0；CP_HQD_AQL_CONTROL 的整个寄存器填 0 表示非 AQL 管理队列，填 1 表示用户 AQL 队列，其余值暂不支持。

MQD 地址、Ring 地址、消费进度回报地址和生产进度读取地址这四组寄存器，均保存完整的 64 位 Host RAM 物理字节地址：

低位寄存器：地址的低 32 位
高位寄存器：地址的高 32 位

例如地址 = 0x1_9000_0000
  ├─ LO = 0x9000_0000
  └─ HI = 0x1

这四组地址不预先右移压缩，对齐与访问范围按第 2.4.2 节校验。Doorbell OFFSET 的 4 字节单位只用于 Doorbell 字段，不改变 Host RAM 地址的字节编码规则。

[DESIGN] CP_HQD_PQ_RPTR 的整个 32 位值保存下一待消费包编号，按模 2^32 推进；回报内存保存相同的 32 位值，MQD 的 64 位 saved_rptr 零扩展保存该值。取槽、满空判断与恢复规则见第 5.2.1 节。

[BOUNDARY] CP_HQD_ERROR 使用 32 位错误编号，首次记录、停止范围和清理后重建规则已按第 7.2 节确定。复位值、读写权限和非法访问处理见第 8.2 节。OFFSET、ENABLE 使用现有 doorbell_control 的空间，MQD 仍为 64 字节，HQD 仍采用上述 15 个寄存器位置；这些编码为已确认设计。

8.2 HQD 的复位值、读写权限与非法访问

Host 首次启动 CP 时需要配置 KIQ；CP 开始运行后，再通过管理命令配置其他队列。下面按这两个阶段说明谁能写 HQD，Host 何时读取配置与状态：

首次启动，CP 保持复位
  → Host 配置 KIQ 的 HQD
  → 最后设置 KIQ.ACTIVE = 1
  → 解除 CP 复位

CP 运行后
  ├─ Host 提交管理命令 → CP 配置或卸载目标队列
  ├─ CP 执行任务      → CP 更新消费进度和错误状态
  └─ Host 读取 HQD    → 查看配置与运行状态

[DESIGN] 本版采用以下复位与访问规则，适用于 HQD 寄存器入口。HQD_SELECT 的有效槽位选择及 CP 地址译码范围见第 8.3 节。

  1. 复位值。 设备冷复位或整体复位时，所有 HQD 寄存器清零，HQD_SELECT = 0。队列处于未激活状态，Doorbell 未启用；容量为 0 表示尚未配置，必须填入合法容量后才能激活。CP 单独复位保留 HQD 内容，故障后的队列恢复列入后续异常恢复扩展，不能据此判断相关访问已经结束。
  2. 访问宽度。 Host 窗口和 CP 直接入口都采用小端、4 字节对齐的 32 位读写，HQD_SELECT 也按对齐的 32 位访问。64 位地址通过低、高两个寄存器分别读写，不支持一次 64 位访问跨过两个寄存器；非法宽度或未对齐请求不能分拆成多个有效访问后部分生效。
  3. Host 与 CP 的写权限。 首次启动时，Host 在 CP 保持复位期间配置 KIQ，并初始化消费位置。CP 运行后，Host 对 HQD 只读，按第 4 节的分工经 KIQ 请求配置 HIQ、经 HIQ 请求配置用户队列，由 CP 执行；Host 仍可写 HQD_SELECT 选择查看对象。CP_HQD_ERROR 对 Host 始终只读，读取不清除错误，由 CP 按第 7.2 节保留首次错误；槽位完成清理并用于建立新队列时，由 CP 初始化错误状态。
  4. 运行期间的字段更新。 Ring 地址、MQD 地址、进度地址、容量、VMID、队列格式和 Doorbell OFFSET，须在队列未激活且相关在途访问已结束后修改。运行期间允许 CP 更新消费进度、错误状态、ACTIVE，以及单独切换 DOORBELL_EN；切换使能时，Doorbell OFFSET 保持原值。ACTIVE 的清零时机按正常卸载及故障停止规则执行。
  5. 非法访问。 非法字段值、保留位置 1、越权写入，以及不支持的访问宽度或对齐都拒绝处理。非法写入保留原值，非法读取返回 0，并记录到全局 ERROR_STATUS.INVALID_CMD。未采用的寄存器位置按规定宽度读取时返回 0，写入按非法访问处理。这类访问不自动清空队列，也不覆盖队列自身的 CP_HQD_ERROR。
  6. 完整配置与读取一致性。 写入地址的低、高两部分期间保持 ACTIVE = 0；完整配置满足容量、地址对齐和范围要求后，才允许设置 ACTIVE = 1。单次 32 位读取返回完整值，跨多个寄存器读取不保证得到同一时刻的快照。Host 读取正在装载的配置，应等待对应管理操作完成；持续变化的进度值另按 9.4 的发布规则读取。

非法访问的错误记录与队列执行错误分别维护。例如，Host 在 CP 运行时试图改写 Queue A 的 Ring 地址，这次写入被拒绝，原地址保留，全局非法命令标志置位；Queue A 的消费位置和已有错误快照保持原状。Host 需要修改队列时，仍应通过管理命令完成相应操作。

[BOUNDARY] 上述读零、保留原值和错误记录是本实验寄存器入口的处理约定，未映射物理地址按第 8.3 节交给 CP 访存异常处理。地址与范围校验不保证后续 Host RAM 访存必然成功，实际访问失败仍按访存错误规则处理。寄存器复位不释放 Ring、MQD、Signal 或任务资源，资源释放仍须确认相关访问结束。设备与固件按以上规则处理 HQD。

8.3 Host 选槽窗口与 CP 本地地址

Host 与 CP 都需要读取用户队列的 Ring 地址。设备内部有 4 份独立 HQD 状态，槽位 2、3 供动态创建的用户队列使用；Host 通过一个选槽窗口访问，CP 通过每个槽位的固定地址访问。两套入口访问同一份状态，Host 窗口不另外保存一份 HQD 副本，完整关系图见HQD 访问说明。

以下假设 CP 已把两条用户队列 A、B 分配到槽位 2、3。以 Queue A 为例，假设其 Ring 地址低位寄存器保存 0x9000_0000。CP_HQD_PQ_BASE 在每组 HQD 内的偏移均为 0x020：

设备内部实际保存的状态：

HQD[2]：Queue A
  └─ CP_HQD_PQ_BASE = 0x9000_0000
                  ▲
                  │ 两条路径都读取这个字段
                  │
Host 路径：
  写 HQD_SELECT = 2
  读 BAR0 + 0x0700 + 0x020
  即 BAR0 + 0x0720
  → 返回 0x9000_0000

CP 路径：
  读 0xffff_0200 + 0x020
  即 0xffff_0220
  → 返回 0x9000_0000

[DESIGN] Host 使用 BAR0 + 0x0600 的 HQD_SELECT 选择槽位，通过 BAR0 + 0x0700～0x07ff 的单个窗口访问所选 HQD。CP 的固定基址为 CP_HQD_BASE = 0xffff_0000，槽位间隔为 0x100，访问地址按“基址 + 槽位编号 × 间隔 + 字段偏移”计算：

CP 本地物理地址：
  0xffff_0000～0xffff_00ff → 槽位 0：KIQ
  0xffff_0100～0xffff_01ff → 槽位 1：HIQ
  0xffff_0200～0xffff_02ff → 槽位 2：供用户队列申请
  0xffff_0300～0xffff_03ff → 槽位 3：供用户队列申请

四个槽位共映射 0x400 字节，即 1 KiB。每个槽位预留 256 字节的寄存器地址范围，其中采用的 15 个 32 位寄存器占 60 字节，其余位置未采用。这里划定的是 CP 的寄存器地址范围，不从前 60 MiB VRAM 分配池中分配 1 KiB；Ring 和 MQD 仍使用 Host RAM，Ring 容量由 CP_HQD_PQ_CONTROL 指定。

HQD_SELECT 只改变 Host 窗口的访问对象，不复制 HQD 内容，也不改变 CP 正在处理的队列。接着将它改为 3 时：

Host 仍读取 BAR0 + 0x0720
  → 现在读取 Queue B 的 CP_HQD_PQ_BASE

CP 仍读取 0xffff_0220
  → 仍然读取 Queue A 的 CP_HQD_PQ_BASE

[DESIGN] HQD_SELECT 只接受完整的 32 位数值 0～3，不能只取低两位。无效选槽拒绝本次写入、保留原值，并置位全局 ERROR_STATUS.INVALID_CMD：

HQD_SELECT 原值 = 2
  → Host 写入 7
  → 拒绝这次写入，HQD_SELECT 仍为 2
  → 置位 ERROR_STATUS.INVALID_CMD

Host 驱动用锁保护“选槽—访问窗口”，写入选择值后先回读确认，再访问窗口；选槽失败就结束本次操作。首次 KIQ 配置和运行后只读 HQD 的权限继续按第 8.2 节执行，运行后仍允许 Host 修改 HQD_SELECT。

[DESIGN] CP 侧的 HQD 映射只覆盖上述 0x400 字节。有效槽位内的未采用寄存器位置，按第 8.2 节使用规定宽度读零，写入拒绝并记录全局错误。0xffff_0400 这样的越界地址不属于 HQD 映射，按未映射访存异常处理，不截断槽号、不取模，也不折返到槽位 0。落在其他已映射区域的地址仍由该区域处理，不能把所有 HQD 范围外的访问都当作寄存器访问。

[BOUNDARY] 本节确定本实验的物理地址映射与选槽行为，不引入虚拟地址或页表翻译，也不规定 AMD 的实际寄存器映射。未映射地址交给 CP 访存异常处理，队列归属、停机与恢复按 9.1.6 和 9.6 的协议落实。HQD 设备入口与固件访问已按上述地址和规则接入。

9.7.2 内存申请、CPU 映射与设备访问地址

调用方需要先取得能够保存 Ring、参数、Signal 或 Kernel 数据的存储，再把相应地址填入管理请求或 AQL。本项规定分配输入、返回对象与地址含义，以及释放前提。

[DESIGN] 已确认：

  1. 创建接口参考 hsaKmtCreateQueue()，传入 Ring 的内存句柄、对象内偏移和字节容量，以及保存 R、W 的共享对象句柄与偏移。实际内存仍由驱动通过上一项分配。容量明确传入，沿用 64 字节～64 KiB、2 的幂，0 非法；不在该底层接口规定默认 4 KiB。第一版只创建用户 AQL Queue，KIQ、HIQ 由驱动初始化路径管理，VMID 固定为 0，不增加优先级等可选策略。
  2. 驱动校验资源并取得引用，内部准备 MQD，经 HIQ 提交映射及后附完成命令。CP 继续选择空闲用户槽位；驱动确认管理结果成功后才交付可用队列。两个名额已满时返回资源不足。失败时不交付有效队列标识；已经交给设备的存储须按既有失败回收条件保留或清理，不能仅因创建调用失败就释放。
  3. 成功返回软件队列标识和 Doorbell 映射资料。库据此建立 CPU 可访问的门铃入口；映射定位信息与映射内入口的字节偏移分别保存，不与 HQD 中按 4 字节编码的 BAR4 偏移混淆。Ring 和进度对象继续由调用方持有，驱动保持必要引用。软件队列标识用于后续管理，与 HQD 槽位编号分开；MQD 地址仍是驱动与 CP 之间的配置，普通调用方不管理 MQD。
  4. 提供最小队列状态查询，返回是否可用、卸载中或故障，以及驱动保存的首次错误和必要的管理诊断。用户态通过队列标识查询，不直接选槽读取 HQD，也不通过查询清除错误。驱动继续通过 MQD 地址关联 IH 记录和队列对象；故障范围、首次记录和资源保留沿用第 7 节。
  5. 销毁接口参考 hsaKmtDestroyQueue()，由调用方先停止生产、完成已开始的发布，并按正常卸载协议等待任务结束和 R == W。库不遍历任务或自动执行高层 Signal 同步。驱动在接受正常卸载前复核队列进度，未排空时返回暂不可用、保持原队列；接受后经 HIQ 卸载，确认设备访问结束、MQD 保存和解绑成功，再完成收尾。故障队列按 9.6 的清理规则处理，不要求先排空。

队列销毁成功后，驱动释放本队列对调用方 Ring、进度对象的引用，库解除自己建立的 Doorbell 映射；调用方另行释放或复用自己的内存。旧通知、旧映射或驱动后续处理尚未结束时，相关资源不能提前复用。已接受的卸载请求若超时或故障，保留队列记录与必要资源，不重复提交原卸载命令，也不自动复位设备。具体管理等待机制沿用第 4.3 节。

调用方经内存接口取得 Ring 和进度存储
  → 创建队列：传入这些对象的句柄、偏移与容量
  → 驱动准备 MQD，经 HIQ 请求映射
  → CP 选择空闲槽位并装载
  → 驱动确认成功，返回队列标识及 Doorbell 映射资料

调用方停止提交，按正常协议排空后请求销毁
  → 驱动经 HIQ 请求卸载
  → CP 结束访问、保存 MQD、解除绑定
  → 驱动和库完成相应收尾
  → 调用方按各对象的寿命条件另行释放内存

9.7.4 事件创建、等待、错误交付与资源收尾

调用方需要把一个任务的完成 Signal 与内核等待事件关联，才能在任务未完成时睡眠。本项确定接口如何返回通知资料，以及驱动怎样把队列故障交给相关等待者。

[DESIGN] 已确认：

  1. 提供事件创建、状态查询、等待和销毁，参考 hsaKmtCreateEvent()、hsaKmtQueryEventState()、hsaKmtWaitOnEvent()、hsaKmtDestroyEvent()。第一版只提供本实验完成通知所需的事件，初始状态为未通知；等待返回不消费通知状态，同一事件可以有多个等待者。事件编号、通知槽大小及通知标记沿用第 2.5 节，不增加应用主动设置、复位事件的通用接口。
  2. 创建事件时，驱动返回事件标识及通知槽的完整 Host 物理地址。调用方在自己的共享 Signal 中填写 event_id、event_mailbox_ptr，并在提交前置 value = 1。Signal 存储继续由所属应用上下文管理；库不自动为每次 Dispatch 创建高层完成对象。通知槽由驱动分配、CP 写入、驱动按协议清零，普通调用方不直接修改通知槽。
  3. 创建事件时登记本次使用的源队列标识，要求队列属于本上下文且可用。驱动保存“队列 → 相关事件”的软件关联；队列故障时，对尚未通知的关联事件保存错误，使等待以失败结束，已通知的事件保留完成状态。晚于故障到来的等待也检查已保存状态，不继续睡眠。这是本实验接口的补充，不是 AMD hsaKmtCreateEvent() 原有的队列参数，也不增加 Signal、MQD 或 HQD 字段。事件分配仍归应用上下文；队列卸载后，已完成事件及其软件记录可继续保留到调用方销毁，不因此占住已归还的 HQD 槽位。本阶段一次事件使用关联一条队列，完成并满足回收条件后再销毁重建，不增加跨队列重绑操作。
  4. 等待输入为事件标识和 32 位无符号毫秒超时。0 表示只检查当前状态，UINT32_MAX 表示无调用方设定的等待上限，其余值为本次事件等待的总时限。已通知时返回成功；期限到达返回 WAIT_TIMEOUT；源队列或设备故障导致等待无法继续时返回 WAIT_FAILURE。库等待的是内核事件；返回成功后，调用方仍须复查 Signal 并执行已确认的读取同步，才能使用任务结果。事件查询不进入睡眠，返回未通知、已通知或失败状态及已保存的错误原因；队列标识仍有效时，也可以查询队列诊断。这里的查询结果由本实验定义；固定版本 hsaKmtQueryEventState() 只有连接、空指针检查，随后返回成功，不能照搬它判断实际通知状态。
  5. 默认 Signal 等待仍由调用方从本次等待开始主动检查约 200 μs，之后将剩余时间交给事件等待，唤醒后复查。库内部不再重复主动检查 200 μs；重复唤醒也不重置原 Signal 等待的总时限。等待超时只结束本次等待，事件、Signal 和任务继续保留；等待故障不会使驱动补写成功 Signal。
调用方已取得 Queue 与共享 Signal 存储
  → 请求创建事件，并登记源 Queue
  → 驱动建立事件、通知槽及源队列关联
  → 返回 event_id 和通知槽 Host 物理地址
  → 调用方填写 Signal，并把 Signal 引用写入 AQL

正常完成：CP 更新 Signal、通知槽，提交 IH 通知
  → 驱动找到所属进程与事件，保存已通知状态并唤醒
  → 事件等待返回，调用方复查 Signal

队列故障：驱动按 IH 记录找到 Queue 并保存错误
  → 该 Queue 的相关事件等待以失败结束
  → 调用方取得错误，资源按既定条件保留或清理

事件销毁及内存回收继续遵守已确认的对象寿命条件。调用方先结束任务和其他线程对对象的使用；仍有在途设备访问、等待者、旧通知或驱动后续处理时，销毁返回暂不可用，保留对象。驱动需要的关联记录保留到最后一次使用结束；不能因为 Signal 已为 0、HQD 的 ACTIVE 已清零，或一个等待调用已经返回，就提前复用事件编号、通知槽、MQD 地址和 Doorbell 入口。

正常退出时，调用方停止生产、完成任务与结果处理，再按依赖关系销毁队列和事件、释放内存，最后关闭连接。进程异常退出后的强制中止、旧映射强制撤销、设备复位和自动恢复，继续放在后续扩展；当前必须保留尚不能安全回收的资源。上层 Signal API、自动任务回收、参数复制和完整 ROCr 运行时不在本节定义。

# QEMU Camp Tutorial

QEMU Camp Tutorial 是 QEMU 训练营的在线技术文档，聚焦 C/Rust 语言与 QEMU 虚拟化/模拟器技术的深度结合，旨在通过系列技术博客、代码示例、原理解析，帮助开发者理解 QEMU 内部机制（如设备模拟、内存虚拟化、中断处理等），并掌握用 C/Rust 开发 QEMU 组件、优化 QEMU 模块的方法。​

无论是虚拟化领域初学者、C/Rust 技术实践者，还是开源爱好者，都能从本项目中获取 QEMU 底层原理的清晰解读与 C/Rust 落地实践的参考案例。
