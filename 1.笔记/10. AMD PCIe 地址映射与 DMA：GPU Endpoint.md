# PCIe GPU Endpoint 中的地址映射、DMA 与 PCIe Transaction

## 0. 文档目标、证据范围与先给结论

本文回答的不是“几个 Linux API 分别做什么”，而是一个完整问题：Host 用户态给出一块 1 MiB 内存后，自研 PCIe GPU 如何取得一个自己能使用的地址，如何收到命令，如何读取 Host 内存并写入 VRAM，如何报告完成，以及每一步究竟由 Host CPU、Root Complex/IOMMU、GPU Endpoint 的哪一部分完成。

贯穿全文的主线是：

```text
User VA 上的 1 MiB Buffer
  → Host 驱动固定或注册其 backing pages
  → 建立 SG 和 DMA mapping，得到 device-visible DMA address/IOVA
  → 将 IOVA、长度、目标 GPUVA 等写入 GPU command/descriptor
  → Host 通过 BAR MMIO 写 doorbell
  → GPU command processor/SDMA 取到命令
  → GPUVM 翻译 GPUVA，SDMA 发起 PCIe Memory Read Request
  → Completion with Data 返回 GPU，SDMA 将数据写入 VRAM
  → GPU 写 completion/fence，并产生 MSI-X
  → Host IRQ/workqueue 唤醒等待者，解除 DMA mapping 并释放页面引用
```

最重要的结论是：`remap_pfn_range()`、`dma_map_*()`、GPUVM page-table mapping、EP outbound address window 是四种不同方向、不同主体、不同页表或地址转换单元的映射；DMA descriptor 是设备内部的工作描述，PCIe TLP 是链路上的传输单元，两者绝不是同一个对象，也通常不是一一对应关系。

本文的源码基线为 `2.源码/linux` 的 commit `248951ddc14de84de3910f9b13f51491a8cd91df`。文中使用以下标签区分证据强度：

* `[SOURCE]`：后面给出的 Linux 源码直接体现该行为。
* `[SPEC]`：属于 Linux DMA API 约束或 PCIe 协议语义，Linux 代码只配置或使用它，不应伪装成由某一段驱动源码“证明”。
* `[INFERENCE]`：从多个层次串起来的工程解释。
* `[EXAMPLE]`：用于教学的最小代码，省略了产品驱动中的并发、进程退出、热拔插和错误恢复细节，不能直接复制进内核。
* `[BOUNDARY]`：公开 Linux 源码与具体 GPU 硬件/固件实现之间的边界。

## 1. 先把“PCIe EP 驱动”拆成三侧

“PCIe EP 驱动”是一个容易引起误解的统称。对一张离散 PCIe GPU 卡，至少要区分三侧：

| **位置**       | **典型组成**                                                                                            | **主要职责**                                                                      |
| ------------ | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Host         | 用户态 runtime、DRM/KFD/PCI function driver                                                             | 分配或注册内存、建立 GPUVA 和 DMA mapping、构造命令、写 doorbell、处理中断和回收资源                      |
| Host 平台      | CPU MMU、PCI core、Root Complex、IOMMU、interrupt remapping                                             | CPU VA→PA、分配 BAR aperture、路由 TLP、IOVA→Host PA、把 MSI/MSI-X message 投递成 CPU IRQ |
| GPU Endpoint | PCIe controller、BAR decoder、doorbell、command processor、GPU MMU、SDMA、VRAM controller、interrupt block | 接收 MMIO、取命令、翻译 GPUVA、发起 Memory Request、访问 VRAM、写 fence、产生 MSI-X               |

`[BOUNDARY]` 对典型离散 GPU 而言，Host 上存在 `amdgpu` 这样的 Linux PCI/GPU 驱动，但 GPU 芯片内部通常并没有另一个 Linux `pci_epf_driver`。GPU Endpoint 的 BAR 匹配、outbound request、SDMA 和 MSI-X 多由硬件及 GPU firmware 完成。

Linux 同时提供另一套 Endpoint Framework，适用于“某个运行 Linux 的 SoC 自身作为 PCIe Endpoint”的场景：

```text
Endpoint Function driver (EPF)：实现某个 PCI function 的功能
        ↓
Endpoint Controller library (EPC)：提供 set_bar/map_addr/raise_irq 等控制器抽象
        ↓
具体 PCIe controller driver：配置 inbound/outbound window 和中断硬件
```

`[SOURCE]` [PCI Endpoint Framework 文档](../2.源码/linux/Documentation/PCI/endpoint/pci-endpoint.rst)列出了 EPC、EPF、configfs 三层，并说明 `pci_epc_set_bar()`、`pci_epc_map_addr()` 和 `pci_epc_raise_irq()` 的职责。本文会用 `pci-epf-test.c` 说明通用 EP 侧机制，但不会声称 AMDGPU 内部调用了这些函数。

## 2. 八种地址：先问“谁拿着它去访问什么”

一个地址不能脱离“地址空间所有者”和“翻译单元”讨论。下面八种名字可能同时指向同一份数据，但不能互相代用：

| **名称**                | **谁使用**                              | **由谁翻译/解释**                              | **最终对象**                                         |
| --------------------- | ------------------------------------ | ---------------------------------------- | ------------------------------------------------ |
| User VA               | Host 用户进程中的 CPU 指令                   | 当前进程 CPU 页表                              | Host page 或映射的 MMIO page                         |
| Kernel VA             | Host 内核 CPU 指令                       | 内核 CPU 页表                                | Host RAM 或`ioremap` 的 MMIO aperture              |
| Host PA               | Host 内存控制器/CPU 物理地址空间                | 平台物理地址解码                                 | Host RAM 或 MMIO resource                         |
| DMA address / IOVA    | PCIe device 作为 requester 发出的访问       | Host IOMMU，或 direct-DMA/platform mapping | Host PA，偶尔也可能是 P2P resource                      |
| PCIe address          | TLP header 中的 address field          | PCIe fabric/RC/目标 completer              | Host memory、BAR 或 peer resource                  |
| EP local address      | Endpoint 内部 CPU/DMA/master port      | EP controller 的 local interconnect/MMU   | EP RAM、VRAM 或 local register                     |
| GPUVA                 | GPU shader/SDMA/command 中的虚拟地址       | GPU MMU/GPUVM page table                 | VRAM physical address或可访问的 system-memory address |
| VRAM PA/local address | GPU memory controller或显存 copy engine | GPU local fabric                         | VRAM cell                                        |

一个示意性的地址链可能是：

```text
User VA 0x00007f10_40000000
  ├─CPU page table→ 离散的 Host pages：PA 0x12345000、0x8a731000、...
  ├─Host DMA API/IOMMU→ IOVA 0x00000080_00000000 ...
  └─AMDGPU GPUVM PTE→ GPUVA 0x00007f10_40000000 映射到这些 IOVA

SDMA 使用 GPUVA 0x00007f10_40000000
  → GPU MMU 查 PTE 得到 system-memory/DMA address
  → PCIe Memory Read Request 携带该 address
  → Host IOMMU 按 requester identity/PASID 等上下文翻译为 Host PA
```

这里 User VA 和 GPUVA 数值可以被 runtime 有意设置成相同，这叫统一虚拟地址体验；数值相等不代表两侧使用同一套页表。

### 2.1 四类映射不能混为一谈

```text
CPU 用户态访问 GPU BAR：
BAR Host physical/MMIO aperture → io_remap_pfn_range() → User VA

GPU 访问 Host RAM：
Host pages/SG → dma_map_sg() → DMA address/IOVA

GPU 指令访问 BO：
GPUVA → amdgpu_vm_bo_map()/page-table update → VRAM address或system DMA address

运行 Linux 的通用 Endpoint 发起 outbound 请求：
EP local window → pci_epc_map_addr() → RC/PCI address
```

它们分别在 CPU 页表、Host IOMMU、GPU page table、EP controller outbound translation 中生效。任何“把 VA 转成 PA 后直接写给设备”的写法都绕开了 DMA API 的设备约束、IOMMU、cache maintenance 和安全隔离。

## 3. CPU 访问 BAR：这是 MMIO，不是 GPU DMA

### 3.1 BAR 从 PCI resource 到 Kernel VA

Host PCI core 枚举设备时读取 BAR，给它分配 Host MMIO aperture。驱动先 enable function、request regions，再把 BAR 映射成 `__iomem` Kernel VA：

```c
/* [EXAMPLE] Host probe skeleton */
static int mygpu_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
    struct mygpu *g;
    int ret;

    g = devm_kzalloc(&pdev->dev, sizeof(*g), GFP_KERNEL);
    if (!g)
        return -ENOMEM;
    g->pdev = pdev;

    ret = pcim_enable_device(pdev);
    if (ret)
        return ret;

    ret = pcim_iomap_regions(pdev, BIT(0), "mygpu");
    if (ret)
        return ret;

    pci_set_master(pdev);
    ret = dma_set_mask_and_coherent(&pdev->dev, DMA_BIT_MASK(48));
    if (ret)
        return ret;

    g->bar0 = pcim_iomap_table(pdev)[0];
    return 0;
}
```

`[SOURCE]` [pci\_endpoint\_test.c](../2.源码/linux/drivers/misc/pci_endpoint_test.c) 的 probe 在约 1265 行设置 DMA mask，在 1267 行 enable device，在 1273 行 request BAR resource，在 1279 行调用 `pci_set_master()`，在 1283 行调用 `pci_ioremap_bar()`。这是一条真实的 Host PCI function driver 初始化路径。

CPU 写 doorbell 的真实数据面为：

```text
Kernel VA (__iomem)
  → CPU page table / architecture MMIO mapping
  → Host MMIO aperture
  → Root Complex 生成 PCIe Memory Write TLP
  → Endpoint BAR decoder 命中 BAR+offset
  → GPU 内部 doorbell register/FIFO
```

这条路径中发起者是 CPU/Root Complex，不是 GPU DMA engine，因此“链路上出现了 PCIe Memory Write”不能推出“发生了 DMA”。

### 3.2 BAR 从 PCI resource 到 User VA

若确实要把 BAR page 暴露给用户态，优先使用 PCI resource-aware helper 或 DRM/UIO 等框架提供的受控 mmap，而不是把任意 PFN 直接交给用户：

```c
/* [EXAMPLE] 仅展示形状；产品代码还必须限制 BAR、offset、长度、权限和进程生命周期。 */
static int mygpu_mmap_bar(struct file *file, struct vm_area_struct *vma)
{
    struct mygpu *g = file->private_data;

    return pci_mmap_resource_range(g->pdev, 0, vma,
                                   pci_mmap_mem, 0);
}
```

`[SOURCE]` [drivers/pci/mmap.c](../2.源码/linux/drivers/pci/mmap.c) 中 `pci_mmap_resource_range()` 先检查 VMA 是否超出 BAR，选择 device 或 write-combine page protection，将 BAR resource start 加入 `vm_pgoff`，最后调用 `io_remap_pfn_range()`。`[SOURCE]` [mm/memory.c](../2.源码/linux/mm/memory.c) 的 `vm_iomap_memory()` 是通用 physical I/O range→VMA helper，也会做范围准备后调用 `io_remap_pfn_range()`。

因此 `remap_pfn_range()`/`io_remap_pfn_range()` 的方向是：

```text
PFN/Host MMIO resource → CPU VMA page-table entries → User VA
```

它不固定普通匿名用户页，不建立 Device DMA mapping，不生成 DMA descriptor，也不启动 PCIe Endpoint 的任何 engine。

### 3.3 MMIO write posting 与 doorbell

`writel(tail, doorbell)` 表示“发布了新的 producer/tail”，不表示设备已取到 descriptor，更不表示 DMA 已经完成。PCI MMIO write 通常是 posted write，CPU 可以在事务真正到达 Endpoint 之前继续执行。

`[SOURCE]` [Documentation/PCI/pci.rst](../2.源码/linux/Documentation/PCI/pci.rst) 的 “MMIO Space and Write Posting” 说明需要在必须确认写已到达时对安全寄存器做 readback。`[SOURCE]` [Documentation/memory-barriers.txt](../2.源码/linux/Documentation/memory-barriers.txt) 的 “KERNEL I/O BARRIER EFFECTS” 说明默认属性下的 `writel()` 会等待同一线程此前的 normal-memory writes，再触发 MMIO；`writel_relaxed()` 不提供同等保证。

不要机械地在所有 doorbell 前加 `dma_wmb()`：descriptor 位于 coherent memory、streaming memory、WC-mapped memory 或 device-local memory时，所需同步不同。正确做法是先明确内存类型和 ownership protocol，再选择普通 `writel()`、DMA barrier、`dma_sync_*()` 或体系结构/设备专用 flush。

## 4. 用户 Buffer 到 Device-visible IOVA

### 4.1 `malloc()` 只给出 User VA

```c
void *buf = aligned_alloc(4096, 1 << 20);
```

此时 `buf` 只是当前进程的 User VA。页面可能尚未 fault in，物理页可以不连续，也可能在 `munmap()`、COW、migration 等事件中变化。PCIe device 不认识进程 CPU 页表，所以不能把该值直接放入一个普通 DMA descriptor。

### 4.2 短期 pin、长期 pin 与可回放 page fault

传统异步 DMA 路径要先使页面在设备访问期间保持有效。Linux 文档明确要求 DMA-pinned pages 使用 `pin_user_pages*()` 而不是普通 `get_user_pages*()`；短期 direct I/O 使用隐含 `FOLL_PIN` 的 pin API，长期不可回放 DMA 通常还要 `FOLL_LONGTERM`。

```c
/* [EXAMPLE] 一次长生命周期、设备只读取 Host 内存的注册路径片段 */
unsigned int gup_flags = FOLL_LONGTERM;
long pinned;

pinned = pin_user_pages_fast(user_start, npages, gup_flags, pages);
if (pinned != npages) {
    if (pinned > 0)
        unpin_user_pages(pages, pinned);
    return pinned < 0 ? pinned : -EFAULT;
}
```

若设备要写 Host pages，需要相应的 write pin 权限；DMA 完成并回收时还要按页面内容是否被设备修改，使用合适的 dirty/unpin helper。所有 partial-pin、SG allocation、DMA-map 失败都必须逆序回滚。

`[SOURCE]` [pin\_user\_pages.rst](../2.源码/linux/Documentation/core-api/pin_user_pages.rst) 明确写出“use `pin_user_pages*()` for DMA-pinned pages”，并把短期 DIO、长期 RDMA、MMU notifier、replayable fault 分为不同案例。它同时说明 `FOLL_LONGTERM` 是更严格的 `FOLL_PIN` 使用场景。

现代 GPU userptr/SVM 往往不是永久 pin 全部页面，而是使用 HMM/MMU interval notifier 跟踪 CPU VMA 变化，配合 GPU 可回放 page fault 动态建立或撤销 GPU PTE。这改变了 resident-page 管理策略，但没有消除“设备访问时必须存在合法翻译和一致生命周期”这一基本约束。

`[SOURCE]` AMDGPU 的 [amdgpu\_ttm.c](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_ttm.c) 中 `amdgpu_ttm_tt_get_user_pages()` 通过 HMM range 获取 userptr pages，`amdgpu_ttm_tt_set_user_pages()` 将其放入 TTM page array；[amdgpu\_hmm.c](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_hmm.c) 注册 invalidation notifier 并协调 userptr eviction。这是“页可变，因此需要 notifier/validation”的真实 GPU 例子，不应简化成永久 GUP。

### 4.3 pages→SG→DMA mapping

固定或验证 pages 后，驱动把离散页面组织成 scatter-gather table，再为“这个具体设备”建立 DMA mapping：

```c
/* [EXAMPLE] */
ret = sg_alloc_table_from_pages(&xfer->sgt, xfer->pages, xfer->npages,
                                offset_in_page(user_addr), length,
                                GFP_KERNEL);
if (ret)
    goto err_unpin;

xfer->orig_nents = xfer->sgt.orig_nents;
xfer->mapped_nents = dma_map_sg(dev, xfer->sgt.sgl,
                                xfer->orig_nents, DMA_TO_DEVICE);
if (!xfer->mapped_nents) {
    ret = -EIO;
    goto err_sg;
}

for_each_sg(xfer->sgt.sgl, sg, xfer->mapped_nents, i) {
    dma_addr_t addr = sg_dma_address(sg);
    size_t len = sg_dma_len(sg);
    /* 把 addr/len 写入硬件能理解的 SG descriptor。 */
}
```

此处最容易写错的是两个计数：

```text
orig_nents：输入 SG entries 数量；解除 mapping 时使用
mapped_nents：DMA API 合并后输出的 DMA segments 数量；填硬件 descriptor 时使用
```

```c
/* 正确的解除方式 */
dma_unmap_sg(dev, xfer->sgt.sgl, xfer->orig_nents, DMA_TO_DEVICE);
```

`[SOURCE]` [dma-api.rst](../2.源码/linux/Documentation/core-api/dma-api.rst) 的 `dma_map_sg()` 小节明确说明返回数量可能小于输入 `nents`，设备应使用 `sg_dma_address()`/`sg_dma_len()`，而 `dma_unmap_sg()` 必须传原始 `nents`。`[SOURCE]` [kernel/dma/mapping.c](../2.源码/linux/kernel/dma/mapping.c) 的 `__dma_map_sg_attrs()` 会在 direct DMA、DMA-IOMMU 和 arch/device `map_sg` backend 之间选择。

### 4.4 IOMMU 实际做了什么

启用 DMA-IOMMU 时，`dma_map_sg()` 的核心不是“查询 PA”，而是为指定 device/domain 分配 IOVA range，建立 IOVA→pages 的 IOMMU PTE，并将可供设备使用的 DMA segments 写回 SG DMA fields：

```text
struct page[]/physical extents
  → 计算 IOVA alignment、segment boundary 和总长度
  → iommu_dma_alloc_iova()
  → iommu_map_sg(domain, iova, ...)
  → __finalise_sg() 写出 sg_dma_address()/sg_dma_len()
```

`[SOURCE]` [drivers/iommu/dma-iommu.c](../2.源码/linux/drivers/iommu/dma-iommu.c) 的 `iommu_dma_map_sg()` 正是上述流程：先做 cache/device sync 与 segment layout，再分配 IOVA，调用 `iommu_map_sg()`，最后 finalise DMA segments。

因此：

```text
无 IOMMU：dma_addr_t 可能等于 Host PA，也可能仍经过平台 offset/bounce mapping
有 IOMMU：dma_addr_t 通常是 IOVA，IOMMU 再把它翻译到 Host PA
```

驱动只能依赖 DMA API 返回的 `dma_addr_t`，不能依赖 `dma_addr_t == phys_addr_t`。

### 4.5 coherent 与 streaming mapping

这两类 DMA memory 解决的问题不同：

| **类型**              | **典型 API**                 | **典型用途**                              | **CPU/device 同步重点**                                                                   |
| ------------------- | -------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------- |
| coherent/consistent | `dma_alloc_coherent()`     | descriptor ring、completion ring、共享控制块 | CPU 与 device 对内容一致可见，但字段发布顺序仍需 ownership/barrier protocol                             |
| streaming           | `dma_map_single/page/sg()` | 一次或一段时间内作为 payload 的普通 buffer         | CPU 和 device ownership 切换时，non-coherent 平台需`dma_sync_*_for_cpu/device()` 或 unmap 完成同步 |

`dma_wmb()` 用于 DMA-capable device 与 CPU 共享的 coherent memory 的写入顺序，例如先写 descriptor payload，再写 ownership bit。它不是 streaming buffer 的 cache maintenance，也不排序所有 MMIO。

`[SOURCE]` [memory-barriers.txt](../2.源码/linux/Documentation/memory-barriers.txt) 明确把 `dma_rmb()`/`dma_wmb()`限定为 consistent memory ordering，并明确说 DMA barriers 不保证 MMIO ordering。`[SOURCE]` [dma-api.rst](../2.源码/linux/Documentation/core-api/dma-api.rst) 给出了 `dma_sync_single/sg_for_cpu/device()` 的 streaming mapping 同步 API。

## 5. Descriptor、Ring、Doorbell：告诉 GPU 做什么

### 5.1 三个对象的层次

```text
Descriptor/command：一个引擎可理解的工作描述
Ring/queue：批量保存命令，并用 producer/consumer 管理所有权
Doorbell：Host 告知 GPU “producer 已推进，请检查队列”
```

一个教学 descriptor 可能长这样：

```c
/* [EXAMPLE] 不是 AMD SDMA 的真实 ABI */
struct mygpu_copy_desc {
    __le64 src_gpuva;
    __le64 dst_gpuva;
    __le32 bytes;
    __le16 opcode;
    __le16 flags;
    __le64 completion_gpuva;
    __le64 sequence;
};
```

它保存的是 engine 执行所需的语义，例如源/目的 GPUVA、长度、opcode、completion address；它通常不保存 PCIe header 的 requester ID、tag、first/last byte enable、sequence number、LCRC 等链路字段。后者由 GPUVM、PCIe transaction layer 和 data-link layer在运行时产生。

### 5.2 发布一个 coherent command ring

```c
/* [EXAMPLE] 假设 ring 来自 dma_alloc_coherent()，doorbell 是默认属性 MMIO。 */
static void mygpu_submit(struct mygpu *g, const struct mygpu_copy_desc *cmd)
{
    unsigned long flags;
    u32 slot;

    spin_lock_irqsave(&g->ring_lock, flags);
    slot = g->producer & (g->ring_size - 1);
    g->ring[slot] = *cmd;

    /* 先发布 descriptor 内容，再发布 producer/ownership。 */
    dma_wmb();
    WRITE_ONCE(g->ctrl->producer, ++g->producer);

    /* 默认属性 writel()把此前 normal-memory writes 排在 doorbell 之前。 */
    writel(g->producer, g->bar0 + MYGPU_DOORBELL);
    spin_unlock_irqrestore(&g->ring_lock, flags);
}
```

产品设计还必须定义：ring full 检查、producer wrap、每个 descriptor 的 owner/valid bit、多个 CPU producer 的锁、GPU consumer 更新、超时、reset generation、进程隔离和恶意命令校验。

### 5.3 Linux 测试驱动中的真实 Host 提交形状

`[SOURCE]` [drivers/misc/pci\_endpoint\_test.c](../2.源码/linux/drivers/misc/pci_endpoint_test.c) 的 `pci_endpoint_test_copy()` 是一个很清楚的最小证据：它分别对源和目的 kernel buffer 调用 `dma_map_single()`，把返回的 DMA addresses 写入 Endpoint BAR 寄存器，然后设置 `COMMAND_COPY`，等待 IRQ，最后 unmap。该例用的是 `kzalloc()` buffer而非用户页，但它证明了“mapping→把 DMA address 交给 EP→写 command→IRQ→unmap”的控制顺序。

### 5.4 AMD SDMA packet 是真实的 engine command

`[SOURCE]` [sdma\_v6\_0.c](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/sdma_v6_0.c) 的 `sdma_v6_0_emit_copy_buffer()` 向 indirect buffer 连续写入 SDMA copy opcode、byte count、64-bit source address 和 64-bit destination address；`sdma_v6_0_ring_emit_fence()` 写入 fence address/sequence，并可追加 trap 触发中断。这里的字段是 SDMA 可见的 GPU/MC address；它是否经过某个进程的 GPUVM 翻译取决于 ring/IB 的提交上下文和具体 ASIC，不能仅凭这个 packet builder 下结论。

这说明 SDMA packet/IB 的层次是：

```text
Host/GPU driver构造的 SDMA command
  → SDMA command fetch/decode
  → 按提交上下文选择直接MC address或GPUVM address translation
  → SDMA 内部拆分 transfer
  → PCIe controller 生成多个 TLP，或 VRAM controller 生成 local requests
```

它不是 PCIe TLP 的软件镜像。

## 6. 一个 Descriptor 如何展开成 PCIe Transactions

假设一个 SDMA copy command 表示：

```text
copy 1 MiB from Host-backed GPUVA to VRAM-backed GPUVA
```

执行时至少发生以下转换：

```text
1个 copy command
  → 按 GPU page boundary、engine burst、alignment 拆成多个内部 memory operations
  → 每个 source GPUVA 经 GPU MMU 得到 system-memory DMA/PCIe address
  → PCIe controller 按 MRRS、4 KiB boundary、credits、outstanding tags 等拆成 Memory Read Requests
  → 每个 read request 返回一个或多个 Completion with Data
  → SDMA 重组数据并按目的 GPUVA 写入 VRAM
```

因此不存在稳定的“1 descriptor = 1 TLP”关系。1 MiB descriptor 往往对应大量 request/completion TLP；反过来，一个 doorbell TLP也可能使 GPU 一次消费多个 ring entries。

### 6.1 常见事务方向

| **操作**                          | **Requester** | **PCIe 事务**                      | **是否需要 completion**                       |
| ------------------------------- | ------------- | -------------------------------- | ----------------------------------------- |
| Host CPU 写 GPU doorbell/BAR     | Root Complex  | Memory Write                     | posted，无 completion TLP                   |
| Host CPU 读 GPU status/BAR       | Root Complex  | Memory Read                      | Endpoint 返回 Completion with Data          |
| GPU SDMA 读 Host buffer          | GPU Endpoint  | Memory Read                      | Root Complex/Host 返回 Completion with Data |
| GPU SDMA 写 Host completion/data | GPU Endpoint  | Memory Write                     | posted，无 completion TLP                   |
| GPU 发 MSI/MSI-X                 | GPU Endpoint  | 向 message address 的 Memory Write | posted；Host interrupt subsystem消费该写       |

“posted”不等于“立即完成”或“绝不会报错”，它表示协议中没有针对该 Memory Write 的正常 completion response。

### 6.2 MPS、MRRS、Tag 与 4 KiB boundary

* `[SPEC]` MPS（Max Payload Size）限制一个带数据 TLP 的最大 payload，影响 GPU 向 Host Memory Write 和 Host 返回 Completion with Data 时的分片。
* `[SPEC]` MRRS（Max Read Request Size）限制 requester 发出的单个 Memory Read Request 请求量；实际 engine 还可能选更小 request。
* `[SPEC]` Non-posted read 使用 Tag 区分多个 outstanding requests，Completion 携带相应 Tag 使 requester 重组返回数据。Tag 是 PCIe transaction 层资源，不是应用 descriptor ID。
* `[SPEC]` Memory Request 不能跨越 4 KiB address boundary，所以即使 MRRS 足够大，边界附近也必须拆分。
* `[SPEC]` flow-control credits、link width/speed、completion latency、IOMMU miss、GPU page fault 和 engine queue occupancy 一起决定吞吐；descriptor 的 `len` 并不直接决定 TLP 大小。

`[SOURCE]` [include/uapi/linux/pci\_regs.h](../2.源码/linux/include/uapi/linux/pci_regs.h) 定义了 Device Control 中 128–4096 byte 的 payload/read-request encodings；[drivers/pci/pci.c](../2.源码/linux/drivers/pci/pci.c) 的 `pcie_set_readrq()`和`pcie_set_mps()`检查并配置 MRRS/MPS。4 KiB boundary、Tag 和 completion 拆分属于 PCIe 协议规则，本文标为 `[SPEC]`，不冒充 Linux driver policy。

## 7. Endpoint 的 inbound 与 outbound 完全不同

### 7.1 Inbound：Host 访问 EP BAR

```text
Host CPU/其他 requester 发出 PCIe address = BAR base + offset
  → EP PCIe controller 做 function/BAR match
  → inbound translation
  → EP local register/RAM/VRAM aperture
```

Host 写 doorbell属于 inbound path。BAR 解决的是“别人如何找到 Endpoint 暴露的窗口”，不是“Endpoint 如何找到 Host buffer”。

`[SOURCE]` Linux EPC 的 `pci_epc_set_bar()` 最终调用具体 controller 的 `set_bar` operation；[pci-epc-core.c](../2.源码/linux/drivers/pci/endpoint/pci-epc-core.c) 约 668 行给出该接口。这能证明软件配置 BAR 的抽象边界，真正的 TLP match 和 local routing 仍由 controller hardware 实现。

### 7.2 Outbound：EP 访问 Host/RC address

通用 SoC Endpoint controller 往往不能让 local DMA master 直接使用任意 64-bit RC address，而需要先配置 outbound window：

```text
EP DMA engine 使用 local physical/window address
  → EPC outbound ATU/window
  → PCIe Memory Request address = RC/Host DMA address
```

`[SOURCE]` [pci-epc-core.c](../2.源码/linux/drivers/pci/endpoint/pci-epc-core.c) 的 `pci_epc_mem_map()` 处理 controller alignment/window size，调用 `pci_epc_mem_alloc_addr()`取得 EP local window，再调用 `pci_epc_map_addr()`把 local physical address 映射到给定 RC PCI address；`pci_epc_mem_unmap()`执行逆操作。[pci-epc-mem.c](../2.源码/linux/drivers/pci/endpoint/pci-epc-mem.c) 的 `pci_epc_mem_alloc_addr()`从 EPC address space 分配 local window 并建立 CPU mapping。

### 7.3 EPF test 的真实 RC→EP DMA 读取

`[SOURCE]` [pci-epf-test.c](../2.源码/linux/drivers/pci/endpoint/functions/pci-epf-test.c) 的 read path 先用 `pci_epc_mem_map()`把 Host 写来的 RC address 映射到 EP local window；若使用 DMAEngine，它对 EP local buffer做 `dma_map_single(..., DMA_FROM_DEVICE)`，再由 `pci_epf_test_data_transfer()`构造 DMA transaction，`dmaengine_submit()`后调用 `dma_async_issue_pending()`。

注意这里存在两层“mapping”，不能合并：

```text
pci_epc_mem_map()：配置 PCIe controller outbound local→RC address window
dma_map_single()：给 EP 本地 DMAEngine 映射它要访问的 local buffer
```

`[BOUNDARY]` 自研 GPU 如果 SDMA 直接接受 GPUVA，并由 GPUVM PTE 指向 Host system address，则 outbound window 可能被 GPU IOMMU/PCIe controller 集成为更复杂的 per-process translation，不一定暴露 `pci_epc_mem_map()`这种软件 API；功能问题仍相同：GPU 发出的 address 如何被路由成 Host IOVA。

## 8. GPUVM：GPU 地址翻译与 Host IOMMU 是两级

这是普通 PCIe DMA 教程最常漏掉的 GPU 特有层次。

```text
GPU shader/SDMA 发出 GPUVA
  → GPU TLB/GPU page table
  → PTE 表示 VRAM local address 或 system-memory DMA address
  → 若目标是 system memory，GPU PCIe requester 发出 Memory Request
  → Host IOMMU 按 device/requester context 将 IOVA 翻译成 Host PA
```

GPUVM 解决“一个 GPU process 的虚拟地址映射到哪个 BO/page”；Host IOMMU 解决“这个 PCIe requester 发出的 DMA address能否访问哪一个 Host physical page”。它们的页表格式、fault handler、TLB 和保护域不同。

### 8.1 AMDGPU 的 userptr→DMA address→GPU PTE 证据链

`[SOURCE]` [amdgpu\_gem.c](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_gem.c) 的 `amdgpu_gem_userptr_ioctl()`检查 User VA/size/flags，创建 GEM object，调用 `amdgpu_ttm_tt_set_userptr()`并注册 HMM；同文件的 VA operation 在 map 时调用 `amdgpu_vm_bo_map()`。

`[SOURCE]` [amdgpu\_ttm.c](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_ttm.c) 的 `amdgpu_ttm_tt_pin_userptr()`把 TTM pages压成 SG table，调用 `dma_map_sgtable(adev->dev, ...)`，再由 `drm_prime_sg_to_dma_addr_array()`得到 page DMA address array。

`[SOURCE]` [amdgpu\_vm.c](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_vm.c) 的 `amdgpu_vm_bo_map()`记录 GPUVA mapping；`amdgpu_vm_bo_update()`对 TT/system pages 取 `bo->tbo.ttm->dma_address`，并把 `pages_addr`交给 `amdgpu_vm_update_range()`更新 GPU page table。

把三段源码合起来得到：

```text
User VA
  → HMM/TTM 得到 struct page[]
  → SG + dma_map_sgtable() 得到 per-page DMA addresses
  → GPUVA mapping object
  → GPU page-table update 使用 DMA address array
  → GPU 访问 GPUVA 时可到达 Host pages
```

这正是“GPUVA→GPUVM→IOVA→Host IOMMU→PA”的代码证据，而不是概念图的臆测。

### 8.2 Compute 访存不一定叫 DMA

更准确的集合关系是：

```text
Device-initiated bus-master memory access
  ├─SDMA/copy engine access
  ├─network/storage DMA engine access
  └─GPU compute core经 cache/GPUVM 对 system memory 的 load/store
```

DMA engine access是 device bus-master access 的一个子集。GPU shader 直接 load 一个 SVM pointer 时同样可能生成 PCIe/CXL memory transactions，但工程上通常称为“compute memory access”或“zero-copy access”，不必硬叫成 SDMA。

### 8.3 DMA 访问与 memory copy 也不是同义词

GPU SDMA 对 Host 发 Memory Read 后，数据可能：

* 被写入 VRAM，于是形成 Host→VRAM copy；
* 被送入设备内部 FIFO/codec，而不是形成持久副本；
* 仅为读取 command/descriptor；
* 与另一个写方向组合成 P2P 或 Host-to-Host copy。

所以“DMA”描述谁主动、通过什么 engine 发起访问；“copy/migration”描述数据的源和最终落点。

## 9. Completion、Fence、MSI-X 与资源回收

“完成”至少有三种不同含义：

```text
PCIe Completion TLP：回答某一个 non-posted Memory Read Request
GPU fence/completion record：说明某个 engine command 达到定义的完成点
Linux completion/dma_fence/event：让内核或用户态等待者观察到该完成
```

它们不应使用同一个笼统的 completion 概念。SDMA 的 read Completion with Data 只表示一部分读数据返回；整个 1 MiB copy 完成通常要等 engine 写 fence。

### 9.1 MSI/MSI-X 是一笔特殊目标地址的 Memory Write

Host 配置 MSI/MSI-X 后，设备获得 message address 和 message data。设备触发向量时，对该 address 发出带该 data 的 posted Memory Write；Host interrupt remapping/APIC/ITS 等模块把它转成 CPU IRQ。

`[SOURCE]` [include/linux/msi.h](../2.源码/linux/include/linux/msi.h) 的 `struct msi_msg`直接保存 `address_lo/address_hi/data`，证明 Linux 配置给设备的是“地址+数据”。`[SOURCE]` [msi-howto.rst](../2.源码/linux/Documentation/PCI/msi-howto.rst) 说明 `pci_alloc_irq_vectors()`/`pci_irq_vector()`的 Host 驱动接口，并说明 MSI ordering保证 interrupt-generating write不能越过此前 data writes。MSI 是 Memory Write 的协议解释属于 `[SPEC]`。

`[SOURCE]` [pci\_endpoint\_test.c](../2.源码/linux/drivers/misc/pci_endpoint_test.c) 约 203–219 行为 INTx/MSI/MSI-X 分配 vectors，并对 `pci_irq_vector()`得到的 Linux IRQ注册 handler。`[SOURCE]` [pci-epf-test.c](../2.源码/linux/drivers/pci/endpoint/functions/pci-epf-test.c) 的 `pci_epf_test_raise_irq()`先更新 status，再调用 `pci_epc_raise_irq()`；这是通用 Endpoint 侧的完成通知例子。

### 9.2 IRQ handler 不等于可以立即释放一切

IRQ handler 应先读取并确认 completion/fence sequence，区分 stale interrupt、多个合并完成和 reset generation；随后再完成 `dma_fence`/waitqueue，通常把可能睡眠的 unmap/unpin 放到合适上下文。

```c
/* [EXAMPLE] 省略并发和设备移除处理 */
static irqreturn_t mygpu_irq(int irq, void *data)
{
    struct mygpu *g = data;
    u32 status = readl(g->bar0 + MYGPU_IRQ_STATUS);

    if (!(status & MYGPU_IRQ_COPY_DONE))
        return IRQ_NONE;

    writel(MYGPU_IRQ_COPY_DONE, g->bar0 + MYGPU_IRQ_ACK);
    queue_work(g->wq, &g->complete_work);
    return IRQ_HANDLED;
}

static void mygpu_complete_work(struct work_struct *work)
{
    struct mygpu_xfer *xfer = find_completed_xfer(...);

    dma_unmap_sg(xfer->dev, xfer->sgt.sgl, xfer->orig_nents,
                 xfer->direction);
    sg_free_table(&xfer->sgt);
    if (xfer->device_wrote_host)
        unpin_user_pages_dirty_lock(xfer->pages, xfer->npages, true);
    else
        unpin_user_pages(xfer->pages, xfer->npages);
    complete(&xfer->done);
}
```

资源回收必须发生在设备不再访问 mapping 之后。仅仅收到 doorbell write completion、某个 PCIe read completion或用户线程超时，都不足以证明 engine 已停止访问这些 IOVA。

## 10. 贯穿示例：1 MiB User Buffer→VRAM

下面把各层压缩成一条可逐点核对的实际流程。

### 10.1 用户态提交

```c
/* [EXAMPLE] userspace */
struct mygpu_copy_to_vram req = {
    .user_ptr = (uintptr_t)buf,
    .bytes = 1 << 20,
    .dst_gpuva = vram_gpuva,
};

if (ioctl(fd, MYGPU_COPY_TO_VRAM, &req) == -1)
    perror("MYGPU_COPY_TO_VRAM");
```

用户态只传 User VA、长度和目标 handle/GPUVA。用户态不查询 PA，也不自行猜 IOVA。

### 10.2 Host 驱动注册源 Buffer

```text
copy_from_user()取得不可变请求参数
  → access_ok/overflow/alignment/size检查
  → pin_user_pages*() 或 HMM registration/fault validation
  → pages[]
  → sg_alloc_table_from_pages()
  → dma_map_sg(DMA_TO_DEVICE)
  → mapped DMA segments/IOVA
```

方向 `DMA_TO_DEVICE` 是站在设备视角：设备读取 Host buffer。若设备写回 Host buffer，应使用 `DMA_FROM_DEVICE`；双向只在确实双向时使用，不能为了省事一律 `DMA_BIDIRECTIONAL`。

### 10.3 建立 GPUVA

有两种常见硬件/ABI形态：

```text
A. SDMA descriptor直接接受一组 DMA segments
   Host驱动把 sg_dma_address/len 逐项写入硬件 SG descriptor

B. SDMA descriptor接受 GPUVA
   Host驱动先把 GPUVA PTE 指向 per-page DMA addresses
   descriptor只保存连续 GPUVA+len，SDMA执行时由 GPUVM逐页翻译
```

现代 GPU 更接近 B；简单自研 copy engine 可能先实现 A。二者都必须尊重 DMA mapping lifetime。

### 10.4 提交并执行

```text
Host：填 command ring
  → 发布 producer
  → writel(doorbell)

GPU：BAR decoder收到 inbound Memory Write
  → command processor读取 producer和command
  → SDMA decode copy
  → GPUVM翻译源/目的 GPUVA
  → 源指向system memory：PCIe Memory Read Requests
  → RC/IOMMU：IOVA→Host PA并读Host RAM
  → Completion with Data返回GPU
  → SDMA写入目的VRAM
```

### 10.5 完成并清理

```text
SDMA所有数据到达定义的完成点
  → 写 fence sequence
  → interrupt block发MSI-X Memory Write
  → Host IRQ handler确认status/fence
  → 唤醒等待者
  → dma_unmap_sg(original nents)
  → sg_free_table()
  → unpin_user_pages()
```

如果用户进程在中途退出，驱动不能立即释放 pages；必须取消/抢占队列并确认 engine quiesced，或让 transfer context持有 mm/BO/page references直至 fence 完成。

## 11. 可实现的最小 Host 驱动骨架

下面代码只用于把生命周期串起来，省略 IDR/handle、DMA fence、runtime PM、热拔插、reset、IOCTL compat、安全校验和多队列。重点是每个资源的获得与释放对称。

```c
/* [EXAMPLE] */
struct mygpu_xfer {
    struct device *dev;
    struct page **pages;
    unsigned int npages;
    struct sg_table sgt;
    unsigned int orig_nents;
    unsigned int mapped_nents;
    enum dma_data_direction direction;
    struct completion done;
};

static int mygpu_map_user(struct mygpu *g, unsigned long uaddr, size_t bytes,
                          struct mygpu_xfer *xfer)
{
    unsigned long first = uaddr & PAGE_MASK;
    unsigned long last;
    size_t span;
    long pinned;
    int ret;

    if (!bytes || bytes > MYGPU_MAX_TRANSFER ||
        check_add_overflow(uaddr, bytes - 1, &last))
        return -EINVAL;
    if (!access_ok((void __user *)uaddr, bytes))
        return -EFAULT;

    span = offset_in_page(uaddr) + bytes;
    xfer->npages = DIV_ROUND_UP(span, PAGE_SIZE);
    xfer->pages = kcalloc(xfer->npages, sizeof(*xfer->pages), GFP_KERNEL);
    if (!xfer->pages)
        return -ENOMEM;

    pinned = pin_user_pages_fast(first, xfer->npages,
                                 FOLL_LONGTERM, xfer->pages);
    if (pinned != xfer->npages) {
        if (pinned > 0)
            unpin_user_pages(xfer->pages, pinned);
        ret = pinned < 0 ? pinned : -EFAULT;
        goto err_pages;
    }

    ret = sg_alloc_table_from_pages(&xfer->sgt, xfer->pages, xfer->npages,
                                    offset_in_page(uaddr), bytes, GFP_KERNEL);
    if (ret)
        goto err_unpin;

    xfer->direction = DMA_TO_DEVICE;
    xfer->orig_nents = xfer->sgt.orig_nents;
    xfer->mapped_nents = dma_map_sg(&g->pdev->dev, xfer->sgt.sgl,
                                    xfer->orig_nents, xfer->direction);
    if (!xfer->mapped_nents) {
        ret = -EIO;
        goto err_sg;
    }

    xfer->dev = &g->pdev->dev;
    init_completion(&xfer->done);
    return 0;

err_sg:
    sg_free_table(&xfer->sgt);
err_unpin:
    unpin_user_pages(xfer->pages, xfer->npages);
err_pages:
    kfree(xfer->pages);
    return ret;
}

static void mygpu_unmap_user(struct mygpu_xfer *xfer)
{
    dma_unmap_sg(xfer->dev, xfer->sgt.sgl,
                 xfer->orig_nents, xfer->direction);
    sg_free_table(&xfer->sgt);
    unpin_user_pages(xfer->pages, xfer->npages);
    kfree(xfer->pages);
}
```

这段代码刻意没有声称“pin 一定是最佳 GPU userptr 方案”。如果硬件支持 replayable faults，产品驱动更可能采用 HMM/notifier/BO validation；若 transfer 很短，`FOLL_LONGTERM`又可能过重。选择取决于映射是否跨越任意长的用户态生命周期，以及 invalidation 时硬件能否停止或重放。

## 12. 自研 GPU Endpoint 还必须实现什么

如果目标不是写一个 demo，而是让上述流程在自研 GPU 上闭环，硬件/固件至少要回答以下问题。

### 12.1 PCIe controller 与地址能力

* BAR size/type、64-bit BAR、prefetchable属性如何定义，哪些 offset 是 register、doorbell、queue aperture或VRAM aperture。
* Inbound BAR hit 后如何路由到 local register/SRAM/VRAM，是否有 function/VF/PASID隔离。
* Outbound requester支持多少地址位，是否支持 64-bit Memory Request，DMA mask应设置多少。
* Host IOVA如何进入 GPU：直接作为 system address、通过 outbound ATU window，还是写入 GPU page-table PTE。
* 是否支持 ATS/PRI/PASID、Address Translation Cache和replayable page fault；不支持时如何保证 pinned mapping lifetime。
* MPS/MRRS、outstanding tags、completion buffer、read reorder与timeout容量是否足以支撑目标吞吐。

### 12.2 Queue/command processor

* Ring base、size、producer/consumer、owner/valid、doorbell和completion record的 ABI。
* Descriptor位宽、endianness、alignment、跨页限制、最大长度、SG或GPUVA模式。
* 多进程/多queue的VMID/PASID绑定，以及 command fetch使用哪个GPUVM context。
* Ring full、doorbell丢失/合并、重复doorbell、wrap、stale generation和reset后的处理。
* Command validation、安全边界、越界GPUVA、无效PTE和恶意descriptor的fault行为。

### 12.3 GPUVM、cache与内存一致性

* GPUVA page size、PTE格式、system/VRAM aperture、权限位、snooped/coherent属性。
* Page-table update与TLB invalidate/ack的顺序，何时允许queue继续执行。
* Host coherent descriptor、streaming payload、WC doorbell和GPU cache之间的可见性协议。
* Non-coherent平台上的cache clean/invalidate责任在 Host DMA API、GPU cache controller还是firmware。
* GPU page fault如何上报、queue是halt、kill还是replay，fault期间mapping能否被回收。

### 12.4 SDMA/执行引擎

* Host↔VRAM、VRAM↔VRAM、Host↔Host和P2P分别支持哪些地址类型。
* 传输如何按 GPU page、4 KiB PCIe boundary、MRRS/MPS和engine burst拆分。
* Completion with Data乱序返回时如何按tag/offset重组，partial completion和poisoned completion如何处理。
* Fence定义是“命令已取走”“所有读已返回”“所有目的写全局可见”中的哪一个。
* Timeout、Unsupported Request、Completer Abort、AER、link down和IOMMU fault如何停止并归因到queue/process。

### 12.5 Interrupt 与恢复

* MSI-X table/PBA位置、vector数、per-queue vector还是共享vector、interrupt moderation策略。
* Fence write与MSI-X write的排序，Host看到IRQ时能否保证此前completion data可见。
* IRQ丢失时是否可poll fence，重复IRQ如何幂等处理。
* FLR、hot reset、GPU reset后如何阻止旧generation命令继续访问已回收IOVA。
* Reset前如何quiesce bus mastering，Host何时才可以 `dma_unmap_*()`和unpin。

## 13. 常见错误与逐点判定方法

### 13.1 常见错误

* 把 User VA 写入普通 DMA descriptor，默认GPU能使用Host进程页表。
* 从 `struct page`取 PA 直接给设备，绕过 `dma_map_*()`。
* 用 `mapped_nents`调用 `dma_unmap_sg()`，而不是原始 `nents`。
* 认为 `dma_map_*()`会生成 descriptor、写 doorbell或启动DMA。
* 把 `remap_pfn_range()`描述成 User VA→PA转换，实际它是建立 PFN/I/O range→VMA mapping。
* 用 `dma_wmb()`替代 streaming mapping 的 `dma_sync_*()`，或认为它能flush posted MMIO。
* 认为 doorbell返回就说明GPU已开始或已完成。
* 认为每个 descriptor恰好对应一个TLP。
* 把所有device主动访问都叫DMA，把所有DMA都叫memory copy。
* 只画 IOVA→Host PA，遗漏 GPUVA→GPUVM→system address 这一级。
* 在收到timeout后立即unmap/unpin，却没有先确认engine停止访问。

### 13.2 调试时每一步都问五个问题

```text
1. 当前地址属于哪个地址空间？
2. 谁是这次访问的 requester？
3. 下一次翻译由 CPU MMU、GPU MMU、EP ATU 还是 Host IOMMU 完成？
4. 这一层保存的是 command/descriptor、page-table entry，还是 PCIe TLP？
5. 哪个 fence/ack 能证明上一层已经不再使用该 mapping？
```

例如看到 `0x8000000000` 时，不要直接称它“物理地址”；先确认它来自 `sg_dma_address()`、GPU PTE、BAR resource、EPC outbound target还是VRAM allocator。

## 15. 最终压缩模型

```text
CPU 主动访问 GPU BAR：
CPU VA
  → CPU page table
  → Host MMIO aperture
  → RC发PCIe Memory Read/Write
  → EP BAR/inbound translation
  → GPU register/doorbell/local memory

GPU SDMA 主动访问 Host RAM：
User VA
  → pages/HMM
  → SG
  → dma_map_*得到IOVA
  → GPU PTE把GPUVA映射到IOVA
  → SDMA command使用GPUVA
  → GPU MMU
  → GPU PCIe Memory Request
  → Host IOMMU把IOVA翻译成Host PA
  → Host RAM

运行 Linux 的通用 EP DMA 访问 Host RAM：
Host驱动提供DMA address
  → EPF取得RC PCI address
  → EPC配置local→RC outbound window
  → EP DMAEngine使用local window address
  → PCIe Memory Request
  → Host IOMMU/Host RAM
```

最终可以用一句话概括：`io_remap_pfn_range()`让 CPU 用户态访问某段 I/O resource，`dma_map_*()`让某个 device安全地访问内存，GPUVM让 GPU engine用 GPUVA访问 BO，EP outbound translation让 Endpoint local master把请求发往RC address；descriptor描述工作，doorbell发布工作，GPU engine执行工作，PCIe controller把访问拆成TLP，IOMMU实施Host侧地址翻译和隔离，fence/MSI-X把完成传回Host。
