# AMD CLR 与 POCL Command Queue 实现差异探究

本文围绕两个问题展开：

1. OpenCL 的 `cl_command_queue` 在 AMD CLR 和 POCL 中分别如何表示；
2. AMD 非 Direct Dispatch、AMD Direct Dispatch 和 POCL/Vortex 分别在哪里解除 command 之间的依赖。

完整的 AQL、ROCr、KFD、MQD、HQD 和 doorbell 路径参见 [AMD 队列提交专题](<./5. AMD 队列提交：从 API 到 AQL 与硬件.md>)。本文只追到“软件 command 如何进入硬件提交队列”为止。

源码基线：AMD CLR 位于 `2.源码/rocm-clr`，版本为 `81277d69e3352e7144ced2ee9601484f9b48d950`；

POCL 位于 `2.源码/pocl`，版本为 `42fad325efaee07915307ab802f1527171b434d0`。文中 POCL/Vortex backend 的逐行证据以该 POCL fork 为准；若追到独立 Vortex runtime，则 `2.源码/vortex` 是公开替代快照 `d76b7f24e658867ab57e3942d7c648c3e6af072d`，不能冒充原本地 worktree `16aa1d...` 的精确版本。

## 1. 先抓住两条主线

对象表示方面：

```text
OpenCL cl_command_queue
    │
    ├── AMD：ICD handle → amd::CommandQueue → amd::HostQueue
    │                                      └── queue_（软件 FIFO）
    │
    └── POCL：struct _cl_command_queue*（完整 C 对象）
```

依赖处理方面：

> AMD 非 Direct Dispatch 不是把 signal 交给后继 kernel，而是由 Host Runtime等待前驱 Event 完成，确认依赖解除后才提交后继。AMD Direct Dispatch 则把依赖转换成 HSA signal + AQL barrier，提前提交后继，由 CP 等待。

POCL/Vortex 与旧 AMD 属于同一个大类：Host 软件先确认依赖满足，再让后继进入设备执行。但它们的 Host 调度结构并不相同。

## 2. 先区分文中的所有 queue

| **对象**                   | **所在层**          | **装的内容**                          | **消费者**                                | **GPU 是否直接可见** |
| ------------------------ | ---------------- | --------------------------------- | -------------------------------------- | -------------- |
| `cl_command_queue`       | OpenCL API/ICD   | 不透明 handle                        | OpenCL API 实现                          | 否              |
| `amd::HostQueue`         | AMD CLR core     | 完整的 C++ Host Queue 对象             | CLR API 和提交逻辑                          | 否              |
| `HostQueue::queue_`      | AMD CLR core     | `ConcurrentLinkedQueue<Command*>` | 非 Direct Dispatch 的`HostQueue::loop()` | 否              |
| `amd::roc::VirtualGPU`   | AMD ROCr backend | 队列级提交上下文                          | CLR backend                            | 否              |
| `VirtualGPU::gpu_queue_` | HSA/ROCr         | `hsa_queue_t*` 和 AQL Ring         | GPU Command Processor                  | 是              |
| POCL`_cl_command_queue`  | POCL core        | 完整的 C command queue 对象            | POCL core/backend                      | 否              |
| Vortex`command_list`     | Vortex backend   | 依赖未满足的`_cl_command_node`          | Vortex notify/worker                   | 否              |
| Vortex`ready_list`       | Vortex backend   | 可以执行的`_cl_command_node`           | Vortex worker                          | 否              |

判断一个 queue 到底是什么，始终先问：它装什么、谁生产、谁消费、GPU 能否直接看到。仅凭名字不能建立对象对应关系。

## 3. API 对象如何表示

### 3.1 AMD：`HostQueue` 是完整对象，`queue_` 只是成员

AMD CLR 的继承关系是：

```cpp
class CommandQueue : public RuntimeObject {
  // context、device、properties、锁、优先级等公共状态
};

class HostQueue : public CommandQueue {
  Thread thread_;
  ConcurrentLinkedQueue<Command*> queue_;
  Command* lastEnqueueCommand_;
  // submission batch 等状态
};
```

源码位置：

* `2.源码/rocm-clr/rocclr/platform/commandqueue.hpp:33`：`CommandQueue`；
* `2.源码/rocm-clr/rocclr/platform/commandqueue.hpp:147`：`HostQueue`；
* `2.源码/rocm-clr/rocclr/platform/commandqueue.hpp:194`：`HostQueue::queue_`。

`HostQueue` 表示完整的 OpenCL Host Queue，拥有 Context、Device、properties、VirtualDevice、同步锁、最近提交的 command 和 submission batch 等状态。

`queue_` 只是其中的一个软件 FIFO，元素类型为 `Command*`，可能指向 kernel、copy 或 marker command。它不保存 AQL packet，也不是 HSA/KFD 硬件队列。

```text
HostQueue::queue_       = Host 软件 Command* FIFO
VirtualGPU::gpu_queue_  = HSA queue handle
AQL Ring                = GPU CP 实际读取的 packet Ring
```

### 3.2 AMD：为什么 `cl_command_queue` 可以恢复成 `HostQueue`

OpenCL 对外只声明不透明指针：

```c
typedef struct _cl_command_queue* cl_command_queue;
```

见 `2.源码/rocm-clr/opencl/khronos/headers/opencl2.1/CL/cl.h:47`。应用程序看不到 `_cl_command_queue` 的内部字段。

CLR 在 `2.源码/rocm-clr/rocclr/platform/object.hpp:31` 建立类型映射：

```cpp
F(cl_command_queue, CommandQueue)
```

创建 queue 时先使用公共基类指针：

```cpp
amd::CommandQueue* queue = nullptr;

if (!(properties & CL_QUEUE_ON_DEVICE)) {
  queue = new amd::HostQueue(...);
} else {
  queue = new amd::DeviceQueue(...);
}

return as_cl(queue);
```

`as_cl()` 返回 `ICDDispatchedObject` 基类子对象的地址。这个基类包含 ICD dispatch table 指针，符合 OpenCL ICD handle 的要求：

```text
amd::HostQueue 完整 C++ 对象
┌────────────────────────────────────┐
│ ReferenceCountedObject 基类部分     │
├────────────────────────────────────┤
│ ICDDispatchedObject 基类部分        │ ◄── cl_command_queue
│   dispatch_                         │
├────────────────────────────────────┤
│ CommandQueue 成员                   │
├────────────────────────────────────┤
│ HostQueue 成员：thread_/queue_/...  │
└────────────────────────────────────┘
```

API 收到 handle 后按相反方向恢复：

```text
cl_command_queue
    → as_amd()
    → amd::CommandQueue*
    → virtual asHostQueue()
    → amd::HostQueue* 或 nullptr
```

所以这不是把两个无关指针裸 `reinterpret_cast`。CLR 自己控制对象布局，`as_cl()` / `as_amd()` 在 ICD 基类视图和公共 `CommandQueue` 之间转换，再由虚函数判断具体类型。相关实现位于 `2.源码/rocm-clr/rocclr/platform/object.hpp:121-141,327,333`和 `2.源码/rocm-clr/rocclr/platform/commandqueue.hpp:89,242`。

### 3.3 POCL：handle 本身就是完整 C 对象

POCL 同样声明：

```c
typedef struct _cl_command_queue *cl_command_queue;
```

但 POCL core 直接定义这个结构体：

```c
struct _cl_command_queue {
  POCL_ICD_OBJECT
  POCL_OBJECT;

  cl_context context;
  cl_device_id device;
  cl_command_queue_properties properties;

  cl_event events;
  struct _cl_event *barrier;
  unsigned long command_count;
  pocl_data_sync_item last_event;

  void *data;
  struct _cl_command_queue *prev, *next;
};
```

见 `2.源码/pocl/lib/CL/pocl_cl.h:1547`。创建时直接分配：

```c
calloc(1, sizeof(struct _cl_command_queue));
```

见 `2.源码/pocl/lib/CL/clCreateCommandQueue.c:79`。

因此 POCL 可以直接访问 `command_queue->context`、`device` 和 `events`，不需要AMD 式的 C++ 对象视图恢复。`POCL_ICD_OBJECT` 仍然把 dispatch 指针放在对象开头，只是 ICD handle 与完整 C 对象共享同一个首地址。

```text
AMD：handle 是内部 C++ RuntimeObject 的 ICD 基类视图
POCL：handle 就是完整 struct _cl_command_queue 的首地址
```

## 4. AMD 新旧提交路径与依赖处理

以下统一使用一个跨队列依赖：

```text
Queue A：Kernel A，产生 Event A
Queue B：Kernel B，等待 Event A
```

`eventWaitList_` 保存的就是 B 的显式前驱 Event。讨论重点是跨队列依赖；同一个in-order queue 的普通顺序通常由该 queue 自身的提交顺序保证。

### 4.1 非 Direct Dispatch：Command 先进入 `queue_`

当 `AMD_DIRECT_DISPATCH == false` 时：

```cpp
void Command::enqueue() {
  queue_->append(*this);
  queue_->flush();
}
```

数据路径是：

```text
OpenCL API 线程
    │ 创建 Command
    ▼
HostQueue::append()
    ▼
HostQueue::queue_
    ▼
HostQueue::loop() 调度线程
    ▼
command->submit(VirtualDevice)
```

对应源码：

* `2.源码/rocm-clr/rocclr/platform/command.cpp:356`：`Command::enqueue()`；
* `2.源码/rocm-clr/rocclr/platform/commandqueue.cpp:315`：`append()`；
* `2.源码/rocm-clr/rocclr/platform/commandqueue.cpp:241`：`loop()`。

### 4.2 旧路径：Host Runtime 等待跨队列 Event

`HostQueue::loop()` 取出 B 后处理其 `eventWaitList_`：

```cpp
for (const auto& it : events) {
  if (it->command().queue() != this) {
    if (it->command().status() != CL_COMPLETE) {
      virtualDevice->flush(head, true);
      tail = head = NULL;
      dependencyFailed |= !it->awaitCompletion();
    }
  }
}
```

执行顺序为：

```text
Queue A                         Queue B 的 Host 调度线程

提交 Kernel A                  从 queue_ 取出 Kernel B
     │                              │
     │                              ├── 检查 eventWaitList
     │                              ├── Event A 未完成
     │                              └── awaitCompletion(Event A)
     │                                         │
     ▼                                         ▼
GPU 执行 A                              Host Runtime 等待
     │                                         │
     └── Event A = CL_COMPLETE ───────────────┘
                                               │
                                               ▼
                                         submit Kernel B
```

最关键的特征是：

> A 未完成时，B 还没有进入 GPU 硬件提交队列。依赖判断和放行发生在 Host Runtime。

### 4.3 当前 command 的依赖为什么会 flush 此前 command

先直接回答这个疑问：B0、B1 没有依赖，所以它们在此前的 loop 迭代中确实已经调用 `submit()`；当前取出的 B2，其 `eventWaitList_` 中也确实只有 Event A。`flush(head)` 之所以还能看到 B0/B1，不是因为它们出现在 B2 的依赖中，而是

因为 `head/tail` 跨多次 loop 迭代保存此前已经提交的 command。关键在于：

> `eventWaitList_` 和 `head/tail` 是两个完全不同的数据结构。
> `eventWaitList_` 属于当前 B2；`head/tail` 是跨多次 `while` 循环累积的已提交command batch。

具体职责是：

```text
current.eventWaitList_：当前 command 依赖哪些前驱 Event
head/tail：此前已经 submit、但尚未统一退休的软件 command batch
```

`head/tail` 在 `while (true)` 外定义：

```cpp
Command* head = NULL;
Command* tail = NULL;

while (true) {
  Command* command = queue_.dequeue();
  ...
}
```

所以每次 `while` 结束后，`head/tail` 不会自动清空。它会跨多次 `dequeue()`保留下来，直到代码显式执行：

```cpp
tail = head = NULL;
```

假设 Queue B 中依次出现 B0、B1、B2，其中只有 B2 等待 Event A。

第一次迭代：

```text
current = B0
B0.eventWaitList = 空

head = B0
submit(B0)

循环结束后：head → B0
```

第二次迭代：

```text
current = B1
B1.eventWaitList = 空

head = B0 → B1
submit(B1)

循环结束后：head → B0 → B1
```

第三次迭代：

```text
current = B2
B2.eventWaitList = Event A

当前软件 batch：head → B0 → B1
```

B2 是在依赖检查之后才被加入 `head/tail`，所以检查到 Event A 未完成时：

```cpp
virtualDevice->flush(head, true);
tail = head = NULL;
dependencyFailed |= !EventA->awaitCompletion();
```

被 flush 的是 B0/B1，不是 B2，也不是 B2 的 `eventWaitList_`：

```text
B2.eventWaitList 触发阻塞等待
        │
        └── 阻塞前先封闭并退休历史 batch B0/B1
```

B0/B1 此时已经调用过 `submit()`，但 submit 只表示工作已经交给 backend，不等于 Runtime 已经确认 GPU 完成，也不等于软件 Event 已经变为 `CL_COMPLETE`。在当前 ROCr backend 中，`VirtualGPU::flush(head)` 会：

```text
releaseGpuMemoryFence()
    ├── 在此前 GPU 工作后建立 barrier
    └── WaitCurrent() 等待完成边界

updateCommandsState(head)
    ├── B0/B1：CL_SUBMITTED → CL_RUNNING → CL_COMPLETE
    └── 释放 batch 持有的 command 引用
```

因此 submit 后仍保留 B0/B1 的原因是：Runtime 还需要一份“哪些软件 command属于这个尚未退休硬件 batch”的记录。`HostQueue::append()` 的 retain 保证 command 在排队/执行期间存活；`loop()` 取出 command 后的第二次 retain 则保证 `head/tail` 在 flush 前始终指向有效对象。`updateCommandsState()` 处理完 batch后再释放这份引用。

```text
HostQueue::queue_：尚未由 loop 处理
        ↓ dequeue
command->submit()：已经交给 backend
        ↓ 保留在 head/tail
VirtualDevice::flush(head)：确认完成并退休软件 batch
```

所以 `head/tail` 不是为了延迟提交，而是为了延迟到可靠的硬件完成边界之后，再统一更新 Event 状态和回收 command 生命周期。

### 4.4 旧路径中的 signal 是完成通知

旧路径底层可以使用 hardware event、HSA signal 或 fence 观察 A 的完成，但 signal 的方向是：

```text
GPU/Backend 完成 A
    ↓
更新 Event A 软件状态
    ↓
唤醒或放行 HostQueue 调度线程
    ↓
Runtime 提交 B
```

旧路径不会把 A 的 signal 编码成 B 的硬件依赖：

```text
不会生成：

Barrier(dep_signal = signal_A)
Kernel B
```

所以更准确的说法是：

> 旧路径可以用 signal 获知前驱完成，但 signal 是“GPU → Host 的完成通知”，不是“GPU 内部执行 B 的依赖条件”。

### 4.5 Direct Dispatch：先提交 B，再由 CP 解依赖

当 `AMD_DIRECT_DISPATCH == true` 时，`Command::enqueue()` 不再经过 `HostQueue::queue_`，而是在当前调用线程处理 `eventWaitList_` 并直接执行 `submit(*queue_->vdev())`。

对于普通 Event：

```cpp
event->notifyCmdQueue(false);
```

`notifyCmdQueue()` 在 Event A 所属 queue 后插入隐藏 Marker，为 A 物化一个GPU 可见的完成点：

```text
Queue A：

Kernel A
   ↓
隐藏 Marker M_A
   └── completion signal = S_A
```

于是：

```text
Event A
    → notify_event_ = M_A
    → M_A.HwEvent() = S_A
```

提交 B 时，`VirtualGPU::profilingBegin()` 从 `Event A.NotifyEvent()->HwEvent()` 取得 `S_A`，加入 barrier 依赖；

`dispatchBlockingWait()` 在 B 前生成 AQL barrier：

```text
Queue B：

AQL Barrier(dep_signal = S_A)
Kernel B
```

完整顺序是：

```text
Host：
提交 Kernel A
提交 Marker M_A，completion_signal = S_A
提交 Barrier，dep_signal = S_A
提交 Kernel B
Host 返回，不等待

GPU CP：
执行 A
  ↓
执行 M_A
  ↓
S_A = 0
  ↓
解除 Barrier
  ↓
执行 B
```

最关键的特征是：

> A 未完成时，B 已经进入 AQL Ring，只是被 CP 挡在 barrier 后面。

对应源码：

* `2.源码/rocm-clr/rocclr/platform/command.cpp:264`：`Event::notifyCmdQueue()`；
* `2.源码/rocm-clr/rocclr/platform/command.cpp:356`：Direct Dispatch 分支；
* `2.源码/rocm-clr/rocclr/device/rocm/rocvirtual.cpp:2133`：Event 转为 external signal；
* `2.源码/rocm-clr/rocclr/device/rocm/rocvirtual.cpp:1296`：生成等待 signal 的 AQL barrier。

### 4.6 User Event 为什么单独保存 dependents

User Event 没有普通 GPU command 作为前驱，不能通过“在前驱 queue 后插入Marker”获得完成点。ROCr 创建 User Event 时直接分配一个初始值为 1 的 HSA signal；`clSetUserEventStatus()` 最终将它置为 0，解除 GPU barrier。

```text
UserEvent.HwEvent
    → AQL Barrier(dep_signal)
    → Kernel B
```

HSA signal 只能表达未释放/已释放，不能表达 OpenCL 的负错误状态。因此 `UserEvent::dependents_` 另外保存依赖它的 command。User Event 失败时，这些 command 的软件状态被设置为 `CL_EXEC_STATUS_ERROR_FOR_EVENTS_IN_WAIT_LIST`。

这解释了 `Command::enqueue()` 中两种处理的分工：

```text
UserEvent.HwEvent      → GPU 等待
UserEvent.dependents_  → OpenCL 软件错误传播
```

相关实现位于 `2.源码/rocm-clr/rocclr/platform/command.hpp:463` 和 `2.源码/rocm-clr/rocclr/device/rocm/rocdevice.cpp:3792,3804`。

### 4.7 submission batch 不是依赖队列

Direct Dispatch 中的 `FormSubmissionBatch()`、`SetBatchHead()` 和 `ResetSubmissionBatch()` 用于批量跟踪 command 的软件完成状态。Marker 作为 batch 完成边界，获得 completion signal 后更新此前 command 的 Event 状态。

```text
submission batch：解决“哪些 command 已经完成”
eventWaitList + barrier：解决“B 必须等待哪些前驱”
```

它既不是 `HostQueue::queue_`，也不是 POCL/Vortex 的 Pending/Ready 队列。

## 5. 两种 Host 软件调度设计：原地等待与 Pending/Ready

AMD 非 Direct Dispatch 与 POCL/Vortex 都由 Host 软件先解除依赖，但它们对“尚未 Ready 的 B”采用了两种不同的保存方式。

### 5.1 旧 AMD：从入口 FIFO 取出后原地等待

每个 `HostQueue` 只有一个 `thread_` 消费自己的 `queue_`。假设 Queue B 中有：

```text
HostQueue B::queue_

B：等待 Queue A 的 Event A
C：与 A 无关
```

旧路径的控制流是：

```text
Thread B 从 queue_ 取出 B
    ↓
发现 Event A 未完成
    ↓
Thread B 进入 awaitCompletion(Event A)
    ↓
C 仍留在 queue_，Thread B 暂时无法再次 dequeue
```

因此，“Queue B 队头阻塞”准确地说阻塞了：

1. Queue B 自己的 `HostQueue::loop()` 线程；
2. Queue B 的 `queue_` 中排在 B 后面的 command。

它不会阻塞 Queue A 或 Queue C 的 Host 调度线程，因为非 Direct Dispatch 模式下每个 `HostQueue` 都拥有自己的 `thread_` 和 `VirtualDevice`：

```text
HostQueue A → Thread A：继续推进 A
HostQueue B → Thread B：等待 Event A
HostQueue C → Thread C：仍可处理 C
```

队头阻塞的根本原因不是 AMD 只有一个全局线程，而是单个 HostQueue 采用：

```text
一个 FIFO + 一个消费者 + 消费者取出 B 后同步等待
```

它没有把 B 停放到独立 Pending 容器后再回来处理后面的 command。当前实现也不是“同一个 HostQueue 多 worker”；如果直接增加消费者，还必须重新处理 in-order 语义、batch、Marker 和 `VirtualDevice` 的提交顺序。

### 5.2 Vortex：把阻塞 command 停放到 `command_list`

POCL core 负责 OpenCL queue/event 语义，再通过 `pocl_device_ops` 把 `_cl_command_node` 交给具体 backend。当前 Vortex backend 在设备私有数据中保存两个调度链表：

```c
_cl_command_node *ready_list;
_cl_command_node *command_list;
```

两个字段见 `2.源码/pocl/lib/CL/devices/vortex/pocl-vortex.c:43` 与同文件 `:46`；`pocl_vortex_submit()` 位于同文件 `:1543-1555`，其中调用：

```c
pocl_command_push(node, &dd->ready_list, &dd->command_list);
```

将 command 按依赖状态分类：

```text
B 提交到 Vortex backend
    │
    ├── Event A 未完成
    │     └── B 停放在 command_list（Pending）
    │
    └── Event A 已完成
          └── B 进入 ready_list（Ready）
```

worker 在 `2.源码/pocl/lib/CL/devices/vortex/pocl-vortex.c:1515-1532` 只从 `ready_list` 取 node，不会从 `command_list` 取出 B 后等待依赖。A 完成时，`pocl_vortex_notify()` 在同文件 `:1578-1605` 将 B 从 `command_list` 移入 `ready_list`，再唤醒 worker：

```text
Event A 完成
    ↓
notify B
    ↓
command_list 删除 B
    ↓
ready_list 插入 B
    ↓
worker 执行 B
```

所以用户所说的“重新引入另一个队列保存阻塞 command”在当前 Vortex backend中基本正确，但应精确称为：

> backend 引入了一个 Pending 链表 `command_list`，与 `ready_list` 一起保存 command node 的调度状态。它不是第二个 OpenCL command queue，也不是硬件 queue。

这使得 Pending 的 B 本身不占住 worker。只要 worker 当前空闲且存在其他 Ready node，它就可以绕开 B，先消费 `ready_list` 中的 node。

### 5.3 当前 Vortex 仍会被同步执行阻塞

“B 的依赖等待不占住 worker”不等于“当前 Vortex worker 完全不阻塞”。当前 Vortex 每个设备只创建一个 `worker_thread`（字段见 `2.源码/pocl/lib/CL/devices/vortex/pocl-vortex.c:57`，创建点见同文件 `:503`），执行 Ready node 时从 `pocl_exec_command()` 进入 `pocl_vortex_run()`，后者在不同命令分支调用 `vx_sync_event()` 等待 runtime event：

```text
pocl_exec_command(node)
    → pocl_vortex_run()
    → vx_enqueue_launch(..., &event)
    → vx_sync_event(event)
```

因此 worker 会同步等待当前 kernel 完成，之后才能取下一个 Ready node。需要区分：

```text
依赖等待阻塞：
Pending 的 B 是否占住调度线程？
    → Vortex：否，B 停放在 command_list

执行阻塞：
worker 提交 A 后能否立刻继续提交 C？
    → 当前 Vortex：否，worker 阻塞在 vx_sync_event(A)
```

所以当前 Vortex 的 Pending/Ready 设计避免了“等待依赖导致的调度器队头阻塞”，但单 worker 加同步执行仍使 Ready command 最终串行运行。

### 5.4 in-order 语义下不一定存在可绕行工作

如果 B、C 位于同一个 in-order queue：

```text
Queue B：B → C
```

C 本来就必须等待 B，因而不会成为可以绕过 B 的独立 Ready command。这时旧AMD 的顺序等待不是额外损失。Pending/Ready 分类真正可能绕开的，是来自其他 queue 的 Ready command，或者 out-of-order queue 中没有依赖 B 的 command。因此不能只根据“是否有两个 list”判断并行性，还要同时看：

```text
调度范围（每 queue / 每 device）
worker 数量
OpenCL queue 是 in-order 还是 out-of-order
backend submit 是同步还是异步
硬件允许多少 command 同时在途
```

## 6.三条路径的最终对照

| **问题**               | **AMD 非 Direct Dispatch** | **POCL/Vortex**                 | **AMD Direct Dispatch** |
| -------------------- | ------------------------- | ------------------------------- | ----------------------- |
| A 未完成时 B 是否已进入硬件提交队列 | 否                         | 否                               | 是，位于 barrier 之后         |
| 谁判断跨队列依赖完成           | HostQueue 调度线程            | POCL/backend 软件逻辑               | GPU Command Processor   |
| 调度线程组织               | 每个 HostQueue 一个线程         | 当前 Vortex 每设备一个 worker          | API 线程直接提交              |
| 依赖等待是否占住调度线程         | 是，只占住 Queue B 的线程         | 否，B 停放在`command_list`           | 否                       |
| 执行是否占住调度线程           | 取决于具体 backend             | 是，当前 Vortex 调用`vx_sync_event()` | Host 不等待，由 CP 推进        |
| signal 的主要角色         | GPU → Host 完成通知           | backend → Host 完成通知             | AQL barrier 的依赖条件       |
| B 的硬件包是否携带 A 的依赖     | 否                         | 否                               | 是，前面插入 barrier          |
| 依赖解除后谁推动 B           | Host Runtime              | Vortex worker                   | GPU CP                  |

根本分界是：

```text
AMD 非 Direct Dispatch / POCL：
Event A
→ Host Runtime 等待或观察 A 完成
→ Host 软件解依赖
→ Runtime/worker 让 B 进入设备执行

AMD Direct Dispatch：
Event A
→ Runtime 转换为 signal S_A
→ Runtime 提交 Barrier(S_A) + B
→ CP 等待 S_A
→ CP 解依赖并执行 B
```

同一个 in-order queue 的普通顺序通常由该 queue 自身的提交顺序保证。上表重点描述跨 queue 的显式 Event 依赖。

## 7. 对象映射与不可等同关系

| **POCL/Vortex**                 | **AMD CLR**                  | **结论**                                                    |
| ------------------------------- | ---------------------------- | --------------------------------------------------------- |
| `_cl_command_queue`             | `amd::HostQueue`             | API 角色近似；一个是 C struct，一个是 C++ 派生对象                        |
| `_cl_command_node`              | `amd::Command` 派生类           | 都承载一次命令及关联 Event                                          |
| POCL Event`wait_list`           | AMD`Command::eventWaitList_` | 都保存前驱；后续依赖实现不同                                            |
| Vortex`command_list/ready_list` | `HostQueue::queue_`          | 不等价；前者按依赖状态分类且是设备级，后者是每 HostQueue 的入口 FIFO                |
| Vortex worker                   | 旧 AMD`HostQueue::loop()`     | 都消费 Host 软件 command；Vortex 迁移 Pending/Ready，旧 AMD 可直接阻塞等待 |
| Vortex`ready_list`              | HSA AQL Ring                 | 不等价；前者是 Host 指针链表，后者是 CP 可见的 packet Ring                  |
| `HostQueue::queue_`             | `VirtualGPU::gpu_queue_`     | 完全不同层次；前者是软件 FIFO，后者关联硬件提交 Ring                           |

## 9. 最终结论

> AMD CLR 的非 Direct Dispatch 路径和 POCL/Vortex 都由 Host Runtime 先确认依赖，再让后继 command 进入设备执行；AMD Direct Dispatch 则把依赖转换为 HSA signal + AQL barrier，提前提交后继 command，由 GPU CP 决定它何时执行。

这个提交模型差异与对象布局差异相互独立：AMD 通过 ICD 基类视图把 `cl_command_queue` 映射为 C++ `HostQueue`；POCL 直接把 `struct _cl_command_queue` 作为完整内部对象。无论采用哪种布局，OpenCL 只规定可观察的 queue 和 Event 语义，并不规定 Runtime 必须用 Host 线程、软件 list还是硬件 barrier 实现这些语义。
