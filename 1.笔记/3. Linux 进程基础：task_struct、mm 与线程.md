# Linux 进程、线程与 `task_struct`

源码路径口径：本文所有未显式写仓库根的源码路径均相对于 `2.源码/linux`，固定版本为 `248951ddc14de84de3910f9b13f51491a8cd91df`。

## 1. 先建立直觉：资源容器与执行流

从用户态看，进程通常是一个资源容器：它组织虚拟地址空间、文件描述符、文件系统上下文、权限和信号处理方式；线程则是一条可以被 CPU 独立调度的执行流，拥有自己的寄存器现场、用户栈、内核栈和调度状态。

```text
Process A
├── 共享资源
│   ├── Address Space
│   ├── File Descriptors
│   ├── Working Directory
│   └── Signal Handlers
└── 执行流
    ├── Thread A1
    ├── Thread A2
    └── Thread A3
```

因此可以先记住一句话：

> 进程强调一组资源的组织与隔离，线程强调一条独立的执行路径。

但这只是用户态概念。Linux 内核并没有分别设计一个“进程对象”和一个“线程对象”，而是使用统一的 Task 模型。

共享地址空间也不等于共享执行上下文。两个线程可以同时在不同 CPU 上进入内核：

```text
CPU 0                         CPU 1
Thread A1                     Thread A2
   │ syscall                     │ syscall
   ▼                             ▼
task_struct A1                task_struct A2
Kernel Stack A1               Kernel Stack A2
```

如果两个线程共用同一个内核栈，系统调用栈帧、局部变量和寄存器保存区会互相覆盖。因此，即使它们属于同一进程，每个线程仍必须有独立的调度和内核执行上下文。

## 2. Linux 的统一 Task 模型

Linux 用 `struct task_struct`描述一个 Task。对普通用户程序来说，一条用户线程对应一个 Task，也就对应一个独立的 `task_struct`。

```text
User Process
├── Thread A1 ──→ task_struct A1
├── Thread A2 ──→ task_struct A2
└── Thread A3 ──→ task_struct A3
```

调度器可以把这些 Task 分别放到不同 CPU 上运行：

```text
CPU 0 ← task_struct A1
CPU 1 ← task_struct A2
CPU 2 ← task_struct A3
```

进程和线程的差异主要不在于是否拥有 `task_struct`，而在于创建 Task 时共享了哪些内核对象：

```text
同一线程组中的两个 Task

task_struct A1 ──┐
                 ├──→ 同一个 mm_struct
task_struct A2 ──┘

两个独立进程中的 Task

task_struct A ─────→ mm_struct A
task_struct B ─────→ mm_struct B
```

所以“Linux 调度的是线程还是进程”这个问题，更准确的回答是：

> Linux 调度器处理的是 Task；普通用户线程是最常见的可调度 Task。用户所说的“进程”通常对应一个线程组及其共享资源，而不是另一个被调度的实体。

## 3. `task_struct` 到底是什么

`task_struct`定义在 `2.源码/linux/include/linux/sched.h`。它很大，但不应把它理解成“装下进程所有内容的巨大结构体”。更准确的理解是：

> `task_struct` 是 Linux 描述和管理一个 Task 的核心对象：一部分状态直接保存在其中，更多资源通过指针关联到各子系统对象。

下面是基于当前仓库 Linux 源码抽取的示意性节选，不是可以替代真实头文件的完整定义：

```c
struct task_struct {
    unsigned int __state;
    void *stack;

    int prio;
    int static_prio;
    int normal_prio;
    unsigned int policy;
    struct sched_entity se;
    const struct sched_class *sched_class;
    cpumask_t cpus_mask;

    struct mm_struct *mm;
    struct mm_struct *active_mm;
    int exit_state;

    pid_t pid;
    pid_t tgid;
    struct task_struct *group_leader;
    struct task_struct __rcu *real_parent;
    struct task_struct __rcu *parent;
    struct list_head children;
    struct list_head sibling;

    const struct cred __rcu *real_cred;
    const struct cred __rcu *cred;
    struct fs_struct *fs;
    struct files_struct *files;
    struct nsproxy *nsproxy;
    struct signal_struct *signal;
    struct sighand_struct __rcu *sighand;

    struct thread_struct thread;
};
```

可以把这些内容分为三层：

| **层次**    | **典型成员**                                    | **作用**                     |
| --------- | ------------------------------------------- | -------------------------- |
| Task 自身状态 | `pid`、`__state`、优先级、CPU affinity、统计信息       | 回答“这个 Task 是谁、现在能否运行、如何调度” |
| 关联的共享对象   | `mm`、`files`、`fs`、`signal`、`sighand`、`cred` | 回答“这个 Task 使用哪些地址空间和进程资源”  |
| 执行上下文     | `stack`、架构相关的 `thread`、系统调用/异常栈帧            | 回答“该 Task 恢复运行时从哪里继续”      |

```text
                           task_struct
                                │
          ┌─────────────────────┼─────────────────────┐
          ▼                     ▼                     ▼
      身份与关系             资源引用              调度与执行
     pid/tgid/parent       mm/files/fs/...       __state/se/stack
```

`task_struct` 是管理中心，但并不独自包含所有执行现场。例如完整的用户寄存器现场可能保存在内核栈上的架构栈帧中，地址空间的 VMA 和页表由 `mm_struct`管理，打开文件由 `files_struct`管理。

## 4. 一个 Task 如何被识别：PID、TGID 与线程组

### 4.1 `pid` 是 Task ID

每个 Task 都有自己的 `pid`。在用户态通常通过 `gettid()`观察当前线程的 Task ID。

### 4.2 `tgid` 是线程组 ID

属于同一用户进程的线程组成一个 thread group，它们拥有相同的 `tgid`。线程组 leader 满足：

```text
leader->pid == leader->tgid
```

例如：

| **用户线程**   | **`pid`/TID** | **`tgid`/Process ID** |
| ---------- | ------------- | --------------------- |
| A1（leader） | 1001          | 1001                  |
| A2         | 1002          | 1001                  |
| A3         | 1003          | 1001                  |

用户态 `getpid()`返回 TGID，`gettid()`返回当前 Task 的 PID/TID。因此用户看到的一个“PID=1001 的多线程进程”，在内核里实际对应多个具有不同 `pid`、相同 `tgid`的 `task_struct`。

```text
Thread Group 1001
├── task pid=1001, tgid=1001, group_leader
├── task pid=1002, tgid=1001
└── task pid=1003, tgid=1001
```

PID namespace 会让同一个 Task 在不同 namespace 中呈现不同编号，因此内核通用代码常使用 `struct pid`和 `task_pid_nr()`、`task_tgid_nr()`等 helper，而不是把所有身份问题简化成直接读取整数成员。

## 5. 进程与线程的本质差异：资源共享关系

Linux 创建新 Task 的核心路径是 `copy_process()`。它先通过 `dup_task_struct()`得到新的 `task_struct`和内核栈，再依据 `clone_flags`决定各类资源是共享原对象还是复制新对象。

### 5.1 `clone_flags` 决定共享什么

| **Flag**        | **共享对象或语义**                    | **没有该 flag 时**              |
| --------------- | ------------------------------ | --------------------------- |
| `CLONE_VM`      | `mm_struct`，即用户虚拟地址空间          | `dup_mm()`复制地址空间描述与页表语义     |
| `CLONE_FILES`   | `files_struct`，即文件描述符表         | `dup_fd()`创建新的 fd table     |
| `CLONE_FS`      | `fs_struct`，即 cwd、root、umask 等 | `copy_fs_struct()`复制 FS 上下文 |
| `CLONE_SIGHAND` | `sighand_struct`，即信号处置表        | 分配并复制信号处置表                  |
| `CLONE_THREAD`  | 加入同一线程组并共享`signal_struct`      | 建立新的线程组级 signal 对象          |

`copy_process()`还强制约束共享关系：`CLONE_THREAD`必须配合 `CLONE_SIGHAND`，而 `CLONE_SIGHAND`必须配合 `CLONE_VM`。这说明 Linux 的“线程”不是一个单独类型，而是一组有约束的共享选择。

Pthread 创建线程时通常会组合使用这些 flag，于是形成我们熟悉的多线程模型：

```text
task_struct A1 ──┬──→ mm_struct
task_struct A2 ──┼──→ files_struct
task_struct A3 ──┼──→ fs_struct
                 ├──→ sighand_struct
                 └──→ signal_struct
```

但“同一线程组中的资源永远全部共享”仍然是过度简化。准确判断应查看创建时的 flags、对象引用计数以及后续 `unshare()`、`exec()`等操作。

### 5.2 一张表看清独立与共享

| **内容**           | **同一进程的普通线程** | **独立进程**     |
| ---------------- | ------------- | ------------ |
| `task_struct`    | 每个线程独立        | 每个 Task 独立   |
| PID/TID          | 独立            | 独立           |
| TGID             | 相同            | 通常不同         |
| 调度状态和调度实体        | 独立            | 独立           |
| Kernel stack     | 独立            | 独立           |
| 用户寄存器上下文         | 独立            | 独立           |
| `mm_struct`      | 通常共享          | 通常复制/独立      |
| `files_struct`   | 通常共享          | fork 后表项语义复制 |
| `fs_struct`      | 通常共享          | 通常复制         |
| `sighand_struct` | 通常共享          | 通常复制         |
| `signal_struct`  | 线程组共享         | 不同线程组独立      |

因此最稳妥的心智模型是：

> 每条执行流都有自己的 Task；“进程”表现为一组 Task 对若干资源对象的共享关系。

## 6. `task_struct` 关联的核心资源

### 6.1 `mm_struct`：CPU 用户地址空间

`task->mm`指向该 Task 使用的用户虚拟地址空间：

```text
task_struct
    │ mm
    ▼
mm_struct
    ├── VMA：code、heap、mmap、stack
    ├── page-table root
    └── 地址空间生命周期与统计
```

同一线程组中的普通用户线程共享 `mm_struct`，所以一个线程修改共享内存，其他线程可以通过同一虚拟地址观察到；它们的用户栈只是位于同一地址空间中的不同 VMA/区间，并非不同 `mm_struct`。

内核线程通常满足 `mm == NULL`，因为它不执行用户地址空间中的代码。调度运行时它仍可能借用前一个用户 Task 的 `active_mm`维持体系结构所需的地址空间上下文，这不表示内核线程拥有该用户地址空间。

### 6.2 `files_struct`：文件描述符表

```text
task_struct
    │ files
    ▼
files_struct
    ├── fd 0 → struct file
    ├── fd 1 → struct file
    └── fd 3 → /dev/kfd 对应的 struct file
```

同一线程组通常共享 fd table，因此一个线程执行 `close(fd)`会影响其他线程使用该 fd。需要区分 `files_struct`和 `struct file`：前者是 fd→file 的表，后者代表一次打开文件产生的内核文件对象；多个 fd table entry还可能引用同一个 `struct file`。

### 6.3 `fs_struct`：路径解析上下文

`fs_struct`保存当前工作目录、根目录和 umask 等信息。相对路径 `open(\"data.bin\", ...)`如何解析，依赖调用 Task 的 FS 上下文。

### 6.4 `signal_struct` 与 `sighand_struct`

两者职责不同：

```text
signal_struct
    线程组级状态、共享pending signals、资源限制和组生命周期

sighand_struct
    信号处置表，例如某个signal使用默认动作、忽略还是handler

task_struct自身
    blocked mask、线程私有pending signals等每线程状态
```

所以“信号属于进程还是线程”不能一句话回答：信号机制同时包含线程组共享状态和每线程状态。

### 6.5 `cred`：当前 Task 的安全身份

`real_cred`和 `cred`是指向不可随意原地修改的 credential 对象的指针，源码注释明确标注为 COW。credential包含 UID、GID、capabilities 和关联安全上下文。

多个 Task 可以引用同一个 credential 对象；权限变化通常通过准备新 credential并替换指针完成。不要把它简化成“所有线程永远共享一个可变权限结构”。

### 6.6 Namespace、cgroup 与其他关联

`nsproxy`连接 mount、PID、network 等 namespace；cgroup关联决定资源控制和统计归属。它们进一步说明 `task_struct`更像各子系统围绕 Task 的连接点，而不是所有资源内容的存放地。

## 7. Task 如何被调度和执行

### 7.1 `__state` 描述可运行性，不等于完整生命周期

当前源码明确区分：

```text
task->__state   ：Task 的可运行/睡眠等调度状态
task->exit_state：EXIT_ZOMBIE、EXIT_DEAD 等退出状态
```

`TASK_RUNNING`的值是 0，它同时表示：

* Task 正在某个 CPU 上运行；
* Task 已经可运行，正在 runqueue 中等待 CPU。

仅查看 `__state`不能区分这两种情况，还需要结合 `on_cpu`、`on_rq`和调度器数据。原文那种把 RUNNING、SLEEPING、ZOMBIE 都画成一个字段控制的简单状态机并不准确，因为 zombie 属于 `exit_state`。

典型睡眠和唤醒过程可以简化为：

```text
Task 等待事件
  → 设置 TASK_INTERRUPTIBLE 或 TASK_UNINTERRUPTIBLE
  → schedule()
  → 从 CPU 让出执行权

事件完成
  → wake_up()/try_to_wake_up()
  → 状态恢复为 TASK_RUNNING
  → 进入可运行队列
  → Scheduler 选择后继续执行
```

### 7.2 调度实体与策略

`task_struct`包含优先级、policy、CPU affinity和不同调度类所需的实体：

```text
task_struct
├── sched_class
├── se   ：fair scheduler entity
├── rt   ：real-time scheduler entity
├── dl   ：deadline scheduler entity
└── cpus_mask/cpus_ptr
```

调度器不是只检查一个 `state`字段，而是结合调度类、优先级、runqueue、CPU affinity、负载和唤醒关系作出决定。

### 7.3 Kernel stack 与 CPU context

每个 Task 有独立的内核栈。用户线程通过 syscall、异常或中断进入内核时，架构入口代码把必要现场组织到该 Task 的内核栈和架构相关结构中。

```text
task_struct
├── stack ───────→ Kernel Stack
└── thread ──────→ Architecture-specific context
```

上下文切换时，内核保存当前 Task 恢复执行所需的状态，切换内核栈和地址空间上下文，再恢复下一个 Task。并非“所有 CPU 寄存器都长期直接存放在 `task_struct`字段里”；具体布局与体系结构和进入内核的路径有关。

## 8. Task 的关系与生命周期

### 8.1 父子、线程组与 ptrace 关系

关键成员包括：

| **成员**         | **含义**                                   |
| -------------- | ---------------------------------------- |
| `real_parent`  | 正常创建/亲缘意义上的父 Task                        |
| `parent`       | 接收 SIGCHLD、被 wait 报告的父 Task；ptrace 时可能变化 |
| `children`     | 该 Task 的自然子 Task 链表                      |
| `sibling`      | 挂入父 Task children 链表的节点                  |
| `group_leader` | 当前线程组的 leader                            |
| `thread_node`  | 当前 Task 在线程组链表中的节点                       |

线程关系和进程树不是同一棵简单树。`children/sibling`描述亲缘关系，`group_leader/thread_node/signal->thread_head`描述线程组，ptrace还会影响 `parent`语义。

### 8.2 从创建到回收

一个 Task 的生命周期可压缩为：

```text
clone()/fork()
  → copy_process()
  → dup_task_struct()
  → 按clone flags复制或共享资源
  → sched_fork()
  → copy_thread()
  → wake_up_new_task()
  → 可运行/睡眠/唤醒/调度
  → do_exit()
  → 线程组与资源退出处理
  → 可能进入EXIT_ZOMBIE等待父进程wait
  → release_task()
```

`task_struct`的生命周期也不等于 `mm_struct`或 `struct file`的生命周期。各对象通过引用计数、RCU和各子系统协议独立管理；Task 退出会释放引用，但共享对象可能仍被其他 Task 使用。

## 9. `current`：驱动如何找到当前调用者

内核中的 `current`返回当前 CPU 正在执行的 Task 的 `task_struct *`：

```c
current->pid
current->tgid
current->mm
current->files
current->cred
```

它不是一个普通全局变量，因为不同 CPU 可以同时运行不同 Task。具体取得方式由体系结构实现。例如当前仓库的 RISC-V `get_current()`直接返回保存在 `tp`寄存器中的 `task_struct *`；x86 则读取 per-CPU `current_task`。

当用户线程执行 `ioctl(fd, ...)`进入驱动时：

```text
User Thread
  → syscall entry
  → current
  → 当前线程的 task_struct
  → current->mm / current->cred / current->files
```

这里的“当前”只在当前执行上下文中成立。把工作异步投递到 workqueue 后，worker 中的 `current`是 worker Task，不再是最初的用户调用者。因此需要跨异步边界使用的 `mm`、credential或驱动对象必须按各自规则提前获取引用，不能稍后重新读取 `current`猜测原调用者。

## 10. 从 Linux Task 到 KFD GPU Process

### 10.1 `/dev/kfd` open 的真实路径

当前 AMD KFD 源码中的 `kfd_open()`执行：

```c
process = kfd_create_process(current);
if (IS_ERR(process))
    return PTR_ERR(process);

filep->private_data = process;
```

这几个对象处于不同层次：

| **对象**               | **所属子系统**               | **表示什么**                            |
| -------------------- | ----------------------- | ----------------------------------- |
| `task_struct`        | Linux task/scheduler    | 当前调用线程                              |
| `mm_struct`          | Linux memory management | 该用户地址空间                             |
| `struct file`        | VFS                     | 本次打开的`/dev/kfd`文件对象                 |
| `kfd_process`        | AMD KFD                 | 与 Linux 地址空间关联的 GPU process context |
| `kfd_process_device` | AMD KFD                 | 该 KFD process在某一 GPU上的状态和 GPUVM 资源  |

### 10.2 KFD 以 `mm_struct`归并同一进程的线程

`kfd_create_process(thread)`先确认 `thread->mm`存在并增加 mm 引用，然后 `find_process(thread, true)`最终按 `thread->mm`查找已有 `kfd_process`。如果不存在，`create_process()`会建立：

```c
process->mm = thread->mm;
process->lead_thread = thread->group_leader;
```

因此同一地址空间中的多个普通线程打开 `/dev/kfd`时，会查找到同一个 primary `kfd_process`并增加引用，而不是为每个 `task_struct`都创建一个独立 GPU process。

```text
task_struct A1 ──┐
                 ├──→ mm_struct X ──→ kfd_process X
task_struct A2 ──┘                       │
                                        ├──→ process queue manager
                                        ├──→ SVM ranges
                                        └──→ per-GPU process-device state
```

KFD 还为该 `mm_struct`注册 MMU notifier，使 CPU 地址空间释放或变化时能够协调 GPU 资源生命周期。因此：

> KFD 的 process概念更接近“与一个 Linux `mm_struct`关联的 GPU 执行与地址空间上下文”，而不是“当前调用线程的 `task_struct`”。

### 10.3 CPU VA 与 GPU VA 的边界

```text
Linux侧
task_struct → mm_struct → CPU User VA → CPU page table

KFD/GPU侧
kfd_process → per-device GPUVM → GPU VA → GPU page table
```

两套地址空间可以通过 SVM/HMM/userptr 等机制建立关联，但 `mm_struct`不是 GPU page table，`kfd_process`也不是 Linux process descriptor。驱动负责在它们之间建立映射、失效通知和生命周期联系。

`filep->private_data = process`只表示该 `struct file`持有一个 `kfd_process`引用，方便后续 ioctl找到驱动上下文；它不表示 `struct file`拥有 Linux 进程，也不表示每次 open 必然创建一个全新的 `kfd_process`。

## 11. 总体心智模型与常见误区

### 11.1 一张总图

```text
                            User Process
                                 │
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
             Thread A                        Thread B
                 │                               │
                 ▼                               ▼
          task_struct A                   task_struct B
                 │                               │
                 ├──── 独立：pid、调度状态、kernel stack
                 │
                 └─────────── 共享引用 ──────────┐
                                                ▼
                          mm / files / fs / signal / sighand
                                 │
                                 ▼
                            CPU User VA
                                 │
                                 │ KFD按mm关联
                                 ▼
                           kfd_process
                                 │
                                 ▼
                      per-device GPUVM / queues
                                 │
                                 ▼
                              GPU VA
```

### 11.2 四个最重要的边界

```text
task_struct
    描述一个Task：谁在执行、如何调度、关联哪些资源

mm_struct
    描述一个CPU用户地址空间：这个Task看到哪些User VA

kfd_process
    描述KFD围绕一个Linux地址空间建立的GPU process context

GPU VM
    描述GPU如何翻译和访问GPU VA
```

### 11.3 常见误区

* **误区：一个进程只有一个 `task_struct`。** 单线程进程可以这样近似；多线程进程有多个 `task_struct`。
* **误区：`task_struct`就是进程拥有的全部资源。** 它大量使用指针关联 `mm_struct`、`files_struct`等独立对象。
* **误区：线程共享一切。** 线程共享部分进程资源，但 PID、调度状态、内核栈、寄存器现场和线程私有信号状态独立。
* **误区：`TASK_RUNNING`只表示正在 CPU 上运行。** 它也表示已可运行、正在 runqueue 中等待 CPU。
* **误区：zombie 是 `__state`中的普通睡眠状态。** 当前内核用独立的 `exit_state`表达 `EXIT_ZOMBIE/EXIT_DEAD`。
* **误区：`current`始终是发起 ioctl 的用户线程。** 异步 worker、IRQ thread等上下文中的 `current`是当时实际运行的 Task。
* **误区：`kfd_process`等于 `task_struct`。** KFD按 `mm_struct`归并普通进程线程，并维护自己的引用和 GPU 资源。
* **误区：CPU VA 与 GPU VA 由同一套页表翻译。** 即使数值相同，CPU MMU和 GPU MMU/GPUVM仍是不同翻译体系。
