# AMD GPU KMD：进程上下文、资源隔离与虚拟化基础

本文回答一条完整主线：同一块 AMD GPU 被多个 Linux 进程同时使用时，内核驱动如何为每个进程建立 GPU 地址空间、内存和 Queue 的所有权，如何把这些状态交给硬件调度，发生 Fault 时如何找到责任进程，进程退出时又如何安全回收；最后再说明这些机制为什么是 GPU 虚拟化的基础，但本身还不等于 vGPU。

先记住五句话：

1. AMD Linux GPU KMD（Kernel Mode Driver，内核模式驱动）不是只有 KFD（Kernel Fusion Driver，内核融合驱动）：AMDGPU DRM（Direct Rendering Manager，直接渲染管理器）管设备、BO（Buffer Object，缓冲对象）和 GPUVM（GPU Virtual Memory，GPU 虚拟内存），KFD 管 compute 进程与 Queue；No-CPSCH（No-Command Processor Scheduling，无命令处理器调度）由 KFD 直接配置驻留，HWS（HardWare Scheduler，硬件调度器）/MES（Micro Engine Scheduler，微引擎调度器）模式由 scheduler firmware 管理驻留，GPU MMU（Memory Management Unit，内存管理单元）最终执行地址隔离。
2. `kfd_process` 是按 Linux `mm_struct`（进程内存描述符）建立的进程级资源总账，不是一块能够直接装入 GPU 的硬件 context；真正的“进程 × GPU”连接点是 PDD（Process Device Data，进程设备数据，`kfd_process_device`）/QPD（Queue Process Device Data，队列进程设备数据，`qcm_process_device`）。
3. PASID（Process Address Space ID，进程地址空间标识）表示一套较长期的 GPU 地址空间身份，Page Table Root 是页表入口，VMID（Virtual Memory ID，虚拟内存标识）是有限的硬件地址翻译槽；VMID 近似 CPU 的 ASID（Address Space Identifier，地址空间标识）/PCID（Process Context Identifier，进程上下文标识）加上一组 VM context register bank 的槽号，而 `VM_CONTEXT[VMID].PAGE_TABLE_BASE` 才承担类似 CR3（Control Register 3，CPU 页表基址寄存器）页表根的作用。
4. 完整的 GPU 切换至少涉及三类可独立复用的状态：地址空间 `PASID/Page Table ↔ VMID`、Queue `MQD（Memory Queue Descriptor，内存队列描述符）↔ HQD（Hardware Queue Descriptor，硬件队列描述符）`、未完成 Wave `CWSR（Compute Wave Save/Restore，计算 Wave 保存/恢复）save area`。它们并非每次 kernel dispatch 都一起切换。
5. 进程隔离解决“不能访问别人的地址、Queue 和 doorbell”；虚拟化还要建立 Guest 设备分配/暴露、DMA（Direct Memory Access，直接内存访问）/IOMMU（Input/Output Memory Management Unit，输入输出内存管理单元）、interrupt 和 Fault/Reset 边界；共享型多租户或可迁移产品再额外需要配额、计费、抗饥饿和迁移生命周期。

## 2. 先建立模型：共享一块 GPU，不等于共享一个地址空间

假设进程 P1 和 P2 都在 GPU0 上使用数值相同的 GPU VA（Virtual Address，虚拟地址）`0x400000`：

```text
P1                                                P2
GPU VA 0x400000                                   GPU VA 0x400000
      │                                                  │
      │ P1 Page Table                                    │ P2 Page Table
      ▼                                                  ▼
BO_A / Physical Pages A                           BO_B / Physical Pages B

Queue_A → MQD_A → P1 address-space context       Queue_B → MQD_B → P2 address-space context
Doorbell slice A                                  Doorbell slice B
PASID_A                                           PASID_B
```

两个数值相同的 VA 可以映射到完全不同的内存。决定访问结果的不是 VA 数值本身，而是发起访问的 Queue/Wave 当前关联了哪套 GPU 页表。只有 P1 通过显式 IPC（Inter-Process Communication，进程间通信）、dma-buf（DMA buffer，DMA 缓冲）或 KFD IPC 机制把 BO\_A 分享给 P2，并且 KMD 又把它映射进 P2 的 GPUVM，P2 才能合法访问 BO\_A；只把 `0x400000` 这个数值发给 P2 没有意义。

因此，“进程 GPU 隔离”不是一个开关，而是以下约束同时成立：

| **隔离对象**       | **KMD 必须建立的边界**                                                 | **最终强制者**                       |
| -------------- | --------------------------------------------------------------- | ------------------------------- |
| GPU 地址空间       | 每个 GPUVM 有自己的 VA mapping 和 Page Table Root                      | GPU MMU                         |
| BO 访问能力        | 当前进程持有合法 handle/reference，并把 BO 映射进自己的 GPUVM                    | DRM/KFD handle lookup + GPU PTE（Page Table Entry，页表项） |
| GPU Page Table | KMD 只允许本进程的合法 mapping 生成有效 PTE 和权限位                             | GPU page-table walker           |
| Queue 所有权      | Queue ID、Ring、MQD 与创建它的`kfd_process/PDD` 关联                     | KFD + HWS/MES/HQD               |
| doorbell       | 进程只 mmap 自己的 doorbell slice，Queue 只占其中一个合法 slot                 | KFD mmap 范围 + doorbell routing  |
| 调度上下文          | Queue 驻留时必须同时使用所属进程的页表状态                                        | KFD/firmware + VMID/HQD         |
| Fault 归属       | Fault提供 VA、访问属性和平台可用的 VMID/PASID；KMD结合来源 device/node反查 GPUVM与进程 | GPU IH（Interrupt Handler，中断处理器）+ AMDGPU/KFD             |
| 生命周期           | 释放`mm`、页表或 BO 前必须先停止 GPU Queue/Wave                             | KFD/AMDGPU + firmware/hardware  |

“BO 所有权”更准确的说法是“BO 的访问能力、引用、mapping 和生命周期”。同一个 BO 可以被显式共享，所以安全条件不是“BO 永远只能属于一个进程”，而是“每一个访问者都必须经授权取得引用，并在自己的 GPUVM 中建立具有正确权限的 mapping”。

## 3. 谁负责什么：KMD 不等于 KFD

### 3.1 职责分层

```text
OpenCL/HIP/ROCr UMD（User Mode Driver，用户态驱动）
    创建 API 对象、选择 GPU、申请内存和 Queue、填 AQL Ring、写 doorbell
                         │
                         ▼
libhsakmt / ioctl ABI
    把用户态请求翻译为 KFD ioctl
                         │
                         ▼
Linux KMD
    ├── AMDGPU DRM：PCI 设备、render node、GEM（Graphics Execution Manager，图形执行管理器）/TTM（Translation Table Manager，翻译表管理器）BO、GPUVM、Page Table、PASID、reset/power
    └── KFD：kfd_process、PDD/QPD、PQM（Process Queue Manager，进程队列管理器）/DQM（Device Queue Manager，设备队列管理器）、compute Queue、MQD、doorbell、event、SVM/fault
                         │
             ┌───────────┴───────────┐
             │                       │
             ▼                       ▼
No-CPSCH：KFD直接配置          HWS/MES scheduler firmware
VMID/HQD并装载MQD             管理Process/Queue驻留、抢占和有限VMID/HQD
             │                       │
             └───────────┬───────────┘
                         ▼
CP（Command Processor，命令处理器）/MEC（Micro Engine Compute，微引擎计算）command front-end
    对已驻留 Queue 取包并发起 kernel dispatch
                         │
                         ▼
GPU hardware
    VMID/Page Table walk、PTE 权限检查、doorbell 解码、CU（Compute Unit，计算单元）/Wave 执行、Fault 产生
```

AMDGPU DRM 与 KFD 是同一个 Linux AMD GPU 内核栈中的两个职责域。KFD 不重新实现一套 BO、GPUVM 和页表管理，而是通过 AMDGPU 暴露的 `amdgpu_amdkfd_*` 接口复用它们。反过来，AMDGPU DRM 的通用 graphics/compute command submission context 也不能替代 KFD 的 HSA Queue、PQM/DQM 和 AQL 用户队列管理。

### 3.2 为什么同时打开 `/dev/kfd` 和 `/dev/dri/renderD*`

两类设备节点和 topology sysfs提供三种不同能力：

| **设备节点**                | **在当前 AMD 栈中的主要作用**                                                                   |
| ----------------------- | ------------------------------------------------------------------------------------- |
| `/dev/kfd`              | 进程级 compute ioctl与控制入口：KFD process、aperture、Queue、event、SVM和 KFD memory ioctl         |
| KFD topology sysfs      | 已注册 GPU/node的发现、能力和`drm_render_minor`等属性快照                                            |
| `/dev/dri/renderD128` 等 | 某个 AMDGPU DRM 设备的非显示 render 接口：`drm_file`、`amdgpu_fpriv`、`amdgpu_vm`、PASID、BO/GEM/TTM |

**\[SOURCE]** render node 的 AMDGPU ioctl 明确允许 GEM、VM、context 和 mmap 等操作；`amdgpu_driver_open_kms()` 又在每个 `drm_file` 打开时分配 `amdgpu_fpriv`、PASID 并初始化 `amdgpu_vm`。KFD 的 `AMDKFD_IOC_ACQUIRE_VM` 随后接收这个 DRM fd，通过 `amdgpu_file_to_fpriv()`取得同一个 `amdgpu_vm`。关键源码分别位于 [amdgpu\_kms.c:1435](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_kms.c#L1435)、[amdgpu\_drv.c:3042](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_drv.c#L3042) 和 [kfd\_process.c:1741](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_process.c#L1741)。

所以对当前 AMD Linux 实现，答案是：**需要 AMDGPU DRM，`/dev/kfd` 不能独立完成 GPUVM/BO/Page Table 的全部工作。** 但这不是硬件规定自研驱动必须有两个设备节点；自研 KMD 可以设计一个统一 fd，只要内部仍然清楚地区分“内存/地址空间管理”和“compute Queue 管理”。AMD 的两节点设计是软件职责和既有 DRM ABI 的选择。

### 3.3 IOMMU 是另一层，不要与 GPUVM 混为一谈

```text
GPU 内部访问：
GPU VA + VMID ──GPU MMU/Page Table──► VRAM 地址或 system-memory DMA address

PCIe 设备访问 Host RAM：
DMA address / IOVA + Requester/PASID ──Host IOMMU──► Host PA
```

GPUVM 控制 GPU 客户端如何解释 GPU VA；IOMMU 控制 PCIe 设备发出的 DMA transaction 可以到达哪些 Host PA。两者都可能使用 PASID 相关信息，但它们不是同一张页表，也不应把“GPUVM 已隔离”直接等价成“Guest DMA 已隔离”。当前本地版本的 `kfd_bind_process_to_device()`只验证 PDD 已取得 DRM VM并维护 runtime-PM 状态，没有在这条函数中展示一个通用 IOMMU SVA bind；因此本文不会声称所有现代 KFD 路径都直接把 `PASID → Linux mm`装入 Host IOMMU。PCIe DMA、IOVA 与 IOMMU 的完整边界见[PCIe 地址与 DMA 专题](<./10. AMD PCIe 地址映射与 DMA：GPU Endpoint.md>)。

## 4. 在应用打开节点之前，GPU 已经被谁发现

### 4.1 PCI/AMDGPU 初始化先建立全局设备资源

应用调用 `open("/dev/kfd")` 时，PCI 枚举和 AMDGPU 设备初始化通常早已完成。AMDGPU probe/init 将硬件资源交给 KFD：

```text
PCI/DRM probe
→ amdgpu_pci_probe → amdgpu_driver_load_kms → amdgpu_device_init（2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_device.c:3709）

amdgpu_device_init 按 IP 块框架分四阶段建立全局资源（不属于任何进程）：
→ ip_early_init     各 IP 块 early_init（GMC 设 gmc_funcs、aperture 结构）
→ asic_init         ATOM BIOS asic_init（BIOS/MC 初始化；asic_type 由 init 开头 flags 确定）
→ ip_init           各 IP 块 sw_init/hw_init（GMC 块 sw_init 集中做内存相关全局初始化；
                    尾部含 amdgpu_amdkfd_device_init：KFD 设备初始化）
→ ip_late_init      各 IP 块 late_init（GMC 只做 IRQ/RAS）

GMC 块 sw_init 里建立的内存全局资源（gmc_v9_0_sw_init）：
→ amdgpu_gmc_vram_location（2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_gmc.c:214）  VRAM aperture（vram_start/end）、FB 窗口
→ amdgpu_gmc_gart_location                      GART aperture
→ amdgpu_vm_adjust_size（2.源码/linux/drivers/gpu/drm/amd/amdgpu/gmc_v9_0.c:1901）       页表结构参数 num_level/block_size/max_pfn
→ amdgpu_ttm_init（2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_ttm.c:2083）           TTM：vram_mgr（`gpu_buddy`，见 2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_vram_mgr.c:915-934）、gtt_mgr（`drm_mm`，见 2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_gtt_mgr.c:356-367）
→ amdgpu_vm_manager_init（2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_vm.c:2832）      VM 管理器：
     ├── id_mgr[每 hub]       管理**非 KFD** VMID（1~first_kfd_vmid-1）
     │                       （KFD 区间 first~last_vmid_kfd 由 DQM 调度时分配，§7.5/§7.6）
     ├── pasids xarray        PASID → vm 全局注册表
     └── vm_update_mode       CPU / SDMA 页表更新模式

KFD 侧（amdgpu_device_ip_init 尾部）
→ amdgpu_amdkfd_device_init()
   ├── compute VMID bitmap
   ├── MEC pipe/queue bitmap
   ├── doorbell aperture/range
   ├── render minor
   └── MES capability
→ kgd2kfd_device_init()
→ kfd_init_node()
   ├── interrupt init
   ├── device_queue_manager_init()       建立该 KFD node 的 DQM
   └── kfd_topology_add_device()         加入全局 KFD topology
```

**\[SOURCE]** `amdgpu_amdkfd_device_init()`把 `compute_vmid_bitmap`、CP Queue bitmap、doorbell 信息和 `drm_render_minor`组成 `kgd2kfd_shared_resources`，再调用 `kgd2kfd_device_init()`；KFD 初始化 node 后创建 DQM并加入 topology。见 [amdgpu\_amdkfd.c:171](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_amdkfd.c#L171)、[kfd\_device.c:742](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_device.c#L742) 和 [kfd\_device.c:620](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_device.c#L620)（`kfd_init_node` 定义）。

这里建立的是全局设备对象和有限硬件资源池，不属于某个应用进程：

```text
amdgpu_device / PCI function
GMC aperture（VRAM/GART 物理地址空间地图）
vm_manager（VMID 分配器、PASID→vm 注册表、页表结构参数）
VRAM manager（vram_mgr，DRM buddy）/ GTT manager（gtt_mgr，drm_mm）
kfd_dev / kfd_node / topology node
DQM
可用 VMID pool
可用 MEC/pipe/HQD pool
doorbell aperture
HWS/MES firmware scheduler
```

> 这些全局资源里，**PASID 分配器、VMID 池、页表结构参数**正是"多进程共享一块 GPU"的硬件契约源头：PASID 是进程长程身份（§7.5）、VMID 是 16 个稀缺翻译槽（§7.5）、页表结构决定每进程 GPUVM 长什么样。详见 [MMU 与页表专题 §7](<./7. MMU 与页表：从 CPU 对照看 GPUVM 的构建、写入与切换.md>)。

### 4.2 `/dev/kfd` 是共享入口，不是“一块 GPU 一个 fd”

`/dev/kfd` 是一个全局字符设备入口。在没有 device-cgroup、容器设备节点和用户态可见性过滤时，多个进程通常发现同一套物理 GPU topology；但每个进程打开后得到自己的 `kfd_process` 引用。`kfd_open()`本身不会重新 probe PCI device：

```c
static int kfd_open(struct inode *inode, struct file *filep)
{
    struct kfd_process *process;

    process = kfd_create_process(current);
    if (IS_ERR(process))
        return PTR_ERR(process);

    filep->private_data = process;
    return 0;
}
```

**\[SOURCE]** `kfd_create_process()`先检查全局 topology 中已有 GPU node，再按当前线程的 `mm`查找或创建 `kfd_process`，见 [kfd\_chardev.c:145](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_chardev.c#L145) 和 [kfd\_process.c:925](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_process.c#L925)。同一进程多次打开 `/dev/kfd`会复用按 `mm`找到的对象并增加引用；不同进程有不同 `mm`，因此得到不同 `kfd_process`。

用户态还要区分“同一进程共享一个 driver对象”和“跨进程共享内核驱动”：ROCr在**每个进程自己的地址空间**中发现并注册一个 `KfdDriver`，这个进程内的多个 `GpuAgent`都保存指向该 driver的指针，所以 `agent->driver().CreateQueue(...)`最终复用同一份进程内 KFD入口；P2则有自己的 ROCr、`KfdDriver`和 `/dev/kfd` fd。二者只是共同进入同一个内核 KFD模块并使用同一物理 GPU，不共享用户态 C++对象。见 [amd\_topology.cpp:99](../2.源码/rocr-runtime/runtime/hsa-runtime/core/runtime/amd_topology.cpp#L99)、[amd\_kfd\_driver.cpp:130](../2.源码/rocr-runtime/runtime/hsa-runtime/core/driver/kfd/amd_kfd_driver.cpp#L130) 和 [amd\_gpu\_agent.h:78](../2.源码/rocr-runtime/runtime/hsa-runtime/core/inc/amd_gpu_agent.h#L78)。这更接近 runtime初始化时“一次发现 driver、随后各 Agent引用它”，而不是为每个 GPU node分别懒创建一个 KFD driver。

### 4.3 用户态通过 topology 找到每个 GPU 对应的 render node

KFD topology 不只给出 GPU ID，也记录对应的 DRM render minor：

```text
/sys/devices/virtual/kfd/kfd/topology/nodes/N/properties
    ...
    drm_render_minor 128
```

**\[SOURCE]** KFD 在 topology node 中填充 `drm_render_minor`，见 [kfd\_topology.c:2039](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_topology.c#L2039)。libhsakmt 的 `hsaKmtOpenKFD()`打开 `/dev/kfd`后读取 sysfs topology；`topology_sysfs_check_node_supported()`读取 `drm_render_minor`并尝试打开对应 render node，见 [openclose.c:153](../2.源码/rocr-runtime/libhsakmt/src/openclose.c#L153) 和 [topology.c:648](../2.源码/rocr-runtime/libhsakmt/src/topology.c#L648)。

因此设备发现顺序是：

```text
AMDGPU/KFD 早已完成设备注册
          │
          ▼
UMD 打开 /dev/kfd，读取已有 topology
          │
          ├── GPU ID
          ├── capability / memory / link properties
          └── drm_render_minor
                    │
                    ▼
          打开 /dev/dri/renderD<minor>
```

不是“只要 open `/dev/kfd`，内核此时才开始发现 GPU”，也不是“一个 `/dev/kfd` fd 对应一块 GPU”。一个进程通常只有一个 KFD入口，却可通过多个 PDD连接多个 topology node；每个 node给出其关联的 render minor，runtime据此打开或复用相应 render fd，并为 compute路径取得 GPUVM。

## 5. 一个进程第一次使用 GPU：完整对象建立过程

### 5.0 总览：一次"接壤"的完整旅程（先见森林）

一个进程从首次用 HSA 到 pdd↔vm 握手的**完整旅程**，用户态在左、内核态在右，一次看懂：

```text
【设备级·一次/GPU——GPU 驱动加载时已建好，与进程无关】
   VMID 0（GART 系统 VM）│ VMID 池（id_mgr 16 槽）│ TTM/GMC aperture
        └──── 这是"仓库和货架规格"，不是某个进程的

【进程级·每进程——进程首次用 HSA，按自己的 mm 建一套】
用户态（ROCr/libhsakmt/libdrm）                内核态（KFD/amdgpu）
────────────────────────────────────          ─────────────────────────────
hsa_init
  │ open("/dev/kfd")      ────►               kfd_create_process(current)
  │                                              → kfd_process（按 mm 键控）
  │                                              → 预建 pdds[]（每 GPU 骨架）     §5.1/5.2
  │
  │ hsaKmtAcquireSystemProperties()   ────►     （§5.4 触发点）
  │   └─ 每个 GPU:
  │       open("/dev/dri/renderD*")  ──►        amdgpu_driver_open_kms
  │                                             → amdgpu_vm + pasid（每 GPU）    §5.3
  │       ioctl(ACQUIRE_VM, drm_fd) ──►         kfd_ioctl_acquire_vm
  │                                             → pdd->drm_priv = vm            §5.4
  │                                              （握手完成：pdd 连上 amdgpu_vm）
  └─ 之后：建队列 → 调度 → 抢 VMID 1-15 → page_table_base 写 VM_CONTEXT[VMID]
          → GPUVM 页表 → PTE → 物理页（详见 [MMU 与页表专题](<./7. MMU 与页表：从 CPU 对照看 GPUVM 的构建、写入与切换.md>)）
```

**两条竖线要分清**：**设备级**（VMID 0/GART/VMID 池）是 GPU 驱动加载时一次建好、所有进程共享；**进程级**（kfd_process/vm/pdd/握手）是每个进程按自己的 mm 独立建一套——进程 A 的握手只连 A 的 pdd，进程 B 必须自己握手。下面 5.1-5.5 就是把这个总览逐块展开。

### 5.1 第一步：创建按 `mm_struct`索引的 `kfd_process`

Linux 的 `task_struct`表示线程；同一进程的线程组通常共享一个 `mm_struct`。KFD 以 `mm`而不是单个线程 PID作为主键：

```text
task_struct T0 ─┐
task_struct T1 ─┼──► mm_struct M ───► kfd_process P
task_struct T2 ─┘
```

`create_process()`初始化的不是硬件寄存器镜像，而是进程级软件总账：

```text
kfd_process
├── mm / lead_thread / mmu_notifier
├── PQM：本进程全部 KFD Queue
├── pdds[]：本进程与各 GPU 的连接
├── event/signal
├── SVM ranges
├── eviction/restore state
└── debug/fault bookkeeping
```

**三个关联锚点各管一件事**（`2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_priv.h`）：

- `mm`：**键**——按它哈希查找（`process->mm == mm`），是"这个 kfd_process 属于哪个地址空间"的身份。
- `lead_thread`：只为 `amd_iommu_bind_pasid` 要一个 `task_struct`（以及安全地拿 mm 引用），**不是主键**。
- `mmu_notifier`：**生命周期锚**——KFD 不持有 mm 引用，靠它等 mm 销毁时被通知、清理 kfd_process。**所以 kfd_process 的生命周期锚定 mm，不锚定 /dev/kfd 的 fd**（进程还活着、关掉 fd 不销毁）。

**\[SOURCE]** `find_process_by_mm()`通过 `process->mm == mm`查找主 context；`create_process()`初始化 PQM、aperture/PDD、SVM 与 `mmu_notifier`，见 [kfd\_process.c:989](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_process.c#L989) 和 [kfd\_process.c:1570](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_process.c#L1570)。

### 5.2 第二步：为可访问 GPU 预建 PDD 骨架

`kfd_init_apertures()`枚举全局 KFD devices，先做 device-cgroup 权限检查，再为允许访问的 GPU 创建 `kfd_process_device`：

```text
kfd_init_apertures(kfd_process P)
  for each allowed kfd_node G:
    kfd_create_process_device_data(G, P)
      pdd->dev       = G
      pdd->process   = P
      pdd->qpd.dqm   = G->dqm
      pdd->qpd.pqm   = &P->pqm
      pdd->alloc_idr = empty
```

**\[SOURCE]** 该枚举与 cgroup 过滤见 [kfd\_flat\_memory.c:381](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_flat_memory.c#L381)，PDD 初始化见 [kfd\_process.c:1685](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_process.c#L1685)。

此时 PDD 只是“P 可以与 G 建立联系”的软件骨架。它还不表示已经打开对应 render node，不保证已有 `amdgpu_vm/PASID`，更不表示已有 Queue、MQD、VMID 或 HQD。

### 5.3 第三步：打开 render node，创建 GPUVM、Page Table Root 与 PASID

对 GPU0 打开 `/dev/dri/renderD128`后，DRM core 建立 `struct drm_file`，AMDGPU open callback 再建立私有状态：

```text
struct file
└── private_data ──► struct drm_file
                      └── driver_priv ──► struct amdgpu_fpriv
                                           └── struct amdgpu_vm
                                               ├── root page-directory BO
                                               ├── VA mappings
                                               └── PASID
```

核心代码顺序可以压缩为：

```c
fpriv = kzalloc(sizeof(*fpriv), GFP_KERNEL);
pasid = amdgpu_pasid_alloc(16);
amdgpu_xcp_open_device(adev, fpriv, file_priv);
amdgpu_vm_init(adev, &fpriv->vm, fpriv->xcp_id, pasid);
file_priv->driver_priv = fpriv;
```

`amdgpu_vm_init()`创建页表 root，并把非零 PASID放入 `adev->vm_manager.pasids` XArray：

```text
(amdgpu_device, PASID) ──► 该设备上的 amdgpu_vm ──► Page Table Root
```

**\[SOURCE]** 见 [amdgpu\_kms.c:1435](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_kms.c#L1435)、[amdgpu\_vm.c:2562](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_vm.c#L2562) 和 [amdgpu\_ids.c:63](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_ids.c#L63)。当前树由全局 `amdgpu_pasid_xa` 为每个 render VM 分配活动期不重复的 PASID；一个进程在不同 GPU 上的 PDD/VM 因而可以持有不同 PASID。每个 `amdgpu_device`仍用自己的 `vm_manager.pasids` XArray完成 PASID→VM 查询，所以 fault 归属必须保留来源 device/node；PASID标识 VM 地址空间而不是 PDD对象本身，并且在对象销毁后可以复用。

render open在 PASID分配失败时可以继续尝试创建 `pasid=0`的普通 DRM VM；但 KFD `ACQUIRE_VM`会拒绝没有 PASID的 VM。因此更准确的结论是：**成功用于 KFD compute的 render VM必须具有非零 PASID**，而不是每次 render open都必然成功获得 PASID。

### 5.4 第四步：`ACQUIRE_VM`把 KFD 的 PDD 与 DRM VM 接起来

**触发时机：进程 HSA 初始化的第一个调用 `hsaKmtAcquireSystemProperties()`**，不是内存分配时，也不是开 render node 时——它内部把"开 render node + ACQUIRE_VM"一次性做完：

```text
进程首次用 HSA（ROCr 初始化）
  → hsaKmtAcquireSystemProperties()              2.源码/rocr-runtime/libhsakmt/src/topology.c:2182
      → topology_take_snapshot()
      → hsakmt_fmm_init_process_apertures(NumNodes)   2.源码/rocr-runtime/libhsakmt/src/fmm.c:2742
          → 每个 GPU：
              open("/dev/dri/renderD%d") + amdgpu_device_initialize()  2.源码/rocr-runtime/libhsakmt/src/fmm.c:2314/2327
              acquire_vm(gpu_id, drm_render_fd) → KFD_IOC_ACQUIRE_VM    2.源码/rocr-runtime/libhsakmt/src/fmm.c:2347/3005
      → hsakmt_init_process_doorbells()
```

libhsakmt 为每个 GPU 缓存 render fd，并在 aperture 初始化阶段发出：

```c
struct kfd_ioctl_acquire_vm_args args = {
    .gpu_id = gpu_id,
    .drm_fd = render_fd,
};
ioctl(kfd_fd, AMDKFD_IOC_ACQUIRE_VM, &args);
```

内核调用链是：

```text
kfd_ioctl_acquire_vm(kfd_process P, gpu_id, drm_fd)
→ 在 P->pdds[] 中找到 PDD(P, GPU)
→ fget(drm_fd)
→ kfd_process_device_init_vm(pdd, drm_file)
   ├── amdgpu_file_to_fpriv() → amdgpu_fpriv
   ├── avm = &amdgpu_fpriv->vm
   ├── amdgpu_amdkfd_gpuvm_acquire_process_vm()
   ├── pdd->drm_priv = drm_file->private_data
   ├── 初始化 KFD IB（Indirect Buffer，间接缓冲）/CWSR 资源
   ├── pdd->pasid = avm->pasid
   └── pdd->drm_file = drm_file
```

这里有一个容易写错的类型关系：

```text
pdd->drm_file  ──► struct file
pdd->drm_priv  ──► struct drm_file
                       └── driver_priv ──► amdgpu_fpriv
                                              └── amdgpu_vm
```

`pdd->drm_priv`不是直接指向 `amdgpu_fpriv`。AMDGPU 的 `drm_priv_to_vm()`宏先把它解释为 `struct drm_file *`，再沿 `driver_priv`找到 `amdgpu_vm`，见 [amdgpu\_amdkfd.h:304](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_amdkfd.h#L304)。`ACQUIRE_VM`实现见 [kfd\_chardev.c:1006](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_chardev.c#L1006) 和 [kfd\_process.c:1741](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_process.c#L1741)。

至此才形成可用于 KFD compute的长期连接；下一节把它放进完整对象图中。

> **设备初始化 vs 进程初始化（最容易混的两个"初始化"）**：
>
> | | 设备初始化（一次/GPU） | 进程初始化（一次/进程） |
> |---|---|---|
> | 时机 | GPU 驱动加载 | 进程首次用 HSA（`hsaKmtAcquireSystemProperties`） |
> | **VMID 0（GART 系统 VM）** | ★ 在这里预留（`amdgpu_vmid_mgr_init` "skip over VMID 0"，GART 表配成 VMID 0 页表） | 不涉及 |
> | VMID 池（id_mgr 16 槽） | ★ 在这里建 | 不涉及 |
> | **kfd_process**（按 mm） | 不涉及 | ★ 在这里建 |
> | **amdgpu_vm**（进程页表） | 不涉及 | 开 render node 时建（VMID 1-15 调度时抢） |
> | **pdd↔vm 握手**（ACQUIRE_VM） | 不涉及 | ★ 在这里做 |
>
> 所以"设备级一次初始化"（VMID 0/GART/VMID 池）和"每进程初始化"（kfd_process/vm/pdd 握手）是两层；进程 A 的握手只连 A 的 pdd，进程 B 必须自己握手——这正是多进程隔离的根源。

### 5.5 一张对象图看清所有关系

```text
task_struct
└── mm_struct
    └── kfd_process                         进程级总账，不是硬件 context
        ├── PQM                             从进程角度管理全部 Queue
        │   └── process_queue_node
        │       └── struct queue
        │           ├── Ring/rptr/wptr properties
        │           ├── MQD memory object
        │           ├── doorbell_id
        │           ├── ctx_save_restore_area / ctl_stack / cwsr_bo
        │           ├── MES gang-context BO（启用 MES时）
        │           └── process/device owner
        ├── event / SVM / mmu_notifier
        └── pdds[]
            └── PDD(P1, GPU0)               进程 × GPU 的连接点
                ├── process ──────────────► kfd_process
                ├── dev ──────────────────► kfd_node
                │                              └── DQM：该 node 全局共享
                ├── drm_file ─────────────► struct file
                │   └── private_data ─────► drm_file
                │       └── driver_priv ──► amdgpu_fpriv
                │           └── amdgpu_vm
                │               ├── PASID
                │               └── Page Table Root
                ├── qpd
                │   ├── pqm / dqm
                │   ├── page_table_base
                │   ├── queues_list
                │   └── vmid                 No-CPSCH 下显式保存
                ├── alloc_idr                KFD memory handle namespace
                ├── process doorbell BO/bitmap
                ├── TBA/TMA + trap-handler memory
                └── MES process-context BO
```

可以用一个矩阵记住 PQM、DQM 与 PDD/QPD：

```text
                 GPU0 DQM          GPU1 DQM
P1 PQM         PDD(P1,GPU0)      PDD(P1,GPU1)
P2 PQM         PDD(P2,GPU0)      PDD(P2,GPU1)
```

PQM 从一个进程的角度管理“一行 Queue”；DQM 从一个 GPU node 的角度管理“一列进程和 Queue”；PDD/QPD 是两者的交点。

## 6. `context`到底是什么：必须按层拆开

驱动源码中的 `context`不是一个唯一对象。把它们混成“GPU context”正是 PASID、VMID、MQD、HQD 容易混乱的根因。

| **名称**                 | **实际对象/状态**                           | **解决的问题**                                 | **是否直接装入硬件**   |
| ---------------------- | ------------------------------------- | ----------------------------------------- | -------------- |
| Linux process context  | `task_struct + mm_struct`             | CPU 线程与进程地址空间                             | 由 CPU 调度/MMU使用 |
| KFD process context    | `kfd_process`                         | 进程级 GPU 资源总账和生命周期                         | 否              |
| Process-device context | PDD + QPD                             | 某进程与某 GPU 的 GPUVM、Queue、doorbell、fault 连接 | 部分字段会被提交       |
| GPUVM context          | `amdgpu_vm + PASID + Page Table Root` | 一套长期 GPU 地址空间                             | 页表根和身份被硬件/固件使用 |
| Hardware VM context    | VMID + VM context registers/TLB（Translation Lookaside Buffer，翻译后备缓冲器）       | 当前哪套页表占用有限翻译槽                             | 是              |
| Queue context          | Ring + MQD；驻留时为 HQD                   | CP 从哪里取包、读写指针和 Queue 属性                   | MQD可装入 HQD     |
| MES process context    | PDD级 GPU-visible process-context BO   | MES中该 process-device的调度状态                 | 由 MES 使用       |
| MES gang context       | Queue级 GPU-visible gang-context BO    | MES中该 Queue/gang的调度状态                     | 由 MES 使用       |
| Wave context           | CWSR save area、control stack、寄存器/PC等  | 抢占未完成 Wave 后恢复                            | 抢占时保存/恢复       |

另有两个常见同名对象不应混入上述链条：OpenCL `cl_context`是 UMD/API 资源域；DRM `amdgpu_ctx`主要服务 DRM command submission。它们都不等于 KFD `kfd_process`或 GPU VMID。

尤其要避免这句话：

```text
错误：MES process_context_addr 指向 struct kfd_process。
```

MES 的 `process_context_addr`指向 PDD 分配的 GPU 可见 context BO；`struct kfd_process`是内核内存中的软件对象，不会原样交给 GPU。

## 7. 隔离如何真正落地：内存、Queue、VMID 与 Fault

### 7.1 BO：先有访问能力，再有 GPUVA mapping

KFD 分配内存的关键步骤是：

```text
AMDKFD_IOC_ALLOC_MEMORY_OF_GPU
→ 从当前 kfd_process 按 gpu_id 找 PDD
→ 要求 PDD 已绑定 DRM VM
→ amdgpu_amdkfd_gpuvm_alloc_memory_of_gpu(..., pdd->drm_priv, ...)
→ 在 pdd->alloc_idr 中为 kgd_mem 分配进程本地 idr_handle
→ 返回 handle = gpu_id << 32 | idr_handle
```

后续 free/map ioctl 不是拿 handle 去全局查找，而是先在**当前 `kfd_process`**&#x4E2D;找 GPU对应的 PDD，再在该 PDD 的 `alloc_idr`中查找：

```c
pdd = kfd_process_device_data_by_id(p, GET_GPU_ID(handle));
mem = kfd_process_device_translate_handle(
          pdd, GET_IDR_HANDLE(handle));
```

**\[SOURCE]** 见 [kfd\_chardev.c:1081](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_chardev.c#L1081) 和 [kfd\_process.c:1851](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_process.c#L1851)。这使 handle 成为当前 PDD命名空间中的访问能力；P2 即使猜到 P1 的 handle 数值，也不会因此在 P2 的 `alloc_idr`中得到 P1 的对象。

但 handle 只解决“软件能否选中对象”。GPU 能否真正访问还取决于 mapping：

```text
AMDKFD_IOC_MAP_MEMORY_TO_GPU
→ 验证 handle 属于当前 PDD
→ 对每个目标 peer PDD取得其 amdgpu_vm
→ amdgpu_amdkfd_gpuvm_map_memory_to_gpu()
→ 更新目标 GPUVM 的 page table
→ 等待 page-table update
→ flush 相关 TLB
```

**\[SOURCE]** 见 [kfd\_chardev.c:1282](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_chardev.c#L1282) 和 [amdgpu\_amdkfd\_gpuvm.c:2018](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_amdkfd_gpuvm.c#L2018)。同一个 BO可以 attach到多个 VM，这正是为什么“BO所有权”不能简化成“一个对象只能属于一个进程”。

### 7.2 GPU Page Table 才是执行时的内存边界

AMDGPU 的 GPUVM支持多级页表和 PTE RWX等属性。执行时，Queue/Wave携带或继承 VMID，GPU MMU选择 `VM_CONTEXT[VMID]`对应的页表根进行 page walk：

```text
Wave memory request
    ├── GPU VA
    ├── access type：read/write/execute/atomic
    └── VMID
          │
          ▼
VM_CONTEXT[VMID].PAGE_TABLE_BASE
          │
          ▼
PDE/PTE walk + permission check
          ├── valid：得到目标地址，继续访问
          └── invalid/permission denied：产生 GPU VM fault
```

因此隔离闭环需要三个软件条件同时成立：

1. 当前进程有合法 BO reference/handle。
2. KMD只把授权的 BO range映射进当前 `amdgpu_vm`。
3. Queue驻留时使用与该 `amdgpu_vm`匹配的 Page Table Root/VMID。

仅满足前两个条件、却让 Queue带错 VMID，仍可能访问另一个地址空间；仅带对 VMID、但 PTE没有 mapping，也只能得到 Fault。

**\[SOURCE]** [amdgpu\_vm.c:60](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_vm.c#L60) 的模块说明明确区分了 GPUVM、VMID、多级页表、PTE RWX属性和非法访问产生 GPU page fault；这里的流程图是对该源码说明与后续 VMID配置代码的归纳。

### 7.3 Queue 创建把所有权延伸到 Ring、MQD 与 doorbell

第一条 Queue的 KFD 主线是：

```text
kfd_ioctl_create_queue(kfd_process P)
→ 按 gpu_id 找 PDD(P,GPU)
→ kfd_bind_process_to_device()：要求 PDD 已 ACQUIRE_VM
→ 分配该 PDD 的 process doorbells（首次）
→ 验证并引用 Ring/rptr/wptr 等 BO
→ pqm_create_queue(P->pqm, GPU, properties)
   ├── 分配 P 内的 queue_id
   ├── 创建 struct queue，记录 process/device owner
   ├── 第一条 Queue：DQM.register_process(qpd)
   │   └── 从 PDD 的 amdgpu_vm 读取 page_table_base
   └── dqm->ops.create_queue()
       ├── No-CPSCH：分配 VMID/HQD并初始化 MQD；active时立即装载
       └── HWS/MES：初始化 MQD并交给 firmware 管理驻留
```

**\[SOURCE]** 入口见 [kfd\_chardev.c:338](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_chardev.c#L338)；PQM 首 Queue 注册见 [kfd\_process\_queue\_manager.c:314](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_process_queue_manager.c#L314)；`register_process()`从 DRM VM读取 PD base并写入 `qpd->page_table_base`，见 [kfd\_device\_queue\_manager.c:1536](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_device_queue_manager.c#L1536)。

Ring地址也不是被内核盲目信任。`kfd_queue_acquire_buffers()`从当前 PDD的 `amdgpu_vm`出发，分别查找并引用 wptr、rptr、Ring、EOP和 CWSR对应的 BO mapping，并校验范围/大小，见 [kfd\_queue.c:234](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_queue.c#L234)。

Queue ownership不是靠 Ring 地址本身表达，而是由这条对象链表达：

```text
kfd_process
  → PQM queue_id namespace
  → PDD(process,GPU)
  → QPD queues_list
  → struct queue
  → Ring BO references + MQD + doorbell_id
```

### 7.4 doorbell 隔离：进程映射一个 slice，Queue 占一个 slot

doorbell 是通知端点，不是 Queue packet，也不是内存页表。KFD 在 PDD第一次创建 Queue 时分配 process-level doorbell BO和 bitmap：

```text
PDD process doorbell slice
├── slot 0 → Queue 0
├── slot 1 → Queue 1
├── reserved slots：SDMA（System DMA，系统 DMA 引擎）/VCN（Video Core Next，视频核心）/IH等
└── free slots
```

`allocate_doorbell()`只从该 QPD 的 bitmap 中选择空 slot，再计算相对于全局 doorbell BAR/aperture 的硬件 offset。用户态 mmap 时，`kfd_doorbell_mmap()`要求映射长度恰好等于一个 process slice，并通过当前 `kfd_process`找到 PDD后才计算物理 doorbell range：

```c
if (vma_size != kfd_doorbell_process_slice(dev->kfd))
    return -EINVAL;
pdd = kfd_get_process_device_data(dev, process);
address = kfd_get_process_doorbells(pdd);
return io_remap_pfn_range(..., address >> PAGE_SHIFT, slice_size, ...);
```

**\[SOURCE]** 见 [kfd\_doorbell.c:106](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_doorbell.c#L106)、[kfd\_doorbell.c:255](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_doorbell.c#L255) 和 [kfd\_device\_queue\_manager.c:571](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_device_queue_manager.c#L571)。

这说明门铃隔离至少包含两层：KMD限制 P1能 mmap 哪一段 aperture；P1 的 Queue再由该段内部的 bitmap分配 slot。数值相同的“进程内 doorbell offset”不一定是全局硬件身份，必须结合 PDD/process slice解释。

### 7.5 PASID、Page Table 与 VMID：长期身份和短期硬件槽

最准确的三层定义是：

```text
PASID
    “这是哪一套逻辑 GPU 地址空间”

Page Table Root
    “这套地址空间实际从哪里开始 page walk”

VMID
    “当前把哪套页表状态装入有限的 GPU 硬件翻译槽”
```

可以类比 CPU，但要类比到正确粒度：

| **CPU 概念**            | **GPU 近似对应**                       | **限定**                                             |
| --------------------- | ---------------------------------- | -------------------------------------------------- |
| 进程的`mm`和 page table   | `amdgpu_vm + Page Table Root`      | 长期软件地址空间                                           |
| CR3中的 Page Table Root | `VM_CONTEXT[VMID].PAGE_TABLE_BASE` | 当前硬件 page walk入口                                   |
| ASID/PCID             | VMID                               | 有限、可复用的地址空间/TLB tag；VMID还选择一组 VM context registers |
| 无严格一一对应对象             | PASID                              | 驱动、GPU及可能的 IOMMU用于识别地址空间的较长期身份，不是驻留槽               |
| CPU core 上的线程寄存器现场    | CU上的 Wave context/CWSR             | 才接近完整执行现场                                          |

所以用户的理解可以修正为：

> VMID可以看成 GPU切换 workload时需要管理的“有限硬件地址空间 tag + VM context register bank槽号”，更接近 ASID/PCID，而不是 CR3本身；该 VMID槽中的 Page Table Base寄存器才对应页表根。VMID不是完整的进程 context，也不会单独保存 Queue读写指针或 Wave寄存器。

因此，如果“通过 VMID切换进程”是指**让 GPU后续访存改用另一进程的页表上下文**，这个类比在地址翻译层成立；如果是指“VMID指向一份包含 Queue状态和 Wave寄存器的完整进程现场，换一个 VMID就完成全部上下文切换”，则不成立。实际切换还可能分别涉及 `MQD ↔ HQD`和 CWSR，三者的触发时机并不相同。

这带来三个直接结论：

1. 同一进程在同一 GPU上的多条 Queue通常共享同一套页表，Queue之间切换未必切换 VMID。
2. 一条已驻留 Queue可以连续消费很多 AQL packet；MEC消费下一个 kernel packet不等于重新装载 VMID或 MQD/HQD。
3. 只有需要抢占未完成 Wave时才需要 CWSR；自然完成或排空 Queue不必每次保存 Wave现场。

### 7.6 No-CPSCH：KFD 显式建立 `PASID/PT ↔ VMID`和 `MQD ↔ HQD`

No-CPSCH路径可以从开源 KMD完整追踪：

```c
dqm->vmid_pasid[allocated_vmid] = pdd->pasid;
set_pasid_vmid_mapping(dqm, pdd->pasid, allocated_vmid);
qpd->vmid = allocated_vmid;
q->properties.vmid = allocated_vmid;
set_vm_context_page_table_base(adev,
                               qpd->vmid,
                               qpd->page_table_base);
kfd_flush_tlb(pdd);
```

**\[SOURCE]** `allocate_vmid()`见 [kfd\_device\_queue\_manager.c:673](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_device_queue_manager.c#L673)。第一条 Queue为 QPD分配 VMID；后续同一 PDD的 Queue复用 `qpd->vmid`；最后一条 Queue销毁时清除 PASID↔VMID映射。它不是每次选中一个 Queue都重新分配 VMID。

随后每条 compute Queue获得确定的 MEC/pipe/queue槽，KFD分配并初始化 MQD；只有 Queue当前 `is_active`时，才立即调用 `load_mqd()`把 MQD装入并启用 HQD。也就是说，No-CPSCH在 Queue创建阶段就静态保留 HQD槽，`is_active`决定的是“现在是否装入并运行”，而不是“是否占有槽位”。该顺序可从先执行 `allocate_hqd()`、后检查 `q->properties.is_active`追踪，见 [kfd\_device\_queue\_manager.c:800](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_device_queue_manager.c#L800) 和 [kfd\_device\_queue\_manager.c:835](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_device_queue_manager.c#L835)。GFX9 MQD把 `q->vmid`写入 `cp_hqd_vmid`，见 [kfd\_mqd\_manager\_v9.c:322](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_mqd_manager_v9.c#L322)。此模式可表示为：

```text
PDD(P1,GPU0)
├── PASID_A
├── Page Table Root A
└── VMID 8
    ├── Queue A → MQD_A → reserved HQD(mec,pipe,slot)；active时load
    └── Queue B → MQD_B → reserved HQD(mec,pipe,slot)；active时load
```

VMID由同一 PDD的 Queue共享；每条已创建的 compute Queue静态保留自己的 HQD槽，active Queue的 MQD才立即装入该槽。这也说明 VMID回答“使用哪套地址翻译上下文”，HQD回答“哪条 Queue当前可被 CP取包”，两者不是同一个调度索引。

### 7.7 HWS/CPSCH（Command Processor Scheduling，命令处理器调度）：KFD交付身份和资源，firmware决定驻留

HWS模式下，KFD不在 `qpd->vmid`中记录一个长期固定、可追踪的实际驻留 VMID，而是向 firmware提供资源池和逻辑对象：

```text
SET_RESOURCES
├── 可用 VMID mask
└── 可用 HQD/queue mask

MAP_PROCESS
├── PASID
├── Page Table base
├── process quantum
├── TBA/TMA
└── process级资源

MAP_QUEUES
├── MQD address
├── doorbell offset
└── wptr address
```

**\[SOURCE]** `MAP_PROCESS`中的 PASID和 page-table base见 [kfd\_packet\_manager\_v9.c:32](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_packet_manager_v9.c#L32)，`MAP_QUEUES`见 [kfd\_packet\_manager\_v9.c:227](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_packet_manager_v9.c#L227)。

**\[BOUNDARY]** 这些字段证明 HWS已获得“这条 Queue属于哪套地址空间”和“MQD在哪里”，但 Linux源码不能证明 firmware当时选择了哪个 VMID/HQD、替换算法、公平性、精确驻留时长，以及地址空间与 Queue状态在 firmware内部的原子切换顺序。因此准确表述应是“firmware从 KMD提供的资源池管理驻留”，而不是虚构一个 KMD侧 `qpd->vmid = X`调用链。

### 7.8 MES：Add Queue 同时携带 process、页表和 MQD

MES路径的 KMD输入更直观：

```c
queue_input.process_id             = pdd->pasid;
queue_input.page_table_base_addr   = qpd->page_table_base;
queue_input.process_context_addr   = pdd->proc_ctx_gpu_addr;
queue_input.gang_context_addr      = q->gang_ctx_gpu_addr;
queue_input.doorbell_offset        = q->properties.doorbell_off;
queue_input.mqd_addr               = q->gart_mqd_addr;
queue_input.wptr_addr              = (uint64_t)q->properties.write_ptr;
queue_input.wptr_mc_addr           = amdgpu_bo_gpu_offset(q->properties.wptr_bo)
                                   + wptr_addr_off;
```

**\[SOURCE]** KFD同时构造用户 GPUVA形式的 `wptr_addr`和由 wptr BO GPU offset计算出的 `wptr_mc_addr`，见 [kfd\_device\_queue\_manager.c:207](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_device_queue_manager.c#L207)。具体 MES packet使用哪个字段取决于代际和 MES API；例如当前 GFX12.0/12.1路径把 `input->wptr_mc_addr`写入 packet的 `wptr_addr`，见 [mes\_v12\_0.c:332](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/mes_v12_0.c#L332) 和 [mes\_v12\_1.c:317](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/mes_v12_1.c#L317)。`mes_add_queue_input`没有要求 KFD指定一个固定 VMID，这进一步说明 KMD交付的是 PASID、Page Table和 Queue描述，具体 VMID/HQD安排由 MES内部管理。

MES/HWS的 Queue驻留调度与 CP/MEC的 packet消费不是同一层：

```text
MES/HWS scheduler：决定哪条逻辑 Queue 获得有限 VMID/HQD 等驻留资源
CP/MEC front-end： 对已经驻留的 Queue 消费/解释 AQL packet并发起 kernel dispatch
CU：              执行 Wave
```

所以可以说“MES调度 Queue驻留”，但不宜再用同一个“调度”概念描述 MEC；更准确的说法是“CP/MEC消费已驻留 Queue中的 packet并发起 dispatch”。一个 Queue驻留后，CP/MEC可以连续消费很多 kernel packet，不需要每个 packet都重新经过 MES Queue驻留决策。

**\[INFERENCE/BOUNDARY]** KMD源码能够证明 scheduler firmware收到了 PASID、Page Table、MQD、doorbell和 wptr等 Queue输入，也能证明 Queue生命周期调用最终进入 HWS/MES接口；它不能逐行证明 CP/MEC firmware内部如何解析 AQL packet、选择 CU或形成 Wave。因此上图是基于公开接口的职责模型，firmware内部 packet parser与 CU派发算法不在本文证据范围内。

### 7.9 CWSR：只保存未完成 Wave，不是另一种 VMID或 MQD

完整切换需要区分三层状态：

```text
地址空间层：PASID + Page Table ↔ VMID
Queue层：   MQD ↔ HQD
Wave层：    CWSR trap + per-Queue context-save area
```

CWSR由两类资源配合：PDD/QPD级的 TBA/TMA和 trap-handler memory；Queue级的 `ctx_save_restore_area`、control stack和对应 BO。KMD并非完全不知道抢占动作：No-CPSCH可以在高层请求 wavefront save或 drain；HWS `UNMAP_QUEUES` packet由 KMD选择 `preempt_queues`或 `reset_queues`，见 [kfd\_packet\_manager\_v9.c:390](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_packet_manager_v9.c#L390)；MES也分别暴露 remove和 reset Queue API，见 [mes\_v12\_1.c:347](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/mes_v12_1.c#L347) 和 [mes\_v12\_1.c:372](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/mes_v12_1.c#L372)。

**\[INFERENCE/BOUNDARY]** Queue被强制抢占且仍有未完成 Wave时，CWSR区域用于保存恢复 PC、SGPR/VGPR、EXEC等执行现场；但开源 KMD不能完整展示 firmware/hardware何时触发 trap、怎样执行请求以及各寄存器的具体保存顺序。本文只保留三层状态边界，详细 dequeue、trap和恢复过程见[硬件队列专题](<./6. AMD 硬件队列：AQL Ring、MQD、HQD 与调度驻留.md>)。

这三个状态层可以独立复用，不能画成每次调度都必然执行：

```text
错误模型：每发一个 kernel → 切 VMID → 装 MQD → CWSR restore

正确模型：Queue可能长期驻留并连续消费 packet；
          同一地址空间的多 Queue可共享 VM状态；
          只有强制抢占未完成 Wave时才需要 CWSR。
```

### 7.10 Fault 如何找到责任进程

Fault record会提供 VA、访问属性以及该平台/中断路径可用的 VMID或 PASID，但不能假定每次 Fault都同时携带二者。完整归属必须始终带上 Fault来源 device/node：

```text
Fault(source device/node, VA, access, available VMID/PASID)
        │
        ├── AMDGPU：(amdgpu_device, PASID) → amdgpu_vm → VM mapping
        │
        └── KFD：source node + PASID/VMID → owning PDD/kfd_process → event/Queue
```

AMDGPU在每个 `amdgpu_device`自己的 XArray中维护 PASID到 VM的映射；`amdgpu_vm_lock_by_pasid(adev, pasid, ...)`必须同时拿到来源 `adev`和 PASID，才能取得并锁住目标 VM。KFD的 `kfd_lookup_process_by_pasid()`可以先遍历 PDD找到所属进程，但若要精确落到某个 PDD，仍要结合 Fault来源 node/device。见 [amdgpu\_vm.c:2932](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_vm.c#L2932)、[amdgpu\_ids.c:63](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_ids.c#L63) 和 [kfd\_process.c:1903](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_process.c#L1903)。

GFX9 No-CPSCH（源码注释称 non HWS）存在一个很有说明力的兼容路径：若 interrupt payload没有 PASID，KFD用 `dev->dqm->vmid_pasid[vmid]`补出 PASID，见 [kfd\_int\_process\_v9.c:304](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_int_process_v9.c#L304)。这正好证明 VMID是当前硬件槽，PASID是可用于反查长期软件对象的身份。

找到进程后并不代表处理方式唯一：

* 合法的 recoverable SVM fault可以补页、更新 PTE、flush TLB后重放。
* 越权或不可恢复访问可以向所属进程报告 memory exception、驱逐/终止其 Queue。
* firmware/hardware挂死可能需要 per-Queue reset、partition reset甚至整卡 reset。

地址归属可以做到 per-process，不等于所有故障都能做到 per-process恢复。Fault与 reset containment的粒度是判断“进程隔离是否已达到虚拟化级故障隔离”的关键指标。

## 8. 进程退出：为什么必须先停 Queue，再释放地址空间

### 8.1 KFD 生命周期锚定 `mm_struct`，不只锚定 fd

主 `kfd_process`注册了 `mmu_notifier`。当 Linux `mm`即将销毁时，KFD必须在 `exit_mmap`释放 CPU进程内存前停止 GPU继续访问这些地址：

```text
mm_struct release
→ kfd_process_notifier_release()
→ kfd_process_notifier_release_internal()
   ├── 从全局 kfd_process table 删除
   ├── cancel eviction/restore work
   ├── kfd_process_dequeue_from_all_devices()
   │   └── 停止 HWS/MES/HQD 中的用户 Queue/Wave
   ├── pqm_uninit()
   └── p->mm = NULL
```

源码注释直接说明：release notifier返回后 `exit_mmap`会释放进程内存，所以必须先 dequeue并销毁 user queues，见 [kfd\_process.c:1326](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_process.c#L1326)。

这解释了为什么“关闭 `/dev/kfd` fd”与“进程 GPU context彻底销毁”不是简单同义词：主 `kfd_process`的安全生命周期与 `mm`和引用计数相连；libhsakmt也会在进程生命周期内缓存 render fds，避免 KFD依赖的 DRM VM被意外更换。

### 8.2 Queue软件对象在 notifier阶段拆除，PDD/BO由后续 worker回收

退出不是一个笼统的“release worker全部清理”，而是两个有先后约束的阶段。第一阶段仍在 MMU notifier调用中，必须在 `exit_mmap`之前完成硬件停用和 Queue软件对象拆除：

```text
kfd_process_notifier_release_internal()
→ kfd_process_dequeue_from_all_devices()
   → DQM process_termination()
      → 解除 Queue驻留/停止执行
      → 释放 MQD并从 DQM注销 process-device
→ pqm_uninit()
   → 释放 Ring/rptr/wptr/EOP/CWSR等 Queue持有的 BO引用
   → 释放 Queue级 MES gang context与 wptr GART mapping
   → 销毁 Queue/PQM软件节点
→ p->mm = NULL
```

这里“释放 Queue持有的 `cwsr_bo`引用”不等于此时必然最终释放底层 BO；如果该 BO还由 KFD内存 handle或其他对象持有，真正的 backing object会等最后一个引用或后续 outstanding-BO清理时回收。`process_termination()`的 No-CPSCH/HWS路径分别见 [kfd\_device\_queue\_manager.c:2827](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_device_queue_manager.c#L2827) 和 [kfd\_device\_queue\_manager.c:2958](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_device_queue_manager.c#L2958)，`pqm_uninit()`见 [kfd\_process\_queue\_manager.c:218](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_process_queue_manager.c#L218)。

第二阶段要等 `kfd_process`引用计数允许释放后，`kfd_process_wq_release()`才反向回收剩余资源：

```text
kfd_process_wq_release()
→ 等待进行中的 GPU reset完成
→ signal eviction fence
→ 释放 outstanding KFD BO及其 GPUVM mappings
→ 销毁 SVM ranges
→ kfd_process_destroy_pdds()
   → 释放 PDD/QPD级 TBA（Trap Base Address，陷阱基址）/TMA（Trap Memory Address，陷阱内存地址）、trap-handler和 IB资源
   → fput(PDD持有的 render file引用)
   → 销毁 alloc_idr
   → 释放 process doorbell BO/bitmap
   → 释放 PDD级 MES process-context BO
   → 销毁 PDD
→ 销毁 event与 kfd_process
```

**\[SOURCE]** worker主线见 [kfd\_process.c:1236](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_process.c#L1236)，PDD内部的 `fput → doorbell → MES process context`顺序见 [kfd\_process.c:1119](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_process.c#L1119)。

PDD持有 render `struct file`引用，所以用户态提前 close原 render fd并不会立刻销毁正在被 KFD使用的 VM。PDD销毁时会 `fput()`这份引用；**只有它释放的是最后一个 file reference**，DRM `postclose`才会随之执行 `amdgpu_vm_fini()`，先从 PASID XArray删除 mapping，再等待相关 fence并释放 page table root。若该文件仍有 `dup()`、继承或其他引用，VM会在更晚的最后一次 `fput()`后销毁。见 [kfd\_process.c:1119](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_process.c#L1119)、[amdgpu\_kms.c:1546](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_kms.c#L1546) 和 [amdgpu\_vm.c:2752](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_vm.c#L2752)。

安全顺序不能反过来：

```text
错误：先 free Page Table/BO/CPU pages，再通知 GPU 停 Queue
正确：先阻止新提交并让 Queue/Wave停止，再解除 mapping和释放 backing
```

否则仍在运行的 Wave可能继续使用已经释放、甚至已经分配给另一个进程的页面，形成 use-after-free和跨进程访问。

## 9. 加入第二个进程：哪些独立，哪些共享

P2加入时不会复制一块 GPU。它读取与 P1相同的全局 topology，但由于 `mm_struct`不同，会重复第 5 章的进程私有部分：创建新的 `kfd_process/PDD`，打开同一个 GPU对应的 render node并获得另一套 `amdgpu_vm/PASID/Page Table`；直到 P2创建第一条 Queue，它的 QPD才被注册进 P1也在使用的同一个设备级 DQM。于是二者拥有独立的软件安全域，却共同竞争同一组物理执行资源。

### 9.1 两个进程各自独立的对象

```text
P1                                            P2
mm_A                                          mm_B
kfd_process_A                                 kfd_process_B
PQM_A                                         PQM_B
PDD_A0                                        PDD_B0
drm_file_A / amdgpu_fpriv_A / amdgpu_vm_A     drm_file_B / amdgpu_fpriv_B / amdgpu_vm_B
PASID_A / Page Table Root A                    PASID_B / Page Table Root B
alloc_idr_A / BO handles A                     alloc_idr_B / BO handles B
doorbell slice A                               doorbell slice B
Queue/MQD A                                    Queue/MQD B
PDD级 TBA/TMA、trap memory A                   PDD级 TBA/TMA、trap memory B
Queue级 CWSR save areas A                      Queue级 CWSR save areas B
PDD级 MES process context A                    PDD级 MES process context B
Queue级 MES gang contexts A                    Queue级 MES gang contexts B
```

### 9.2 两个进程共享并竞争的物理/设备级资源

```text
同一个 PCI function / amdgpu_device
同一个 KFD node和 DQM
同一个 VRAM/TTM物理容量池
同一组 CU、cache、memory controller和带宽
有限的 VMID pool
有限的 HQD/MEC pipe/queue pool
全局 doorbell aperture中的不同 slice
同一个 HWS/MES scheduler与 reset domain（具体 ASIC/partition而定）
```

可以用下表检查隔离边界：

| **对象**                    | **P1/P2是否各自独立** | **备注**                                                           |
| ------------------------- | --------------- | ---------------------------------------------------------------- |
| `kfd_process`、PQM         | 是               | 分别按`mm`创建                                                        |
| PDD/QPD                   | 是               | 每个“进程 × GPU node”一份                                              |
| `amdgpu_vm`、PASID、PT root | 是               | 每个 render`drm_file`建立；对象销毁后 ID可复用                                |
| BO handle namespace       | 是               | BO本体可以经显式 IPC共享                                                  |
| GPU VA数值                  | 可重复             | VA相同不表示 memory相同                                                 |
| Queue ID、MQD              | 是               | Queue ID只在对应进程/PQM语境中解释                                          |
| doorbell mapping          | 是               | 底层 aperture共享，映射 slice和 slot受限制                                  |
| VMID/HQD                  | 否，属于有限池         | No-CPSCH中首 Queue为 PDD分配 VMID、每条 compute Queue保留 HQD；HWS/MES可动态复用 |
| CU、VRAM容量、cache、带宽        | 否               | 需要调度、配额或 partition才能提供 QoS                                       |
| reset/fault domain        | 不一定             | 取决于硬件和固件支持的 containment粒度                                        |

### 9.3 “隔离”不自动等于“无侧信道、无残留状态、性能独占”

**\[INFERENCE]** GPUVM和 Queue ownership主要解决直接越权访问，但多个进程仍可能共享 cache、TLB、CU寄存器资源、memory controller、性能计数器和 reset domain；这些共享结构可能形成残留状态、时序侧信道或性能干扰。因此还要区分三类目标：

```text
Memory safety isolation
    P1不能通过普通 load/store直接访问 P2未授权的页面

Information-flow isolation
    切换时清理可能残留的寄存器/cache/微架构状态，降低数据残留与侧信道

QoS / performance isolation
    为 CU、VRAM容量、带宽、Queue数和执行时间提供配额与计费
```

**\[SOURCE]** 当前源码在 HWS `MAP_PROCESS`中根据 `enforce_isolation`设置 `exec_cleaner_shader`，同时提供 cleaner shader与 isolation控制接口，见 [kfd\_packet\_manager\_v9.c:32](../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_packet_manager_v9.c#L32) 和 [amdgpu\_gfx.c:1820](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_gfx.c#L1820)。这些机制以及 XCP/compute partition说明真实驱动还要处理地址隔离之外的问题，但它们不是 `kfd_process + PASID`自动带来的保证。评估自研 GPU时必须分别列需求，不能用一句“支持多进程”覆盖三者。

## 10. 进程隔离、资源分区与完整 GPU 虚拟化

### 10.1 四类相关但不严格递进的能力

| **能力/机制** | **使用者看到什么**                       | **主要解决什么**                        | **仍缺什么**                   |
| --------- | --------------------------------- | --------------------------------- | -------------------------- |
| 原生多进程隔离   | 同一 Host OS中的同一个物理 GPU             | 地址、BO、Queue、doorbell、Fault归属      | Guest设备、强 QoS、独立 reset未必具备 |
| 时间复用/超额订阅 | 多个逻辑 Queue竞争有限 VMID/HQD/CU        | 资源复用和利用率                          | 不自动保证公平性、强 QoS或物理资源独占      |
| 空间资源分区    | XCP/compute/memory partition等资源子集 | 切分 CU/内存/引擎，可改善 QoS和 fault domain | 仍不必然有 Guest可见虚拟 PCI设备      |
| 完整虚拟化     | Guest看到可枚举、可驱动的 GPU或 VF（Virtual Function，虚拟功能，SR-IOV）/vGPU      | 跨 OS/租户的设备、DMA、资源和故障边界            | 需要完整管理面与硬件/固件支持            |

这四类能力不能画成必须逐级经过的阶梯：时间复用与空间分区可以单独使用，也可以组合；完整虚拟化可以采用整卡直通、基于时间复用的 vGPU或空间分区/VF，不要求产品先实现全部中间形态。调度公平性同样来自明确的策略、配额和抢占机制，而不是“支持超额订阅”自动获得。

原生进程隔离的对象链：

```text
kfd_process + PDD + amdgpu_vm/PASID + Queue/MQD + doorbell
```

是虚拟化可复用的底层构件，但它没有回答以下问题：

* Guest如何发现、配置和 reset一个虚拟 PCI/平台设备。
* Guest提交的 MMIO、doorbell、Queue和内存请求如何被截获、验证或直通。
* Guest DMA如何被 Host IOMMU限制在自己的 Host/Guest memory范围。
* 若多个 Guest共享资源，CU、VRAM、带宽、VMID/HQD和执行时间如何配额、计费和防止饥饿。
* 一个 Guest的 hang/RAS（Reliability, Availability, Serviceability，可靠性/可用性/可服务性）/Fault能否只 reset自己，而不影响其他租户。
* 若产品要求迁移，暂停、恢复、snapshot和热插拔如何保存完整设备状态。

因此 `kfd_process`不是 vGPU，PDD不是虚拟 PCI function，PASID也不是 Guest ID。

### 10.2 SR-IOV、直通和 mediated vGPU分别增加什么

```text
整卡 PCI passthrough
    Hypervisor把整个 PCI function交给一个 Guest；Host IOMMU负责 DMA边界。

SR-IOV
    PF在 Host管理物理设备和多个 VF；Guest枚举自己的 VF，VF拥有受限的配置、MMIO、interrupt和资源视图。

Mediated/software vGPU
    Host KMD或管理器向 Guest仿真/复用设备接口，并验证或翻译 Guest命令；灵活但软件边界更重。
```

**\[SOURCE]** 当前 AMDGPU源码存在明确的 SR-IOV VF分支和 PF/VF通信/受限 MMIO路径，例如 [amdgpu\_virt.c:926](../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_virt.c#L926)。这只能证明 AMDGPU包含 SR-IOV虚拟化支持构件，不表示所有 ASIC、所有 KFD能力或所有 reset粒度都相同。

**\[BOUNDARY]** mediated vGPU是通用实现方式；当前本地 AMDGPU源码证据只能直接支撑其 SR-IOV VF路径，本文不据此声称该源码树实现了 AMD mediated-device backend。

若某个 VF/产品组合向 Guest暴露可用的 AMDGPU/KFD compute能力，Guest内部仍可为不同进程建立 `amdgpu_vm/PASID/kfd_process/Queue`；此时存在两层隔离：

```text
Host/Hypervisor层：Guest A/VF A  ↔ Guest B/VF B
Guest KMD层：      Process A1    ↔ Process A2
```

前一层需要 VF/vGPU接口和 IOMMU/DMA隔离，后一层继续使用本文讲的 GPUVM、PASID、Queue ownership等机制。

### 10.3 PASID、VMID与虚拟化 ID不是一回事

| **ID**          | **作用域与含义**             | **不是什么**             |
| --------------- | ---------------------- | -------------------- |
| PID/TGID        | Linux任务/进程身份           | GPU地址空间 ID           |
| PASID           | 一套 GPUVM或设备进程地址空间的身份标签 | 固定硬件槽、Guest ID       |
| VMID            | GPU内部有限的活动地址翻译槽        | 永久进程 ID、完整执行 context |
| Queue ID        | PQM/用户 ABI中的 Queue句柄   | HQD物理槽               |
| VF ID / vGPU ID | 虚拟设备或租户身份              | PASID或 VMID          |

一个 VF内部可以有多个 PASID；一个 PASID的 Queue在不同时刻可以占不同 VMID/HQD；同一个 VMID也可以随时间复用于不同 PASID。把它们画成一一对应关系会直接导致错误的资源生命周期设计。

## 11. 面向自研 GPU KMD 的最小实现清单

以下不是要求照搬 AMD结构名，而是要求保留等价职责。

### 11.1 设备级初始化

* **\[DESIGN]** 枚举物理 GPU或 partition，建立稳定 device ID与用户可见节点。
* **\[DESIGN]** 初始化全局 DQM等价物、VMID/HQD/doorbell资源池、interrupt与 reset domain。
* **\[DESIGN]** 向 UMD发布每个 GPU的 memory aperture、Queue能力、render/memory接口关联。

### 11.2 进程与 process-device连接

* **\[DESIGN]** 以 `mm_struct`或等价安全主体为主键建立进程级资源总账；线程共享，fork/exec语义明确。
* **\[DESIGN]** 为每个“进程 × GPU”建立 PDD等价物，连接进程、设备、地址空间、Queue、doorbell和 Fault统计。
* **\[DESIGN]** 明确 fd关闭、`mm`退出、异常终止和 reset时谁持有引用、谁触发最终回收。

### 11.3 GPUVM 与内存能力

* **\[DESIGN]** 每个进程/设备建立独立 GPUVA mapping、Page Table Root和长期地址空间 ID。
* **\[DESIGN]** BO handle必须位于进程或 fd命名空间，不能用裸内核指针或全局可猜 ID作为授权。
* **\[DESIGN]** map/unmap更新 PTE权限，完成 page-table write ordering后再做定向 TLB invalidation。
* **\[DESIGN]** 显式 IPC必须创建新的接收方引用和 mapping；裸 GPU VA不能作为共享凭证。

### 11.4 Queue、doorbell 与调度

* **\[DESIGN]** CREATE\_QUEUE时验证 Ring、rptr/wptr、CWSR等地址都属于调用者 GPUVM并具有正确权限。
* **\[DESIGN]** 为每条 Queue创建 MQD等价的可保存描述，至少包含 Ring、index、doorbell、地址空间关联和抢占状态。
* **\[DESIGN]** doorbell mmap只能覆盖调用进程被授权的 slice；Queue slot由进程内 bitmap或 capability分配。
* **\[DESIGN]** Queue驻留必须原子关联正确的 Page Table/VMID和 MQD/HQD，禁止“Queue属于 P1，页表却来自 P2”。
* **\[DESIGN]** 区分 Queue驻留调度与 kernel packet消费；一条驻留 Queue应能连续处理多个 packet。

### 11.5 Fault、抢占和回收

* **\[DESIGN]** Fault record必须报告 VA、访问类型和来源 engine/node，并提供至少一种可解析的上下文身份：直接给 PASID，或给出能通过设备级映射恢复 PASID的 VMID。
* **\[DESIGN]** 支持从地址空间 ID反查 process-device、Queue/event和 BO mapping；不可恢复错误只终止责任主体的能力应尽量优先。
* **\[DESIGN]** 若支持抢占未完成 Wave，需要 CWSR等价的 save/restore ABI；不要把 MQD保存误当成 Wave寄存器保存。
* **\[DESIGN]** `mm`或 GPUVM销毁前先禁止新提交、停止/抢占 Queue并等待硬件不再访问，再释放 PTE、BO和 Host pages。

### 11.6 若目标是虚拟化，按所选模型增加能力

以下不是每条虚拟化路径都必须由自研 KMD全部实现，应先选择产品模型：

* **\[DESIGN] Common：**&#x8DE8; Guest边界时必须明确设备如何分配/暴露、DMA如何受 Host IOMMU限制、interrupt如何路由，以及 Fault/Reset由 Host还是 Guest负责。
* **\[DESIGN] Passthrough：**&#x6574;卡直通主要依赖 Hypervisor的 PCI assignment、IOMMU和 interrupt remapping；Host KMD不必再实现 VF、virtio或 mediated command ABI。
* **\[DESIGN] SR-IOV：**&#x82E5;选择 PF/VF，需要 PF资源管理、VF配置/MMIO/doorbell/interrupt边界、PF-VF协议和 VF级 reset/RAS归属。
* **\[DESIGN] Mediated：**&#x82E5;选择 mediated/software vGPU，需要 Guest可见虚拟设备 ABI、Host侧命令验证/翻译、Queue与内存 capability检查。
* **\[DESIGN] Product：**&#x43;U、VRAM、带宽、Queue、VMID/HQD配额、计费、抗饥饿以及 snapshot/migration是多租户 QoS或可迁移产品的附加目标，不应反推为整卡直通的通用前置条件。

可以把自研 KMD的最小控制流收敛为：

```text
device_probe()
  → init_global_resource_pools()
  → publish_topology()

process_open(mm)
  → get_or_create_process_context(mm)
  → create_process_device_skeletons()

address_space_create(process, device)
  → create_gpu_vm()
  → allocate_address_space_id()

address_space_attach(process, device, vm_capability)
  → validate_and_reference_existing_gpu_vm()

memory_alloc/map(process_device, handle, gpu_va, permissions)
  → update_page_table()
  → flush_tlb()

queue_create(process_device, ring, indices, optional_cwsr)
  → validate_all_gpu_addresses()
  → allocate_doorbell_slot()
  → build_mqd()
  → schedule(address_space + queue_context)

fault_interrupt(source_device, va, access, optional_vmid, optional_pasid)
  → lookup_process_device(source_device + available_context_id)
  → recover_or_signal_owner()

process_release(mm)
  → stop_new_submission()
  → preempt_or_drain_queues()
  → wait_no_hardware_access()
  → unmap_and_free_resources()
```

这里的 `vm_capability`是抽象授权对象：在 AMD当前双节点 ABI中可以由 render fd间接提供，在统一驱动 ABI中也可以是同一 fd内的受检 handle。`optional_cwsr`只在支持未完成 Wave抢占时存在，不是最小 Queue创建的强制输入。

## 12. 最终记忆模型

```text
长期软件身份与所有权：
Linux mm
  └── kfd_process
      └── PDD(process,GPU)
          ├── holds ref ──► struct file
          │                  └── drm_file → amdgpu_fpriv
          │                                   └── amdgpu_vm
          │                                       └── PASID + Page Table Root
          ├── BO handles/mappings
          ├── process doorbells
          └── Queue ── Ring + MQD

短期硬件驻留：
PASID + Page Table Root ──► VMID
Queue MQD               ──► HQD
未完成 Wave             ──► CWSR save area（仅抢占需要时）

执行与反查：
No-CPSCH：KFD直接保留 HQD并按 active状态装载 MQD
HWS/MES：scheduler firmware从逻辑 Queue中选择驻留对象
                   │
                   ▼
CP/MEC消费/解释驻留 Ring中的 AQL packet并发起 dispatch
  → CU Wave在对应 VMID地址翻译上下文中访存
  → Fault报告来源 device/node、VA、访问属性和可用的 VMID/PASID
      ├── 有 PASID：AMDGPU以 (device, PASID)反查 amdgpu_vm
      └── 只有 VMID：先由 source device的 VMID映射恢复 PASID
  → KFD结合 source node和恢复后的 PASID定位 PDD与 kfd_process
```

一句话收束：

> `kfd_process`是进程级资源总账，PDD/QPD是“进程 × GPU”的连接点，AMDGPU `amdgpu_vm`提供 PASID和 Page Table，PQM/DQM把进程 Queue与设备调度连接起来；Queue驻留时，PASID/Page Table通过有限 VMID参与地址翻译，MQD通过有限 HQD参与取包，只有抢占未完成 Wave时才需要 CWSR。它们共同实现原生多进程隔离，也是 GPU虚拟化的底层基础；要跨越到虚拟化，还要按所选直通、SR-IOV或 mediated模型补齐 Guest设备、DMA/IOMMU、interrupt和 Fault/Reset边界，共享型产品才进一步要求资源配额与计费。
