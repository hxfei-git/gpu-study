## 1. 全局地图：两条能力轴，一个交汇点

整个 GPU 栈可以压成两条**正交的能力轴**。它们是本笔记库的两条主线，也是理解一切的地图。

### 1.1 轴 A：内存能力（常规显式 → SVM 扩充）

**轴 A 分两条子路径，后者是前者的扩充**：

```text
子路径 1（常规，所有 GPU 通用）：显式分配 + 搬运 + 同步
  cl_mem/KFD alloc → BO（VRAM/GTT/host-pinned）→ copy/map/unmap → event
  GPU 访问 host 内存：注册 + 映射（显式）
  详见 [常规内存机制](<./2. 常规内存机制：GPU 内存分配与 CPU↔GPU 访问.md>)

子路径 2（SVM，扩充）：共享地址 + 按需补页
  coarse-grain ─► fine-grain buffer ─► fine-grain system + HMM
  裸指针共享，无显式搬运，fault 自动补页
  详见 [SVM 专题](<./9. AMD SVM：共享内存、统一地址空间与页面迁移.md>)
```

这条轴回答：**CPU 和 GPU 怎么共享内存？——常规靠"搬运"，SVM 靠"共享地址"；SVM 复用常规的
BO/GPUVM/页表地基，只增量"共享 VA + fault 补页"（见常规内存机制 §8）。**

> 两条子路径都站在同一个地基上：**GPUVM 页表**。这块地基本身拆成一篇从零教的专题——[MMU 与页表](<./7. MMU 与页表：从 CPU 对照看 GPUVM 的构建、写入与切换.md>)（CPU x86 对照 + 页表怎么建/写/切）。

### 1.2 轴 B：调度能力（队列 / device-enqueue）

```text
Host 提交 kernel ──────► GPU 侧 device-enqueue 子任务
  CPU 写 AQL + doorbell      GPU 调度器写 AQL + doorbell
```

这条轴回答：**谁有资格往队列里提交工作？** Host、还是 GPU 自己。详见 [队列提交专题](<./5. AMD 队列提交：从 API 到 AQL 与硬件.md>) 与 [Device Enqueue 专题](<./8. AMD Device Enqueue：Host Command、AmdAqlWrap 与 AQL.md>)。

### 1.3 交汇点：device-enqueue 的三个内存问题

两条轴在 device-enqueue 处交汇。**但这里极易画错关系**——最错误的表述是"SVM 是 device-enqueue 的地基"。正确拆法：一次 device-enqueue 涉及三块内存，**各自对 SVM 的需求完全不同**：

| # | 内存对象 | 必须满足 | 需要 SVM 吗 |
|---|---|---|---|
| **① 队列本体** | ring、MQD/wptr、`AmdAqlWrap` 池、`virtualQueue_`/`schedulerQueue_` | GPU 可写（设备可见内存） | **不需要**——GTT/VRAM buffer + GPU 映射即可 |
| **② 参数传递** | child kernel 的 kernarg buffer | GPU 可读 | **机制上不需要**——参数默认被**拷**进 wrap 的 kernarg 区域 |
| **③ 参数指向的数据** | child 通过参数解引用访问的 buffer | GPU 能访问**那个地址** | **这才是 SVM 真正发挥作用的地方** |

```text
无 SVM 的 device-enqueue：        有 SVM 的 device-enqueue：
  child 参数 → 拷进 kernarg buffer     child 参数是共享指针 → 免拷贝
  child 访问 host 数据 → 先拷或映射      child 直接读写 host 地址（零拷贝）
  可行，代价是拷贝                     可行，代价是维护共享/一致性
```

**结论**：
- device-enqueue 的**可行性**由 ① 决定（GPU 能写队列）——**不依赖 SVM**。
- **粗/细粒度 SVM** 影响的是 ③ 与同步代价（coarse 需要 map/unmap 交接，fine 一致+原子），**不影响 enqueue 能不能做**。
- 两条轴真正的耦合点只有一个：**当 ③ 选择"共享 VA 免拷贝"时**，即"GPU 自己调度，且子任务零拷贝访问 host 数据"——这是两条轴的乘积，不是包含关系。

### 1.4 容易画错的关系（反面清单）

| 错误表述 | 正确表述 |
|---|---|
| "SVM 是 device-enqueue 的地基" | device-enqueue 只需 GPU 可写内存；SVM 只决定 ③ 要不要拷贝 |
| "粗粒度 → 细粒度自动包含" | 三种粒度是不同能力，不构成包含阶梯（SVM 专题 §6.1） |
| "GPUVM 隔离 = Guest DMA 隔离" | GPUVM 管 GPU 内地址翻译；IOMMU 管 PCIe DMA 到 Host PA，是两层（主模型 §3.3） |
| "device-enqueue 必须先有 SVM" | 先有队列本体(①)；参数(②)和数据(③)怎么传由是否共享地址决定——是**依赖关系**，不是时间先后 |

## 2. 一个进程的完整旅程（8 步骨架）

> 骨架沿用你确认的 8 步。每步统一用五个维度描述：**做什么 / 关键对象 / 关联专题 / 隔离视角 / 自研落地**。
> 下文"关键对象"用 AMD 概念描述；**自研 GPU（MCU-firmware CP + 无 IOMMU）的设计**见 [自研 GPU 设计专题](<./12. 自研 GPU 设计：MCU-CP、内存交互与设备调度.md>)。

### ① Host malloc 内存 → 建立 SVM 地址空间

> 本步是 SVM 入口。**常规入口**（`clCreateBuffer` → BO → copy/map，所有 GPU 通用）见
> [常规内存机制](<./2. 常规内存机制：GPU 内存分配与 CPU↔GPU 访问.md>)——SVM 是它的扩充。

- **做什么**：进程 malloc/mmap 一块内存，声明 GPU 可访问；KFD 建立 `svm_range`，GPU 页表按需（fault 时）填充。
- **关键对象**：进程 VA → `svm_range` → GPU PTE；coarse/fine-grain 粒度；`mmu_interval_notifier` 负责 CPU 侧失效回调。
- **关联专题**：[SVM 专题](<./9. AMD SVM：共享内存、统一地址空间与页面迁移.md>) §2（五机制）、§7.2（svm_range 建立）。
- **隔离视角**：这块内存最终归**哪个进程的 GPUVM**；PASID 是它的长期身份；GPU PTE 是执行时的物理边界。
- **自研落地**：需要一个 `svm_range` 等价物 + GPU PTE 更新 + CPU 页表失效通知。

### ② 创建队列、映射 doorbell

- **做什么**：创建 HSA Queue（ring 在 GPU 可见内存），分配 MQD、doorbell slot。
- **关键对象**：`kfd_process` → PDD → QPD → `struct queue` → MQD → doorbell；调度侧 DQM（HWS / No-CPSCH 二选一）。
- **关联专题**：[队列提交专题](<./5. AMD 队列提交：从 API 到 AQL 与硬件.md>) §3（控制面）、[硬件队列专题](<./6. AMD 硬件队列：AQL Ring、MQD、HQD 与调度驻留.md>)（MQD/HQD）。
- **隔离视角**：doorbell 是**每进程一个 slice、每队列一个 slot**；MQD 归属 PDD；首条 Queue 时 DQM 注册 QPD 并取页表基址。
- **自研落地**：queue 对象 + MQD 等价物 + doorbell 分配（进程内 bitmap + 全局 aperture 约束）。

### ③ 提交 Parent kernel

- **做什么**：Host 构造 64 字节 AQL packet，发布到 ring，写 doorbell，CP 取包执行。
- **关键对象**：`NDRangeKernelCommand` → `hsa_kernel_dispatch_packet_t` → ring → doorbell → CP。
- **关联专题**：[队列提交专题](<./5. AMD 队列提交：从 API 到 AQL 与硬件.md>) §4（数据面一）、[Device Enqueue 专题](<./8. AMD Device Enqueue：Host Command、AmdAqlWrap 与 AQL.md>) §2（AQL packet 逐字段）。
- **隔离视角**：CP 通过 MQD 中的 **VMID** 在正确页表下取包；doorbell 路由归到正确队列。
- **自研落地**：AQL 类似的 packet ABI + ring 发布协议（预留槽→写 body→release header→doorbell）。

### ④ Parent 在 GPU 上 device-enqueue 子任务

- **做什么**：Parent kernel 调用 `enqueue_kernel`，GPU 调度器产生 Child 任务并提交。
- **关键对象**：`AmdAqlWrap`（含 embedded Child AQL）→ `virtualQueue_` 提交池 → Scheduler → `schedulerQueue_` ring → doorbell → CP。三条队列各有分工：`virtualQueue_`（CP 不读，无 MQD）/ `gpu_queue_` + `schedulerQueue_`（CP 读，有 MQD）。`gpu_queue_` 即步骤 ③ Host 提交所用的 ring——两条路径在 CP 入口汇合（Device Enqueue 专题 §6.3）。
- **关联专题**：[Device Enqueue 专题](<./8. AMD Device Enqueue：Host Command、AmdAqlWrap 与 AQL.md>) §4-§6、[队列提交专题](<./5. AMD 队列提交：从 API 到 AQL 与硬件.md>) §6（数据面三）。
- **隔离视角**：此处回到 [1.3 的三个内存问题](#13-交汇点device-enqueue-的三个内存问题)——队列本体(①)归哪个 GPUVM、参数(②)拷到哪、数据(③)走 SVM 还是拷贝。
- **自研落地**：设备调度器放 MCU firmware（不占 CU）——详见 [自研 GPU 设计专题 §5](<./12. 自研 GPU 设计：MCU-CP、内存交互与设备调度.md>)。

### ⑤ 子任务访问 SVM 指针 → GPU fault → 恢复闭环

- **做什么**：Child 访问尚未映射/迁移的 SVM 地址 → GPU page fault → KFD 恢复页表 → wave 重试。
- **关键对象**：GPU 中断 → fault record（VA/访问属性/VMID/PASID）→ PASID 反查 `kfd_process` → `svm_range_restore_pages` → `hmm_range_fault` 收页 → 写 GPU PTE → TLB flush → 通知重试。
- **关联专题**：[SVM 专题附录 C](<./9. AMD SVM：共享内存、统一地址空间与页面迁移.md>)（恢复闭环全链）、[硬件队列专题 §8](<./6. AMD 硬件队列：AQL Ring、MQD、HQD 与调度驻留.md>)（中断通路）、[主模型](<./4. AMD KMD 主模型：进程上下文、资源隔离与虚拟化.md>) §7.10（fault 归属）。
- **隔离视角**：fault 必须落到**责任进程**；有 PASID 直接反查，只有 VMID 时由来源 device 的 VMID 映射恢复 PASID（主模型 §7.10）。
- **自研落地**：recoverable fault 路径 + 队列 pause/resume；离散 VRAM 下迁移还需**带进程身份的 DMA 拷贝引擎**（详见 [自研 GPU 设计专题 §3.4](<./12. 自研 GPU 设计：MCU-CP、内存交互与设备调度.md>)）。

### ⑥ 完成信号回传 Host Event

- **做什么**：Child/依赖完成后，completion signal 触发 Host Event COMPLETE。
- **关键对象**：`completion_signal` → HSA signal → CLR Event；Direct（CP barrier 等待）/ Non-direct（Host worker 等待）两条路径。
- **关联专题**：[队列提交专题](<./5. AMD 队列提交：从 API 到 AQL 与硬件.md>) §5.4（完成回传）、§6.7（device→host 完成桥接）、[Device Enqueue 专题](<./8. AMD Device Enqueue：Host Command、AmdAqlWrap 与 AQL.md>) §6（两条路径在 CP 入口汇合）。
- **隔离视角**：signal 归属哪个进程/队列；`child_counter`/`parent_wrap` 保证 Parent 只在子图收敛后完成。
- **自研落地**：completion 机制（signal 内存位置 + 唤醒路径）。

### ⑦ 隔离视角贯穿

**贯穿 ①-⑥ 的所有对象，归属链**：

```text
PASID    这套地址空间是谁的（长期身份）
VMID     当前哪套页表占有限硬件翻译槽（短期租借）
doorbell 谁有资格提交（每进程 slice / 每队列 slot）
页表      执行时物理边界（GPU PTE 权限）
handle   软件访问能力（PDD.alloc_idr 命名空间）
```

- **关联专题**：[主模型](<./4. AMD KMD 主模型：进程上下文、资源隔离与虚拟化.md>) §3、§5.5、§7（隔离落地）、§9（双进程对照）。
- **自研落地**：主模型 §11 的最小实现清单，就是逐条自研清单。

### ⑧ 自研落地：每步 AMD 对应什么、自研造什么

| 旅程步骤 | AMD 关键机制 | 自研 GPU 等价物（详见自研 GPU 设计专题） | 难度 |
|---|---|---|---|
| ① SVM | `svm_range` / `mmu_interval_notifier` / HMM | range 管理 + 失效通知 + fault 恢复 | 高 |
| ② 队列 | `kfd_process`/PDD/QPD/MQD/doorbell | 进程资源总账 + firmware 队列描述符 + 门铃 | 高 |
| ③ 提交 | AQL ring 发布协议 | packet ABI + ring | 中 |
| ④ device-enqueue | `AmdAqlWrap` + Scheduler | 设备调度器（MCU firmware，§5） | 高 |
| ⑤ fault 闭环 | `svm_range_restore_pages` | recoverable fault + 队列暂停（§3.4） | 高 |
| ⑥ 完成 | signal/Event | 完成通知 | 中 |

## 3. 贯穿视角：隔离如何生效

隔离不是"一个开关"，而是下列约束同时成立（详见主模型 §2）：

| 隔离对象 | KMD 建立的边界 | 最终强制者 |
|---|---|---|
| GPU 地址空间 | 每 GPUVM 独立 VA mapping + PT root | GPU MMU |
| BO 访问能力 | handle 在 PDD 命名空间 + 合法 mapping | KFD/DRM lookup + GPU PTE |
| 页表 | 只允许本进程合法 mapping 生成有效 PTE | page-table walker |
| Queue | Queue ID/MQD 关联创建者 PDD | KFD + HWS/MES/HQD |
| doorbell | 进程 mmap 自己的 slice，Queue 占合法 slot | KFD mmap 范围 + routing |
| Fault | 由来源 device + PASID/VMID 反查归属 | GPU IH + KFD/AMDGPU |

**贯穿 8 步的记忆方法**：每走一步，都问一次"**这个对象属于谁、硬件凭什么知道它属于谁**"。答案永远是 PASID（身份）/ VMID（翻译槽）/ doorbell（提交）/ 页表（边界）+ handle（访问能力）五件套的组合（简化记忆时取前四件套，完整列表见上表）。

> \*注：上表"最终强制者"列基于 AMD 专用 CP 硬件 + IOMMU。自研 MCU-CP + 无 IOMMU 架构下的替换，见 [自研 GPU 设计专题 §2](<./12. 自研 GPU 设计：MCU-CP、内存交互与设备调度.md>)。

### 6.2 "同一地址，不同层的翻译"（CPU/GPU/IOMMU）

```text
CPU 侧：进程 VA ── CPU MMU ──► Host PA
GPU 侧：GPU VA  + VMID ── GPU page table ──► VRAM 或 system-memory DMA address
DMA 侧：DMA address/IOVA + PASID ── Host IOMMU ──► Host PA
```

三层各管各的。SVM 让"进程 VA ≈ GPU VA"（共享地址），但 GPU 页表与 CPU 页表仍是两张表，靠 `mmu_notifier`/HMM 保持语义一致。自研平台即使没有 Host IOMMU，驱动也必须把 DMA API 返回的 `dma_addr_t` 交给设备，不能自行假定它恒等于 CPU 物理地址；此时缺少的是 PASID/IOMMU 提供的 DMA 重映射与隔离层——详见 [自研 GPU 设计专题 §3.1](<./12. 自研 GPU 设计：MCU-CP、内存交互与设备调度.md>)。

### 6.9 完整叙事场景：SVM × device-enqueue（F1）

**场景一句话**：Host 用 SVM 共享数据 → 提交 Parent kernel → Parent 在 GPU 上 device-enqueue 子任务 → 子任务零拷贝访问共享数据（缺页按需补）→ 完成回传 Host。**这是把两条主线缝成一条的完整脚本。**

> **[BOUNDARY]** 本地源码能验证 CLR 的 `AmdAqlWrap` ABI、virtual/scheduler queue 创建和 KFD fault 恢复，但本地 Device Library 只有迁移说明，不能逐行证明 slot reserve/READY 发布算法。下图中“设备库原子预留”和“MCU 扫描/发布 child”是 [第 12 章](<./12. 自研 GPU 设计：MCU-CP、内存交互与设备调度.md>)采用的 **[DESIGN]** 路径，不应读成当前 AMD Device Library 的源码事实。

```text
① Host malloc 数据 → 注册 SVM（coarse-grain）         §2①
   svm_range 建立；host 写数据（CPU 拥有）
② 创建队列（gpu_queue_ + virtualQueue_ + schedulerQueue_） §2② / F4
   队列本体 = GPU 可见 GTT 内存，非 SVM          ← 三个内存问题 ①
③ Host 提交 Parent kernel                        §2③
   AQL → gpu_queue_ → doorbell → MCU(CP) 取包；参数含 SVM 数据指针
④ Parent device-enqueue 子任务                    §2④ / F4
   设备库(CU)：原子预留 AmdAqlWrap slot（不经过 MCU）
     拷贝 child 参数到 kernarg 区域             ← 三个内存问题 ②（拷贝）
     release READY + 通知 MCU
   MCU：扫描 → 查 wait-list → 发布 child AQL → 自己消费
⑤ 子任务访问 SVM 指针 → fault → 恢复              §2⑤ / F2 / 硬件队列§8 + 自研§4
   child 解引用 → GPU MMU walk → PTE 无效
   XNACK 暂停 → MCU(兼任IH) 写 fault ring → MSI → 主机
   主机 restore → HMM收页 → dma_map → 写PTE → flush → retry
   数据访问 = SVM 共享（零拷贝）                  ← 三个内存问题 ③
⑥ 子任务完成 → Parent 子图收敛 → 完成回传 Host       §2⑥
⑦ 隔离贯穿：PASID/VMID/doorbell/页表归属             §3
⑧ 自研落地：每步等价物                             §4 导航表
```

**三个内存问题的落点**（场景正好走完 §1.3 的三种情况）：

| 内存对象 | 场景位置 | 需要 SVM 吗 | 实际形态 |
|---|---|---|---|
| 队列本体（virtualQueue_/schedulerQueue_/AmdAqlWrap 池） | ②④ | 否 | GPU 可见 GTT buffer |
| child 参数 kernarg | ④ | 否（默认拷贝） | wrap 的 kernarg 区域 |
| 共享数据（SVM 指针指向的 buffer） | ⑤ | **是** | 进程 GPUVM 映射，fault 按需补页 |

**隔离贯穿**（⑦）：共享数据归进程 GPUVM（PASID 身份）；队列归进程 PDD（doorbell slice/MQD）；fault 落回责任进程（PASID 反查）；全程 P1 看不到 P2 的共享数据（各自页表）。

**自研落地（⑧）**：MCU 三合一（CP+IH+设备调度器）；GPU 页表 + PASID（软件身份）；coarse-grain 同步（fence + 所有权）；SDMA 拷贝 + retryable fault；设备库（slot 原子预留）+ MCU 调度。设计细节见 [自研 GPU 设计专题](<./12. 自研 GPU 设计：MCU-CP、内存交互与设备调度.md>)。

**叙事脚本（一句收束）**：

> "进程 malloc 数据 → 注册 SVM → 提交 Parent → Parent 在 GPU 上 device-enqueue 子任务 → 子任务零拷贝访问共享数据（缺页由主机按需补页，GPU 重试）→ 完成回传 Host。全程每个对象都有 PASID/VMID/doorbell/页表兜底隔离。"
