# AMD GPU 硬件队列：AQL Ring、MQD、HQD 与调度驻留

本文只回答一个问题：MQD（Memory Queue Descriptor，内存队列描述符）、HQD（Hardware Queue Descriptor，硬件队列描述符）、HWS（HardWare Scheduler，硬件调度器）/MES（Micro Engine Scheduler，微引擎调度器）与 CP（Command Processor，命令处理器）/MEC（Micro Engine Compute，微引擎计算）分别是什么，以及它们在运行时如何配合；该链及每一跳的文件、函数、输入和输出见[队列提交专题 §3](<./5. AMD 队列提交：从 API 到 AQL 与硬件.md#3-控制面从-hsa-queue-创建到-kfd-交接>)。

源码路径口径：本文所有未显式写仓库根的源码路径均相对于 `2.源码/linux`，固定版本为 `248951ddc14de84de3910f9b13f51491a8cd91df`。

## 1. 先把四个对象分开

最直观的比喻是：AQL（Architected Queuing Language，结构化队列语言）Ring 是一张光碟，AQL packet 是光碟上的一首曲目；MQD 是播放器配置单；HQD 是 CP/MEC 内真正插入并播放光碟的一个播放器槽位。CP/MEC 是读取曲目、解析并把工作发给 CU（Compute Unit，计算单元）的执行机构。

```text
AQL Ring                AQL Packet             MQD                            HQD
┌────────────────┐      ┌────────────┐         ┌──────────────────────┐      ┌──────────────────────┐
│ P0 │ P1 │ P2…  │      │一次 dispatch│         │ring base/size        │      │一个 CP/MEC 驻留槽位    │
└────────────────┘      └────────────┘         │rptr/wptr 地址         │ ──→ │当前 Queue 的活体状态   │
     工作存储               一条工作             │doorbell、VMID、资源    │      │CP 据此取包、执行        │
                                                 └──────────────────────┘      └──────────────────────┘
```

因此必须排除三个误解：

1. HQD 不是另一条 AQL Ring，也不是普通软件对象；它是有限的硬件 Queue 上下文，表现为一组 `CP_HQD_*` 寄存器和运行状态。
2. MQD 不是 packet；它描述一条 Queue 的位置、格式、地址空间和资源。一个 MQD 对应的 Ring 中可以持续出现很多 packet。
3. HWS/MES 调度的是“哪个逻辑 Queue 此刻占用 HQD”；CP/MEC 的 packet parser 消费的是“当前 HQD 指向的 Ring 中的 packet”。这两个循环有关联，但不是同一个循环。

| **对象**     | **生命周期**            | **主要拥有者**             | **保存什么**                           |
| ---------- | ------------------- | --------------------- | ---------------------------------- |
| AQL Ring   | HSA（Heterogeneous System Architecture，异构系统架构）/KFD（Kernel Fusion Driver，内核融合驱动）Queue 创建至销毁 | ROCr（ROCm Runtime，ROCm 运行时）/Producer 与 CP 共享 | 可复用的 packet slot、读写进度              |
| AQL packet | 发布至 CP 消费           | Producer 写入，CP/MEC 读取 | 一次 dispatch/barrier 等工作            |
| MQD        | KFD Queue 创建至销毁或更新  | KFD/HWS/MES           | Ring、pointer、doorbell、VM、资源配置的内存镜像 |
| HQD        | 被调度到硬件槽位期间          | CP/MEC/HWS/MES        | 当前 Queue 的驻留硬件配置与执行状态              |

## 2. 硬件队列的本质：一条可被 CP 消费的调度通路

“硬件队列”不是芯片上孤立刻死的 FIFO。对于一条 compute Queue，它至少由以下状态共同形成：GPU 可访问的 AQL Ring、生产/消费索引、doorbell、MQD，以及一个当前可用的 HQD 或由 HWS/MES 维护的待驻留状态。

```text
No-CPSCH 的活动 Queue：
  Ring + rptr/wptr + doorbell + MQD + 已装入的具体 HQD

CPSCH/HWS 或 MES 的逻辑 Queue：
  Ring + rptr/wptr + doorbell + MQD + runlist/MES 调度状态
  只有被选择执行时，才占用一个有限 HQD
```

AMD CP 相关角色可按职责理解：MEC 是 compute Queue 的命令执行前端；它取 AQL packet、解析 dispatch 并发射 GPU 工作。HWS 或 MES 则负责逻辑 Queue 的驻留、抢占和切换。SDMA（System DMA，系统 DMA 引擎）有其专用 packet/Ring，不应因为也有 Queue 就推导它能消费 AQL kernel dispatch packet。

### 2.1 CP、MEC、HWS/MES 各自调度什么

**\[INFERENCE]** KFD/ROCr 的 Queue 接口可以确认“Queue 被映射、被驻留、被 CP 消费”这些边界，但不能逐行展示固件内部的 packet parser。因此下面是按公开角色建立的架构模型：MEC 处理已经驻留的 compute Queue 中的 packet；HWS/MES 管理逻辑 Queue 是否获得驻留；两者不要混为同一个 scheduler。

```text
AMD GPU 的相关角色（不同代际的具体组合可不同）：

┌────────────────────────────────────────────┐
│ MEC（Micro Engine Compute）                 │
│ 已有驻留 Queue：读取 Ring，解析 dispatch，发射 CU 工作 │
├────────────────────────────────────────────┤
│ HWS / MES                                   │
│ 逻辑 Queue：决定驻留、抢占、恢复与 HQD 分配  │
├────────────────────────────────────────────┤
│ PFP / ME 等其他 CP 前端                     │
│ 处理其所属的命令流和前端职责；不能据此断言   │
│ 所有 AQL compute packet 必经相同路径         │
└────────────────────────────────────────────┘
```

因此用户态写入 AQL Ring、发布有效 header 并敲 doorbell 后，CP 只会在相应 Queue 已经拥有可运行硬件状态时取包。doorbell 的含义是“Producer 推进了生产进度”，不是 packet 本体，也不替代 MQD/HQD 中的 Queue 配置。

### 2.2 通用 MCU 可以复用协议，不能替代 GPU 执行端

**\[INFERENCE]** Doorbell、共享描述符和调度循环是一种通用的设备接口模式：

```text
AMD GPU CP/MEC       NVMe 控制器             自研 MCU/小型 CP
读取 Queue/MQD       读取 submission queue    读取共享 Ring
消费 AQL/命令包       消费 DMA 命令            做 ready/dispatch 判断
发射 CU wave         驱动 NAND/DMA           通知执行引擎或软件 worker
```

所以 MCU 可以实现 Queue 注册、doorbell、依赖判断、Ring 消费和调度策略；但要执行 GPU kernel，仍必须配合计算核心、能理解 kernel ABI 的命令处理器或软件 worker。MCU 实现的是调度通路，不会天然变成 MEC。

## 3. MQD 怎样变成可运行的 HQD

### 3.1 MQD 是 HQD 的可保存配置镜像

以 GFX9 KFD 为例，`2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_mqd_manager_v9.c:271` 的 `update_mqd()` 将 `struct queue_properties` 编码到 `struct v9_mqd`。MQD 字段的名字直接带有 `cp_hqd_`，说明它就是将来要装入 HQD 的寄存器镜像。

| **Queue 输入**                 | **MQD/HQD 字段**                         | **CP 使用方式**                        |
| ---------------------------- | -------------------------------------- | ---------------------------------- |
| `queue_address`、`queue_size` | `cp_hqd_pq_base_*`、`cp_hqd_pq_control` | 定位 Ring 与环形边界                      |
| `read_ptr`                   | `cp_hqd_pq_rptr_report_addr_*`         | 回报 CP 已消费到的位置                      |
| `write_ptr`                  | `cp_hqd_pq_wptr_poll_addr_*`           | 观察 Producer 已发布到的位置                |
| `doorbell_off`               | `cp_hqd_pq_doorbell_control`           | 将这个 Queue 的 doorbell 关联给 CP        |
| `vmid`                       | `cp_hqd_vmid`                          | 在正确 GPU 地址空间访问 Ring、packet、kernarg |
| context-save 字段              | `cp_hqd_ctx_save_*`                    | 为可抢占的 wave/控制栈状态提供 backing area    |

当 Queue 格式是 AQL 时，代码会设置 slot-based wptr 等 AQL 控制位。特别要注意单位：`load_mqd()` 的源码注释明确，AQL write pointer 按 64 B packet 计数，PM4/CP write pointer 按 dword 计数；因此它传入 `wptr_shift = 4` 进行适配。这只是 pointer 单位转换，**不是**把 AQL packet 重新打包成 PM4。

### 3.2 no-CPSCH：MQD 直接成为确定 HQD 的寄存器状态

no-CPSCH 的语义是逻辑 Queue 创建后立即取得一个确定 HQD，因此 MQD 可以直接装入该槽位。`kgd_gfx_v9_hqd_load()` 先锁住指定 `pipe_id/queue_id`，把 MQD 中从 `CP_MQD_BASE_ADDR` 到 `CP_HQD_PQ_WPTR_HI` 的连续字段写入 HQD 寄存器；然后启用 doorbell、让 CP 从 GPU 可访问的 wptr 地址发起一次 poll、启动 EOP fetcher，并置 `CP_HQD_ACTIVE.ACTIVE=1`。此时该 HQD 已能直接消费这个 Ring。至于该模式如何分配 pipe/queue、创建失败如何返回，由主文档的调用链负责说明。

```text
MQD（内存镜像） ── load_mqd / hqd_load ──> HQD（pipe, queue 的活动寄存器状态）
```

### 3.3 CP 如何取包和推进读指针

HQD 配置完成后，运行时是一个高频生产/消费协议：

```text
Producer：预留 wptr → 等待空 slot → 写 packet body → release 发布有效 header
          → 更新 wptr → 写 doorbell

CP/MEC：读取 HQD 中 Ring base/size、VMID 和 Queue 格式
        → 检查 doorbell/wptr
        → 按当前 rptr 取得下一个 slot 的 header/body
        → 解析并执行 packet
        → 推进硬件 rptr，并写回 rptr_report 地址
```

CP 的确通过 HQD 读取 Ring 配置、并通过 rptr/wptr 管理消费进度；但它不会为每个 packet 重读 MQD 或重配 HQD。MQD→HQD 属于低频控制面，packet 的读取、执行和 rptr 推进属于高频数据面。

**rptr/wptr 有两个副本：持久（MQD）vs 活（HQD 寄存器）**

```c
// MQD 里存的是硬件 rptr/wptr 的持久副本（2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_mqd_manager_v9.c:286-289）
m->cp_hqd_pq_rptr     // 持久 rptr
m->cp_hqd_pq_wptr_lo  // 持久 wptr
// HQD 装载时把 MQD 的 rptr/wptr 装进寄存器（活副本）
WREG32(mmCP_HQD_PQ_RPTR, m->cp_hqd_pq_rptr);   // kgd_gfx_v9_hqd_load
```

**读写指针的更新时机（这是关键）**：

| 谁 | 更新什么 | 什么时候 | 更新到哪 |
|---|---|---|---|
| UMD（Producer） | **wptr** | 发布 packet 后 | 队列控制区的 wptr 内存（`cp_hqd_pq_wptr_poll_addr` 指向的地址） |
| CP/MEC（Consumer） | 读 wptr | 敲 doorbell / 轮询时 | 从 `wptr_poll_addr` 读 |
| CP/MEC | **推进 rptr（活副本）** | **每次取包后** | **HQD 的 `CP_HQD_PQ_RPTR` 寄存器** + 写回报地址 `rptr_report_addr`（内存，让 UMD 回收 slot） |
| 换出时（context save） | **同步 rptr** | 队列被驱逐/抢占时 | **HQD 的活 rptr 写回 MQD 的 `cp_hqd_pq_rptr`** |

**CP 的职责（明确）**：
- CP 只管**活副本**：读 wptr、推进 **HQD 的 rptr 寄存器**、写回报地址。
- CP **从不修改 MQD**——MQD 的 rptr/wptr 是**持久存档**，只有换出时驱动/固件把 HQD 状态 dump 回去。
- 所以"CP 一次次消费推进 rptr"只影响 HQD 寄存器 + 内存回报地址；**MQD 的 rptr 只有换出时才同步**，下次调度 load 用存档续跑。

> **一句话**：rptr/wptr 有两副本——**HQD 寄存器（活，CP 高频更新）+ MQD（持久，换出时才同步）**。CP 只管活副本，MQD 是换出/换入的存档点。

## 4. CPSCH/HWS：逻辑 Queue 怎样竞争有限 HQD

### 4.1 创建时不分配 HQD

HWS 模式下，逻辑 Queue 有自己的 doorbell 和 MQD，但创建时不绑定一个确定 HQD。因此逻辑 Queue 数量可以大于同时驻留 HQD 数量。

```text
逻辑 Queue： Q0/MQD0  Q1/MQD1  Q2/MQD2  Q3/MQD3
                         │ HWS 调度
有限 HQD：    HQD0 ← Q0  HQD1 ← Q1       Q2/Q3 尚未驻留或待换入
```

### 4.2 一次驻留更新的语义

当创建、激活、停用、驱逐或恢复 Queue 时，控制面更新的是可运行逻辑 Queue 的集合，而非让 CP 遍历所有 MQD：

```text
1. 使旧的逻辑 Queue 集合退出或可被抢占。
2. 确认旧驻留状态已经停止，才允许替换映射。
3. 提交新的 process/Queue 描述，其中每条 Queue 指向自己的 MQD、wptr 与 doorbell。
4. HWS 从可运行集合中选择 Queue，将其映射到有限 HQD 并使 CP 开始消费对应 Ring。
```

底层 `MAP_QUEUES` packet 为每条 Queue 携带 MQD GPU 地址、wptr 地址与 doorbell offset，并要求由 HWS 决定槽位。故分工是：KFD 说明“哪些逻辑 Queue 可以运行、其 MQD 在哪里”；HWS 说明“此刻哪些 Queue 进入哪些 HQD”。具体函数调用与 fence 观察点由主文档集中列出。

**边界：** 开源 KFD 能证明 runlist 构造、`UNMAP_QUEUES` 的 fence 等待和“由 HWS 决定槽位”这一接口契约，但不能证明某一代 HWS firmware 使用固定轮转、严格优先级或其他具体选队算法。不能把未公开 firmware 策略写成 Linux 驱动事实。

### 4.3 上下文切换切的是什么

Queue 切换并非复制 AQL Ring，也并非每执行一个 packet 就切换。它分三层：

| **对象**    | **保存/恢复内容**                                                     | **典型触发**               |
| --------- | --------------------------------------------------------------- | ---------------------- |
| Queue 驻留  | HQD 的 Ring、VMID、doorbell、资源配置和运行状态                              | 新 Queue 映射、驱逐、资源或优先级变化 |
| Wave 执行现场 | wave、control stack、work-group state 等 context-save backing area | Queue 可抢占、挂起和恢复        |
| Packet 进度 | rptr/wptr 及 Ring slot                                           | 正常 packet 消费循环         |

典型 CPSCH 切换先发 `UNMAP_QUEUES` 并等待 fence；可抢占状态被保存后，HWS 将另一个逻辑 Queue 的 MQD/状态装入可用 HQD，恢复必要的 wave 上下文，再允许 CP 继续取其 Ring。尚未消费的 packet 不需要搬运，仍由该 Queue 原来的 rptr/wptr 协议管理。`context-save` 地址也不是“下一个 packet 的地址”，而是执行现场的存放区。

## 5. MES：另一条 firmware 调度路径

启用 MES 时，KFD 的 CPSCH 创建路径不是上传 HWS runlist，而是走 `add_queue_mes()`，向 MES firmware 提交 `MES_SCH_API_ADD_QUEUE`，携带 process、page table 与 Queue/MQD 等信息。之后的驻留、抢占和恢复由 MES 管理。MES 与 HWS 解决相似的“逻辑 Queue 到有限硬件执行状态”问题，但接口和 firmware 所有权不同，不能将两者混作同一实现。

## 6. 最终记忆模型

```text
MQD：一条逻辑 Queue 的可保存配置镜像
HQD：一个有限的、当前可运行的 CP/MEC 硬件槽位
HWS/MES：决定哪个逻辑 Queue 获得 HQD
CP/MEC：在已驻留 HQD 上消费 AQL Ring，并推进 rptr
doorbell：通知 CP 生产者推进了 wptr，不传递 packet 本体
```

所以“CP 通过 HQD 取包、推进读指针”是正确的；更完整的说法是：**调度器先让逻辑 Queue 的 MQD 成为某个 HQD 的驻留上下文，CP 才能依据该 HQD 的 Ring 与地址空间配置消费 packet；rptr/wptr 是这条已经驻留 Queue 的数据面进度，而不是 HWS/MES 的 Queue 选择算法。**

## 8. 中断与通知通路（MSI-X → IH（Interrupt Handler，中断处理器）ring → dispatch）

**\[SOURCE]** 本文前面的 MQD/HQD 讲"队列如何被消费"，本节补上"GPU 如何通知 CPU"——中断路径。这是 queue ring 模式的又一次复用。

**基本处理方式（AMD 代码链路）**：

```text
request_irq：一个 MSI-X 向量                       2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_irq.c:321（pci_alloc_irq_vectors）
  └─ amdgpu_irq_handler()                         2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_irq.c:200
       └─ amdgpu_ih_process() 读 IH ring          2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_ih.c:209
            └─ while (rptr != wptr) 逐条取 entry
                 └─ amdgpu_irq_dispatch()         2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_irq.c:468
                      ├─ 解码 client_id/src_id → 查注册表 → IP 块 handler
                      └─ 没人认领 → amdgpu_amdkfd_interrupt() → KFD
```

**关键认知**：

1. **一个 MSI-X 承载全部 GPU 中断**。`pci_alloc_irq_vectors(adev->pdev, 1, 1, ...)`，注释直写 "we only need one vector"（`2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_irq.c:321`）。
2. **IH ring 就是 ring + rptr/wptr 模式**——生产者是 GPU 硬件（写 wptr），消费者是驱动（读 ring、写回 rptr）。和 AQL ring 同构，只是生产/消费角色反过来。
3. **分发表路由**：`adev->irq.client[client_id].sources[src_id]`（`2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_irq.c:511`），解码出 client_id/src_id 后查表调用对应 IP 块处理器；没人认领则交给 KFD 兜底。
4. **fault 经此到达 KFD**：GMC/MMU（Memory Management Unit，内存管理单元）fault → IH ring → dispatch 无人认领 → `amdgpu_amdkfd_interrupt` → KFD → `amdgpu_vm_handle_fault` → `svm_range_restore_pages`（完整闭环见 [SVM 专题附录 C](<./9. AMD SVM：共享内存、统一地址空间与页面迁移.md>)）。
5. **中断延迟原则**：每个事件触发中断（AMD 默认），handler 批量清空；fault 等 wave 的必须即时，完成类可攒批——判断标准：wave 在不在等。
