# 自研 GPU 设计：MCU-CP、内存交互与设备调度

本文把前 11 章中的 AMD/Linux 机制压缩成一套可实现的自研 GPU 边界。目标架构假定使用 MCU firmware 充当 Command Processor（CP），Host 侧没有可供设备使用的 IOMMU/PASID 地址翻译服务。

> **[BOUNDARY]** 本文是设计文档，不是现有硬件的实现说明。`[SOURCE]` 只表示本仓库中的 AMD/Linux/POCL/Vortex 源码能够证明对应机制；`[DESIGN]` 表示建议的自研取舍，不能反向解释成 AMD 硬件事实。

## 1. 设计前提与最小目标

第一阶段只承诺以下能力：

1. Host 创建 buffer、建立 GPU 可见映射并显式提交 command；
2. MCU 校验 command、选择进程地址空间并驱动执行引擎；
3. completion/fault 能回到创建该队列的进程；
4. 所有跨 CPU、MCU、GPU、DMA 引擎的状态变化都有明确的发布与回收顺序；
5. SVM、recoverable fault、migration 和 device-enqueue 按阶段叠加，不作为最小系统的前置条件。

**[DESIGN]** 最小可信链路应当先做成：

```text
Host command
  → KMD 校验 handle / GPUVA / queue ownership
  → 写 ring body
  → release 发布 header 或 valid bit
  → doorbell
  → MCU 选择 address-space context
  → engine 执行
  → 写 completion
  → IRQ / event 唤醒 Host
```

## 2. 哪些 AMD 机制不能直接照搬

| 类别 | AMD 中的形式 | 自研结论 |
|---|---|---|
| **必须保留的语义** | per-process GPUVM、queue ownership、发布顺序、fault 归属、completion | 必须实现等价边界，否则不能安全多进程 |
| **可替换的编码** | AQL packet、MQD/HQD 字段、doorbell aperture | 可以换成自定义 ABI，但必须有版本、长度、权限和地址校验 |
| **AMD 专用硬件** | MEC/HWS/MES、IH ring、VMID bank | 由 MCU、软件调度表和自研中断记录替代 |
| **不能假定存在** | Host IOMMU、PASID translation、XNACK、HDP/L2 特定 flush 指令 | 必须通过平台能力表显式声明 |
| **应分阶段实现** | fine-grain SVM、migration、device-enqueue | 先完成显式 buffer 和 Host submission，再逐层加入 |

**[DESIGN]** 三条避坑规则：

1. “没有 IOMMU”只表示没有 Host IOMMU 重映射/隔离层，不表示 DMA 地址恒等于 CPU 物理地址。
2. “MCU 是 CP”只替换取包、校验和调度职责，不自动替代 GPU MMU、cache coherence 或 DMA engine。
3. “复用 AQL”只能复用 packet 思想；如果没有对应的 HSA runtime、signal 与 memory-scope 实现，就不能宣称兼容 HSA。

## 3. 内存交互规格

### 3.1 无 Host IOMMU 时的地址契约

同一个 allocation 至少可能出现四种地址，接口中必须显式区分：

| 名称 | 产生者 | 消费者 | 禁止的假定 |
|---|---|---|---|
| CPU VA | 进程/内核 VMA | CPU | 不能直接交给设备 |
| CPU PA/PFN | CPU 页表与内存管理 | 内核 | 不能绕过 DMA API 后直接写进 descriptor |
| `dma_addr_t` | `dma_map_*()`/DMA API | 设备或 Host bridge | 即使无 IOMMU，也可能包含平台 offset、mask 或 bounce 约束 |
| GPUVA | KMD 的 per-process GPUVM | GPU page walker/engine | 必须在当前进程 GPUVM 中查表，不能当作全局地址 |

**[SOURCE]** 本地 Linux [DMA API 文档](<../2.源码/linux/Documentation/core-api/dma-api.rst>)规定设备应使用 mapping API 返回的 DMA address；[dma-iommu.c](<../2.源码/linux/drivers/iommu/dma-iommu.c>)只是其中一个 backend。PCIe、IOMMU 与 GPUVM 的两层边界见 [第 10 章](<./10. AMD PCIe 地址映射与 DMA：GPU Endpoint.md>) §4、§8。

**[DESIGN]** 自研 descriptor 中使用 `dma_addr_t` 或 GPUVA，由一个显式 `address_kind` 字段区分；MCU 不接受“猜测这是 PA”的裸 64-bit 地址。没有 Host IOMMU 时，PASID 可以继续作为软件进程身份，但不能冒充 DMA translation key。

### 3.2 Allocation、mapping 与回收

建议每个 buffer 维护以下最小账本：

```text
buffer_id
owner_process_id
size
placement                 RAM / device-local
cpu_mapping_state
dma_mapping_state         direction + dma_addr/sg_table
gpuva_mapping_state       gpuva + permissions + address-space id
in_flight_refcount
```

**[DESIGN]** 回收顺序固定为：停止新提交 → 等待 in-flight fence → 从 GPUVM 解除映射 → 失效 GPU TLB（若存在）→ unmap DMA → 释放页面。handle 关闭只能减少用户态引用，不能跳过仍在执行的硬件引用。

**[SOURCE]** AMD 的对象、DMA address 与 GPU PTE 分层可从 [amdgpu_ttm.c](<../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_ttm.c>)、[amdgpu_vm.c](<../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_vm.c>) 和 [amdgpu_amdkfd_gpuvm.c](<../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_amdkfd_gpuvm.c>) 对照；完整解释见 [第 2A 章](<./2A. Linux 内存管理基础：从物理内存、PFN 与 struct page 到 GEM、TTM、HMM.md>)。

### 3.3 Cache 可见性与 completion

**[DESIGN]** 每条 producer→consumer 边必须同时回答三件事：

```text
producer 的写何时完成？
写入经过的 cache/写合并缓冲何时对 consumer 可见？
哪个 release 状态告诉 consumer 可以开始 acquire？
```

推荐统一为：

```text
写 data/body
  → 执行该内存域所需的 clean/flush/writeback
  → release fence
  → 发布 valid/header/completion

consumer acquire 读取状态
  → 必要时 invalidate
  → 读取 data/body
```

**[BOUNDARY]** AMD 的 HDP、GL2、AQL acquire/release scope 是具体平台实现。自研平台应定义自己的 cache domain 表，不能把“总是 flush L2/HDP”写死成跨平台规则。本地 Linux [memory-barriers.txt](<../2.源码/linux/Documentation/memory-barriers.txt>)还明确区分 normal memory、DMA coherent memory 与 MMIO ordering；三者不能由一个通用 barrier 代替。

### 3.4 SDMA、页表更新与 recoverable fault

**[DESIGN]** DMA/copy command 至少携带：owner/address-space id、source/destination address kind、length、权限、completion target。MCU 在启动引擎前重新校验 mapping，不能只信用户态填入的地址。

页表更新顺序是：

```text
准备 PTE backing
  → 写入完整 PTE
  → 保证 PTE 对 page walker 可见
  → 失效对应 GPU TLB / page-walk cache（若实现）
  → 允许队列恢复或新 command 执行
```

没有 Host IOMMU 不影响这条 GPU 侧顺序。只有明确不实现 GPU TLB/page-walk cache 的简化版本，才能省略失效动作，但仍需保证“PTE 先可见、访问后发生”。

recoverable fault record 至少包含：

```text
device_id + queue_id + address_space_id
faulting GPUVA + read/write/execute
retryable/fatal + engine/wave token
```

**[SOURCE]** AMD 的公开恢复链可从 [amdgpu_vm.c](<../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_vm.c>) 的 `amdgpu_vm_handle_fault()` 进入 [kfd_svm.c](<../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_svm.c>) 的 `svm_range_restore_pages()`；页面迁移由 [kfd_migrate.c](<../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_migrate.c>) 处理。自研实现只借鉴“归属→收页/迁移→映射→失效→重试”的状态机，不复制 AMD 寄存器协议。

### 3.5 GPU→CPU 读回的发布顺序

**[DESIGN]** GPU/SDMA 把数据写入 Host 可见内存后，必须先完成该路径需要的 cache 与 DMA 可见性动作，再发布 completion。Host 观察到 completion 后做 acquire，再读取数据。

```text
GPU/SDMA 写 payload
  → device-side visibility action
  → release completion
  → Host acquire wait
  → 必要的 dma_sync_*_for_cpu()
  → CPU 读取 payload
```

coherent mapping 可能不需要显式 `dma_sync_*`，streaming mapping 通常需要；具体规则由 allocation/mapping type 决定，不能只根据“数据位于 RAM”判断。

## 4. 中断与通知通路

MCU 可以兼任 CP 与中断记录生产者，但 Host/KMD 仍负责权限、进程生命周期和可睡眠的恢复工作。

| 事件 | MCU/设备侧职责 | Host/KMD 职责 |
|---|---|---|
| command completion | 写 completion record，保证 payload 先可见，触发 IRQ | 校验 queue/sequence，完成 fence/event，唤醒进程 |
| retryable page fault | 停住责任 wave/queue，记录完整 fault 身份 | 查 owner/mm，补页/迁移/写 PTE，通知 retry |
| fatal fault | 阻止继续取包，保存诊断上下文 | 隔离责任队列/进程，回收资源，必要时 reset engine |
| device reset | 停止所有 engine，递增 reset generation | 让旧 queue/token 全部失效，重建硬件状态 |

**[SOURCE]** AMD 的 IRQ 解码与 fault 分发分别可从 [amdgpu_irq.c](<../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_irq.c>)、[amdgpu_ih.c](<../2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_ih.c>) 和 [kfd_int_process_v9.c](<../2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_int_process_v9.c>) 对照。MSI/MSI-X 只负责把通知送到 Host，不替代 completion record 的内存顺序。

## 5. Device Enqueue 的 MCU 等价层

**[BOUNDARY]** 本地 `2.源码/rocm-device-libs` 只有迁移说明 README，没有 `enqueue_kernel` builtin 或 `__amd_scheduler_rocm` 的设备端实现。因此下面只固定本仓库能验证的 ABI 边界与一套自研协议，不声称复现 AMD 的内部算法。

**[SOURCE]** CLR 的 [rocsched.hpp](<../2.源码/rocm-clr/rocclr/device/rocm/rocsched.hpp>) 定义 `AmdAqlWrap`、wait list、parent/child counter 与 `SchedulerParam`；[rocvirtual.cpp](<../2.源码/rocm-clr/rocclr/device/rocm/rocvirtual.cpp>) 创建 virtual/scheduler queue 并传入 GPUVA。它能证明 Host runtime 与设备调度代码之间需要共享 ABI，不能证明缺失 Device Library 的 slot 扫描细节。

**[DESIGN]** 自研 device-enqueue 分成两个职责域：

```text
Parent kernel / device library（CU 上）
  1. 原子预留 slot
  2. 写 child descriptor、kernarg 与 wait list
  3. release 发布 READY
  4. 通知 MCU

MCU scheduler
  5. acquire 读取 READY
  6. 校验 owner、GPUVA、权限、依赖和资源上限
  7. 转成内部 engine command 并提交
  8. 收敛 child completion，更新 parent counter/event
```

MCU 负责调度、校验和提交，但 slot 的并发预留仍由 device library/Parent 执行；二者不能被含糊地合称为“都在 MCU 上”。每个 slot 必须带 generation 与 owner，reset 或进程退出后旧 slot 不得重新生效。

第一版不必支持任意递归 enqueue。建议限制 child 深度、每 parent 的 slot 数、kernarg 大小和最大 wait-list 长度，并在资源耗尽时返回可诊断错误。

## 6. 分阶段实现顺序

| Stage | 能力 | 通过条件 |
|---|---|---|
| 0 | 单进程、显式 buffer、Host submission | command/fence 顺序正确，错误地址被拒绝 |
| 1 | pinned Host memory 与 DMA mapping | 全程只使用 DMA API 返回地址，回收无在途引用 |
| 2 | per-process GPUVM 与 queue isolation | 两进程相同 GPUVA 映射不同 backing，不能越权访问 |
| 3 | recoverable fault | fault 能唯一归属，补页后只重试责任队列 |
| 4 | migration/prefetch | placement 改变不破坏 GPUVA 与 completion 语义 |
| 5 | device-enqueue | READY 发布、依赖、child completion、reset generation 均可验证 |
| 6 | fine-grain coherence/atomics | memory scope 与 cache 协议有硬件和并发测试支撑 |

**[DESIGN]** 只有前一阶段的隔离、顺序和错误恢复测试通过后，才进入下一阶段。否则更高级功能会把同一个根因扩散到更多状态机。

## 7. AMD 与自研构件映射

| AMD/Linux 构件 | 提供的语义 | 自研等价物 |
|---|---|---|
| `kfd_process` / PDD | 进程及进程×设备资源总账 | KMD process context + per-device context |
| PASID | 长期进程身份；有 IOMMU 时还可参与 DMA translation | 软件 `address_space_id`；无 IOMMU 时不承担 DMA translation |
| VMID / VM_CONTEXT | 在途执行使用哪个 GPU 页表根 | MCU context slot + GPU MMU root register/table |
| AQL ring + doorbell | packet 发布与通知 | versioned command ring + release valid/header + doorbell |
| MQD/HQD | 队列保存态与硬件驻留态 | RAM queue descriptor + MCU run state |
| HWS/MES/MEC | 队列调度与 command processing | MCU scheduler/CP |
| IH ring + IRQ source | 异步事件记录与分发 | MCU event ring + MSI/MSI-X/平台 IRQ |
| SDMA | copy、页表写入、fence | 自研 DMA/copy engine；无独立引擎时由受控 MCU copy path 替代 |
| `svm_range` + HMM | 进程 VA range、页状态与 fault 协调 | KMD VA-range registry + OS page notifier/fault service |
| `AmdAqlWrap` + Device Library scheduler | device-enqueue 的共享 ABI 与 child 调度 | versioned child slot ABI + CU producer + MCU consumer |
