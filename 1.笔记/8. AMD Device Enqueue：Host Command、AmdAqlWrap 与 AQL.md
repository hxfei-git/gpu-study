# AMD OpenCL Device Enqueue：Host Command、AmdAqlWrap 与 AQL Packet

本文是对 [AMD OpenCL 队列提交跟踪](<./5. AMD 队列提交：从 API 到 AQL 与硬件.md>)“数据面三”的概念补充，只回答一个问题：一次 OpenCL Kernel 工作在 Host Runtime、Device Runtime 和 GPU CP 面前分别长什么样。

全文固定使用四种证据标签：

* **\[SOURCE]**：本地固定版本源码可以直接证明。
* **\[SPEC]**：HSA/OpenCL ABI 或 API 语义要求。
* **\[INFERENCE]**：由可见结构和调用点得到的实现解释。
* **\[BOUNDARY]**：本地缺少实现源码，结论只能到接口或 ABI 边界为止。

本地 AMD CLR 基线为 `2.源码/rocm-clr`；HSA packet 定义来自 `2.源码/rocr-runtime`。本地 `2.源码/rocm-device-libs` 只有 README，因此无法逐行验证 Device Library 如何填充 `AmdAqlWrap`，也无法逐行验证 `__amd_scheduler_rocm` 的扫描和发布算法。

## 1. 先建立正确的四层对象模型

先记住一句话：

> Host `Command` 是完整的 OpenCL 软件任务对象；`AmdAqlWrap` 是 GPU 可见的 Device-Enqueue 任务控制块；AQL Kernel Dispatch Packet 是交给 CP 的最终 64 字节启动描述；MQD 则描述 CP 应该从哪条硬件 Queue 取这些 packet。

```text
Host 提交：

OpenCL API
  -> Host NDRangeKernelCommand
  -> hsa_kernel_dispatch_packet_t
  -> gpu_queue_ AQL Ring
  -> MQD/HQD/CP

Device Enqueue：

enqueue_kernel()
  -> AmdAqlWrap（含 embedded Child AQL）
  -> virtualQueue_ 提交记录池
  -> Scheduler 判断 readiness
  -> schedulerQueue_ AQL Ring
  -> MQD/HQD/CP
```

这四层不能按名字中的 `queue` 或 `command` 相互等同：

| **对象**                         | **核心问题**                            | **生产者**                         | **消费者**          | **CP 是否直接解释**  |
| ------------------------------ | ----------------------------------- | ------------------------------- | ---------------- | -------------- |
| Host`NDRangeKernelCommand`     | OpenCL 请求了什么，依赖和 Host 状态是什么         | OpenCL Runtime                  | CLR backend      | 否              |
| `AmdAqlWrap`                   | 哪个 Child 正在等待，它何时 ready，属于哪个 Parent | Parent/Device Library           | Scheduler Kernel | 否              |
| `hsa_kernel_dispatch_packet_t` | 现在具体启动哪个 Kernel，网格、参数和资源是什么         | Host backend 或 Device Scheduler | CP               | 是              |
| MQD                            | AQL Ring 在哪里，如何寻址、通知、隔离和调度          | KMD/firmware                    | CP/HWS           | 是，但它不是 command |

## 2. AQL Packet 到底是什么

**\[SPEC]** AQL 是 Architected Queuing Language。AQL Queue 的 Ring 由固定大小的 packet slot 组成；Kernel Dispatch、Barrier 和 Agent Dispatch 是不同 packet 类型。本文讨论的 `hsa_kernel_dispatch_packet_t` 只是 AQL packet 的一种。

**\[SOURCE]** `hsa_kernel_dispatch_packet_t` 定义在 `2.源码/rocr-runtime/runtime/hsa-runtime/inc/hsa.h:2959-3070`，其大小为 64 字节：

| **Byte offset** | **字段**                 | **大小** | **CP 使用方式**                                       |
| --------------- | ---------------------- | ------ | ------------------------------------------------- |
| 0               | `header`               | 2 B    | Packet 类型、barrier bit、acquire/release fence scope |
| 2               | `setup`                | 2 B    | NDRange 维度数                                       |
| 4               | `workgroup_size_x`     | 2 B    | Local size X                                      |
| 6               | `workgroup_size_y`     | 2 B    | Local size Y                                      |
| 8               | `workgroup_size_z`     | 2 B    | Local size Z                                      |
| 10              | `reserved0`            | 2 B    | 必须为 0                                             |
| 12              | `grid_size_x`          | 4 B    | Global size X                                     |
| 16              | `grid_size_y`          | 4 B    | Global size Y                                     |
| 20              | `grid_size_z`          | 4 B    | Global size Z                                     |
| 24              | `private_segment_size` | 4 B    | 每个 work-item 的 private/scratch 请求                 |
| 28              | `group_segment_size`   | 4 B    | 每个 work-group 的 group/LDS 请求                      |
| 32              | `kernel_object`        | 8 B    | 已加载 Kernel 的 opaque executable handle             |
| 40              | `kernarg_address`      | 8 B    | Kernarg buffer 的 GPU VA                           |
| 48              | `reserved2`            | 8 B    | 标准 ABI 保留字段                                       |
| 56              | `completion_signal`    | 8 B    | Dispatch 完成时更新的 HSA signal                        |

可以把一个 Kernel Dispatch Packet 读成一条硬件启动指令：

```text
LAUNCH kernel_object,
       grid=(grid_x, grid_y, grid_z),
       workgroup=(wg_x, wg_y, wg_z),
       args=kernarg_address,
       scratch=private_segment_size,
       lds=group_segment_size,
       completion=completion_signal
```

### 2.1 AQL Packet 包含什么、不包含什么

**\[SPEC]** `kernel_object` 是可执行 Kernel 的不透明句柄，不是代码字节本身；`kernarg_address` 只是参数缓冲区地址，参数值不内嵌在 packet 中。

Kernel Dispatch Packet 包含：

* Kernel 可执行句柄；
* Grid 和 work-group 大小；
* Kernarg 地址；
* LDS/private memory 请求；
* Packet 内存序和 barrier 属性；
* 一个 completion signal。

它不包含：

* `cl_kernel` 或 Host C++ `Kernel` 对象；
* 任意长度的 OpenCL Event wait-list；
* `clk_event_t`、Parent/Child 关系或 Child 计数；
* Host callback、CL Command 状态或 submission batch；
* Queue 的 Ring base、rptr、wptr、doorbell、VMID 或优先级；
* Kernel 参数的所有权和回收策略；
* Global work offset；它通常由编译器 ABI 通过 hidden kernarg 传递。

**\[SOURCE]** CLR ROCr backend 在 `2.源码/rocm-clr/rocclr/device/rocm/rocvirtual.cpp:4139-4155` 中把 `KernelCodeHandle()`、global/local size、kernarg 地址、LDS 和 private-memory 大小写入 dispatch packet。

**\[SOURCE]** 同文件 `dispatchGenericAqlPacket()` 先预留 AQL Ring slot，等待空间，复制 packet payload，最后用 release publication 写入有效 header。AQL header 的 Invalid/有效 packet type 解决 Ring slot 的发布原子性，但它不是 `FREE/READY/BUSY/DONE` 这种完整任务生命周期。

## 3. Host `NDRangeKernelCommand` 是完整的软件任务对象

**\[SOURCE]** CLR 的 `Command` 定义在 `2.源码/rocm-clr/rocclr/platform/command.hpp:298`，继承自 `Event`；`NDRangeKernelCommand` 定义在同文件 :1313。

```text
Event
├── CL_QUEUED/SUBMITTED/RUNNING/COMPLETE 状态
├── callback 列表
├── profiling 时间戳
├── HwEvent / dependent HwEvents
└── Host waiter/notification 状态

Command
├── HostQueue*
├── cl_command_type
├── Event wait-list
├── next/batch-head 关系
├── command wait bits
└── backend 私有数据

NDRangeKernelCommand
├── Kernel& kernel_
├── NDRangeContainer sizes_
├── parameters_
├── sharedMemBytes_
└── cooperative/multi-device launch 属性
```

Host Command 回答的是“OpenCL 请求了什么以及 Runtime 如何管理它”，不是“CP 应该读取哪几个二进制字段”。它可以使用 C++ 对象、动态容器、Host 指针、锁、callback 和引用计数，因此不是稳定的 GPU ABI，也不会整体复制进 AQL Ring。

### 3.1 Host Command 如何收敛成 AQL

```text
NDRangeKernelCommand::kernel_
  -> Device Kernel / loaded symbol
  -> KernelCodeHandle()
  -> AQL.kernel_object

NDRangeKernelCommand::parameters_
  -> 分配并复制 kernarg buffer
  -> AQL.kernarg_address

NDRangeKernelCommand::sizes_.global/local
  -> AQL.grid_size/workgroup_size

Kernel metadata + sharedMemBytes_
  -> AQL.private_segment_size/group_segment_size

Host Event/HwEvent
  -> completion_signal，或额外的 AQL Barrier Packet
```

**\[INFERENCE]** 一次 Host `NDRangeKernelCommand` 不能机械理解为“整个对象变成一个 AQL packet”。Backend 只抽取一次 dispatch 的硬件启动信息；依赖、profiling、batch 和完成结算可能产生额外 Barrier/Marker packet，或继续保存在 Host Runtime。

## 4. `AmdAqlWrap` 是 Device 侧任务控制块

**\[SOURCE]** `AmdAqlWrap` 定义在 `2.源码/rocm-clr/rocclr/device/rocm/rocsched.hpp:37`：

```text
AmdAqlWrap
├── state
├── enqueue_flags
├── command_id
├── child_counter
├── completion
├── parent_wrap
├── wait_list
├── wait_num
├── reserved[5]
└── hsa_kernel_dispatch_packet_t aql
```

字段按职责分成两组：

| **组**               | **字段**                               | **回答的问题**            |
| ------------------- | ------------------------------------ | -------------------- |
| Device Runtime 管理信息 | `state`、`enqueue_flags`、`command_id` | 记录是否已预留、已发布、执行中或完成   |
| Parent/Child 完成图    | `child_counter`、`parent_wrap`        | Parent 是否仍有未收敛的后代    |
| Device Event 依赖     | `completion`、`wait_list`、`wait_num`  | Child 等待谁，完成后更新谁     |
| 最终硬件启动描述            | `aql`                                | 依赖满足后，CP 应如何执行 Child |

**\[INFERENCE]** 在当前 64-bit 字段布局中，前面的 Device Runtime metadata 合计 64 字节，embedded AQL 又是 64 字节，因此一个 Wrap 自然形成 128 字节布局。自研 ABI 若采用类似结构，仍应以显式 `static_assert(sizeof/offsetof)` 固化，而不能仅依赖 C++ 自然对齐。

`AmdAqlWrap` 的关键性质是：

```text
AmdAqlWrap = Device-Enqueue 语义信封 + embedded Child AQL
```

其中 `wait_list` 和每槽 kernarg 并不内嵌在 Wrap 中，而是指向 `virtualQueue_` backing allocation 内为该 slot 预留的区域。

### 4.1 生命周期为何不能只靠 AQL Ring slot 保存

```text
AmdAqlWrap:
FREE -> RESERVED -> READY -> BUSY -> DONE -> FREE

AQL Ring slot:
Invalid -> Published -> CP consumed -> reusable
```

Child packet 被 CP 取走后，AQL Ring slot 可以很快复用；但是 Device Runtime 仍要保存 Child completion、`AmdEvent`、`parent_wrap` 和 `child_counter`，直到整个 Parent/Child 子图收敛。因此，长生命周期的 Device-Enqueue 状态不能只存放在短生命周期的硬件 Ring slot 中。

## 5. 三种对象的逐语义映射

| **语义**             | **Host`NDRangeKernelCommand` / `Event`** | **`AmdAqlWrap`**                     | **AQL Kernel Dispatch Packet**    |
| ------------------ | ---------------------------------------- | ------------------------------------ | --------------------------------- |
| Kernel 身份          | `Kernel& kernel_`                        | 由 RuntimeHandle/kernel table 填入`aql` | `kernel_object`                   |
| 参数快照               | `parameters_`                            | 每槽 kernarg buffer                    | `kernarg_address`                 |
| Global size        | `sizes_`                                 | 写入 embedded`aql`                     | `grid_size_xyz`                   |
| Local size         | `sizes_`                                 | 写入 embedded`aql`                     | `workgroup_size_xyz`              |
| Global offset      | `sizes_`                                 | Hidden kernarg                       | 无直接字段                             |
| LDS/private memory | Kernel metadata +`sharedMemBytes_`       | 写入 embedded`aql`                     | segment-size 字段                   |
| API/Event 依赖       | `eventWaitList_`                         | `wait_list` / `wait_num`             | 无任意 wait-list                     |
| 软件任务状态             | CLR Event status                         | `state`                              | 仅有 Ring publication 的 packet type |
| Parent/Child 图     | Host Command/batch 对象                    | `parent_wrap` / `child_counter`      | 无                                 |
| API 完成对象           | CLR`Event`                               | `completion` / `AmdEvent`            | 不认识 OpenCL Event                  |
| 硬件完成通知             | `HwEvent` 转译                             | Scheduler 安排                         | `completion_signal`               |
| Callback           | CLR callback list                        | 无                                    | 无                                 |
| Profiling          | Host profiling object                    | `AmdEvent.timer[]`                   | signal/扩展机制                       |
| 数据结构性质             | Host 私有 C++ 对象                           | AMD 私有 GPU ABI                       | 标准 HSA GPU ABI                    |
| 直接消费者              | CLR backend                              | Device Scheduler                     | CP                                |

这张表体现了同一个收敛过程：

```text
丰富的软件任务语义
  -> readiness evaluator
  -> 最小硬件启动描述
```

Host 路径的 evaluator 是 Host Runtime/CLR backend；Device-Enqueue 路径的 evaluator 是 Scheduler Kernel。两条路径最终都向 CP 提交标准 AQL。

## 6. 两条数据路径在哪里相同、哪里不同

### 6.1 常规 Host Kernel

```text
clEnqueueNDRangeKernel
  -> NDRangeKernelCommand 保存 Kernel、NDRange、参数和 Event wait-list
  -> Host Runtime/Backend 判断依赖并准备 kernarg
  -> 构造 hsa_kernel_dispatch_packet_t
  -> 发布到 gpu_queue_ AQL Ring
  -> doorbell
  -> CP 根据该硬件 Queue 的 MQD 取包并执行
```

### 6.2 Device-Side Child Kernel

```text
enqueue_kernel
  -> Parent/Device Library 预期预留 AmdAqlWrap
  -> 捕获 Child kernarg
  -> 填写 embedded Child AQL
  -> 填写 wait-list、completion、parent 和 child bookkeeping
  -> release-publish AQL_WRAP_READY
  -> Scheduler 检查 Device Event readiness
  -> 将 ready wrap 中的 aql 发布到 schedulerQueue_ AQL Ring
  -> doorbell
  -> CP 根据该硬件 Queue 的 MQD 取包并执行
```

**\[BOUNDARY]** 本地源码能证明 `AmdAqlWrap` ABI、`virtualQueue_` allocation、hidden queue address handoff、`schedulerQueue_` 创建以及 Scheduler 参数；不能逐行证明 Device Library 如何填充每个字段，也不能逐行证明 Scheduler 如何 copy packet 和推进所有状态。因此上面 Parent/Device Library 和 Scheduler 内部步骤属于受 ABI 约束的实现解释。

### 6.3 两条路径在 CP 入口处汇合

```text
Host Command
  -> Host readiness evaluator
  -> gpu_queue_ 中的标准 AQL ---------+
                                         +-> CP -> execution engine
AmdAqlWrap
  -> Device readiness evaluator
  -> schedulerQueue_ 中的标准 AQL -----+
```

从 CP 的 Kernel Dispatch 入口看，Host Kernel 与 Child Kernel 都是 `hsa_kernel_dispatch_packet_t`。差异发生在 packet 进入硬件 Ring 之前，以及 completion 之后由谁维护更高层的软件状态。

## 7. 为什么 Device 侧不只写 AQL Packet

这不是因为 Device 侧不能构造 AQL。`AmdAqlWrap` 本身已经嵌入了标准 Child AQL；额外的 Wrap metadata 用来承载标准 dispatch packet 不表达的 OpenCL 语义。

如果 Parent 把所有 Child 直接放入 FIFO 硬件 Ring，会遇到：

1. `clk_event_t` 不是 HSA `completion_signal`，标准 dispatch packet 不保存任意 Device Event wait-list。
2. Ring 头部的 Child 依赖未满足时，后面的 ready Child 可能发生队头阻塞；如果前者的依赖又需要后者执行，甚至可能失去前向进展。
3. 多个 work-item/work-group 并发 enqueue 需要独立的 slot/event 分配和发布状态。
4. Parent 的完成条件包含 Child/Grandchild 子图，标准 dispatch packet 不保存 `parent_wrap` 和 `child_counter`。
5. 硬件 Ring slot 在 CP 取包后即可复用，不能作为长生命周期完成图的存储。

**\[INFERENCE]** `virtualQueue_` 的 slot pool 允许 Scheduler 跳过依赖未满足的 READY record，选择其他可运行 Child，再把最终 packet 推入 FIFO 硬件 Ring。

直接 Device-to-AQL 设计仍然可行，但必须满足至少一种条件：限制 Device Event、wait-list 和嵌套语义；由 firmware/CP 原生解释这些语义；或在 AQL Ring 外维护等价 side metadata。也就是说，直接写 AQL 可以改变状态放置位置，但不会消灭这些状态。

## 8. `AmdAqlWrap`、AQL Ring 与 MQD 的准确关系

MQD 不是另一种 AQL packet，也不是另一种 Wrap。它是 Queue 级控制状态。

**\[SOURCE]** GFX9 MQD 初始化路径位于 `2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_mqd_manager_v9.c:271`，其中把：

* `queue_address` 写入 `cp_hqd_pq_base_lo/hi`；
* `read_ptr` 写入 `cp_hqd_pq_rptr_report_addr_lo/hi`；
* `write_ptr` 写入 `cp_hqd_pq_wptr_poll_addr_lo/hi`；
* doorbell 写入 `cp_hqd_pq_doorbell_control`；
* VMID 写入 `cp_hqd_vmid`。

正确对象关系是：

```text
AmdAqlWrap::aql
  ~= AQL Ring 中的一条 Kernel Dispatch Packet

schedulerQueue_ / gpu_queue_
  ~= 由 MQD 描述并由 CP 消费的硬件 Queue

AmdVQueueHeader + AmdAqlWrap[]
  ~= Device Runtime 的提交记录池和依赖图

amd::DeviceQueue
  ~= OpenCL API/config 层的逻辑 on-device queue 对象
```

因此：

```text
virtualQueue_    -> CP 不读取 -> 不需要 MQD
gpu_queue_       -> CP 读取   -> 有对应的 KFD/MQD 状态
schedulerQueue_  -> CP 读取   -> 有对应的 KFD/MQD 状态
```

## 9. 最终记忆模型

```text
Host Command
  = Host 内存中的完整 OpenCL 任务对象
  = API 语义、依赖、状态、callback、profiling、Kernel 和参数

AmdAqlWrap
  = GPU 内存中的 Device-Enqueue 任务控制块
  = Device Event、Parent/Child 状态、slot 生命周期 + embedded AQL

AQL Kernel Dispatch Packet
  = 64 字节硬件启动描述
  = 执行谁、启动多大、参数在哪、资源多少、完成通知谁

MQD
  = 硬件 Queue 描述符
  = Ring 在哪、索引在哪、doorbell 是谁、属于哪个地址空间、如何调度
```

判断任意字段属于哪一层时，只问四个问题：

1. 它描述的是 API/依赖语义，还是已经 ready 的硬件执行？
2. 它的消费者是 Host Runtime、Scheduler，还是 CP？
3. 它的生命周期是一次 API Command、一次 Child record，还是整条硬件 Queue？
4. 它是 Host 私有对象、Device Runtime 私有 ABI，还是标准硬件 packet ABI？

回答这四个问题，就不会再把 Host Command、`AmdAqlWrap`、AQL packet、AQL Ring 和 MQD 混为同一个“队列对象”。
