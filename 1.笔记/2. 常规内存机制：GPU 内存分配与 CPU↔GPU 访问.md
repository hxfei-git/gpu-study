# 常规 GPU 内存分配与 CPU↔GPU 访问机制

> 本文讲**所有 GPU 通用的内存范式**：显式分配（device/host buffer）+ 显式搬运（copy/map）+ 显式同步。
> **SVM（共享虚拟内存）不是另一套体系，而是在常规机制之上的一种扩充**——它复用 BO/GPUVM/页表，
> 额外提供"共享 VA + 按需补页 + 迁移"。本文从 AMD 实现出发梳理常规路径；SVM 的扩充见
> [SVM 专题](<./9. AMD SVM：共享内存、统一地址空间与页面迁移.md>)。
>
> **前置地基**：如果 PFN、`struct page`、SG、DMA address、GEM、TTM、HMM 之间的层级还不清楚，
> 先读 [Linux 内存管理基础 2A](<./2A. Linux 内存管理基础：从物理内存、PFN 与 struct page 到 GEM、TTM、HMM.md>)。
> 本文重点使用这些对象串 API 和数据路径，不再重复它们的基础定义。

源码路径口径：CLR/OpenCL/HIP 位于 `2.源码/rocm-clr`，ROCr/libhsakmt 位于 `2.源码/rocr-runtime`，Linux AMDGPU/KFD/DRM/TTM 位于 `2.源码/linux`。固定版本见 [源码清单](<../2.源码/README.md>)；下文已把同名文件展开到完整仓库路径，避免把 CLR `memory.cpp`、libhsakmt `memory.c` 与 Linux `mm/memory.c` 混为一谈。

## 1. 定位：常规是地基，SVM 是扩充

两种内存访问范式：

```text
常规（显式）：CPU 内存和 GPU 内存是"两个域"，靠 API 搬运
  cl_mem / KFD alloc → BO（VRAM / GTT / host-pinned）
  CPU→GPU：WriteBuffer / map（SDMA 拷贝 / staging）
  GPU→CPU：ReadBuffer / map（读回）
  GPU 访问 host 内存：注册/pin → 映射进 GPUVM
  同步：queue order + event/fence

SVM（扩充）：CPU 和 GPU 是"一个地址空间"
  裸指针两端共享；编程模型层无显式拷贝
  底层机制可变：直接访问 host RAM / 页面迁移 / 显式 prefetch（见 §6.4）
  同步：fault 恢复 + coarse/fine-grain 一致性
```

**核心结论**：先有常规的 BO/GPUVM/页表/PDD 这套地基，SVM 才可能在其上加"共享地址 + fault 恢复"。
SVM 不是对常规的替代，而是对常规的**扩充**——它复用地基，只在"地址共享方式"和"数据搬运方式"上做增量。

## 2. 总框架：谁访问谁、怎么访问（定海神针）

理解 CPU↔GPU 内存的一切，先钉死这张表——**谁、访问哪块内存、用什么机制**。

### 2.1 访问矩阵

|               | 访问**RAM**（系统内存）                | 访问**VRAM**（显存）                                               |
| ------------- | -------------------------------------------- | ------------------------------------------------------------------------ |
| **CPU** | 正常（CPU MMU，不走 PCIe）                   | **经 BAR**（CPU 发起的 PCIe read/write TLP）——**不是 DMA** |
| **GPU** | **DMA**（GPU 发起，经 GPUMMU → PCIe） | 本地（快，不走 PCIe）                                                    |

三个关键认知：

1. **CPU 访问 VRAM = CPU 发起，不是 DMA**。DMA 这个词**只用在 GPU（设备）发起访问时**。
2. **GPU 访问 RAM 一定是 DMA**——设备绕过 CPU 直接访问 host 内存。
3. **任何内存访问最终都走 PCIe TLP**（CPU 经 BAR、GPU 经 DMA 都是），区别只在**谁发起**。

### 2.2 访问（读/写） vs 拷贝（读+写）

|              | 访问                          | 拷贝/搬运                                   |
| ------------ | ----------------------------- | ------------------------------------------- |
| 动作         | 对内存做**读或写**      | **读源 + 写目标** = 数据从 A 复制到 B |
| 例子         | CPU 读 VRAM；GPU 读 host 数据 | SDMA 把 VRAM 拷到 host                      |
| 有中间缓冲吗 | 无（直接）                    | 有（目的地缓冲）                            |

**"零拷贝"的含义**：没有中间缓冲（CPU 直接读 VRAM），**不是"数据不过 PCIe"**——数据仍物理地走总线（TLP），只是不经过 staging 这个中间站。

### 2.3 DMA 的定义：设备绕过 CPU

**DMA（Direct Memory Access）= 设备不经过 CPU，直接访问内存。**

- 关键词是"**设备**"和"**绕过 CPU**"。
- CPU 自己访问内存（哪怕经 BAR 到 VRAM）是 CPU 的本职，**不叫 DMA**——CPU 就是执行 load/store，没有"绕过自己"这回事。
- 所以这个不对称是**定义本身造成的**：DMA 专指"设备发起的、绕过 CPU 的访问"。

```text
CPU 访问任何内存（含 VRAM）   = 正常内存访问（CPU 是执行者）
GPU 访问任何内存（含 RAM）    = DMA（设备是执行者，绕过 CPU）
```

### 2.4 PCIe DMA vs SDMA

**不是竞争关系，是"能力层 vs 引擎层"：**

|        | PCIe DMA                                                 | SDMA                                     |
| ------ | -------------------------------------------------------- | ---------------------------------------- |
| 是什么 | **通用机制**：设备经 PCIe 总线访问 host 内存的能力 | **GPU 内专用拷贝引擎**             |
| 谁有   | 任何 PCIe 设备（GPU/NIC/NVMe）都有                       | GPU 内部的一个引擎                       |
| 做什么 | 设备发起读/写 TLP 到 host                                | 专门做"读 A → 写 B"的拷贝               |
| 关系   | 机制/能力层                                              | **建立在 PCIe DMA 之上**的拷贝服务 |

**GPU 里多个引擎都会 DMA 访问 RAM**（全是设备发起），SDMA 只是其中"拷贝专用"的那个：

| 引擎                       | 干什么                     | 访问 RAM 吗                 |
| -------------------------- | -------------------------- | --------------------------- |
| **CU（计算核心）**   | 跑 kernel，load/store 指令 | ✅ 经 GPUMMU → PCIe（DMA） |
| **SDMA（拷贝引擎）** | 专门做拷贝（读源+写目标）  | ✅ 拷贝专用                 |
| **CP/MEC**           | 读队列 ring、取 AQL 包     | ✅                          |

**证据**（GPU 页表能指向系统内存）：`2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_vm.c` 模块说明原文——"GPUVM page tables can contain a mix of VRAM pages and system pages"、"GPU clients (i.e., engines on the GPU) use GPUVM VMIDs to access memory"；`2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_ttm.c:1441` 对 GTT/系统内存 BO 打 `AMDGPU_PTE_SYSTEM` 标记。所以 CU/CP/SDMA 访存走 GPUVM，遇到 SYSTEM PTE 就把请求路由到 PCIe → RAM。

### 2.5 CPU 直接访问 GPU 内存（BAR）

```text
CPU load/store → CPU MMU → BAR 窗口 → PCIe read/write TLP → VRAM
```

**核心认知**：VRAM 是被访问的资源，BAR 是 CPU 访问它的**窗口**。**Large BAR 和 Small BAR 的区别不是"有没有 BAR"，而是"CPU 能通过 PCIe BAR 一次性看到多少 VRAM"。**

**Large BAR**（Resizable BAR 配置成覆盖全部/大部分 VRAM）：CPU 把整个或大部分 VRAM 放进自己的 PCIe MMIO 地址空间 → 直接读/写 VRAM（零中间缓冲，数据仍过 PCIe，**不需要 staging**）。

**Small BAR（非 large BAR）**：只暴露一个小 aperture（如 256MB），CPU 不能一次覆盖整个 VRAM。驱动访问 VRAM 数据有**三条路径**（不是只有 staging）：

```text
① aperture remap    移动 BAR 窗口指向不同 VRAM 区域（早期窗口机制）
② staging buffer    SDMA 拷到 host 可见缓冲（§5.1 机制 B）
③ page migration    把 VRAM 页迁到 host RAM 再访问
```

具体走哪条取决于 GPU、驱动和内存模型；② staging 的**完整链路见 [§5.1](#51-cpu-直接访问-gpu-内存map完整调用链-两条机制)**。

**一句话**：Small/Large BAR 的本质区别 = **"CPU 能通过 PCIe BAR 一次性看到多少 GPU VRAM"**，不是"有没有 PCIe BAR"。**注意：即使是 Large BAR，"一次性看到"也只是地址可翻译，CPU 每次 load/store 仍经 PCIe TLP 逐次完成，不是批量搬运。**

**更精确的直访条件**：CPU 能否直访某个 VRAM buffer，**不是"是否全 BAR 映射"，而是"buffer 是否落在当前 CPU 映射的窗口（BAR/aperture）里"**：

| 情况                       | 能否直访                        |
| -------------------------- | ------------------------------- |
| 大 BAR（全部 VRAM 在窗口） | 任意 buffer 都能直访            |
| 小 BAR，buffer 在窗口内    | 能（不需 staging）              |
| 小 BAR，buffer 在窗口外    | 不能 → staging / 换窗口 / 迁移 |
| PersistentDirectMap        | 该 buffer 能（专门持久映射）    |

**所以"直访"不是全有或全无，而是窗口粒度问题**——窗口内直访、窗口外 staging。CPU 直访 VRAM 的唯一机制就是 PCIe BAR 窗口（GTT 是系统内存，不算此列）。

## 3. 内存分配域（常规）

| 域                                 | 物理位置                 | GPU 访问                                           | CPU 访问                          | AMD 对应                                                      |
| ---------------------------------- | ------------------------ | -------------------------------------------------- | --------------------------------- | ------------------------------------------------------------- |
| **VRAM（device-local）**     | 设备本地                 | 快（本地）                                         | 经 BAR（大 BAR 直映射）或 staging | `AMDGPU_GEM_DOMAIN_VRAM`                                    |
| **GTT（系统内存）**          | 系统 RAM                 | 经 PCIe DMA（GART 窗口，**GPU→host 方向**） | 直接                              | `AMDGPU_GEM_DOMAIN_GTT`                                     |
| **host-pinned / registered** | 系统 RAM（用户已有页面） | USERPTR 注册后经 GPUVM 映射                        | 直接                              | `KFD_IOC_ALLOC_MEM_FLAGS_USERPTR` / `CL_MEM_USE_HOST_PTR` |

**\[SOURCE]** `cl_mem` 的四种常见 Flag 决定 backing 形态（详见 SVM 专题 §4.2）：

| 创建方式                  | 应用 pointer 的角色          | backing 候选                               |
| ------------------------- | ---------------------------- | ------------------------------------------ |
| 默认`CL_MEM_READ_WRITE` | 无 host pointer              | GPU memory pool（VRAM），失败回退系统内存  |
| `CL_MEM_COPY_HOST_PTR`  | 只作初始数据源               | 建 device backing 后复制，不保留原 pointer |
| `CL_MEM_USE_HOST_PTR`   | 应用提供并保留 backing       | register/pin 后映射进 GPUVM                |
| `CL_MEM_ALLOC_HOST_PTR` | Runtime 分配 host-accessible | host pool allocation + 允许 GPU 访问       |

**关键认知**：device pool / host pool 描述的是"首选位置 + 可访问性"，**不表示绕过 GPU 页表**。
任何域进入 GPUVM 都要走 KFD 分配 + 映射（见 §7）。

**方向区分（容易混的点）**：

- **PUBLIC VRAM / large BAR** = **CPU→GPU 内存**方向（CPU 访问 VRAM）。
- **GTT** = **GPU→host 内存**方向（GPU 经 PCIe 访问系统 RAM）。
- 两者方向相反。GTT 的意义是"GPU 直接读/写 host 数据"（省一次拷贝）和"GPU 把结果写回 host"（小 BAR 上 CPU 拿 GPU 结果的 staging 路径），**不是让 CPU 访问 GPU 内存**。

### 3.1 内存分配 flag 全解析（GTT / pin / USERPTR / cl_mem flags）

**KFD 的三个内存域是不同的 flag（2.源码/linux/include/uapi/linux/kfd_ioctl.h:414-418），不是包含关系：**

```c
KFD_IOC_ALLOC_MEM_FLAGS_VRAM      (1<<0)   // VRAM：GPU 本地显存
KFD_IOC_ALLOC_MEM_FLAGS_GTT       (1<<1)   // GTT：系统内存映射进 GPUVM（驱动分配）
KFD_IOC_ALLOC_MEM_FLAGS_USERPTR   (1<<2)   // USERPTR：用户提供的 host 指针（pin）
KFD_IOC_ALLOC_MEM_FLAGS_DOORBELL  (1<<3)
KFD_IOC_ALLOC_MEM_FLAGS_MMIO_REMAP(1<<4)
```

**GTT ≠ pin（关键区分，内核证据）**：

|          | GTT                | pin（USERPTR）                 |
| -------- | ------------------ | ------------------------------ |
| KFD flag | `GTT` (1<<1)     | `USERPTR` (1<<2)             |
| backing  | 驱动分配的系统内存 | **用户提供的** host 指针 |
| 谁分配   | 驱动               | 用户已分配好                   |
| 内核路径 | `2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_amdkfd_gpuvm.c:1749` | `2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_amdkfd_gpuvm.c:1757` |

**GTT 是"GPU 侧看到的 backing 域"（系统内存映射进 GPUVM）；pin 是"host 页是否被固定"（OS 不能换出/迁移）。不同 flag、不同路径。** 但 GTT 需要稳定 host 页，实现中常涉及 pin——**相关但不相等**。

**USE_HOST_PTR / ALLOC_HOST_PTR ≠ GTT**：它们是不确定 backing 的 OpenCL 语义，runtime 按实现选：

- `CL_MEM_ALLOC_HOST_PTR`：runtime 分配 host 可访问 backing（可能 GTT / host pool）。
- `CL_MEM_USE_HOST_PTR`：用户提供指针 → USERPTR/pin。
- **不等于"都是 GTT"**——runtime 可走 host/GTT/staging/VRAM 多种方案（libhsakmt 的 `hsakmt_fmm_allocate_host` 与 `hsakmt_fmm_allocate_device` 分流，分别见 `2.源码/rocr-runtime/libhsakmt/src/memory.c:186` 与同文件 `:207`）。

**KFD alloc flag 属性位（2.源码/linux/include/uapi/linux/kfd_ioctl.h:420-428）**：

```c
WRITABLE      (1<<31)   // 可写
EXECUTABLE    (1<<30)   // 可执行
PUBLIC        (1<<29)   // host 可见（大 BAR 才允许 VRAM PUBLIC）
NO_SUBSTITUTE (1<<28)
AQL_QUEUE_MEM (1<<27)
COHERENT      (1<<26)   // 一致性
UNCACHED      (1<<25)
EXT_COHERENT  (1<<24)
CONTIGUOUS    (1<<23)   // 连续
```

**完整分流**：`hsaKmtAllocMemoryAlign`（`2.源码/rocr-runtime/libhsakmt/src/memory.c:115`）→ 系统内存路径 `hsakmt_fmm_allocate_host`（GTT/USERPTR）或 VRAM 路径 `hsakmt_fmm_allocate_device` → KFD ioctl 按 VRAM/GTT/USERPTR flag 走不同内核路径。

**分配 API → 汇聚点 → KFD 域（CL/HIP 到 KFD 的完整地图）**：

```text
hipMalloc / hipHostMalloc / hipMallocManaged / clCreateBuffer / clSVMAlloc
  → SvmBuffer::malloc / Context::svmAlloc（2.源码/rocm-clr/rocclr/platform/memory.cpp:1528 / 2.源码/rocm-clr/rocclr/device/rocm/rocdevice.cpp:2341）
  → amd::Buffer::create（2.源码/rocm-clr/rocclr/device/rocm/rocmemory.cpp:771，★ 按 cl_mem_flags 选 backing 的闸门）
       ├─ 默认/device    → deviceLocalAlloc（VRAM）→ KFD_VRAM
       ├─ ALLOC_HOST_PTR → hostAlloc（host pool）  → KFD_GTT
       ├─ USE_HOST_PTR   → 用户提供的指针          → KFD_USERPTR（pin）
       └─ SVM/fine-grain → SVM 路径                → KFD_SVM
  → hsaKmtAllocMemory（2.源码/rocr-runtime/libhsakmt/src/memory.c:107）
  → hsakmt_fmm_allocate_device（VRAM）或 hsakmt_fmm_allocate_host（GTT/USERPTR）
  → KFD_IOC_ALLOC_MEMORY_OF_GPU（按 flag 走不同内核路径）
```

| API                                            | backing          | KFD flag     |
| ---------------------------------------------- | ---------------- | ------------ |
| hipMalloc / clCreateBuffer(默认)               | VRAM             | `VRAM`     |
| hipHostMalloc / clCreateBuffer(ALLOC_HOST_PTR) | host pool / GTT  | `GTT`      |
| hipHostRegister / clCreateBuffer(USE_HOST_PTR) | 用户指针（pin）  | `USERPTR`  |
| hipMallocManaged / clSVMAlloc                  | SVM / fine-grain | `SVM` 路径 |

**USERPTR ≠ GTT（再厘清）**：两者最终都会得到 `ttm->pages[]` 和 `ttm->dma_address[]`，但页面来源相反：

- USERPTR：先有用户 CPU VA 和页面；HMM 从 CPU 页表取得 PFN，再转成 `struct page`。
- GTT：先创建 BO；TTM 从 system RAM/TTM pool 分配 `struct page`，再 mmap 给用户。

`hsaKmtRegisterMemory` 是 libhsakmt API 名称；当前 KFD UAPI 中，常规 USERPTR 注册落到
`KFD_IOC_ALLOC_MEMORY_OF_GPU + KFD_IOC_ALLOC_MEM_FLAGS_USERPTR`，真正写进程 GPUVM 则是另一次
`AMDKFD_IOC_MAP_MEMORY_TO_GPU`。所以“取得/稳定页面”和“写 GPU PTE”仍是两个阶段，详见 §6.2。

**两种 pin（host 页 vs GPU BO，机制不同）**：

|          | Host 页 pin                         | GPU BO pin（`amdgpu_bo_pin`）         |
| -------- | ----------------------------------- | --------------------------------------- |
| 对象     | host 物理页                         | GPU BO（VRAM/GTT）                      |
| 管理者   | OS 虚拟内存（mlock/get_user_pages） | **TTM**（内存管理器）             |
| 防止什么 | OS 把页换出/迁移                    | **TTM 把 BO 在 VRAM↔GTT 间移动** |
| 作用     | 物理地址稳定                        | 锁在指定域 +（GTT）绑定进 GART          |

**GPU BO pin（`amdgpu_bo_pin`，2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_object.c:932）何时用**——防止 TTM evict/move、保证硬件/固件稳定访问：

| 场景           | 示例                                                           |
| -------------- | -------------------------------------------------------------- |
| 显示/扫描输出  | DCE framebuffer 必须常驻 VRAM（`2.源码/linux/drivers/gpu/drm/amd/amdgpu/dce_v6_0.c`、`2.源码/linux/drivers/gpu/drm/amd/amdgpu/dce_v8_0.c`、`2.源码/linux/drivers/gpu/drm/amd/amdgpu/dce_v10_0.c`） |
| 编解码固件     | UVD/VCE/VCN 的 buffer 常驻 VRAM（`2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_uvd.c`）                |
| KFD 稳定内存   | KFD 分配的 GPU 内存（2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_amdkfd_gpuvm.c:1534）              |
| KFD GTT 工作区 | gtt_mem（MQD/runlist）pin 到 GTT（2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_amdkfd_gpuvm.c:2244） |
| 门铃/MES 队列  | doorbell / MES wptr pin 保稳定（`2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_userq.c` / `2.源码/linux/drivers/gpu/drm/amd/amdgpu/mes_userqueue.c`） |

**共同点**：需要硬件/固件**持续稳定访问、不能被打断**（evict/移动）的 BO 才 pin。对于
GTT BO，`amdgpu_bo_pin` 的重点是阻止 TTM 迁移/换出并保持 GART resource 稳定；它不等价于
“对用户页执行一次 GUP/`mlock`”。USERPTR 页面有效性由 HMM/notifier 路径管理，二者不要混为一种 pin。

## 4. 数据通路一：拷贝（搬运）

拷贝 = 数据被复制到另一个物理位置。由 GPU 侧引擎（SDMA 或 CU）执行。

### 4.1 CPU → GPU（WriteBuffer）

```text
写数据到 GPU：
  clEnqueueWriteBuffer → queue command → SDMA copy（或 shader copy）
  → 数据从 CPU 内存搬进 GPU 内存 → event 完成
```

### 4.2 GPU → CPU（ReadBuffer）

```text
读回数据：
  clEnqueueReadBuffer → queue command → SDMA copy
  → 数据从 GPU 内存搬回 CPU 内存 → event 完成
```

**GPU→CPU 方向的一致性关键**：拷贝完成后，GPU 侧要 flush（L2/HDP）再写 completion signal，
CPU 才能安全读。所需动作取决于数据路径和 ASIC：关键约束是先完成对应 cache/内存域的可见性操作，再以 release 顺序发布 completion；不能把所有平台都简化成固定的 L2/HDP flush（见 [自研 GPU 设计 §3.3/3.5](<./12. 自研 GPU 设计：MCU-CP、内存交互与设备调度.md>)）。

### 4.3 拷贝：从 API 到引擎的完整链路（blit 引擎）

**什么是 blit**：blit 源自图形学的 BitBLT（bit block transfer，块传输）——早期指"把一屏像素块搬走"。GPU 驱动把它泛化为**所有内存拷贝/搬移操作**（buffer copy、image copy、fill 等）。ROCclr 的 `BlitManager`（及子类 Host/Dma/KernelBlitManager）就是**拷贝管理器**：它统一处理这些操作，并把每个拷贝派发给合适的引擎（SDMA/shader/CPU）。**blit 不是某个引擎，是"决定用哪个引擎搬数据"的那一层。**

**完整链路（框架）**——拷贝的 **read（D2H）和 write（H2D）** 两条路径，从 CL/HIP 接口追到引擎。用缩进嵌套表示递进（每层调用下一层、层层深入，不是平级）。

【读 D2H】：

```text
clEnqueueReadBuffer（2.源码/rocm-clr/opencl/amdocl/cl_memobj.cpp:577）                ─┐
```

**关键认知（read/write 同构）**：

- **方法选择在 submitReadMemory/submitWriteMemory**：按另一端类型选 copyBuffer（内存对象）或 readBuffer/writeBuffer（裸指针）。
- **执行在 blitMgr_**（KernelBlitManager 选路器）：内部再分 CPU/SDMA/shader。
- **继承**：KernelBlitManager ⊃ DmaBlitManager ⊃ HostBlitManager——每层一个版本，执行最派生 override。
- 缩进越深 = 调用栈越深：接口 → 命令 → 设备（选方法）→ 拷贝机（选路器）→ 引擎。
- **map（CPU 直访）不在这节**——它是"直接访问"而非"拷贝"，完整链路见 §5.1。

**一个接口，三种实现（链路的骨架）**：三条路径**不是三个割裂的机制**，而是同一个 `BlitManager` 接口下的三种实现。类层级：

```text
BlitManager（基类接口，2.源码/rocm-clr/rocclr/device/blit.hpp:22）
  └─ HostBlitManager（2.源码/rocm-clr/rocclr/device/blit.hpp:252）← CPU memcpy
       └─ DmaBlitManager（2.源码/rocm-clr/rocclr/device/rocm/rocblit.hpp:30）         ← SDMA（hsa_amd_memory_async_copy）
            └─ KernelBlitManager（2.源码/rocm-clr/rocclr/device/rocm/rocblit.hpp:294）← shader（copy kernel）
```

ROCm 实例化 `KernelBlitManager`（2.源码/rocm-clr/rocclr/device/rocm/rocvirtual.cpp:1890），一个对象同时具备三种能力；UMD 统一走 `blitMgr().xxx` 同一入口，内部按条件选引擎。

**三条引擎路径**：

| 路径                     | 谁搬                                          | 特点                                              |
| ------------------------ | --------------------------------------------- | ------------------------------------------------- |
| **SDMA 引擎**      | 专用 DMA 硬件，独立 ring                      | 快、异步、**不占 CU**                       |
| **CU/shader 拷贝** | CUs 跑 copy kernel（`dst[i]=src[i]`）       | **占计算资源**，但灵活（可边拷边转换/填充） |
| **CPU 拷贝**       | host`memcpy`（先 cpuMap 成 CPU 可见，再搬） | 占 host，慢                                       |

**引擎选路分歧**（`DmaBlitManager::readBuffer`，2.源码/rocm-clr/rocclr/device/rocm/rocblit.cpp:38）：

```c
if (blocking_blit_ && (disableReadBuffer_ ||
    (srcMemory.isHostMemDirectAccess() && !srcMemory.isCpuUncached()))) {
  return HostBlitManager::readBuffer(...);   // ← CPU 拷贝（大 BAR）
}
// else → hsaCopyStagedOrPinned(...)          ← SDMA（非直访）
```

**规则**：CPU 能直接访问（大 BAR）→ CPU 搬；CPU 摸不到（非大 BAR）→ SDMA。因为 CPU 直访时用 load/store 直接读更省（不用提交 SDMA 命令 + 等异步 fence）。

**readBuffer vs copyBuffer 不是引擎区别（关键正交修正）**：readBuffer/copyBuffer 是"**目标类型**"（裸 host 指针 vs 内存对象），SDMA/CPU/shader 是独立的"**引擎**"维度，两者交叉：

|                         | 目标 = 裸 host 指针（readBuffer）                | 目标 = 内存对象（copyBuffer）       |
| ----------------------- | ------------------------------------------------ | ----------------------------------- |
| **引擎 = CPU**    | `cpuMap`+`memcpy`（大 BAR 直访）             | host memcpy 兜底                    |
| **引擎 = SDMA**   | **pin 裸指针 + `hsaCopyStagedOrPinned`** | `hsa_amd_memory_async_copy`       |
| **引擎 = shader** | 少见                                             | `shaderCopyBuffer`（copy kernel） |

**readBuffer 本质也是一种 copy**（把 GPU 数据拷到 host），区别只在"目标怎么准备"：裸指针要 pin/cpuMap，内存对象直接 GPUVM 可用。**之前把两个维度压成一个（readBuffer=CPU、copyBuffer=SDMA）是错的，特此修正。**

**各引擎实现细节**：

CPU 拷贝（`HostBlitManager::readBuffer`，2.源码/rocm-clr/rocclr/device/blit.cpp:19）：

```c
HostBlitManager::readBuffer(srcMemory, dstHost, ...) {
  void* src = srcMemory.cpuMap(vDev_, CpuReadOnly);  // ① 拿到 GPU 内存的 CPU 可见地址
  std::memcpy(dstHost, src + origin[0], size[0]);    // ② CPU load/store 直接搬（经 BAR）
  srcMemory.cpuUnmap(vDev_);                         // ③ 解除映射
}
```

cpuMap 拿到什么（`Memory::allocMapTarget`，2.源码/rocm-clr/rocclr/device/rocm/rocmemory.cpp:104）：

```c
if (isHostMemDirectAccess())          // 直访（大 BAR）
  return (char *)deviceMemory_;       // ★ GPU 内存的 CPU 可见地址（经 BAR 摸到 VRAM）
if (IsPersistentDirectMap())
  return persistent_host_ptr_;
// 非直访：分配 host 可见 staging 缓冲
allocateMapMemory(size);              // mapMemory_ = staging buffer
return mapMemory_->getHostMem();      // ★ staging 的 host 指针（先 SDMA 拷进去）
```

→ cpuMap 拿到的**不是裸 PA**，而是驱动建好的"能摸到 GPU 物理内存的 CPU 虚拟地址"：

- **直访（大 BAR）**：`deviceMemory_`——GPU 物理内存经 BAR 映射到 CPU 地址空间的地址，CPU 直接读。
- **非直访**：新分配的 **staging 缓冲**——它在**系统内存**（`CL_MEM_ALLOC_HOST_PTR` → host pool），CPU 直接访问、GPU 经 GPUVM 访问（两端可访问）。

**关键：staging 的"两端可访问"只对目标（dst）成立；拷贝要读的源（src = GPU 内存/VRAM）CPU 仍然碰不到。** 所以进入 `blitMgr().readBuffer(src=GPU内存, dst=staging)` 后，`isHostMemDirectAccess()` 判断的是 **src**（GPU 内存）——src 在 VRAM、CPU 不可直访 → **触发 SDMA**（GPU 读自己 VRAM、写 staging）。只有 src 也可直访（大 BAR）时才走 CPU memcpy。

CU 拷贝（"GPU 自己搬内存"）：copy kernel 派发到 compute 队列，每个 work-item 做 `load src → store dst`。如果 src/dst 在系统内存，CU 的 load/store 经 **GPU MMU 被翻译成 PCIe DMA 事务**——GPU 用自己的访存指令（经 MMU→PCIe）替 CPU 完成了 memcpy。

```text
copy kernel: out[i] = in[i]      // 每个 work-item 搬一个/几个元素
  → 派发到 compute 队列（AQL dispatch 包）
  → CU 并行：load（经 MMU→PCIe 读系统内存）→ store（经 MMU 写）
  → 成千上万 work-item 并行 = 一次 memcpy
```

SDMA 拷贝：`DmaBlitManager` → `hsa_amd_memory_async_copy` → SDMA ring（拷贝描述符）→ SDMA 引擎。

**SDMA 描述符谁写**：

- **通常 CPU 写**（驱动栈）：UMD 请求 → 内核驱动 `amdgpu_emit_copy_buffer` 把拷贝塞进 IB → 写 SDMA ring → wptr → doorbell。
- **内核驱动也会主动下发**：迁移（`svm_migrate_copy_memory_gart`）、页表更新（amdgpu_vm_sdma）、ttm 拷贝——都是 CPU 侧内核态写描述符。
- **GPU 自己写**：理论可行（SDMA ring 就是内存 + doorbell，GPU shader 能写 + 敲，= device-enqueue 机制），但 ROCm 的 device-enqueue 主要让 GPU 写 **compute 队列的 AQL**，**SDMA ring 的标准提交方是 CPU**。

**结论**：上层 API 只管"我要拷贝这段数据"，选引擎是 blit 管理器的策略——对 UMD 完全透明。**AMD 是一套后端，CL/HIP 在命令层（`amd::ReadMemoryCommand`）就汇合**，之后共用同一套后端（这是"一个接口三种实现"的最强证据）。

### 4.4 拷贝的全栈追踪（UMD → ROCr → libhsakmt → KFD）

> 本节是对 §4-§6 所有传输路径（Pin / Staging / SVM）的统一落点总结，**可先跳过，读完 §5-§6 再回来看**。

| 路径                   | UMD（CLR/HIP）                                         | ROCr API                                           | libhsakmt                | KFD ioctl → KMD 内部                                                                                             |
| ---------------------- | ------------------------------------------------------ | -------------------------------------------------- | ------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| **USERPTR/注册** | `clCreateBuffer(USE_HOST_PTR)` / `hipHostRegister` | `hsa_amd_memory_lock`（注册）                    | `hsaKmtRegisterMemory` | `KFD_IOC_ALLOC_MEMORY_OF_GPU(USERPTR)` → HMM 收集页面 + DMA map；随后 `KFD_IOC_MAP_MEMORY_TO_GPU` → GPU PTE |
| **Staging**      | `clEnqueueWriteBuffer`（普通 malloc）                | `hsa_amd_memory_pool_allocate`（staging buffer） | `hsaKmtAllocMemory`    | `KFD_ALLOC_MEMORY_OF_GPU` → staging BO → 拷贝 host→staging→device                                           |
| **SVM**          | `clSVMAlloc` / `clSetKernelExecInfo(SVM_PTRS)`     | `hsa_amd_svm_attributes_set`                     | `hsaKmtSVMSetAttr`     | `KFD_SVM`（kfd_ioctl_svm）→ `svm_range_set_attr` → mmu_notifier → fault 恢复                               |

**KMD 内部落点**：

```text

        → 两次拷贝（host→staging→device），host 本身不建映射

        → GPU fault → svm_range_restore_pages → HMM 收页 → dma_map → 写 GPU 页表 → retry
```

## 5. 数据通路二：直接访问（map / 注册）

直接访问 = 一方直接读写另一方的内存，无中间缓冲（但数据仍过 PCIe）。

**方向澄清（两个方向的主动方不同）**：

- **方向 A：CPU 主动 → GPU 内存**（本节的 map、以及 §4 的拷贝）——显式、API 驱动，CPU 发起。
- **方向 B：GPU 主动 → CPU 内存**（§5.2 的准备 + kernel 执行时的访问）——隐式，**实际访问发生在 GPU kernel 执行时**（CU 直接访存 GTT/SVM，见 §6.5），注册/pin 只是准备。

**本节的 map（§5.1）是方向 A（CPU 主动操作 GPU 内存）**；§5.2 是方向 B 的"准备"（建立 GPUVM 映射），真正的 GPU 访问发生在 kernel 执行时。

### 5.1 CPU 直接访问 GPU 内存（map）——完整调用链 + 两条机制

**完整调用链**（map 是"直接访问"命令，不走 §4 拷贝的 blitMgr 选路）：

```text
【CL】clEnqueueMapBuffer（2.源码/rocm-clr/opencl/amdocl/cl_memobj.cpp:3025）
  → Memory::allocMapTarget（2.源码/rocm-clr/rocclr/device/rocm/rocmemory.cpp:104）—— ★ 预分配 map 目标（决定直访还是 staging）
  → new amd::MapMemoryCommand(CL_COMMAND_MAP_BUFFER)
  → submit(device) → device.submitMapMemory()
  → VirtualGPU::submitMapMemory（2.源码/rocm-clr/rocclr/device/rocm/rocvirtual.cpp:3087）
       ├─ 直访（getHostMem() != nullptr）→ cacheWriteBack + addVACache → 直接返回 GPU 内存地址
       ├─ PersistentDirectMap → NOP（已持久映射，直接返回）
       └─ staging → blitMgr().readBuffer / copyBuffer（把数据拷进 staging）
  → CPU 用返回的指针读写
【unmap】clEnqueueUnmapMemObject → UnmapMemoryCommand → submitUnmapMemory（2.源码/rocm-clr/rocclr/device/rocm/rocvirtual.cpp:3186）
  → staging 时 blitMgr().writeBuffer（同步回 GPU 内存）
```

**重要区分**：`cpuMap`（2.源码/rocm-clr/rocclr/device/rocm/rocmemory.cpp:172）是 **HostBlitManager 的内部工具**（CPU 拷贝引擎用来拿 CPU 可见地址），**不是 map 命令的实现路径**——map 命令走的是上面 `submitMapMemory` 的三分支。`cpuMap` 的细节见 §4.3 的 CPU 拷贝引擎。

**HIP 说明**：HIP 没有 `clEnqueueMapBuffer` 的直接等价——CPU 访问 GPU 内存用 `hipMemcpy`（拷贝）或 `hipMallocManaged`（SVM）。map 是 CL 特有的经典 API。

**返回的 host 指针有两种底层机制**（由 `allocMapTarget` 预分配时决定）：

**机制 A：直接映射（大 BAR / persistent direct map）——两边访问同一物理地址**

```text
map 时：mapTarget 直接指向 GPU 物理内存（经 BAR，CPU 页表 → BAR 窗口 → VRAM）
unmap 时：不拷贝
→ CPU（经 CPU 页表）和 GPU（经 GPUVM）访问同一块 VRAM 物理内存
```

**机制 B：staging 拷贝（非大 BAR）——SDMA 拷到 host，unmap 同步回**

```text
map 时：allocMapTarget（host 可见缓冲）→ blitMgr().readBuffer（SDMA 拷 GPU→staging）
host 读写 staging
unmap 时：blitMgr().writeBuffer（SDMA 拷 staging→GPU，同步回）
```

**代码证据**：机制 A/B 的实现在 §4.3 的 CPU 拷贝引擎（`HostBlitManager` 封装的 `cpuMap`/`cpuUnmap`，分别见 `2.源码/rocm-clr/rocclr/device/rocm/rocmemory.cpp:172` 与同文件 `:193`）——map 命令的 staging 分支调 `blitMgr().readBuffer` 时会走到它。完整代码与"src 判断"见 §4.3。

**一句话**：**大 BAR（或 persistent direct map）→ 直接映射，map/unmap 都不拷；非大 BAR → staging，map 时 SDMA 拷过来、unmap 时拷回去。**

### 5.2 GPU 访问 CPU 内存的准备（注册/pin）

**这是方向 B 的“准备”**：先让驱动认识现有 CPU VA 对应的页面，再把这些页面映射进目标
GPUVM。真正的读写发生在 GPU kernel 执行时（CU load/store 经 GPUVM 和 PCIe 访问 RAM），
不是注册 API 本身。

当前 ROCr/libhsakmt + KFD 的常规 USERPTR 路径是：

```text
CL_MEM_USE_HOST_PTR / hipHostRegister / hsaKmtRegisterMemory
  → AMDKFD_IOC_ALLOC_MEMORY_OF_GPU(flags=USERPTR)
  → mmap_offset 字段作为输入，携带已有 CPU VA
  → HMM 遍历 CPU 页表：CPU VA → hmm_pfns[] → struct page[]
  → SG + dma_map_sgtable() → dma_address[]
  → AMDKFD_IOC_MAP_MEMORY_TO_GPU
  → amdgpu_vm_bo_map() 记录 GPUVA 区间
  → amdgpu_vm_bo_update() 把 dma_address[] 写入 GPU PTE
  → GPU 可访问这批原有 host page
```

这里没有独立的 REGISTER_MEMORY 类 KFD ioctl。`hsaKmtRegisterMemory` 是用户态
libhsakmt API；到 KFD UAPI 后，注册由 `ALLOC_MEMORY_OF_GPU(USERPTR)` 表达，GPUVM 映射由
`MAP_MEMORY_TO_GPU` 表达。

**与 SVM 的区别**：常规 USERPTR 要显式注册、显式 map 并管理生命周期；SVM 可以在 GPU fault
后按需收集页面、补 GPU PTE。两者都可能使用 HMM，但触发时机和生命周期不同。

## 6. 地址翻译与页表建立（GPUVA vs CPU VA）

### 6.1 核心纠正：GPU 拷贝不直接用原始 CPU 虚拟地址

runtime 在派发前把 CPU VA 翻译成 GPUVA，kernel 拿到的都是设备可见地址。

### 6.2 让 host 内存对 GPU 可见的路（何时建页表）

先纠正“分配”和“映射”容易混在一起的地方：

| 阶段            | USERPTR BO                                                      | GTT BO                                       |
| --------------- | --------------------------------------------------------------- | -------------------------------------------- |
| backing 从哪来  | 用户原有 CPU VMA/page                                           | TTM 从 system RAM/TTM pool 分配 page         |
| BO 分配时做什么 | HMM 收集页面并建立 DMA mapping                                  | 创建`ttm_tt`、分配 page 并建立 DMA mapping |
| 何时记录 GPUVA  | `amdgpu_vm_bo_map()`                                          | `amdgpu_vm_bo_map()`                       |
| 何时写 GPU PTE  | `AMDKFD_IOC_MAP_MEMORY_TO_GPU` 后的 `amdgpu_vm_bo_update()` | 同左                                         |
| PTE 地址来源    | `ttm->dma_address[]`                                          | `ttm->dma_address[]`                       |

因此，GTT BO 的**物理 backing 可以在 BO create/validate 时建立**，但进程 GPUVM PTE 仍由
`MAP_MEMORY_TO_GPU` 阶段建立，不能把“有 backing”与“已经映射进某个进程 GPUVM”混为一谈。

#### 6.2.1 USERPTR BO：从已有 CPU VA 找到同一批页面

USERPTR 不是通过 `remap_pfn_range()` 找 PFN。用户态先把原 CPU VA 作为
`mmap_offset` 输入字段传给 KFD：

```text
libhsakmt hsakmt_fmm_allocate_host()
  mmap_offset = (uint64_t)mem
  flags |= KFD_IOC_ALLOC_MEM_FLAGS_USERPTR
  → AMDKFD_IOC_ALLOC_MEMORY_OF_GPU
```

KFD 在 `amdgpu_amdkfd_gpuvm_alloc_memory_of_gpu()` 中取出 `user_addr`，随后：

```text
init_user_pages()
  → amdgpu_ttm_tt_get_user_pages()
  → amdgpu_hmm_range_get_pages()
  → hmm_range_fault()
```

`amdgpu_hmm_range_get_pages()` 设置 `HMM_PFN_REQ_FAULT`。`hmm_range_fault()` 遍历当前进程
CPU 页表，必要时先把匿名页 fault 进来，并把带 HMM 标志的 PFN 写入 `hmm_pfns[]`。随后：

```c
ttm->pages[i] = hmm_pfn_to_page(range->hmm_range.hmm_pfns[i]);
```

因此前半条链是：

```text
CPU VA
  → mm_struct / VMA / CPU PTE
  → HMM hmm_pfns[]
  → hmm_pfn_to_page()
  → ttm->pages[]
```

TTM bind USERPTR 时再建立设备 DMA 视图：

```text
amdgpu_ttm_tt_pin_userptr()
  → sg_alloc_table_from_pages(ttm->pages[])
  → dma_map_sgtable(adev->dev, ...)
  → drm_prime_sg_to_dma_addr_array(..., ttm->dma_address[])
```

此时各对象保存的是：

```text
hmm_pfns[]           CPU 页表查询结果（PFN + HMM flags）
ttm->pages[]         Linux 的物理页对象
ttm->sg              物理页合并后的 scatter-gather 描述
ttm->dma_address[]   这个 GPU PCI 设备可使用的 DMA 地址/IOVA
```

用户再调用 `hsaKmtMapMemoryToGPU()`：

```text
AMDKFD_IOC_MAP_MEMORY_TO_GPU
  → amdgpu_amdkfd_gpuvm_map_memory_to_gpu()
  → amdgpu_vm_bo_map(entry->va, ...)       记录 GPUVA → BO/offset
  → amdgpu_vm_bo_update()
       pages_addr = bo->tbo.ttm->dma_address
  → amdgpu_vm_update_range()
  → amdgpu_vm_ptes_update()
  → CPU 或 SDMA updater 写 GPU PTE
```

CPU updater 和 SDMA updater 最终都会通过 `amdgpu_vm_map_gart()` 从
`pages_addr[index]` 取该页的 DMA 地址作为 PTE address 部分。

USERPTR 的完整数值链是：

```text
CPU VA
  → CPU PTE/PFN
  → struct page
  → SG
  → dma_map_sgtable()
  → DMA address / IOVA
  → GPUVM PTE
  → GPUVA
```

**源码锚点**：`2.源码/rocr-runtime/libhsakmt/src/fmm.c:2071`（CPU VA 作为 USERPTR 输入）、
`2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_hmm.c:168-213`（`amdgpu_hmm_range_get_pages`，其中 `hmm_range_fault` 调用点在 `:202`）、`2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_ttm.c:798`（PFN→page）、
`2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_ttm.c:811`（SG/DMA map）、`2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_vm.c:1313`（读取 `dma_address[]`）、
`2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_vm_cpu.c:73` / `2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_vm_sdma.c:219`（写 PTE）。

#### 6.2.2 GTT BO：TTM 先分配页面，再分别映射给 CPU 和 GPU

libhsakmt 首先只预留一个地址区间：

```text
aperture_allocate_area_aligned()
  → mmap(PROT_NONE, MAP_ANONYMOUS | MAP_NORESERVE, ...)
```

这个 `PROT_NONE` VA 只有地址空间，没有为 GTT BO 提供 backing page。随后该 VA 作为
`args.va_addr` 传给 KFD，而 `flags=KFD_IOC_ALLOC_MEM_FLAGS_GTT` 使内核创建 GTT BO：

```text
amdgpu_amdkfd_gpuvm_alloc_memory_of_gpu()
  → amdgpu_gem_object_create(domain=AMDGPU_GEM_DOMAIN_GTT)
  → amdgpu_bo_create()
  → ttm_bo_init_reserved()
  → ttm_bo_validate()
  → ttm_bo_handle_move_mem()
  → ttm_tt_create() / ttm_bo_populate()
  → amdgpu_ttm_tt_populate()
  → ttm_pool_alloc()
```

`ttm_sg_tt_init()` 先为 `ttm->pages[]`、`ttm->dma_address[]` 分配数组；真正的 RAM page
由 TTM pool 提供，pool 没有可复用页面时落到：

```c
alloc_pages_node(pool->nid, gfp_flags, order);
```

某些平台也可走 `dma_alloc_attrs()`。TTM 随后对这些页面执行 `dma_map_page()`，将结果填入：

```text
ttm->pages[]          = TTM 分配的 system RAM pages
ttm->dma_address[]    = GPU 设备看到的 DMA 地址/IOVA
```

这里不需要单独保存一份 `phys_addr_t pa[]`：`struct page` 已经标识物理页；真正交给设备时，
Linux 要求通过 DMA API 得到 `dma_addr_t`。

KFD 返回 `amdgpu_bo_mmap_offset()` 生成的 DRM mmap token。对于 host-accessible 分配，
libhsakmt 用它替换前面的 `PROT_NONE` 区域：

```text
mmap(mem, size, PROT_READ | PROT_WRITE,
     MAP_SHARED | MAP_FIXED, gpu_drm_fd, mmap_offset)
```

CPU 第一次访问时：

```text
amdgpu_gem_fault()
  → ttm_bo_vm_fault_reserved()
  → page = ttm->pages[page_offset]
  → page_to_pfn(page)
  → vmf_insert_pfn_prot()
  → CPU PTE
```

而 GPU 侧仍要通过 `AMDKFD_IOC_MAP_MEMORY_TO_GPU` 建立进程 GPUVM：

```text
GPUVA = mem->va
  → amdgpu_vm_bo_map()
  → amdgpu_vm_bo_update()
  → ttm->dma_address[]
  → GPU PTE
```

GTT BO 的完整双向映射是：

```text
                         ┌→ page_to_pfn() → CPU PTE → 用户 CPU VA
TTM 分配 struct page[] ──┤
                         └→ dma_map_page() → DMA address/IOVA
                                                → GPU PTE → GPUVA
```

**源码锚点**：`2.源码/rocr-runtime/libhsakmt/src/fmm.c:1540` 与同文件 `:1570`（预留 VA 与 BO mmap）、
`2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_amdkfd_gpuvm.c:1709`（KFD GTT BO 创建）、`2.源码/linux/drivers/gpu/drm/ttm/ttm_bo.c:929`（create 内 validate）、
`2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_ttm.c:1221`（populate）、`2.源码/linux/drivers/gpu/drm/ttm/ttm_pool.c:147` 与同文件 `:283`（page 分配入口与 `dma_map_page()`）、
`2.源码/linux/drivers/gpu/drm/ttm/ttm_bo_vm.c:183`（CPU fault 插 PFN）、`2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_vm.c:1261`（GPUVM update）。

#### 6.2.3 “同一 PA”与 IOMMU 的精确说法

CPU 和 GPU 最终访问的是同一批 `struct page` 对应的 Host RAM，但 GPU PTE 中的数值不一定
等于 Host PA：

```text
无 Host IOMMU/direct DMA：
  GPU PTE 中的 dma_addr_t 通常接近 Host PA

有 Host IOMMU：
  GPUVA → GPU PTE 中的 IOVA → Host IOMMU → Host PA
  CPU VA → CPU PTE/PFN                    → 同一个 Host PA
```

因此更准确的说法是：**CPU 页表和 GPU 的 DMA/IOMMU 地址链最终收敛到同一个
`struct page`/Host physical page，而不是保证两边页表中保存相同的地址数值。**

### 6.3 Pin 与 Staging 是什么、何时用

**Pin（钉住）**：让设备 DMA 生命周期内使用的 host page 保持有效，并为设备建立稳定的 DMA
mapping。传统路径常用 GUP/长期锁页；AMDGPU USERPTR 这里使用 HMM + MMU interval notifier 跟踪
CPU 映射变化，再由 `amdgpu_ttm_tt_pin_userptr()` 建 SG/DMA mapping。函数名虽然有 `pin_userptr`，
但不能简单等价成一次永久 `mlock()` 或 `FOLL_LONGTERM`：CPU 页表变化时，notifier 会使映射失效并
触发重新验证。

```text
USERPTR 准备：HMM 跟踪 + 页面收集 + SG/DMA mapping
  CPU VA → HMM PFN → struct page → SG → dma_addr_t
GPUVM 映射：
  GPUVA → GPU PTE(dma_addr_t) → 同一 host page
```

**Staging（中转）**：用一块 GPU 可见的临时缓冲当中转，不直接访问 host 缓冲。

```text
Staging 本质：多一次拷贝
  host 数据 → 拷进 staging buffer → 再拷到目标
  全程 GPU 不碰原始 host 缓冲
```

**何时用哪个**（2.源码/rocm-clr/rocclr/device/rocm/rocblit.cpp 的 getBuffer 选择逻辑）：

|          | Pin                                                    | Staging                                 |
| -------- | ------------------------------------------------------ | --------------------------------------- |
| 做法     | 锁物理页 + 直接 DMA 到 host 页                         | 多一次拷贝中转                          |
| 代价     | pin 系统调用 + 锁页占内存                              | 多一次拷贝                              |
| 何时用   | **大传输、缓冲反复复用**（注册内存）——省双拷贝 | **小传输、一次性**——省 pin 开销 |
| 失败回退 | pin 失败 → 回退 staging                               | —                                      |

**一句话**：能直接 DMA 就 pin（省拷贝），不划算就 staging（省 pin 开销）。

**staging buffer 是什么内存、从哪来**：

- **staging buffer 永远是 GTT 类**（系统内存 + GPUVM 映射，**两端可访问**）——它必须满足"GPU 能写进来（SDMA 拷入）+ CPU 能读出去"。不是裸 host RAM（GPU 碰不到），也不是裸 VRAM（CPU 碰不到）。
- **来源（两种场景）**：

| 场景                         | staging buffer 从哪来                                                                                       | 类型             |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------- |
| **read/write（copy）** | `gpu().Staging().Acquire()`（设备 Staging 池）                                                            | GTT 类           |
| **mapBuffer**          | `allocateMapMemory`：先 `findMapTarget`（设备 map 池复用），没有再新建 `CL_MEM_ALLOC_HOST_PTR` buffer | **GTT 类** |

```c
// 2.源码/rocm-clr/rocclr/device/rocm/rocmemory.cpp:73 —— mapBuffer 的 staging
bool Memory::allocateMapMemory(size_t allocationSize) {
  amd::Memory* mapMemory = dev().findMapTarget(owner()->getSize());  // 复用池
  if (mapMemory == nullptr) {
    mapMemory = new amd::Buffer(context, CL_MEM_ALLOC_HOST_PTR, size);  // 新建 → host pool/GTT
  }
  mapMemory_ = mapMemory;
}
```

**所以 staging 和 ALLOC_HOST_PTR 是同一类内存**（GPU 可见的 host 内存 = GTT 类），只是分配来源不同（Staging 池 vs allocateMapMemory）。

### 6.4 SVM 底层机制可变（编程模型 vs 数据移动）

**精确表述**：SVM 是**编程模型**（指针/地址空间共享），**不是"一定无搬运"**。底层机制有三种可能：

| 底层机制                    | 有无数据移动                                                                               | 代码证据                                                                                                             |
| --------------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| **直接访问 host RAM** | **无**——GPU 页表以 DMA address/IOVA 指向 host page（SYSTEM PTE），GPU 经 PCIe 直访 | `svm_range_dma_map`（2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_svm.c:207），`best_loc` 留在 RAM 时不迁移                                               |
| **页面迁移**          | **有**——数据从 RAM 搬到 VRAM（或反向），SDMA 拷贝                                  | `svm_migrate_to_vram`（`2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_migrate.c:918`）/ `svm_migrate_vram_to_ram`（同文件 :796）；两者使用同文件 :126 的 `svm_migrate_copy_memory_gart` |
| **显式 prefetch**     | **有（用户主动）**——`PREFETCH_LOC` 属性触发立即迁移                              | `KFD_IOCTL_SVM_ATTR_PREFETCH_LOC` → `svm_range_trigger_migration`（2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_svm.c:729/3596）                         |

**"无显式拷贝"是编程模型层的说法，不等于底层无数据移动。** SVM 复用的地基（BO/GPUVM/页表/SDMA）让它三种底层机制都能跑。

**为什么迁移**：GPU 频繁访问的数据放 VRAM（本地快），CPU 频繁访问的放 RAM（本地快）。迁移 = 把**唯一的物理副本**搬到离访问方近的地方。**数据始终单副本，只是"家"会搬。** 参考 [SVM 专题](<./9. AMD SVM：共享内存、统一地址空间与页面迁移.md>) §7.6。

**顺带纠正**：SVM 不等于一定用 Unified Memory（`cudaMallocManaged` 只是 SVM 的一种 API 形态）；SVM 的底层也可能有显式/隐式数据移动，不只是"共享即零拷贝"。

### 6.5 GPU 访问 host 内存的授权：映射由驱动建（隔离本质）

**GPU 从不自己建立 host 内存的映射——它只走驱动建好的 GPUVM。** 驱动建映射 = 授权：

```text
驱动（CPU 内核侧）：
  ① 取得 host page（USERPTR: HMM 从 CPU 页表取；GTT: TTM 分配）
  ② dma_map → 该 GPU 设备可使用的 DMA 地址/IOVA
  ③ amdgpu_vm_update_range → 写 GPU 页表（GPUVA → dma_addr_t，SYSTEM PTE）
  ④ flush GPU TLB
GPU：走表 → 访问
```

**何时建（两条授权方式，都是驱动建，区别在时机）**：

| 方式                               | 驱动何时建 GPU 页表                      | GPU 访问时                                               |
| ---------------------------------- | ---------------------------------------- | -------------------------------------------------------- |
| **显式授权**（pin/注册/GTT） | **提前建好**（host 决定给 GPU 用） | 直接访问，不 fault                                       |
| **SVM 指针**                 | **不提前建**（按需）               | 首次访问 fault → 驱动按需建（restore_pages）→ GPU 重试 |

**隔离本质**：GPU 能访问 host 内存 = 驱动在 GPUVM 里建了对应 PTE。**驱动不建，GPU 就访问不到**（fault 或越权）——所以 GPU 对 host 内存的访问能力完全由驱动建立的分页表决定，这就是隔离边界（P1 的驱动只给 P1 的 GPUVM 建映射，P2 摸不到 P1 的数据）。

**补充：GPU 取数不是 SDMA**。GPU 计算内核拿 CPU 数据，默认是 CU 的 load/store **直接访存**（经 GPUMMU → PCIe，前提是驱动已建映射），**不是 SDMA 拷贝引擎**。SDMA 只做"搬运到固定位置"（迁移/驻留），且通常由驱动发起——GPU 计算内核不自己发 SDMA（"GPU 主动取数据"靠直接访存，不靠 SDMA 搬运）。

### 6.6 谁决定"这块内存 CPU 可直访"（PUBLIC/PRIVATE 机制）

**"CPU 能否经 BAR 直访某块显存"的决定，不是逐 buffer 查窗口，而是两层分工：**

```text
用户态决定意图：分配时设 HostAccess → libhsakmt 转 PUBLIC（2.源码/rocr-runtime/libhsakmt/src/fmm.c:1753-1754）
   if (mflags.ui32.HostAccess) ioc_flags |= KFD_IOC_ALLOC_MEM_FLAGS_PUBLIC;

内核决定可行性：
   kfd_dev_is_large_bar（设备初始化时查 local_mem_size_private/public，2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_chardev.c:1047）
   分配时强制：PUBLIC + VRAM + 小BAR → 拒绝（2.源码/linux/drivers/gpu/drm/amd/amdkfd/kfd_chardev.c:1147）
   "Alloc host visible vram on small bar is not allowed"
```

**结论**：**成功分配 PUBLIC VRAM = 一定 CPU 可直访**（内核强制保证：小 BAR 根本不让分配 PUBLIC VRAM）。UMD 据此给 buffer 打 `HostMemoryDirectAccess` flag，拷贝时查它选 CPU 直访还是 staging。

**小 BAR 的现实**：PUBLIC VRAM 被拒绝 → **没有"CPU 访问 VRAM"的直接途径**。"针对暴露 aperture 专门分配 visible VRAM"是 amdgpu DRM（graphics）的概念，不是 KFD compute 路径。小 BAR 上 CPU 可访问的"GPU 内存"走 GTT（§3）——注意那是 **GPU→host 方向**，不是 CPU→VRAM。

### 6.7 GART、GTT 与进程 GPUVM：不要强行套成固定两级翻译 **[SOURCE]**

三个名字分别回答不同问题：

| 名称                 | 回答的问题                                           | AMD 源码对象/路径                                  |
| -------------------- | ---------------------------------------------------- | -------------------------------------------------- |
| **GTT**        | BO 的 backing 是否位于 system RAM                    | `AMDGPU_GEM_DOMAIN_GTT` / `TTM_PL_TT`          |
| **GART**       | 设备全局 GART aperture 如何映射 system pages         | `amdgpu_gart_bind()` / VMID 0 system VM          |
| **进程 GPUVM** | 某进程的 GPUVA 映射到哪个 VRAM 或 system DMA address | `amdgpu_vm_bo_map()` / `amdgpu_vm_bo_update()` |

TTM 把 GTT BO 放入 `TTM_PL_TT` 时，`amdgpu_ttm_backend_bind()` 确实可以调用
`amdgpu_gart_bind()`，把 `ttm->dma_address[]` 绑定进设备全局 GART aperture。这给 BO 一个
GART/global GPU address，供需要该地址形式的内核或全局访问路径使用。

但是，**不能因此推导出每个进程 GPUVM 的 SYSTEM PTE 都先写 GART aperture 地址，再固定经过
VMID 0 做第二级翻译。** 对普通 KFD 进程 GPUVM，源码路径是：

```c
/* amdgpu_vm_bo_update(), mem_type == TTM_PL_TT */
pages_addr = bo->tbo.ttm->dma_address;
```

随后 CPU updater：

```c
value = p->pages_addr ?
        amdgpu_vm_map_gart(p->pages_addr, addr) : addr;
amdgpu_gmc_set_pte_pde(..., value, flags);
```

这里 `amdgpu_vm_map_gart()` 的名字容易误导；它当前所做的是按页索引
`pages_addr[addr >> PAGE_SHIFT]`，返回该 system page 的 DMA 地址。SDMA updater 也取同一个
`ttm->dma_address[]` 来生成 PTE。

因此本章讨论的常规 KFD USERPTR/GTT 进程映射应画成：

```text
GPUVA
  → 进程 GPUVM PTE（SYSTEM，address = dma_addr_t）
  → [如启用 Host IOMMU：IOVA → Host PA]
  → PCIe / coherent fabric
  → system RAM page
```

而设备全局 GART 路径是另一种有效地址路径：

```text
GART aperture address
  → VMID 0 / GART table
  → system page 的 DMA address
```

两条路径共享同一批 `ttm->pages[]`/`ttm->dma_address[]`，但不能把 GART 表描述成所有进程
SYSTEM PTE 后面必经的第二级页表。

GART 表仍由驱动在设备初始化时建立；`amdgpu_gart_map()` 把 host DMA address 写入表项。
VMID 0 保留给 system VM，进程使用其他 VMID。这里的关键边界是：

> **GTT 是 backing 域，GART 是设备全局 aperture 映射，GPUVM 是每进程 VA 映射；三者相关，
> 但不是“GTT 数据必然经过 GPUVM→GART 两级翻译”的包含关系。**

## 7. AMD 实现层：内存对象（BO/GEM/TTM）与 KFD 内存 ioctl

### 7.1 底层内存对象：BO 是 GEM 与 TTM 的三层合一

**在 DRM 里，"一块 GPU 内存"不是裸指针，而是一个多层对象。** 用户态拿到的 `cl_mem` / HIP 指针背后，是这样一个三层合一：

```c
// 2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_object.h —— 一个对象同时服务两层（示意子集，非完整定义）
struct amdgpu_bo {
    struct ttm_buffer_object  tbo;       // TTM 层（tbo.base 就是 GEM 对象）
    struct ttm_bo_kmap_obj    kmap;      // CPU 映射（内核侧 amdgpu_bo_kmap → writeq，见 [MMU 页表专题 §8.3](<./7. MMU 与页表：从 CPU 对照看 GPUVM 的构建、写入与切换.md>)）
    u32 preferred_domains;               // 允许住哪个内核域（§3.1 flag 映射到：VRAM / GTT / CPU）
    u64 flags;
    struct amdgpu_vm_bo_base *vm_bo;     // 页表 / VA 关联
    struct kgd_mem           *kfd_bo;    // KFD 内存对象关联
};
// 链：amdgpu_bo ⊃ ttm_bo ⊃ drm_gem_object（2.源码/linux/include/drm/ttm/ttm_bo.h:102 tbo.base = drm_gem_object）
```

- **GEM（Graphics Execution Manager）——对象/API 层**：`drm_gem_object` 是用户态**句柄**背后的对象，提供句柄生命周期、mmap、**dma-buf 共享**（fd 跨进程/跨设备）、引用计数。它**故意很薄**，真正的实现由驱动填充。
- **TTM（Translation Table Manager）——放置/后备层**：`ttm_buffer_object` 管"这块内存**物理住哪**"——内存域（VRAM/GTT/System）、放置与**迁移**（换出/换入）、system backing 的 `struct page[]`/DMA address、GART 绑定、LRU 换出、swap。它提供 GPUVM 建表所需的 backing 信息，但**进程 GPUVM PTE 的写入属 VM 层，不属 TTM**，见 [MMU 页表专题 §8](<./7. MMU 与页表：从 CPU 对照看 GPUVM 的构建、写入与切换.md>)。
- **amdgpu_bo**：AMD 私有层，把 `preferred_domains`（§3.1 flag 映射到的内核域）、`flags`、VM/页表关联、KFD 关联挂在 TTM BO 上。

> **一句话**：GEM = "**用户态拿着的对象**"（句柄/mmap/dma-buf）；TTM = "**backing 住哪、有哪些 page/DMA address**"（域/迁移/换出）；VM 层 = "**这些 backing 映射到哪个 GPUVA**"。amdgpu 的一个 `amdgpu_bo` 把这些层关联起来。

### 7.2 KFD 内存 ioctl（BO/GPUVM 基础）

```text
AMDKFD_IOC_ALLOC_MEMORY_OF_GPU
  → 从当前 kfd_process 找 PDD → 分配 BO
  → 在 PDD.alloc_idr 中建 handle（进程本地命名空间）

AMDKFD_IOC_MAP_MEMORY_TO_GPU
  → 验证 handle 属于当前 PDD → 更新目标 GPUVM 页表 → flush TLB

AMDKFD_IOC_ALLOC_MEMORY_OF_GPU + KFD_IOC_ALLOC_MEM_FLAGS_USERPTR
  → "注册 host 内存"（GPU 访问 CPU 内存的常规方式）= 用 USERPTR flag 分配 BO，
    HMM 收集用户页面并建立 DMA mapping；随后仍需 MAP_MEMORY_TO_GPU 写进程 GPUVM
  → 没有独立的 KFD REGISTER_MEMORY ioctl
```

**\[SOURCE]** 主模型 §7.1：handle 在 PDD 命名空间 = 访问能力；P2 猜不到 P1 的 handle 数值。
BO 可 attach 多个 VM，所以"BO 所有权"不是"一个对象只属于一个进程"，而是"每个访问者都要合法引用 + 合法 mapping"。

### 7.3 完整例子：`hipMalloc(1MB)` 到物理 VRAM（无跳链）

把 7.1（三层对象）和 7.2（ioctl）串成一条无跳链，**每一跳都标注它属于 GEM / TTM / amdgpu / VM 哪一层**。下方从 `amdgpu_bo_create` 开始仅写 `:行号` 的锚点，均对应 `2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_object.c`：

```text
用户: hipMalloc(1MB)
  → ROCr → libhsakmt → KFD_IOC_ALLOC_MEMORY_OF_GPU (flags=VRAM)
  ↓
amdgpu_amdkfd_gpuvm_alloc_memory_of_gpu   (2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_amdkfd_gpuvm.c:1709)
  domain = AMDGPU_GEM_DOMAIN_VRAM        ← 从 flags 决定住哪个域
  ↓
amdgpu_gem_object_create(...)            (2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_gem.c:167)   ← KFD 建 BO 的入口
  ↓
amdgpu_bo_create_user → amdgpu_bo_create (2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_object.c:628)
  ├─ [GEM]    drm_gem_private_object_init(&bo->tbo.base, size)  ← :669
  │           创建 drm_gem_object：refcount、mmap vma_node、dma-buf 可导出（后续步骤）
  ├─ [amdgpu] bo->preferred_domains = bp->domain；bo->vm_bo = NULL  ← :672
  │           （KFD 侧：flags=VRAM → domain=VRAM；若 apu_prefer_gtt 则 domain=GTT，2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_amdkfd_gpuvm.c:1733）
  ├─ [TTM]    bo->tbo.bdev = &adev->mman.bdev                     ← :692
  ├─ [TTM]    amdgpu_bo_placement_from_domain(bo, domain)        ← :695 把域转成 placement
  ├─ [TTM]    ttm_bo_init_reserved(&adev->mman.bdev, &bo->tbo, …) ← :706
  │           ★ 内部直接调 ttm_bo_validate（2.源码/linux/drivers/gpu/drm/ttm/ttm_bo.c:970）
  │             → ttm_bo_mem_space → vram_mgr（amdgpu_vram_mgr_new）
  │               → gpu_buddy_alloc_blocks 划 VRAM 区间（如 offset 0x1234000）
  │           → 此时 BO 已经"住进" VRAM（物理划好了！）
  └─ 返回 gobj = &bo->tbo.base（即 drm_gem_object）
  ↓
drm_gem_handle_create(...)                ← [GEM] 建用户态 handle
  ↓
用户拿到 handle（一个数字）——指向：一个对象 + 一段 VRAM 物理
  ↓
之后: KFD_IOC_MAP_MEMORY_TO_GPU
  → [VM 层] amdgpu_vm_bo_map → amdgpu_vm_bo_update
      建 amdgpu_vm_bo_base（attach 到进程 GPUVM）
      填 GPUVM 页表 PTE（GPU VA 0x4000000 → VRAM 0x1234000）
```

**关键认知（这条链最容易跳过的点）**：**VRAM 物理区间在 `amdgpu_bo_create` 内部就划好了**——`ttm_bo_init_reserved`（2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_object.c:706）内部直接调 `ttm_bo_validate`（2.源码/linux/drivers/gpu/drm/ttm/ttm_bo.c:970），走到 `vram_mgr`（`amdgpu_vram_mgr_new` → `gpu_buddy_alloc_blocks`）划下真实区间。所以"create 之后还要单独 validate 才划物理"是错的——**划物理发生在 create 过程里**，不是之后某次 map/pin。

**逐层归纳**：

| 层               | 在这条链里做的具体事                                                                                                                                                    |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **GEM**    | `drm_gem_private_object_init`（身份/refcount/mmap）+ `drm_gem_handle_create`（handle）——管"对象怎么被持有"                                                        |
| **TTM**    | `amdgpu_bo_placement_from_domain`（域→placement）+ `ttm_bo_init_reserved`（内部 validate → `vram_mgr` 划 VRAM）——管"物理住哪"，**划物理就在 create 里** |
| **amdgpu** | `preferred_domains`/`flags`/`vm_bo`/`kfd_bo`——管 AMD 私有信息                                                                                                 |
| **VM**     | `amdgpu_vm_bo_map` + GPUVM PTE——管"VA↔PA 映射"（不是 GEM 也不是 TTM，**且要 map 之后才有**）                                                                 |

> **结论**：GEM 建对象身份 → TTM 在 create 内部划物理 → amdgpu 挂私有信息 → **VM 层补 VA 映射（要 map 之后才有）**。**GEM 和 TTM 从头到尾不碰 VA 映射**——VA 映射是最后 VM 层的活。把"内存对象"理解成"VA↔PA 映射"，是只看到了最后一层。

### 7.4 `amdgpu_bo_create` 逐字段追踪：填了什么、怎么关联、何时用

只看调用链还是难，是因为没看**每个字段在哪一步被填、以后什么时候被读**。把 `amdgpu_bo_create`（2.源码/linux/drivers/gpu/drm/amd/amdgpu/amdgpu_object.c:628）逐行拆开；下表所有 `:行号` 继续指向该文件：

| 步 | 代码（行号）                                                                | 层     | 填了什么字段                                                                              | 何时用                                              |
| -- | --------------------------------------------------------------------------- | ------ | ----------------------------------------------------------------------------------------- | --------------------------------------------------- |
| ① | `kvzalloc(bp->bo_ptr_size)` :666                                          | ——   | **分配 amdgpu_bo 结构体本身**（清零）                                               | 这就是"对象"本尊                                    |
| ② | `drm_gem_private_object_init(&bo->tbo.base, size)` :669                   | GEM    | **drm_gem_object**：refcount=1、size、mmap 的 vma_node                              | 用户态 handle / mmap / dma-buf 导出                 |
| ③ | `bo->tbo.base.funcs = &amdgpu_gem_object_funcs` :670                      | GEM    | **GEM 对象的方法表**（mmap/export 回调）                                            | 用户 mmap、导出时调用                               |
| ④ | `bo->vm_bo = NULL` :671                                                   | amdgpu | **VM attach 链表头**（初始空）                                                      | MAP_MEMORY_TO_GPU 时 attach 上`amdgpu_vm_bo_base` |
| ⑤ | `bo->preferred_domains = bp->preferred_domain ? … : bp->domain` :672-673 | amdgpu | **首选域**（本例 VRAM）                                                             | 喂给 placement → 决定物理住哪                      |
| ⑥ | `bo->allowed_domains = preferred (+GTT)` :674-678                         | amdgpu | **允许的域**（VRAM 外还允许 GTT，因为可能被换出到 GTT）                             | 迁移/换出时                                         |
| ⑦ | `bo->flags = bp->flags` :680                                              | amdgpu | **创建标志**（CPU_ACCESS_REQUIRED 等）                                              | kmap、mmap、行为开关                                |
| ⑧ | `bo->tbo.bdev = &adev->mman.bdev` :692                                    | TTM    | **绑定全局 TTM 设备**                                                               | 所有 TTM 操作的前提                                 |
| ⑨ | `amdgpu_bo_placement_from_domain(bo, domain)` :695-697                    | TTM    | **把域转成 TTM placement**（候选放置方案列表）                                      | `ttm_bo_init_reserved` 内部划物理时用             |
| ⑩ | `bo->tbo.priority` :698-701                                               | TTM    | **换出优先级**                                                                      | 内存压力换出时决定谁先被踢                          |
| ⑪ | `ttm_bo_init_reserved(&adev->mman.bdev, &bo->tbo, …)` :706               | TTM    | **★ 内部直接调 `ttm_bo_validate`（2.源码/linux/drivers/gpu/drm/ttm/ttm_bo.c:970）→ `vram_mgr` 划真实物理区间** | 对象正式生效，**物理在这步就划好了**          |
| ⑫ | `amdgpu_bo_unreserve` :736                                                | ——   | 解锁                                                                                      | 返回给调用者                                        |

**三个关键"怎么关联"**：

1. **三层靠"内嵌"（containment）关联，不是指针**：`amdgpu_bo` 结构体里**内嵌** `ttm_buffer_object tbo`，`tbo` 里**内嵌** `drm_gem_object base`。`&bo->tbo.base` 就是 GEM 对象的地址——三个"层"其实是**一个连续内存里的三层嵌套**，不是三个分离的对象。
2. **域 → placement → 内部 validate 是一条链**：⑤⑥ 的 `preferred/allowed_domains` → ⑨ 的 `placement` → ⑪ 的 `ttm_bo_init_reserved`（内部调 `ttm_bo_validate`）决定"物理住哪"。**"住哪"不是填一个字段就完了，是三个字段接力，且发生在 create 内部**。
3. **vm_bo 是"外挂链表"，不是内嵌**：④ 初始 NULL，MAP 时才 attach `amdgpu_vm_bo_base`（每个 GPUVM 一个，串成链表）。所以**"VA 映射"是后挂上去的**，不是 BO 自带的。

> 这条逐字段链回答"为什么 BO 是对象而不是 VA↔PA 映射"：**BO 里根本没有"VA 字段"**——④ 的 vm_bo 初始是 NULL，VA 映射是之后外挂的。BO 装的是身份（GEM）、物理放置（TTM）、AMD 私有（域/flags）——映射是最外层的事。

## 8. 常规 vs SVM 分界

| 维度               | 常规（显式）                         | SVM（扩充）                     |
| ------------------ | ------------------------------------ | ------------------------------- |
| 分配               | `cl_mem` / KFD alloc，返回 handle  | 裸指针（malloc/mmap）           |
| 搬运               | 显式 copy / map / unmap              | 无（共享地址，按需补页）        |
| GPU 访问 host 内存 | 显式注册 + 映射                      | 指针直接可用（fault 自动补）    |
| 同步               | queue order + event                  | fault 恢复 + coarse/fine 一致性 |
| 生命周期           | API 显式管理（free/unmap 主动调用）  | 随 mm / pointer 生命周期        |
| 适用场景           | 明确生命周期、数据量小、需要精细控制 | 大共享数据、零拷贝、稀疏访问    |

**选择判据**：能接受显式搬运 + 生命周期管理 → 用常规；需要零拷贝大共享 + 不想管搬运 → 用 SVM。

## 9. SVM 作为常规的扩充（收束）

**SVM 复用的地基**：BO、GPUVM、页表、PDD、fault 机制——全是常规路径已有的东西。

**SVM 加的增量**：

```text
共享 VA：进程 VA ≈ GPU VA（同一地址两端可见）        ← 常规只有 GPUVA，不共享
按需补页：GPU fault → 恢复 PTE → 重试              ← 常规靠显式 map，SVM 靠自动
迁移：RAM ↔ VRAM 按需移动数据                      ← 常规靠 copy，SVM 靠 fault 驱动
```

**演进逻辑**（从常规到 SVM 的递进，也是理解顺序）：

```text
常规（显式 copy/map）──► coarse-grain SVM（所有权交接）
──► fine-grain buffer SVM（一致 + 原子）
──► fine-grain system SVM + HMM（任意指针 + 按需缺页）
```

## 10. 三大 API 的常规使用方式（OpenCL / CUDA / HIP）

### 10.1 使用场景（pin / staging / SVM 三路）

**场景**：把一段数据交给 GPU 计算，三种 API 写法对应三条底层路径。

**方式 A——普通传输（默认，runtime 内部决定 pin 或 staging）**：

```c
// HIP：普通 host 内存 + 显式搬运（小传输→staging，大传输→临时 pin）
float *h = (float *)malloc(bytes);          // 普通 host 内存（未注册）
float *d; hipMalloc(&d, bytes);
hipMemcpy(d, h, bytes, hipMemcpyHostToDevice);   // runtime 内部选路

// OpenCL：同样，普通 malloc + WriteBuffer
cl_mem d = clCreateBuffer(ctx, CL_MEM_READ_WRITE, bytes, NULL, &err);
clEnqueueWriteBuffer(queue, d, CL_TRUE, 0, bytes, h, 0, NULL, NULL);
```

**方式 B——显式 Pin（注册 host 内存，反复用、GPU 直接 DMA 到它）**：

```c
// HIP：钉住现有 host 内存
float *h = (float *)malloc(bytes);
hipHostRegister(h, bytes, 0);               // ★ 钉住 → 物理页锁住 + 映射进 GPUVM
float *d_h;
hipHostGetDevicePointer(&d_h, h, 0);        // 拿到 GPU 侧设备指针（GPUVA）
// 现在 d_h 是 GPU 可访问的地址：host 写 h，GPU 读 d_h（同一物理页）
// ... 反复多次 kernel 用它，都不需要再搬运 ...
hipHostUnregister(h);

// OpenCL：CL_MEM_USE_HOST_PTR 注册
cl_mem buf = clCreateBuffer(ctx, CL_MEM_READ_WRITE | CL_MEM_USE_HOST_PTR,
                            bytes, h, &err);
// buf 的 backing 就是 h 的物理页（钉住 + GPUVM 映射）
// host 写 h，GPU kernel 用 buf（GPUVA），数据直接可见，无 staging
```

**方式 C——SVM / managed（共享指针，零拷贝）**：

```c
// HIP：统一内存
float *m;
hipMallocManaged(&m, bytes);                // ★ CPU/GPU 共享同一指针
// host 直接写 m，GPU kernel 直接读 m（同一地址），按需缺页迁移

// OpenCL：clSVMAlloc
float *m = (float *)clSVMAlloc(ctx, 0, bytes, 0);
clSetKernelArgSVMPointer(kernel, 0, m);     // SVM 指针直接作参数
clSVMFree(ctx, m);
```

**场景选择表**：

| 场景                                | 该用哪条路                      | 为什么                               |
| ----------------------------------- | ------------------------------- | ------------------------------------ |
| 一次性小传输（临时数据）            | A：默认（runtime 自动 staging） | 省 pin 开销                          |
| 大传输、缓冲被反复用（注册内存）    | B：显式 Pin                     | 一次钉住，多次直接 DMA，省每次双拷贝 |
| 需要 CPU/GPU 共享大块数据、稀疏访问 | C：SVM / managed                | 零拷贝、按需补页，不用管搬运         |
| host 内存不适合直接 DMA（不可 pin） | A：自动回退 staging             | runtime 兜底                         |

**一句话**：**数据反复用 → 注册（pin）；一次性 → 交给 runtime（staging）；想零拷贝共享 → SVM。**

### 10.2 三大 API 对照表

| 常规操作                       | OpenCL                                         | CUDA                                                | HIP                                      |
| ------------------------------ | ---------------------------------------------- | --------------------------------------------------- | ---------------------------------------- |
| 分配 GPU 内存（device）        | `clCreateBuffer`（默认 flag）                | `cudaMalloc`                                      | `hipMalloc`                            |
| 分配 host 可访问内存（pinned） | `clCreateBuffer` + `CL_MEM_ALLOC_HOST_PTR` | `cudaMallocHost` / `cudaHostAlloc`              | `hipMallocHost`                        |

| UMD 调用                                       | 底层机制（本文）                                                                  |
| ---------------------------------------------- | --------------------------------------------------------------------------------- |

### 10.3 HIP 实际例子（完整常规路径）

```c
// HIP：底层走 ROCm/KFD，每步标注对应本文机制
__global__ void vecAdd(const float *a, const float *b, float *c, int n) {
    int i = threadIdx.x + blockIdx.x * blockDim.x;
    if (i < n) c[i] = a[i] + b[i];
}

int main() {
    const int n = 1 << 20;
    const size_t bytes = n * sizeof(float);

    // §3 分配 device 内存 → KFD_ALLOC_MEMORY_OF_GPU → BO（VRAM）
    float *d_a, *d_b, *d_c;
    hipMalloc(&d_a, bytes);
    hipMalloc(&d_b, bytes);
    hipMalloc(&d_c, bytes);

    float *h_a = (float *)malloc(bytes);
    float *h_b = (float *)malloc(bytes);
    float *h_c = (float *)malloc(bytes);
    for (int i = 0; i < n; i++) { h_a[i] = (float)i; h_b[i] = (float)i; }

    // §4 CPU→GPU：SDMA copy（HIP runtime 内部向 KFD 提交拷贝）
    hipMemcpy(d_a, h_a, bytes, hipMemcpyHostToDevice);
    hipMemcpy(d_b, h_b, bytes, hipMemcpyHostToDevice);

    // 提交 kernel（走 AQL 队列路径，见"AMD 队列提交"）
    vecAdd<<<n / 256, 256>>>(d_a, d_b, d_c, n);
    hipDeviceSynchronize();   // §6 队列顺序 + fence（完成信号）

    // §4 GPU→CPU：SDMA copy 读回
    hipMemcpy(h_c, d_c, bytes, hipMemcpyDeviceToHost);

    hipFree(d_a); hipFree(d_b); hipFree(d_c);
    free(h_a); free(h_b); free(h_c);
    return 0;
}
```

### 10.4 OpenCL 实际例子（含 Map/Unmap 直接访问）

```c
// OpenCL：device 初始化/编译省略（clGetDeviceIDs/clCreateContext/clCreateCommandQueue/clBuildProgram）
int main() {
    const int n = 1 << 20;
    const size_t bytes = n * sizeof(float);

    // §3 分配 device 内存 → BO（VRAM）
    cl_mem d_a = clCreateBuffer(ctx, CL_MEM_READ_ONLY,  bytes, NULL, &err);
    cl_mem d_b = clCreateBuffer(ctx, CL_MEM_READ_ONLY,  bytes, NULL, &err);
    cl_mem d_c = clCreateBuffer(ctx, CL_MEM_WRITE_ONLY, bytes, NULL, &err);

    float *h_a = (float *)malloc(bytes);
    float *h_b = (float *)malloc(bytes);
    float *h_c = (float *)malloc(bytes);

    // §4 CPU→GPU：SDMA copy
    clEnqueueWriteBuffer(queue, d_a, CL_TRUE, 0, bytes, h_a, 0, NULL, NULL);
    clEnqueueWriteBuffer(queue, d_b, CL_TRUE, 0, bytes, h_b, 0, NULL, NULL);

    // 提交 kernel（clEnqueueNDRangeKernel，略）

    // §4 GPU→CPU：SDMA copy 读回
    clEnqueueReadBuffer(queue, d_c, CL_TRUE, 0, bytes, h_c, 0, NULL, NULL);

    // §5.1 Map：CPU 直接访问 GPU 内存（large BAR 直映射，或非大 BAR 经 staging）
    float *mapped = (float *)clEnqueueMapBuffer(queue, d_c, CL_TRUE, CL_MAP_READ,
                                                0, bytes, 0, NULL, NULL, &err);
    // 直接读 mapped 里的结果...
    clEnqueueUnmapMemObject(queue, d_c, mapped, 0, NULL, NULL);
    clFinish(queue);

    clReleaseMemObject(d_a); clReleaseMemObject(d_b); clReleaseMemObject(d_c);
    free(h_a); free(h_b); free(h_c);
    return 0;
}
```

**host 注册变体**（GPU 访问"现有 host 内存"的常规方式，§5.2）：

```c
// HIP：hipHostRegister(h_ptr, bytes, 0)   → KFD USERPTR BO → MAP_MEMORY_TO_GPU
// OpenCL：clCreateBuffer(ctx, CL_MEM_USE_HOST_PTR, bytes, h_ptr, &err) → register/pin → GPUVM
```

| B | 显式 pin | 注册 host allocation → kernel 访问映射地址 | GPU 是否可访问、解除注册前是否需要显式同步 |
| C | SVM | 同一 pointer 由 Host 与 kernel 交替访问 | capability、map/unmap 或 fine-grain 同步要求、是否发生 fault/migration |
| D | VRAM map | map/unmap 一个 device buffer | 返回地址对应直映射还是 staging；必须结合命令流与内存域判断 |
| E | staging 选路 | 固定 API，改变 host allocation 类型与大小 | runtime 在何种条件下选择 pin、staging 或直接映射 |

### 测试重点二：拷贝与迁移验证

| 实验 | 对照方法 | 能直接证明什么 | 不能单独证明什么 |
|---|---|---|---|
| T1 | 同一 API 下比较 pageable 与 pinned host memory，并扫描 size | 不同分配方式存在稳定性能差异 | 仅凭带宽不能断言具体多了一次 RAM copy |
| T2 | 结果只生产一次，Host 重复消费 N 次 | 每次消费是否都需要显式传输 | 首次变慢不等于一定发生了迁移 |
| T3 | map/unmap 与显式 read/write 对照，并校验数据 | 两条 API 的端到端成本与正确性 | 耗时相近不等于底层路径相同 |

### 判定规则

1. **[SOURCE]** 先用本章列出的本地 runtime/KMD 入口确认该版本具备哪些候选路径。
2. **[INFERENCE]** 带宽、首触延迟和驻留量只能作为选路线索，不能单独充当“发生了几次拷贝”的证明。
3. **[SOURCE]** 要确认 staging、SDMA 或 migration，必须再观察该测试主机可用的命令流 trace、DMA/PCIe 计数器或驱动日志；工具名称和参数随 ROCm/内核版本变化，不在本文固定。
4. **[BOUNDARY]** WSL2 等虚拟化环境呈现的是虚拟设备模型，不能替代真实 AMD ROCm Linux 主机上的 BAR、KFD 和 PCIe/DMA 结论。
